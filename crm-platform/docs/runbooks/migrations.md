# Migrations

## Rules

1. **Applied migrations are immutable.** The runner records a sha256 of each
   file and refuses to proceed if one changed. Fix forward with a new
   migration.
2. **Additive first.** Add a column, backfill, switch reads, then drop the old
   one — in separate deploys. A rename in one step breaks whatever is still
   running the old code.
3. **Migrations run as the owner**, the app runs as `crm_app_user`. Both URLs
   are in `.env`.
4. **New tables need RLS.** Table privileges are inherited from
   `ALTER DEFAULT PRIVILEGES`; enabling and forcing RLS and writing the policy
   is per-table and cannot be defaulted.
5. **Update the Drizzle schema in the same commit**, then run
   `pnpm db:verify-schema`. It compares every Drizzle table with the migrated
   database and fails on anything that would break at runtime; CI runs it too.

## Writing one

```bash
pnpm db:new add_widgets      # creates packages/db/migrations/0009_add_widgets.sql
```

Comment the **why**. The SQL already says what.

```sql
-- 0009_add_widgets
-- Widgets are per-org configuration for the X integration. Physical table
-- rather than the generic records store because the send path reads them on
-- every message and JSONB extraction there would show up in p99.

CREATE TABLE widgets (
  org_id      bigint NOT NULL REFERENCES organizations (id) ON DELETE CASCADE,
  id          bigint GENERATED BY DEFAULT AS IDENTITY,
  uuid        uuid NOT NULL DEFAULT gen_random_uuid(),
  name        text NOT NULL,
  created_at  timestamptz NOT NULL DEFAULT now(),
  updated_at  timestamptz NOT NULL DEFAULT now(),
  row_version integer NOT NULL DEFAULT 1,
  PRIMARY KEY (org_id, id),
  UNIQUE (org_id, uuid)
);

ALTER TABLE widgets ENABLE ROW LEVEL SECURITY;
ALTER TABLE widgets FORCE  ROW LEVEL SECURITY;
CREATE POLICY tenant_isolation ON widgets FOR ALL
  USING      (org_id = current_org_id() OR app_is_privileged())
  WITH CHECK (org_id = current_org_id() OR app_is_privileged());

CREATE TRIGGER trg_widgets_touch BEFORE UPDATE ON widgets
  FOR EACH ROW EXECUTE FUNCTION touch_row();
```

## Statements that cannot run in a transaction

Put `-- @no-transaction` on the **first line** of the file:

```sql
-- @no-transaction
-- Index on a 12M-row table: CONCURRENTLY avoids the write lock, and cannot
-- run inside a transaction block.

CREATE INDEX CONCURRENTLY IF NOT EXISTS idx_contacts_college
  ON contacts ((data ->> 'college_tag'));
```

Needed for:

- `CREATE INDEX CONCURRENTLY` / `DROP INDEX CONCURRENTLY`
- `ALTER TYPE ... ADD VALUE`
- `VACUUM`, `REINDEX CONCURRENTLY`

**Rule:** every `CREATE INDEX CONCURRENTLY` in a `-- @no-transaction` file says
`IF NOT EXISTS`. The statement and its `_migrations` record are two steps
(CONCURRENTLY cannot share a transaction), so a crash between them leaves the
index built and the file unrecorded. The rerun must skip that index, not fail
on it.

**What the runner does** (`packages/db/src/migrator.ts`):

- Before it runs such a file, it reads the index names the file creates. If one
  of them is **INVALID**, or still being built by another session, it stops with
  the recovery text and runs nothing from that file. It never drops the index
  itself.
- Invalid indexes the file does not create are not checked.
- A **valid** index left unrecorded is adopted: `IF NOT EXISTS` skips the build,
  the file is recorded and the run continues. No manual step. Adoption happens
  only when the index's definition is the one the file builds (checked on an
  empty temporary copy of the table, rolled back). A valid index of the same
  name with another definition stops the run and is not adopted. Drop it with
  `DROP INDEX CONCURRENTLY` if it is not wanted, then rerun.
- A statement the runner cannot read (a `CREATE INDEX CONCURRENTLY` that is
  schema-qualified, for example) stops the run. Write it unqualified.

**A failed build** (a `CONCURRENTLY` build that errors or is interrupted) leaves
an **invalid index** behind. The planner never uses it. Find every one:

```sql
SELECT indexrelid::regclass FROM pg_index WHERE NOT indisvalid;
```

If `pg_stat_progress_create_index` shows the build still running, wait for it.
Otherwise drop the index and rerun:

```sql
DROP INDEX CONCURRENTLY <index_name>;
```

then `pnpm db:migrate`. `pnpm db:verify-schema` reports an invalid index as an
error.

## Enums

```sql
-- @no-transaction
ALTER TYPE campaign_status ADD VALUE IF NOT EXISTS 'archived';
```

Values are **append-only** — Postgres cannot remove one. Mirror the change in
`packages/contracts/src/common/enums.ts` in the same commit.

## Applying

```bash
pnpm db:migrate    # apply pending
pnpm db:status     # applied / pending / modified / missing-file
pnpm db:reset      # dev only: drop schema, re-migrate, re-seed
```

`db:status` exits non-zero on `modified` or `missing-file`, which is what CI
checks.

Concurrent runners are serialised by a session advisory lock, so two app
instances booting together cannot race.

## Zero-downtime changes

| Change                | How                                                         |
| --------------------- | ----------------------------------------------------------- |
| Add a nullable column | safe, one step                                              |
| Add a NOT NULL column | add nullable → backfill in batches → set NOT NULL           |
| Rename a column       | add new → dual-write → backfill → switch reads → drop old   |
| Add an index          | `CONCURRENTLY IF NOT EXISTS`, with `-- @no-transaction`     |
| Drop a column         | stop reading it, deploy, **then** drop in a later migration |
| Change a column type  | new column + backfill; in-place rewrites lock the table     |

Backfills on large tables go in batches with a pause, not one statement:

```sql
UPDATE contacts SET lifecycle_stage = 'new'
WHERE lifecycle_stage IS NULL AND id IN (
  SELECT id FROM contacts WHERE lifecycle_stage IS NULL LIMIT 10000
);
```

## Before production

- [ ] Applied cleanly from scratch in CI
- [ ] Runtime estimated against production-sized data
- [ ] No long `ACCESS EXCLUSIVE` lock on a hot table
- [ ] Forward-compatible with the currently deployed code
- [ ] RLS enabled, forced, and a policy written for every new table
- [ ] Drizzle schema updated in the same commit
- [ ] A rollback plan exists (a forward migration, not a `down`)
