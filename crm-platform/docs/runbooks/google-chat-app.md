# Google Chat app for the alert bridge

Replaces plain incoming webhooks with a real Chat app so alert cards get buttons and can be edited. Code: `tools/chat-bridge/chat-app*.mjs`, `chat-api.mjs`. Feature flag `CHAT_APP_ENABLED` (default `false` = webhooks exactly as before).

## What the official docs say (read 2026-10-22)

| Question | Answer | Source |
|---|---|---|
| App auth with a service account | Scope `https://www.googleapis.com/auth/chat.bot`, no admin approval. Scopes `chat.app.*` need one-time admin approval. Key: Cloud console, IAM & Admin, Service Accounts, create JSON key (Google says exporting a key is not recommended in production). | https://developers.google.com/workspace/chat/authenticate-authorize-chat-app |
| Post a message | `POST /v1/spaces/{space}/messages`, app auth scope `chat.bot`. Body needs `text` or `cardsV2`. Thread: `thread.threadKey` in the body plus query `messageReplyOption=REPLY_MESSAGE_FALLBACK_TO_NEW_THREAD`. `messageId` optional (`client-...`). Max 32,000 bytes. | https://developers.google.com/workspace/chat/create-messages |
| Update a message | PATCH with `updateMask`. The create-messages page does not cover it; the "update messages" guide does. The app can only edit messages it created. NOT re-read in detail, see "Not verified". | https://developers.google.com/workspace/chat/update-messages |
| Posting into a space the app is not in | Not allowed with app auth: "The Chat app must be a member of the space" (exception: spaces the app creates itself). So the app must be added to each of the three spaces. | create-messages page above, authenticate page above |
| Verifying events from Chat | Bearer token in `Authorization` (also in `authorizationEventObject.systemIdToken`); return 401 on failure. Non add-on app, audience "Project Number": self-signed JWT, `iss` = `chat@system.gserviceaccount.com`, `aud` = project number, certs at `https://www.googleapis.com/service_accounts/v1/metadata/x509/chat@system.gserviceaccount.com`. Audience "HTTP endpoint URL": OIDC ID token, email `chat@system.gserviceaccount.com`, aud = endpoint URL. Add-on apps use a different issuer (`service-PROJECT_NUMBER@gcp-sa-gsuiteaddons...`). | https://developers.google.com/workspace/chat/verify-requests-from-chat |
| Reactions as the app | NOT possible. `spaces.messages.reactions.create` supports user authentication only (scopes chat.messages, chat.messages.reactions, chat.messages.reactions.create); the authentication table marks app authentication as not supported. So there is no "add eyes reaction on claim" step; the claim is shown by the edited card (and the thread reply). | https://developers.google.com/workspace/chat/create-reactions , https://developers.google.com/workspace/chat/authenticate-authorize |
| Configuration page | Cloud console, Chat API, Configuration. App name (max 25), avatar URL, description (max 40), Enable interactive features, Functionality "Join spaces and group conversations", Connection settings "HTTP endpoint URL", Visibility (up to five individuals or Google Groups of your org). Non add-on: clear "Build this Chat app as a Google Workspace add-on". Needs a Business/Enterprise Workspace, a project with OAuth consent screen, Chat API enabled. Roles: Chat apps Owner/Viewer. | https://developers.google.com/workspace/chat/configure-chat-api |

The bridge implements ONLY the non add-on, audience = **Project Number** mode (self-signed JWT). Choose "Project Number" in the console. The OIDC "HTTP endpoint URL" mode is not implemented.

Event responses used (from the Chat interaction docs, https://developers.google.com/workspace/chat/receive-respond-interactions): a card click is answered synchronously with `{"actionResponse":{"type":"UPDATE_MESSAGE"}, "text":..., "cardsV2":[...]}` which edits the clicked message in place; a refusal is a `NEW_MESSAGE` with `privateMessageViewer` (only the clicking user sees it).

## How it works

- Flag on: first-firing alert cards and thread replies are created through `chat.googleapis.com` as the app (token from the service-account JWT bearer grant, cached). If the API call fails after retries, that one message goes to the webhook (plain card, no buttons).
- Card buttons: "I'm on it" / "Release" / "Open PR" (repo pull request list) / "Open Grafana". Click = `CARD_CLICKED` with parameters `incidentId`, `action`. Claim goes to the incident store (`resolver.claim` / `releaseClaim` when the team-incident-flow resolver is merged; otherwise an in-memory fallback in `chat-app.mjs`). Success: the card is edited to "eyes NAME is working on this" with a Release button. Claim by another user: refused with a private message. Only the owner can release.
- `POST /chat-app/events`: 401 unless the bearer token verifies (RS256 signature against the fetched certs, kid, iss, aud = `CHAT_APP_AUDIENCE`, exp); body max 64 KB (413); per IP rate limit `CHAT_APP_RATE_PER_MIN` default 60 (429). Events: `ADDED_TO_SPACE` welcome, `CARD_CLICKED`, `MESSAGE` ("claim INC-id", "status", otherwise help).
- Space id per channel: `CHAT_SPACE_<CHANNEL>` (for example `CHAT_SPACE_CRITICAL=spaces/AAAA`) or derived from the existing webhook URL.
- Test-only overrides (`CHAT_APP_TOKEN_URL`, `CHAT_APP_CERTS_URL`, `CHAT_API_BASE`) are ignored unless `CHAT_ALLOW_ANY_HOST=1`. Never set that in production.
- Status line (app mode): the first row of every incident card, from creation: "🟡 Status: Open, nobody has taken it yet" -> "🔵 Status: In progress, **NAME** is working on this since HH:MM UTC" -> "🔵 Status: In progress, PR #N raised by **NAME**" -> "✅ Status: Resolved by PR #N (NAME)" / "Resolved by release sha" / "Cleared on its own". Names are bold (`<b>`, escaped first). The "Suggested action: Claim it" row is removed once the incident is claimed or resolved. RESOLVED stays a bridge decision only.
- Deploy failure (`POST /incidents`, kind `deploy_failure`) follows the same flow in app mode: ONE interactive card in the deploy channel (attempted sha, live sha, PRs, merged by, duration; unknown values omitted), edited in place for claim, PR and the release that resolves it, with no thread replies or announce. Webhook mode, or a failed card create, keeps the old text + "Incident update" card and thread lines.
- PR merged (real time): the bridge polls GitHub every `PR_POLL_SECONDS` (default 60, min 30) for each incident that has a PR (`GET /repos/$GITHUB_REPO/pulls/N`, 6 s timeout, read-only token from the `github_read_token` secret, file `GITHUB_TOKEN_FILE` default `/run/secrets/github_read_token`; no file = polling off). When merged, the SAME card shows "🟣 Status: PR #N merged by LOGIN at HH:MM UTC, waiting for the release to go live" plus a timeline entry (webhook mode: one thread line). RESOLVED is still decided only after the release and verification. A PR closed without merge shows "PR #N was closed without merging, needs a human" and the incident goes back to escalated (never auto-resolved). `GET /incidents` exposes `prMerged`/`prClosed`. Deploy: create `secrets/github_read_token` next to the other secrets before `up -d gchat-bridge` (compose now requires the file).
- One card per incident (app mode only): the firing card is created once and then EDITED in place (PATCH) for every step: claim ("NAME is working on this since HH:MM UTC"), note (shown as "What NAME found", escaped and cut), PR raised (number, summary, allow-listed github PR link, who), PR live in a release, and resolved (header becomes RESOLVED; "How it was resolved": by PR #N (summary) raised by NAME in release sha7, or "cleared on its own, no code change, after N min"; what it measured, how long, peak, verified-clear time). A "Timeline" section lists the last 8 steps with time and actor. The merger is not known to the bridge, so it is not shown. Alertmanager's own resolved notification edits this card instead of posting a second message; the "Still firing" repeat reply and the top-level "announce" lines are also dropped. Claims through the REST incident API (`incident-cli`) edit the card too. If the card could not be created through the API (webhook fallback) or the edit fails, the old thread replies and announce lines are used for that incident. Webhook mode (flag off) is unchanged except the resolved card text: "What it measured / How long it lasted / Peak vs threshold / What cleared it / Owner" replaces "What it was" and "Value now".

## Console checklist (owner)

1. https://console.cloud.google.com : pick or create the project (a Workspace org project). Note the **project number** (Dashboard, Project info). That is `CHAT_APP_AUDIENCE`.
2. APIs & Services, Library, search "Google Chat API", Enable. Make sure the OAuth consent screen is configured (APIs & Services, OAuth consent screen), internal is fine.
3. IAM & Admin, Service Accounts, Create service account (name `threadwise-alerts-bot`, no project roles needed). Open it, Keys, Add key, Create new key, JSON. Download once.
4. Put the key on the server, never in git or chat: `/opt/desk/secrets/chat_app_sa_json`, `chmod 640`, owner root, group the deploy group. Delete the downloaded copy.
5. Google Chat API, Manage, Configuration tab:
   - App name `Threadwise Alerts`; avatar URL optional; description e.g. "Alert cards with claim buttons".
   - Enable interactive features: ON. Functionality: tick "Join spaces and group conversations".
   - Build this Chat app as a Google Workspace add-on: OFF (confirm Disable).
   - Connection settings: HTTP endpoint URL = `https://prometheus-desk.wabo.ai/chat-app/events`.
   - Authentication audience: **Project Number**.
   - Visibility: the people or the Google Group that may install it (max five individuals or groups).
   - Logs: tick "Log errors to Logging". Save.
6. Workspace admin (admin.google.com): Apps, Google Workspace, Google Chat, Chat apps (or "Apps > Google Chat > Settings"): make sure users may "Install apps" / "Allow users to add and interact with Chat apps". If the org restricts apps to an allowlist, add the app. The Google docs do not describe an extra approval for a private app limited by Visibility; the exact admin menu names above are from memory and were NOT verified in a console.
7. Add the app to each space: in Google Chat open the space, space name menu, "Apps & integrations", "Add apps", search `Threadwise Alerts`, Add. Do it for the critical, slow queries and deployments spaces. Get each space id from the space URL (`chat.google.com/room/AAAA...`) and keep for step 8.
8. Server: in `/opt/desk/.env` set `CHAT_APP_ENABLED=true`, `CHAT_APP_AUDIENCE=<project number>`, `CHAT_APP_SA_FILE=/opt/desk/secrets/chat_app_sa_json`, and if the webhook URLs are not enough `CHAT_SPACE_CRITICAL=spaces/AAAA` (also `_SLOWQUERY`, `_DEPLOY`). Run `observability-up.sh` (writes `chat-app.yml` for Traefik), then recreate: `docker compose -f docker-compose.yml -f observability.compose.yml up -d --force-recreate gchat-bridge`.
9. Test: `curl -s -o /dev/null -w '%{http_code}\n' -X POST https://prometheus-desk.wabo.ai/chat-app/events` must print 401 (route reachable, token required). In a space type `@Threadwise Alerts status`. Fire a test alert, press "I'm on it": the card must change to "NAME is working on this"; press it as a second person: only that person sees a refusal.
10. Rollback: set `CHAT_APP_ENABLED=false` in `/opt/desk/.env`, run `observability-up.sh` (deletes `chat-app.yml`), recreate `gchat-bridge`. Webhooks keep working throughout, they are never removed.

## Sentry issues as incidents

With a Sentry token the bridge polls Sentry (every `SENTRY_POLL_SECONDS`, min 30) and opens ONE incident/card per Sentry issue: a new error/fatal issue (first seen < 15 min ago), a regression, or a spike (>= `SENTRY_SPIKE_EVENTS`, default 20, events in the last hour on a known issue). Fatal and spikes go to the critical space, the rest to the Other space (`gchat_other_url`, or the Chat app space). Issues that already existed when the bridge started are ignored unless fatal or >= 10 events/h. The card and `incident-cli show` carry title, culprit, link and up to 5 in-app stack frames (untrusted text). RESOLVED only after the PR is merged, a release containing it is live, and Sentry shows the issue resolved or 15 min with no new event; an issue resolved in Sentry with no PR resolves as "resolved in Sentry by <name or unknown>". No token file or an empty one = feature off.

Owner setup (do not paste the token in chat):
1. Sentry, Settings, Developer Settings, New Internal Integration (org `geta-ai-cj`). Permissions: Project Read, Event Read, Organization Read; nothing else (issue write is not needed). Save, copy the token.
2. Put it on the server without echoing it: `ssh root@<prod> 'read -rs T; umask 077; printf %s "$T" > /opt/desk/secrets/sentry_token; chmod 640 /opt/desk/secrets/sentry_token'` (paste, Enter).
3. Run `GCHAT_URL_DIR=/nonexistent bash observability-up.sh </dev/null` in `/opt/desk` (non-interactive), then recreate `gchat-bridge`.
4. If Sentry is on the EU region set `SENTRY_API_BASE=https://de.sentry.io` in `/opt/desk/.env`. Optional: `SENTRY_PROJECTS=slug1,slug2`, `SENTRY_ENV`, `SENTRY_SPIKE_EVENTS`. Rollback: empty the file (`: > secrets/sentry_token`) and recreate `gchat-bridge`.

## Not verified

Nothing here was run against real Google or real Sentry (tests use local fakes; the Sentry response fields, region base URL and the activity/`set_resolved` shape are from the API docs only). Unverified: exact UPDATE_MESSAGE / privateMessageViewer response shape for a sync response, patch `updateMask` details (the card edit uses `updateMask=text,cardsV2` and was only run against a fake Chat API), that a Google x509 cert from the certs URL loads with `createPublicKey` (done with raw public keys in tests), the CARD_CLICKED field names for your app type (code reads both `common.parameters` and legacy `action.parameters`), Workspace admin menu names, and that Traefik forwards the Google request unchanged.
