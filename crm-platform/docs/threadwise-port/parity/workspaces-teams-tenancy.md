# Parity: workspaces-teams-tenancy (WSP), PR 1: members and teams

Scope of this file: TW-WSP-015 to 022, 046 and the member part of 047 (backend), and the Members and Teams screens. The API
rows come from automated tests; the screens (015..019 and 022) were compared with the running Reference by the Playwright twin test
(section "Twin run" below).

Evidence is automated (real Postgres, real Redis, the real Nest app): `apps/api/test/e2e/workspaces-teams-tenancy/members-teams.e2e.spec.ts`
(one block per TW-WSP id, one named test per acceptance criterion), `test/integration/workspaces-teams-tenancy/members-teams-schema.spec.ts`
(the migration chain with the RBAC presets, RLS, constraints, repositories as the restricted role) and
`test/unit/workspaces-teams-tenancy/member-rules.spec.ts` (tiers and the act-on rule).

**One role model.** This domain does not define roles or keys: it uses the RBAC domain's five workspace presets (Owner = `system_key`
`admin`, Admin = `workspace_admin`, Manager, Agent, Viewer), its keys (`org.member.invite`, `org.member.role_assign`,
`inbox.team.manage`) and its `WorkspaceRoleRulesService` for who may hand out which role (decisions D-RBAC-05, D-RBAC-06 in
[roles-permissions.md](roles-permissions.md)). What stays here is the member lifecycle.

## Status

Built (API + migration + tests): TW-WSP-015, 016, 017, 018, 019, 020 (role model: tiers read from the RBAC presets, act-on rule), 021
(as accept-by-link), 022, 046 (rank guard, applied to the member actions). Not in this PR: TW-WSP-001..014 and 023..045, the
admin staff-user screens (046's original home is `Admin\UsersController`, see below), the web screens.

## TW-WSP-046 and the admin staff-user screens

046's original home is the platform admin's user screens (create, edit, suspend, import accounts across workspaces), which belong to
TW-WSP-038..045 and are not built here. This PR applies the same rule (actor rank must be at least the target's, only an Owner hands out Owner and Admin) to every member
action: through RBAC's `WorkspaceRoleRulesService` for handing out and changing roles, and `member-rules.ts` for remove and reset. The
existing staff-user module (`apps/api/src/modules/admin/users`) uses the same service now, so the two screens cannot disagree.

## Blocked / not built

- Ownership transfer (explicit action) and "leave workspace" are not built; Reference has neither.
- Teammates' avatars (`avatarUrl` is null): the account domain serves only the caller's own picture.
- Realtime presence: values are whatever the inbox stored in `agent_statuses`; no feed exists yet (TIB/TCHAT).
- Invitation mail goes out right after the commit rather than through an outbox consumer: the mail adapter lives in AUTH and there is
  no worker consumer for it yet; a crash between commit and send leaves a pending member whose link can be sent again with "resend".

## Twin run: Members and Teams screens (TW-WSP-015..019, 022)

Playwright twin test, spec `apps/web/e2e/workspaces-teams-tenancy/parity/TW-WSP-015-022.twin.mjs`, Reference 127.0.0.1:8000 against our web
(dev server) and API, scratch database `crm_wsp`. Final state at depth full: 142 scenarios per side (page probes, the invite and
create-team forms with the full value matrix, members list search/filter, member removal, and 16 custom flows: list, search and
filter, invite result and API rules, re-invite of a removed address, role change (screen and API), remove and reset (screen and
API), team create, edit, delete and API rules): no defects, 73 intended differences (below), nothing left in review. Not compared
live: the agent view of the page (a second Reference login would need a temporary password typed into Reference), see the open decision above.

Defects the run found and that were fixed (all inside this domain): the Teams page showed no error state for several seconds when its
data failed (it now reports the access summary failure at once, like Members); after a rejected submit focus did not move to the first
invalid field in the invite and team dialogs; the required fields were not marked required for assistive technology; every keystroke
in the member search replaced the table with placeholder rows (the previous rows now stay, dimmed, until the answer arrives); names
kept invisible characters (zero-width space or joiner) at their ends, which Reference strips (member and team names now trim them).

Same behaviour (compared, equal): both forms' fields, limits and tab order; every generated value case (empty, spaces, boundaries,
unicode, emoji, right-to-left, markup, script, SQL quote, tabs, combining marks, case, padding) accepted or rejected alike, stored
values equal, nothing executes; Enter submits, double click sends once, server error and offline keep the typed values and the form
usable, cancel with typed data then reopen is clean; duplicate email (exact, case, padded) is refused alike; invite returns success and
lists the person as pending; role change feedback and persistence; remove asks first, cancel keeps the row, confirm removes it and it
stays gone; reset asks first and confirms; no-session requests are refused alike on every endpoint; unknown ids and invalid input are
refused alike where Reference refuses; team create with a member, rename and strategy change persist, delete asks first, cancel keeps it;
no console or page errors, no accessibility regression, three viewports without overflow, keyboard traversal, access without a session.

## Teams v2 (BL-381, after the first port)
