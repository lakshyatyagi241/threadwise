# Parity evidence: channel-wechat (WECH)

Reference 1.7.0 vs branch `lakshya/channels/wechat`. Inventory: [inventory/channel-wechat.md](../inventory/channel-wechat.md). API reference:
[docs/api/channel-wechat.md](../../api/channel-wechat.md). Wiring: [wiring/channel-wechat.md](../wiring/channel-wechat.md).

Nothing here was run against a real WeChat Official Account (no AppID, AppSecret or certified Service Account was available), and the
Playwright twin run against the running Reference was not done. Every WeChat call in the tests goes to a fake that records what it was
asked and answers what a test says; the HTTP client (`wechat-api.client.ts`) itself has no test.

## Evidence

- `apps/api/test/unit/channel-wechat/wechat-rules.spec.ts`: 31 tests. Signature (a known sha1 value, wrong token, wrong timestamp, empty), message signature, AES decrypt (round trip with an encryptor written from WeChat's published algorithm in `test/support/wechat-crypto.ts`, wrong key, wrong AppID, damaged and empty payloads), the XML reader (CDATA, entities, DOCTYPE refused, first value wins), every packet kind, the ledger key, the 48 hour window and its boundary, text clipping, tag ids.
- `apps/api/test/e2e/channel-wechat/wechat-channels.e2e.spec.ts`: 10 scenarios on real Postgres and Redis. Connect (secrets encrypted, none returned, token cached with its expiry, inbox channel mirrored, audit and event), WeChat refusing the credentials, validation, a re-pasted AppID keeping its address, a second account, the server config only for managers, re-check, pause and resume, disconnect, tenant isolation and permissions.
- `.../wechat-inbound.e2e.spec.ts`: 20 scenarios. The GET handshake (valid, every kind of wrong signature, unknown address, paused channel, safe-mode encrypted echo), the POST signature, the flood limit, the first message (thread keyed by the OpenID with its case kept, contact, unread, `wx_id` learnt), a redelivery stored once, two followers, the same OpenID on two accounts, nickname and photo learnt afterwards and asked once, a profile WeChat will not give, follow, unfollow and other events, a menu tap, an image downloaded with the token, voice text, location, link, unknown type, an image WeChat will not hand over, a bad or oversized or entity-declaring body, AES safe mode.
- `.../wechat-sender.e2e.spec.ts`: 23 scenarios through the real `ChannelDispatcher`. The registered adapter and its capabilities, a send with the account's token, one send per client reference, the 2048 character cut, the window refused before WeChat is called, a template message, a paused or removed account, each WeChat refusal code, a transport failure, the token (cached, replaced five minutes before expiry, ONE fetch for four racing sends, refreshed once on 40001, twice at most, a refused token request shown on the channel), files (caption first, voice, video, document refused, unreadable, over 10 MB, refused upload), and downloading a follower's file.
- `.../wechat-broadcasts.e2e.spec.ts`: 24 scenarios. The audience, the compose page, a draft with a frozen audience (forged and repeated OpenIDs dropped, text encrypted), fewer than two recipients, all and tag audiences, form validation, foreign channel and template, Send queueing one job, the one call for all followers, a tag and a list (with the broadcast uuid as `clientmsgid`), the copy into each thread without raising unread, a paused channel before and after Send, the worker processor, a failed broadcast and its retry, a transport failure, a duplicate client message id, Retry refused for a draft or a fresh send, recovery of a send stuck for 15 minutes, list order and the 50 cap, delete in any status, deleting the channel, permissions.
- Web (vitest): `compose-model.test.ts`, `connect-model.test.ts`, `broadcast-model.test.ts` (the create rule, the connect rule, the row button), `channel-card.test.tsx` (what a manager and a reader see, the Token never fetched until asked), `channel-cards.test.ts` (the WeChat chooser card).

## Intended differences from Reference

| #   | Area                          | Reference                                                      | Here                                                                                                                                                                      |
| --- | ----------------------------- | -------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | Access                        | Plan flags `access_wechat`, `wechat_broadcasts`, no role check | Permission keys `wechat.channels.read` and `.manage`, `wechat.broadcasts.read` and `.manage`, and the one plan feature `extra_channels`.                                  |
| 2   | Webhook address               | `/api/wechat/inbound/{token}`                                  | `/v2/wechat/inbound/{token}`. An address already pasted into WeChat must be pasted again.                                                                                 |
| 3   | The Token                     | Printed on the hub page for everyone                           | Shown only when a person who manages the channel asks (Show); the connect modal shows it once from what they typed. The AppSecret and the EncodingAESKey are never shown. |
| 4   | Connect form                  | Inline on the hub page, a "(Phase 2)" tag on safe mode         | A modal (decision of the channel port brief); the safe-mode option works, so it has no tag.                                                                               |
| 5   | Safe mode without a key       | Accepted, then every encrypted message is silently dropped     | Refused with a message (422, and in the form).                                                                                                                            |
| 6   | URL check in safe mode        | Echoes the encrypted `echostr`, which WeChat rejects           | Checks `msg_signature`, decrypts and answers the plain text. Not verified against WeChat.                                                                                 |
| 7   | Tag audience without a number | Accepted, sends to tag 0                                       | The tag ID is required (a number; 0 is allowed).                                                                                                                          |
| 8   | Where the mass send runs      | Inside the Send request                                        | In a worker job (`wechat-broadcast`, one attempt); the row goes Draft, Sending, Sent or Failed. The list polls while it sends.                                            |
| 9   | Double send protection        | None                                                           | The broadcast uuid is WeChat's `clientmsgid`, a duplicate (45065) ends the broadcast `done`, and a send stuck for 15 minutes can be retried. Unverified against WeChat.   |
| 10  | Retry                         | The Send button works again on a failed broadcast              | Same button; a `retry` endpoint and `canRetry` exist for it, with their own event.                                                                                        |
| 11  | Pause                         | None                                                           | None (a mass send cannot be taken back). The generic start, pause, retry, delete of the other channels has no pause here.                                                 |
| 12  | `wx_id`                       | Declared, shown, never filled                                  | Filled from the first inbound message (`ToUserName`).                                                                                                                     |
| 13  | Redelivery                    | No dedup: WeChat's retries stored the message again            | Stored once (ledger key the `MsgId`, or event, user and time).                                                                                                            |
| 14  | Profile fetch                 | Before the thread is shown, blocking the answer                | After the answer, with a 5 second cap; the thread starts as "WeChat" and takes the nickname when WeChat gives one.                                                        |
| 15  | Placeholder text              | `[image]`, `[video]`, `[voice]` stored as the message text     | The inbox shows the file itself; only a voice note with WeChat's speech text, a location, a link or an unknown type has text.                                             |
| 16  | Delete a channel              | Its broadcasts stay and refuse to send                         | The schema cascades: its broadcasts and recipients go.                                                                                                                    |
| 17  | Ids                           | Numeric database ids in URLs                                   | Uuids.                                                                                                                                                                    |
| 18  | Rate limit                    | 240 a minute per address                                       | Same, per routing token, in Redis (429).                                                                                                                                  |
| 19  | Menu and Insights buttons     | On the hub when a channel exists                               | Not shown: the pages are not built (TW-WECH-017, 018 blocked).                                                                                                            |
| 21  | Replay                        | A signed request is accepted whatever its timestamp            | A timestamp more than ten minutes from now is refused (403), on GET and POST, so a seen URL cannot be replayed.                                                           |
| 22  | Safe-mode downgrade           | A plain packet is processed in safe mode                       | Ignored: a safe-mode account only trusts encrypted packets.                                                                                                               |
| 23  | Concurrent connect            | Could make two rows for one AppID                              | Serialised by an advisory lock per workspace and AppID.                                                                                                                   |
| 20  | Select all                    | None                                                           | None (Telegram's compose has one; this one keeps Reference's list).                                                                                                       |

Known and left as they are (found in review): a channel's error is cleared by any signed push, not only by a good token (as in Reference); a send whose answer was lost is retried relying on WeChat's `clientmsgid` window (unverified, about a day); a failed queue add resets the broadcast to draft; a video reply uses its own media id as thumbnail (as in Reference); an inbound video is not downloaded (WeChat answers a link, not bytes), it is stored without the file.

## Stubbed inputs and open gaps

| Item                                | Real owner                                 | Effect now                                                                                                                                                                  |
| ----------------------------------- | ------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Flow and keyword automation         | flow-runtime-engine, routing, auto-reply   | None of it is called from this module. The thread is a `wechat` channel, so the inbox's inbound listeners see every stored message; whether a WeChat flow starts is theirs. |
| Inbox template picker               | team-inbox-conversations                   | Lists WhatsApp templates only, so no inbox screen sends a WeChat template message; the adapter and the dispatcher accept one.                                               |
| Reply window wording                | chat-conversations                         | The dispatcher's refusal text says "24 hour"; the window here is 48 hours (the adapter reports 48, which the thread's window countdown reads).                              |
| ConsentGate on the broadcast sender | contact-consent                            | `broadcast-sender.service.ts` is listed as a known gap: WeChat resolves an all-followers or tag audience, so it cannot be screened per contact.                             |
| Plan flags and the platform switch  | plans-subscriptions-trials, platform admin | One plan feature; `wechat_channels_limit` and `wechat_enabled` are not enforced (Reference never enforced the limit).                                                       |

## Not verified

- No call reached WeChat. Not exercised against the real service: the token request, the custom, template and mass-send APIs, the media upload and download, the user info call, the parameters `clientmsgid`, `is_to_all` with `tag_id`, the error codes 45015, 45047, 43004, 40003, 45065 and 45028, the AES URL check, and the access-token invalidation behaviour.
- The 5 second limit of WeChat's webhook under a slow media download is not measured; a retry is harmless (deduplicated).
- The screens were typechecked, linted and render-tested, not opened in a browser and not compared with the running Reference.
- Translations were written by a model, not reviewed by native speakers; the WeChat product terms (Official Account, Service Account) in it, nl, pl, tr, hi, bn, ur, th, vi, id, ko, ja and the right-to-left languages in particular deserve a native check.
