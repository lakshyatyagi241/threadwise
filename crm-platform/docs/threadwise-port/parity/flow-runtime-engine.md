# Parity: flow-runtime-engine (FLR)

What differs from Reference 1.7.0, and why. Status per feature is in the [tracker](../tracker/vedant.md); the map of what is wired where is in
[wiring/flow-runtime-engine.md](../wiring/flow-runtime-engine.md). Everything below was built from the inventory and the reference source
(`node/services/flowService.js`, `app/Services/Flow/FlowEnrollmentService.php`, `app/Services/Flows/FlowNormalizer.php`).

## The decision the inventory asked for: live runs in memory (QUIRK)

Reference holds every run in one Node process. A restart, a deploy, a device disconnect, the 30-minute sweeper (which deletes a run an hour after
it STARTED, even one the customer answered a second ago) or a second keyword ends a run silently, and a Delay longer than about an hour never
finishes. **Decision: fix it.** A run is a row (`flow_runs`) and a step is a queued job; a Delay is `status = sleeping` with a wake-up time. What
that changes for an author: a flow may wait days; an idle wait is measured from the last activity (10 minutes for a typed keyword, 24 hours for
a flow started by enrolment, an event or a campaign, because nobody is at the keyboard when those begin); a run lives at most a week unless a
Delay needs longer (then the wake-up plus a day). What it does not change: one live run per customer per channel, a new start replaces the old
one, the loop guard stays at 20, a flow ends only at an End node or when nothing tappable remains.

## Not built, and what it costs the author today

- **Template node (026).** On the Cloud API a flow started by enrolment, an event or a campaign cannot open a conversation with free text, so it
  fails `SERVICE_WINDOW_CLOSED`. Keyword-started flows are unaffected (the customer wrote first). Needs the template library's lookup (TPL).
- **Integration and AI nodes (030 to 048).** The node is kept in the graph and the run notes "no executor" and moves on; nothing is lost when
  the editor saves one.
- **Other-channel engines and the call flow (060 to 069).** The runtime sends through the inbox's channels (WhatsApp Cloud API, QR, Telegram,
  web chat, simulator). Facebook, Instagram, TikTok, LINE, Viber, WeChat, email and voice have no inbox channel adapter yet.
- **Producers that do not exist yet:** `order.placed` (commerce), `contact.opt_in` with `optedIn: true` (a person re-subscribing), the routing
  rule's `trigger_flow`, the lead webhook's flow, the Instagram and Facebook hand-off. Each is one call to `FlowTriggerService` or
  `FlowLaunchService.start`; the consumer for the two events is in place.
- **A customer's file as an answer** is held as `chatmedia:<key>` in the variable (Reference stored a public link). A Media node can send it back;
  a webhook or a sheet cannot read it until those nodes exist.

## Nodes, integrations and the analytics screens (TW-FLR-026 to 069)

- Built, each with unit and e2e specs in `test/unit|e2e/flow-runtime-engine/`: Template, Book appointment, Commerce shop, WhatsApp Form (the commerce group); AI, Sub-flow
  and natural-language ordering; Webhook, Code, Google Sheets, Docs, Form and Meet, AI call; Tag, Assign agent, Deal, Copy-to-number, WhatsApp-to-Instagram link. The
  analytics screen gained history, error and retry tabs. Evidence: 218 unit and 80 e2e tests in this domain, all passing; the analytics tabs were also opened in a real browser.
  Nothing ran against real Google, MySQL, Meta or an AI vendor, and there is no Playwright twin run.
- Deviations: conversation mode with extraction answers in plain language each turn and extracts once on exit (Reference forced JSON every turn, which sent raw JSON to the
  customer); Sub-flow refuses an unpublished, paused or other-workspace flow (Reference served any id from any tenant) and does not return to the parent; with no AI agent engine,
  Chatbot passes the node instead of ending the run; Webhook adds an `Idempotency-Key`, refuses private hosts and redirects, and its `_threadwise` envelope has empty device fields
  because the run does not carry channel details; MySQL requires a public host; Google nodes use UTC; Google Form waits on a run, not on a `google_form_sessions` table, with a
  per-org token; Tag acts on the contact, not the conversation, and removing a missing tag no longer creates it; Assign agent with a team and no member keeps the thread on the
  team (only the manual strategy exists); Deal moves across pipelines with the deal and fires `deal.stage_changed`; Copy-to-number reads the 24-hour window from the target's own
  thread; ordering takes the workspace from the API key, reads an English reply as typed and translates only when unclear; analytics counts launches that failed before a run
  existed, dates are UTC, paging is by cursor, a retry that fails again is a 200 with `outcome: failed`, and "skipped" is an extra outcome.
- Editor-saved flows: `compileGraph` applies the editor's field mapping (`flbToRuntimeData`) and the Template, AI and AI call nodes resolve the template / assistant uuid the editor
  saves, scoped by workspace (`flow-refs.ts`); an integer id still works. Proof: `compile-flb-hook.spec.ts`, `flow-refs.spec.ts` and `editor-flows.e2e.spec.ts`. Instagram's send,
  ask, quick replies, link buttons and AI reply run on the shared executors and both WhatsApp hand-offs have a node (deviations: postback buttons of an Instagram button
  message are not kept; direct mode launches through the outbox and the launch service rather than Reference's enrol call). The 16 types still without an executor:
  the `cf_*` call flow, `ig_products`, `fb_products`, `fb_gallery`, `ig_lead`, `fb_lead`, `ig_reply_comment`, `fb_reply_comment` and `tg_payment`.
- Known limits: a Deal step can create two deals if its write loses the compare-and-set and the step re-runs (no idempotency key on deals); Mirror mode copies only what Message and
  Media record; the Code node starts a worker per run and `vm` is not a hard security boundary.
- Not built, with the reason: see the wiring map (AI agent hand-off, MySQL driver, voice call adapter, Google account store, shop adapter, voice and photo orders, Telegram
  payment, the call flow).

## Workflow additions (beyond Reference)

Not Reference features: the team's gap list against the older workflow product, built as TW-FLR-072 to 082. Deviations from a plain port are
deliberate: a list, field or update made by a flow never starts list or update flows (Reference's Tag step never did either, and it stops
loops); a field-match flow runs once per value a contact takes; a schedule starts at most 5,000 people per occurrence; an abandoned cart is
announced when the store's first cart follow-up is due; date matches read custom contact fields only. Evidence: `crm-nodes`,
`schedule-rules`, `sheet-nodes`, `flow-events` unit specs and the `flow-workflow-gaps` e2e. No Playwright run and no real Google, Shopify or
WooCommerce delivery.
