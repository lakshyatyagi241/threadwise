## Differences from Reference

1. **The OAuth state is sealed, not a session value.** There is no PHP session here, so the state is an encrypted, 15 minute value naming the organization, the user and the store; the callback is a public route (Shopify redirects a bare browser) and carries the user in that state. The same login-CSRF guard, and a callback for a different store than the one asked for is refused.
2. **The callback ends on the Shopify screen**, `/shopify?shopify=connected|error&message=...`, as the Facebook one does; Reference redirected with a session flash.
3. **A webhook address is `/v2/shopify/webhook/{secret}`** (and `/v2/woocommerce/webhook/{secret}`): webhooks are registered at connect time, so a store connected here already has the right address; a store connected in Reference has to be connected again.
4. **A WooCommerce address is checked against private and loopback ranges** before any call (Reference would call anything the merchant typed); `ECOM_ALLOW_PRIVATE_STORE_URLS` turns it off for a store on the same network. Shopify calls only `*.myshopify.com`, validated at every call, and never follows a redirect.
5. **Reconnecting removes the old webhooks with the old key**, then saves; Reference did the same but swallowed every failure silently, the port logs how many webhooks registered.
6. **Disconnect is `DELETE` and answers 204**; Reference redirected with a flash.
7. **The Shopify secret is never shown and a save is audited** with the names of the fields that changed, not their values.
8. **Every page is read** (up to ten pages: 2,500 products, orders or customers on Shopify, 1,000 on WooCommerce); Reference read only the first 250 or 100 and dropped the rest without saying so. A cut-short read is recorded (`incomplete` in the sync stats).
9. **The import runs in a worker**, and "Sync now" answers at once with the store's totals and `importQueued`; Reference imported inside the request and returned the counts. The connect lands on the store screen without waiting.
10. **A Shopify product with no SKU gets `SHOPIFY-<id>`**; Reference saved an empty SKU, which anything that finds a product by SKU (reorder, the flow commerce node) cannot use. Availability is set from stock too (Reference left every product "in stock").
11. **An empty phone no longer hides a filled one.** WooCommerce sends `""` for a blank field; Reference fell through only on null, so an empty billing phone hid the shipping phone. The first filled value is used, for phone and country.
12. **Two products with one slug both import** (the second gets its id on the end); a customer is found by number as digits or with a `+`; the customer group id is kept on the store so a renamed group is still the one used.

13. **A webhook is answered at once and worked in the worker.** The address is `POST /v2/shopify/webhook/{secret}` or `/v2/woocommerce/webhook/{secret}`; the secret only finds the store (through a SECURITY DEFINER lookup, no tenant exists yet) and the signature proves the sender: `bad hmac` / `bad signature` (401) and `not found` (404) as Reference. Reference did the work inside the request.
14. **A delivery id is remembered for a day**, so a store's retry of a delivery already taken is dropped (Reference processed every retry again). A delivery that cannot be queued answers 503 and forgets the id, so the store retries.
15. **A WooCommerce `order.<status>` automation fires once per order and status**; Reference messaged on every update that carried the status. Only the cart steps wait for a delay (as in Reference), as their own delayed job; every other automation sends at once whatever delay was saved.
16. **A failed message says why on the log row** (no Cloud API number connected, template not approved, no phone), and a failing step never stops the mirror upkeep that follows it.
17. **Saving automations validates the template and the sender** (Reference saved whatever id arrived): a template of another workspace, an automation turned on without a template, or a "send from" number that is not connected is a 422. The template travels as its uuid, never its internal id.
18. **Messages go out through the chosen "send from" number, else the workspace's default engine**, as Reference's notifier: a Cloud API number sends the approved template with the numbered values; the unofficial engine and Twilio send the template as rendered text (header, body and footer, named and numbered tokens filled, unknown ones removed). Not yet on the text engines: the template's buttons and carousel, and Twilio's content-SID path (Reference sent buttons on the unofficial engine and a content SID on Twilio); the body text is sent instead.
19. **Delivered** (`fulfillments/update` with `shipment_status = delivered`) reads the customer from the mirrored order and falls back to the shipment's destination phone, as Reference; its context also carries the shipment's tracking fields, which Reference left blank.
20. **App uninstalled** clears the token to an empty string (the column is NOT NULL here, null in Reference) and the connected time; the row, mapping and logs stay.
21. **The privacy webhooks** (`POST /v2/shopify/compliance`) behave as Reference (401 `bad hmac` before reading, then always 200); the shop is found case-insensitively through a SECURITY DEFINER lookup, and `customers/redact` with no phone erases all of the shop's logs, as Reference does.
22. **The automation list** is Reference's 16 Shopify and 21 WooCommerce types; `fulfillments/update` and `app/uninstalled` are webhooks handled, not automations to map. A delivery logs `skipped` when no automation is active, `sent` or `failed` after the send, as Reference.
23. **A COD reply settles the confirmation once.** The pending row is closed with a guarded update, so two replies arriving together answer the customer once (Reference read, then wrote). Everything else is as Reference: yes or no words, the newest pending row for the number, the mirrored order becomes `confirmed` or `cancelled`, WooCommerce's real order goes to `processing` or `cancelled`, a `cod/reply` log, and the same two answers.
24. **The thank-you, stock "Done!" and concierge answers go as plain text through the same sender** (the chosen or default engine, no template), as Reference's raw sender did.
25. **The WooCommerce risk score looks up the customer by the same normalised number the mirror stores, and leaves the order being scored out of its own history.** Reference matched the raw billing digits against normalised numbers (a local number never matched) and, because the mirror was already updated, an international number counted its own order, so "first-time buyer" almost never fired.
26. **The prepaid nudge, Delivered and the WooCommerce status automations go to the customer only** (as Reference's pseudo events), whatever `send_to` says; a missing phone or template writes no log row.
27. **Back in stock** reads the product's previous state before the mirror is updated and fires only on out to in, as Reference. Joining the list is once per customer and product while waiting (an advisory lock makes a double message safe); only a product that carries the store's own id can be waited for (Reference's Shopify side also matched products with none and stored an empty id); the "Done!" answer goes as session text on the Cloud API number. Customers are marked notified whether or not their send worked, as Reference, so a restock tells each at most once.
28. **Cart recovery steps are delayed jobs**, not scheduled-message rows: each step waits at least 60 seconds (an hour when no delay is set), and an order for the shopper's number removes the pending jobs and closes the recovery, as Reference cancelled its scheduled messages. A job that could not be removed is stopped when it comes due because its recovery is closed. The step fills the template with the checkout's values (name, checkout link); Reference's scheduled message carried the template with no values. The step's outcome is logged as `cart/step2` or `cart/step3`, which Reference did not log. The checkout token is stored encrypted.
29. **Offer and win-back run in the worker.** The request checks the plan, the template and that the audience is not empty, writes the `offer/broadcast` or `winback/broadcast` log row and answers `{ok, total, queued}`; the worker sends one by one and writes `{sent, failed}` and the first error on that row. Reference looped inside the request and answered `{ok, sent, failed, total}`. The messages for empty audiences and unknown templates are the same.
30. **The win-back segment is limited to the store's own orders for both stores** (Reference's Shopify side read every order of the workspace). The offer's contact name is the first word of the contact's name (Reference had a separate first-name field). The group and the template travel as uuids.
31. **The concierge keeps its pending address edit in Redis for 15 minutes** (Reference used its cache) and answers as session text on the Cloud API number. Intents, answers, gates and logs (`order/edit-request`, `order/edit-apply`, `reorder`, `loyalty/query`, `review/reward`) are Reference's; the reward goes through the same sender (and the store's chosen "send from" number) as every other automation. A reorder mints a pending WooCommerce order for the last basket by sku through the REST API, as Reference's link builder did; the flow commerce node's use of that builder stays blocked (TW-ECOM-036).
32. **`EcomInboundService.handleInbound(orgId, phone, text)`** runs Shopify COD reply, Shopify stock opt-in, WooCommerce COD reply, WooCommerce stock opt-in and the WooCommerce concierge in that order, each guarded and none stopping the others, and returns the names of the handlers that took the message. The team inbox calls it for every inbound message (a hook the inbox owns); the catalog concierge that Reference runs after these belongs to the catalog domain.
33. **The Shopify dashboard is limited to the store's own rows.** Reference listed every product and order of the workspace (any source) and the 50 newest contacts of any kind under "Customers"; the port shows products and orders that came from the store and the members of its customer group, and the counts are those, labelled as the mirror (Reference's "from Shopify counts API" label was not true). The WooCommerce lists are live from the store as in Reference (10 each, newest first) and the sales report is the store's own 30 days; a store that does not answer leaves them empty. Coupons are the workspace's active checkout coupons.
34. **The dashboard answers in one read** (`GET /{shopify|woocommerce}/stores/:id/dashboard`) instead of a page render per tab.
35. **The dashboard's template list carries each template's engine and Cloud API account** (Reference's `engineKey` rules) so the screen can narrow it to the chosen "send from" number, and leaves out templates of other channels (Instagram, Facebook, Telegram, ...) that a WhatsApp automation cannot send.
36. **The store screens are `/shopify` and `/woocommerce`** with the tab in `?tab=`, built from the dashboard API: connect page (setup rail, form, guide), status card, tab rail with counts, webhook health card, "Sync now" (queues the import and reads the dashboard again after a few seconds, where Reference reloaded), Disconnect with a confirmation. Shopify's approval redirect returns with `?shopify=connected|error&message=` and is shown once.
37. **Not yet on the screens:** the Invoices tab (TW-ECOM-035, waits for the invoicing domain's panel) and the WooCommerce companion plugin download card in Settings (TW-ECOM-032, an owner decision). The "Send" button on a Shopify product card links to the catalog composer (`/catalog/send?product=<id>`), which the catalog domain provides; "Integrations" in the breadcrumb is plain text because the Integrations hub is not built yet.
38. **Differences in the lists:** the WooCommerce products tab shows stock (in or out) where Reference showed the publish status and the Woo customers table has no "Joined" column (the dashboard row carries the order count and spend, as the Shopify one); the Shopify automation card shows the admin number only when the admin is a recipient, as Reference, and the WooCommerce card never shows it (Reference has no field there either, so "Admin only" on WooCommerce has no number to send to).

## Shims

- `StoreMirror` (`_shims/sql-store-mirror.ts`): writes `wa_products`, `wa_orders`, `contacts` and the customer group directly until the catalog, checkout and contacts domains export their writers (a contact is created without a quota check or a `contact_identities` row, as the Facebook and Telegram channels do).
- `EcomTemplates` (`_shims/sql-ecom-templates.ts`): reads `wa_templates` (sendable: not submitted to Meta, or approved) until the templates domain exports its lookup.
- `CommerceSender` (`_shims/engine-commerce-sender.ts`): sends through the chosen or default engine's number using the broadcasts engine adapter (Cloud API templates) and the shared outbound layer (text for the unofficial engine and Twilio).
- `EcomPlanGate` (`_shims/open-gates.ts`): `integration_shopify` and `integration_woocommerce` are not in the plan catalogue; every check passes.
