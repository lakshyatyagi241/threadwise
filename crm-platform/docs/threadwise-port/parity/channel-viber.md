# Parity evidence: channel-viber (VIB)

Reference 1.7.0 vs branch `lakshya/channels/viber`. Inventory: [inventory/channel-viber.md](../inventory/channel-viber.md). API reference:
[docs/api/channel-viber.md](../../api/channel-viber.md). Wiring: [wiring/channel-viber.md](../wiring/channel-viber.md).

Evidence so far is automated. Nothing was run against Viber itself and the Playwright twin run against the running Reference has NOT been done (see "Not verified").

- `apps/api/test/e2e/channel-viber/viber-channels.e2e.spec.ts`: 12 scenarios (connect with the account check, the encrypted token, the registered webhook and the inbox channel; the same account again; a rejected token; a short token; a refused webhook; re-hook; toggle; disconnect; tenant isolation; permissions; a removed channel's webhook) against a real Postgres and a fake Viber.
- `apps/api/test/e2e/channel-viber/viber-inbound.e2e.spec.ts`: 21 scenarios (unknown token, wrong, missing and foreign signatures, the raw body, the validation ping, a paused channel, a junk body; first message and its thread, contact and channel liveness; redelivery by token; reopen; a name arriving later; two users and two workspaces; picture, location, contact, sticker and unknown types; subscribe, conversation_started and unsubscribe; receipts on a reply, a failed receipt, a receipt applied to a thread message; insights).
- `apps/api/test/e2e/channel-viber/viber-sender.e2e.spec.ts`: 12 scenarios (the adapter is registered and live; a reply as the bot with the token returned; a gone, paused and foreign channel; status 6; an empty text; picture, video and file replies; a send through the real `ChannelDispatcher`, idempotent per client reference; a Viber refusal; a deleted channel and an unsupported kind; a local-disk file).
- `apps/api/test/e2e/channel-viber/viber-broadcasts.e2e.spec.ts`: 22 scenarios (audience and a subscribe-only user; draft freeze, forged ids, encrypted body, empty and no-recipient refusals, attachment kinds and size; a template and its keyboard; a 302-user run as calls of 300 and 2 with `failed_list`, the token on each row and the inbox mirror; a rejected call failing its batch, then retry and start; picture and video; a channel paused after Start; pause then start without double sends; start, retry, pause refusals; delete mid-run; list totals; delivered, seen and failed receipts reaching the broadcast, the mirrored message and a retry; another workspace's token; isolation; permissions).
- `apps/api/test/unit/channel-viber/*.spec.ts`: 40 tests (routing token, https address, signature on the raw body, big message tokens, attachment rules, the events and message kinds, Viber message objects and keyboards, a batch's `failed_list`, insights days and rates).
- `apps/web/src/features/channel-viber`: 22 tests (compose rules, row buttons, insights numbers; the hub, broadcasts list and insights screens rendered with the English messages, a missing key being an error).

## Intended differences from Reference

| #   | Area                            | Reference                                                                                                      | Here                                                                                                                                                                                                                                                                                                                          |
| --- | ------------------------------- | -------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | Access                          | Plan flags `access_viber`, `viber_broadcasts`; no workspace-role guard                                         | Permission keys `viber.channels.read                                                                                                                                                                                                                                                                                          | manage`, `viber.broadcasts.read | manage`; one plan feature `extra_channels` on every controller (foundation decision). |
| 2   | Webhook address                 | `/api/viber/inbound/{token}`                                                                                   | `/v2/viber/inbound/{token}`. Existing webhooks must be re-registered once ("Re-hook").                                                                                                                                                                                                                                        |
| 3   | Ids                             | Numeric database ids in URLs                                                                                   | Uuids.                                                                                                                                                                                                                                                                                                                        |
| 4   | Connect answer                  | Redirect back with a flash message                                                                             | 201 with the channel and a `webhookError` field; a refused webhook is not an HTTP error.                                                                                                                                                                                                                                      |
| 5   | Receipts on broadcasts          | The mirrored copy and the recipient kept no message token, so `delivered` and `seen` never reached a broadcast | **Improvement (asked for).** The call's message token is stored on every recipient (a batch of up to 300 shares one, so a receipt is matched on token and user); `delivered`, `seen` and `failed` stamp the row and the broadcast's totals, and the thread copy moves too. Migration `20261203090200_vib_receipt_tokens.sql`. |
| 6   | A failed receipt                | Only flipped the outbound inbox message                                                                        | Also turns that broadcast recipient failed with Viber's reason, so Retry sends it again.                                                                                                                                                                                                                                      |
| 7   | Send loop                       | Driven by an open browser tab (a batch every 500 ms); closing it paused it                                     | A worker job (`viber-broadcast`); closing the page does not pause it. "Pause" replaces "Resume".                                                                                                                                                                                                                              |
| 8   | Counters                        | Incremented per row                                                                                            | Recomputed from the recipient rows after each batch, so an interrupted batch cannot drift them.                                                                                                                                                                                                                               |
| 9   | The "Sending" tile              | Counted over the 50 rows listed                                                                                | Counted over all broadcasts (the totals are one query).                                                                                                                                                                                                                                                                       |
| 10  | Subscribe in the inbox          | A thread with no message is allowed                                                                            | The inbox holds no empty thread, so a subscribe (or conversation_started) of a new user leaves one small system line "Subscribed to the Viber account". No line is added to a thread that exists.                                                                                                                             |
| 11  | Where the thread lives          | `conversations` with `channel = viber` and the key `viber:<channelRowId>:<userId>`                             | One `viber` inbox channel per Viber account (its handle the channel's row id; paused or removed = switched off), a thread keyed by the Viber user id (case kept) on it. Replies from the inbox leave from that channel.                                                                                                       |
| 12  | Storing a message               | Direct SQL, no dedup                                                                                           | The shared inbound pipeline: a redelivered event is stored once (ledger key = Viber's message token, kept as text because it is a 64 bit number), with unread, reopen and realtime.                                                                                                                                           |
| 13  | Video and file size             | Sent as 1 byte                                                                                                 | The real size when known (an uploaded file, a reply from the inbox); 1 for a pasted address of unknown size, as Reference.                                                                                                                                                                                                    |
| 14  | Attachment on compose           | File picker (26 MB, jpg, jpeg, png, gif, mp4)                                                                  | An address of such a file, or an upload through the workspace storage (`POST /v2/media/marketing`, which allows 20 MB, below Viber's 26 MB). Reference's extra 6 MB through the picker is not reachable; a larger file can be hosted and its address pasted.                                                                  |
| 15  | Insights window                 | Delivered, seen and failed counted over all time under "(7d)" labels                                           | Counted over the same seven days as the rest. Bug fix.                                                                                                                                                                                                                                                                        |
| 16  | Mirror of a file-only broadcast | An empty bubble                                                                                                | The bubble reads `[image]` or `[video]`.                                                                                                                                                                                                                                                                                      |
| 17  | Connect form                    | Inline on the page                                                                                             | Inline on the page (same). The brief for this port mentioned a connect modal; Reference's screen has none, so none was built.                                                                                                                                                                                                 |
| 18  | Delete of a channel             | Its broadcasts stay and refuse to start                                                                        | The schema cascades: deleting a channel deletes its broadcasts and recipients.                                                                                                                                                                                                                                                |
| 19  | `{{name}}` in a body            | Not replaced (one message goes to 300 users)                                                                   | Same: a body is sent as written.                                                                                                                                                                                                                                                                                              |

## Not verified

- **Nothing was run against Viber.** No auth token, no real webhook delivery: the REST client (`ViberBotApiFactory`: header, body shape, `status` handling, 64 bit token parsing) is covered only by the pure-function tests and through the fake. The signature rule is tested against HMAC values computed in the test, not against a delivery signed by Viber.
- The Playwright twin run against the running Reference was not done; screens were compared with the Blade source only.
- Viber's picture rules (size, format) and the `rich_media` messages (Reference's `richMediaMessage` builder, unused by its screens) are not ported.
- The flood limit (240 a minute per token) is not covered by a test.
- Inbound file download from Viber's CDN was not exercised against the real host (the test only proves a non-Viber address is refused and the message is still stored).
- The 3-second polling while a broadcast is sending is not covered by a test.
- Flow and automation hand-off (TW-VIB-017): the flow runtime's launch for `viber` was not exercised.
