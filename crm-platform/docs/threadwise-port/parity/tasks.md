# Parity evidence: tasks (TW-TASK-001 .. 014)

Reference 1.7.0 (Docker reference, workspace user `user@threadwise.test`, workspace "Parity Workspace", UTC) against our build at branch
`lakshya/contacts/contacts-port` (working tree on top of `dfcdceb`), run on 2026-10-02 by a Playwright + HTTP pass on both apps.
Scope: the My tasks screen, create, edit, complete and reopen, delete, assignee, links, overdue buckets, filters, empty and
boundary states, double submit, permissions, 390 px, RTL, XSS. Companion file for deals: [deals-pipelines.md](deals-pipelines.md).

The Tasks hub (tabs, bulk actions, drawer, notifications, mirrored deal timeline tasks) is an **owner-requested extension**
(product-extensions.md, item 5 and 10); Reference has a minimal page. Every difference that comes from it is `intended` and cites
that item. Differences that settle a "Differences to decide" row cite the `D-nn` of
[the inventory](../inventory/tasks.md#port-decisions).

## How this was run, and its limits

- Reference side: UI actions in Chromium for what a person does (page, modal, complete, reopen, delete), and in-page `fetch` with the
  page's CSRF token for the boundary cases, followed by read-only `SELECT`s on the reference database to see what was stored. The
  reference answers about one request a minute (a single-threaded `php artisan serve` shared with other sessions), which is why the
  matrix is narrower than the one run on our side.
- Our side: the same inputs through the web app (Playwright) and the API (`/v2/tasks`), including a second user with a read-only
  role (viewer) and the seeded Agent (own scope).
- The reference workspace has no subscription package, so every feature flag defaults to on there: **the plan gate cannot be
  reproduced on the reference** (rows marked "not verifiable"). On our side the 422 `PLAN_FEATURE_LOCKED` answer is covered by the
  e2e suite and was exercised in the browser with an intercepted response.
- The worker process was not running during the session, so the due-reminder sweep and the notification consumers were checked
  through the existing rows and the e2e suite, not live.

## Not verifiable here

- The plan gate on the reference (no package defined, features default on) and our real plan lock beyond the intercepted response.
- The due reminder sweep and the assigned, due and completed notifications end to end (worker not running).
- The reference's RTL layout, double submit and script-in-title behaviour on the tasks page.
- Calendar, CRM dashboard and copilot consumers (other domains).

## Decisions for the owner

1. Delete asks for confirmation in ours (Reference deletes at once). Kept as part of the hub; say if it must go.
2. The retry button on a plan-locked screen does nothing useful; a link to the plan page is the better action (not done: needs the billing route).
3. `apps/web/src/features/tasks/api/mock-server.ts` (and the `deals` twin) ships a development stand-in behind a flag. PORTING_RULES section 5 says no mock data in the app; the stand-in is only reachable by a flag and is used by the unit tests, so it was left. Decide whether to move it to `test/`.
