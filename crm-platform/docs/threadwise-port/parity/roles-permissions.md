# Parity evidence: roles-permissions (TW-RBAC-001 .. 037)

Reference 1.7.0 against our build, branch `claude/loving-knuth-mkvuog`, 2026-10-02. Companion files: [inventory](../inventory/roles-permissions.md),
[wiring map](../wiring/roles-permissions.md).

## How this was checked, and its limits

- **The reference app did not run in this session** (the sandbox has PHP but no MySQL/MariaDB), so Reference's behaviour here comes from its
  source (controllers, seeder, policies, Blade views, JS) and the inventory entry, which the inventory itself says was derived by static
  analysis of v1.7.0 (open question 20). Rows that depend on the reference's runtime behaviour say so. The first person with the
  reference running should replay the scenarios in the tables below with `threadwise-verify-parity` and flip any `source` row that disagrees.
- Our side is proven by tests that run against a real Postgres and Redis: `apps/api/test/e2e/roles-permissions/platform-rbac.e2e.spec.ts`
  (35 tests), `workspace-roles.e2e.spec.ts` (17 tests), `apps/api/test/unit/roles-permissions` and the web unit tests under
  `apps/web/src/features/roles-permissions`. The existing integration suites (24 files, 440 tests) pass with the two migrations applied.
- Screens were exercised in Chromium against the running API and web app (see the UI section).

Legend: **same** = equivalent; **intended** = differs on purpose (decision id and reason); **blocked** = needs another domain's feature,
tracked in the wiring map; **source** = matched from Reference's source, not from a live run.

## Decisions (intended differences)

| Id        | Decision                                                                                                                                                                                                                                                                                                                                                                                                                                                                  | Why                                                                                                                                                                                                                                             |
| --------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| D-RBAC-01 | The seeder's "re-run overwrites seeded roles" behaviour is not ported: the 101 keys and six roles are seeded once by a migration; later keys arrive by migration                                                                                                                                                                                                                                                                                                          | TW-RBAC-001 rule 1 and its port note; silently wiping an admin's edits is a defect                                                                                                                                                              |
| D-RBAC-02 | Super Admin is locked in the database (no rename, no stripped permission, no delete, no emptied holder list); the 16 `platform.*` keys cannot be deleted                                                                                                                                                                                                                                                                                                                  | TW-RBAC-007 rule 3, TW-RBAC-013 rule 1: Reference let an admin rename or strip the role the checks name, or delete a key and fail a check closed for everybody. Security hardening, approved by the domain owner by the inventory's own port notes |
| D-RBAC-03 | Roles list/permissions search and filters work (inert in Reference); the create-permission name is validated on the composed name with a strict format (Reference 500'd on a composed duplicate and accepted any text); unknown permission names are refused (Reference dropped them silently); role `description` is stored and "start from template" copies a role's permissions; the inert Scope select and the unstored permission label/description inputs are dropped        | TW-RBAC-005, 006, 011, 012, 022 port notes                                                                                                                                                                                                      |
| D-RBAC-04 | The legacy `users.role` string is not ported. Suspension is `users.status`, platform-admin recognition is the operator identity pool (`platform_operators`), and the billing/plan bypass for platform-owned workspaces belongs to PLAN/BILL as an explicit flag                                                                                                                                                                                                           | TW-RBAC-017 port note; the string had a different accepted-value list in each of nine places                                                                                                                                                    |
| D-RBAC-05 | The five workspace roles are per-organization presets. The existing top preset (`system_key = 'admin'`) is displayed **Owner**; **Admin**, **Manager**, **Agent**, **Viewer** are `workspace_admin`, `manager`, `agent`, `viewer`. Owner and Admin hold every key; Admin lacks only the owner-only keys (billing, plan purchase, `org.delete`, `org.owner_settings.manage`). A trigger gives every new permission key to Owner and Admin, which closes README decision D4 | TW-RBAC-004 port note; keeping the key `admin` for the top preset keeps every domain migration that grants to `system_key = 'admin'` correct                                                                                                    |
| D-RBAC-06 | Role-change rules close the Reference gaps: the target's current role is checked too (an Admin cannot demote an Owner or another Admin), a custom role can only be handed out by someone who holds everything in it, an organization always keeps an Owner (also in the database), the previous roles are audited                                                                                                                                                            | TW-RBAC-026 rules 2, 7 and port note; TW-RBAC-023                                                                                                                                                                                               |
| D-RBAC-07 | Reference's three owner-test spellings (`owner_user_id`, pivot owner, pivot owner-or-admin) become permissions: `org.owner_settings.manage` and `org.delete` (Owner only), `admin.settings.manage` (Owner and Admin)                                                                                                                                                                                                                                                         | TW-RBAC-034 port note; the primary-owner marker (`organizations.settings.ownerUserId`) stays for the account page                                                                                                                               |
| D-RBAC-08 | Landing follows permissions: a user who can open the dashboard lands there, one who can only work conversations lands in the inbox (Reference: Agent and Viewer to the team inbox, Manager and above to the dashboard)                                                                                                                                                                                                                                                       | TW-RBAC-035 port note                                                                                                                                                                                                                           |

## Not verified here

- Anything that needs the reference running (see the limits above).
- The platform inbox and impersonation consumers (019, 020), the member invite/remove/reset flows (027), conversation and inbox gates
  (028..032), the owner-only settings adoption (034): they depend on features that do not exist in this repository yet. Each is `blocked`
  in the tracker with the owning feature id; the keys they must use are registered and tested.
