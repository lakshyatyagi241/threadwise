# Parity: team inbox, conversations and assignment (TIB1 / TIB2, Phase 1 API)

What the Phase 1 API does differently from Reference, and what was not compared. Rules and routes: [docs/api/team-inbox-conversations.md](../../api/team-inbox-conversations.md).
The screens (A4) and the ingest and send pipeline (A1) have their own parity notes. **Not compared against the running reference**: the plan's
verification note applies (no signed-in reference session; behaviour here is from the Reference source and the inventory entries TW-TIB1-003, 004, 009,
010, 013, 017, 019, 032, 034, 038 and TW-TIB2-020 to 022). Status of every row: `intended`, pending sign-off by the domain owner.

## Not built here, recorded

Template send is built (picker, `kind: 'template'`), and the thread draws a template message as WhatsApp shows it (TW-TIB1-011): header text or a
media/location marker, the body with the values filled in, the footer, and the buttons as rows (quick reply, URL, call, copy code), from `template.preview`
(see `docs/api/team-inbox-conversations.md`). A media header shows only its kind: the file is not stored with the message. Labels, bulk, archive and pin routes, saved replies, saved views,
mention notifications, presence and typing, the AI takeover on human reply (nothing can attach an AI agent yet), and the sweep of expired uploads are later
phases (plan 5). The plan cap (`PLAN_LIMIT_REACHED`) is enforced by the core's dispatcher for metered channels; the simulator is never metered, so it is not
exercised by this domain's tests.

## Composer: share a location, contact cards and buttons — `intended` (contacts and buttons are additions)

- **Location** matches Reference ("Share a location": latitude and longitude validated to real ranges, an optional place name and address), as a `Share` dialog tab.
- **Contact cards and buttons are not in Reference's chat composer.** Added at the project owner's request (2026-10-11), because our channel layer, flows and inbound side already
  carry both kinds, so the inbox could show customers' cards and button picks but not send them. `POST /inbox/conversations/:id/messages` accepts `kind: "location" | "contacts" | "interactive"`
  (reply buttons, up to 3 titles of 20 characters; a list of up to 10 rows in up to 10 sections, row titles 24 characters, descriptions 72, a section title on each once there are two; or one http(s) link button). They are free-form messages: they need the open window and a channel that carries them
  (`capabilities.media` has `location` / `contact`, `capabilities.interactive` is true: WhatsApp Cloud API and the simulator). A QR-linked number sends locations and contact cards (one message, one vCard per
  card, no 24 hour rule) and refuses buttons and lists with `CHANNEL_CAPABILITY_UNSUPPORTED`. Button ids are `btn-1`..`btn-3` and list row ids `row-1`.., so a customer's pick comes back as a
  `button_reply` / `list_reply` with that id.
- Not provable here: delivery of a contact card or a button message on a live Cloud API number (needs a real WABA). The Meta payload builders are covered by `test/unit/whatsapp/meta-outbound-rich.spec.ts`; the send path by `rich-send.spec.ts`.
- Evidence: `test/unit/chat-conversations/rich-send.spec.ts`, `apps/web/.../lib/share.test.ts`, `components/share.test.tsx`.

## Saved replies (TW-TIB1-024)

Reference: a `saved_replies` table (shortcut, title, body, category, `used_count`, shared or personal), a picker opened by the "Shortcuts" tab or a
`/` typed into an empty box, a management modal for holders of `savedreply.manage`, `{{device_phone}}`/`{{device_name}}` expanded in the browser, the
plan cap `saved_replies_limit`. Ported with the same fields, ordering by use, search over shortcut, title and body, shared or personal at creation only,
create gated by the manage right and the cap counting every row. Wiring: [wiring/saved-replies.md](../wiring/saved-replies.md), API: [api/saved-replies.md](../../api/saved-replies.md).
