# Intended deviations from Reference: product extensions requested by the project owner

[PORTING_RULES.md](../PORTING_RULES.md) says features and UI do not change, and that a deviation is allowed only when documented
and approved. Everything below deviates on purpose. Each item was requested by the project owner (Lakshya) in chat on
2026-10-02; the rule text says only the human can waive a rule, in words, per case, so each entry states the words. Status:
**owner-requested, pending sign-off by the domain owner and reviewer**. Items 7, 8 and 9 (proposals and estimates, invoicing, the
tax engine) were compared side by side with the running reference on 2026-10-02: see [sales-proposals-estimates.md](sales-proposals-estimates.md)
and [sales-invoices-payments.md](sales-invoices-payments.md). The other items were not.

Standing product direction given by the owner: the product targets small businesses that want one bundled tool, so build what a
small business needs even when Reference does not have it, and make money and tax features country-aware.

## Segments

Owner-requested on 2026-10-02 (same status as the items above: **owner-requested, pending sign-off by the domain owner and
reviewer**). Reference has contact groups (static lists a person fills by hand: ported as `contact-groups`, unchanged) and nothing that
fills itself. Not compared with the reference, because the reference has no such feature. API: [../../api/segments.md](../../api/segments.md).

What it is. A **group** is a static list (manual membership). A **segment** is a saved rule, `{ name, description, color?,
visibility private|shared, owner, rules }`; membership is never stored, it is the rule evaluated against `contacts` right now. Rules are
a tree of AND/OR groups (depth 3, 50 conditions) over the same filters the contacts list has (stage, status, tags any/all/none,
groups, source, owner, consent, imported, search, created/updated/last-activity dates with relative operators, and custom properties
by type), validated strictly by `@crm/contracts` and shared with the web rule builder. One condition builder
(`contact-predicates.ts` / `contact-conditions.ts`) serves the list, the bulk actions, the export and a segment.

Differences from the existing contact features, on purpose:

| Area                    | Deviation                                                                                                                                                                                              | Why                                                                                                            |
| ----------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------- |
| Contacts filter         | `segmentId` and six date windows (`createdFrom/To`, `updatedFrom/To`, `lastActivityFrom/To`) were added to the list query, and so to every bulk action's `filter` (select all matching) and the export | The segment condition has to combine with the list's other filters, and its date operators needed the same SQL |
| Usage responses         | `GET /status-options/usage` and `GET /fields/usage` rows carry `segments`; tag, group, stage/status and property deletes put the affected segments in their audit row and event                        | A delete must not silently break a rule. It never blocks (the condition goes invalid and is flagged)           |
| Optimistic lock trigger | `segments` uses `segments_touch()` instead of `touch_row()`: identical, except that a write touching only the cached count or the usage stamp does not bump `row_version`                              | A count refresh or the worker sweep would otherwise turn the editor's next save into a 409                     |
| Visibility              | Private segments are visible to the owner and to callers holding `record.segments.update` with scope `all` (the admins); a segment that cannot be seen is 404                                          | Matches "private visible only to owner and admins" without a second admin concept                              |
| Counts                  | Cached 5 minutes, counted under a 3 second statement timeout (`countApproximate`), refreshed by a worker sweep for segments used in the last day                                                       | A segment can be any rule over millions of rows; no request waits on it                                        |

Not built (decisions for the owner): a segment as a broadcast or campaign audience (the broadcasts and campaigns owner will call
`SegmentsService.resolveMembers` / `countMembers`, documented in the API doc); "refresh on contact change" push updates (membership is
always computed, so there is nothing to push; only the cached counts lag by up to 5 minutes); dynamic exports or tags that keep
following the rule (tag and add-to-group are snapshots); org-timezone date boundaries (days are UTC); relative "owner is me".

## Call recording consent and lifecycle (BL-144): a new feature on top of operator recording, not a port

Reference starts recording every inbound call as soon as it is answered (no notice, no consent, no limit), stores the file on the public disk under a
guessable URL, and never deletes it. The privacy spec (gap G3) and the voice-bot requirements ask for the opposite defaults, so this port changes the
behaviour of TW-CALL-019 on purpose:

- **Off by default.** Recording is a workspace switch (decision D7). Reference had no switch.
- **Notice and consent before any audio.** The teammate reads a versioned notice; the person's answer (spoken yes, or announcement then continue) is
  saved on the call with the method, time, teammate, notice version and the notice's sha-256. The ConsentGate (`call_recording`) is the one decision
  point; the server refuses an upload without a granted answer (`CALL_RECORDING_CONSENT_REQUIRED`) and the browser does not arm its recorder before it.
  Inbound calls are no longer recorded automatically.
- **Retention.** A daily sweep deletes recordings after the workspace's days (default 90, 7 to 365). Reference kept them forever.
- **Deletion and legal hold.** One recording can be deleted by hand (the call stays), or held; both audited.
- **Erasure and export** already reach the file through the rights service; the manifest text now says how long it is kept.

What is **not** verified: a real call with a real microphone (no WhatsApp session here), that an announcement is legally enough in any country (counsel),
and the browser recorder on every browser (only the Chromium path is exercised by tests that stub `MediaRecorder`).

Decisions for the owner: (1) whether `announcement` mode should exist at all or be hidden until counsel confirms it for a region; (2) one notice text
per workspace today, per language and per region later (requirement 1 and 3); (3) recordings that existed before this change start their 90-day clock
when the migration runs, not at their original date; (4) whether a legal hold on a recording should block a rights erasure of the same person (today the
erasure wins and removes the file, as the rights service has no per-call hold); (5) whether consent should also be written to the contact consent
ledger once BL-140b adds purposes other than marketing and service.
