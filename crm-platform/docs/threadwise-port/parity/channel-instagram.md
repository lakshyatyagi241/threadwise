## Differences from Reference

1. **Linking is limited to listed accounts.** Reference saved any engine account id that came with a username, so one tenant could link another's account and read its messages through the pull. The port links only an account the engine lists to this workspace or to this person (by email); anything else is 404 `IG_ACCOUNT_NOT_FOUND`. A security fix, no screen can reach the old behavior.
2. **The engine address is guarded.** Calls refuse private, loopback and link-local destinations (checked at connection time, so a rebinding name cannot slip through) and never follow redirects, unless `ADDONS_ALLOW_PRIVATE_ENGINE_URLS` is on. Reference had no guard.
3. **Unlink is one transaction and says how many threads went** (`purgedThreads`); Reference deleted them in a transaction too but returned only a flash.
4. **Messages get their own delete.** In this schema messages carry no foreign key to their thread, so unlink deletes them by name before the threads.

5. **The connection flag is written only when it changes.** Reference wrote it (and a last-inbound time nobody reads) on every push; here a busy engine does not rewrite a platform setting per message, and the last-inbound time is not stored.
6. **The push path is `/v2/instaflow/inbound`**, not `/api/instaflow/inbound`: the engine's push address is entered on its side and has to be updated once.
7. **A thread's title is never overwritten by a later message.** Reference's guard keeps an operator's title but its next line reset the title on every message; the port keeps the guard's intent.
8. **A thread's clock only moves forward** (`greatest`), so an old message cannot drag it back; Reference set it to each message's time.
9. **A first pull never answers history.** A pulled message older than 10 minutes is stored but runs no automation; Reference's pull would have replied to every old message of every thread on the first pull after linking.
10. **A pulled message with no id is skipped**; it cannot be told from one already stored and Reference stored it again on every pull.
11. **The account name on a pulled message is the linked account's own** (Reference filled it with the customer's handle). The pull runs in a worker on a 20 second sweep instead of inside the inbox poll.

12. **Running a flow has its own permission** (`ig.flows.run`); Reference allowed anyone who could reply. A bridge answer of `ok:false` on a 200 counts as a failure (Reference counted any 2xx as sent).

13. **An account's threads are told apart exactly.** Reference matched `ig:<account>` plus one wildcard character, so account `1` also listed account `12`'s threads; the port matches the two real separators (`_` and `:`).
14. **A send is capped at 200 threads** and runs five at a time; Reference's broadcasts page had no cap and sent one by one inside the request, which could outlive it. The pickers still list up to 2000 per account.
15. **A broadcast's mirrored message keeps the engine's id** (Reference's broadcasts page dropped it, so the pull showed every sent message a second time).
16. **No broadcast record is kept**, as in Reference: the answer carries `{sent, failed, errors}` (up to five reasons of 120 characters; Reference's page showed only the counts) and each message that went shows in its thread. A thread that is not this organization's or not Instagram counts as failed.

17. **The connected message is believed only from the engine's own origin** (Reference took a window message from any origin), and an account id from the return address or the message is linked by the server only if the engine lists it to this workspace or person.
18. **"Connect via Meta"** (the embedded business login, shown when the platform has a login configuration) belongs to the native add-on and is not built (TW-IG-020). The explanatory note says "this workspace" where Reference named its own product, since the product name is not fixed here.
19. **The reply-only compose is its own screen** (`/instagram/broadcast`), because the port's broadcast composer has no channel switch: account, template (fills an empty message), `{name}` message up to 1000, search, select all (first 200), the window badge per conversation, and the result sentence ("Instagram broadcast sent — N delivered, M failed." or "Could not send to any recipient. Check the Instagram connection.").

20. **Where the thread lives**: one `instagram` channel per linked account (its handle the engine's account id, kept in step on link and unlink), a thread keyed by the engine's thread key on it, stored lower-cased. Unlinking the last account still deletes every Instagram thread; the channels stay, switched off.
21. **Storing a message** goes through the shared inbound pipeline; the engine's message id is the ledger key, so the push and the pull showing the same message, or our own send coming back, store it once (as before). Buttons ride on the message (`meta.buttons`) and are added to a row stored without them. The per-message `meta.instagram` (account, handle, avatar, trace id) is no longer kept.
22. **Attachments**: copied into the inbox store through a guarded download (Meta's media hosts only, public addresses only, no redirects, 25 MB); from any other address the message is kept as an image/file without it. A reply from the inbox is text or one file (through a short-lived link: needs a cloud bucket). Sending a template with buttons from the inbox is not offered yet (the inbox's template picker is Cloud API only); the reply-only broadcast composer still sends them.
23. **Who sent a reply-only broadcast message** is kept on the message (`sender_user_id`), as Reference kept `user_id`.

## Shims

- `InstagramPlanGate` (`_shims/open-gates.ts`): `access_instagram` is not in the plan catalogue; every check passes.
- `InstagramInboxIngest` (`_shims/chat-instagram-ingest.ts`): real; over chat-conversations. The sender becomes a lead contact keyed by the sender id here, because the inbox does not create contacts for a channel with no phone.
- `InstagramTemplates` (`_shims/sql-instagram-templates.ts`): reads `wa_templates` where the channel is instagram until the templates domain exports a lookup.
- `InstagramPlanGate.assertBroadcast`: the plan's `broadcast` feature; every check passes until the catalogue carries it.
- `InstagramAutomation` (`_shims/open-gates.ts`): the keyword auto-reply rules (TW-IG-017); nothing replies until that domain exports them.
