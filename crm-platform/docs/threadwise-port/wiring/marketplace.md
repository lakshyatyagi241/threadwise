# Wiring map: marketplace (MKT)

An owner-requested extension, not a Reference port: Reference only has the code-extension loader and billing add-ons (`addons-extension-registry`,
ADD), which load uploaded code into the one running process and have no catalogue, no per-workspace install and no scopes. The spec is
[marketplace-mini-apps-and-integrations.md](../../specs/marketplace-mini-apps-and-integrations.md); there is no Reference inventory page, so this file is
the inventory and the wiring map in one. API and rules: [docs/api/marketplace.md](../../api/marketplace.md); runbook:
[marketplace-publish-listing.md](../../runbooks/marketplace-publish-listing.md). Deviations from the reference:
[product-extensions.md](../parity/product-extensions.md), item 20. What this change builds is **spec phase 0 and the backend of phase 1**
(M-01, M-03, M-04, M-05, M-08 backend, M-09, M-10, M-16 backend); there is no web UI yet (a UI agent follows).

## Tables

| Table                           | Owner of the row | Notes                                                                                                                                          |
| ------------------------------- | ---------------- | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| `marketplace_categories`        | platform         | `(kind, slug)` unique; tenants read the active ones                                                                                            |
| `marketplace_apps`              | platform         | listing; `current_version_id` is what a new install gets; `install_count` kept by a trigger (does not move `row_version`)                      |
| `marketplace_app_versions`      | platform         | manifest and recipe jsonb, `scopes text[]`, review state                                                                                       |
| `workspace_app_installations`   | tenant           | granted scopes, config, sealed credentials, hints, health, `pending_version_id` for re-consent; one per `(org, app)`                           |
| `marketplace_consents`          | tenant           | append-only ledger (install, reconsent, uninstall with the data choice); outlives the installation                                             |
| `marketplace_connections`       | tenant           | public key, sealed secret, poll schedule and cursor, lead source id (no foreign key: the pipeline's tables are another domain's), counters     |
| `marketplace_connection_events` | tenant           | one row per delivery id: the door's idempotency guard and the recent-events list; no lead data; trimmed after 30 days                          |
| `market_requests`               | platform         | one per `(kind, normalised name)`; readable by all, insertable by a workspace as itself, changed only by the operator; `vote_count` by trigger |
| `market_request_votes`          | tenant           | one per `(org, request)`                                                                                                                       |

Drizzle mirror: `packages/db/src/schema/marketplace/tables.ts`. Platform tables follow `whatsapp_providers` (forced RLS, privileged writes) with a
tenant `SELECT` policy for what is published or installed. SECURITY DEFINER functions: `marketplace_connection_lookup(public_key)` (two ids, called
by the public door only), `marketplace_bump_install_count()` and `market_requests_bump_votes()` (triggers; a workspace cannot update the platform
row). Referenced tenant tables: `users` (composite keys on `installed_by` and `consented_by`, set null on delete).

## Worker

Queue `mkt-pull` (`QUEUES.MKT_PULL`, own queue so a slow portal cannot hold a lead from another door). `PullSweepService` (every 30 seconds,
privileged) lists active pull connections that are due and queues one job per connection (job id = the connection); `PullProcessor` runs
`PullRunService`, which moves the cursor only after the leads are in. An hourly trim deletes delivery rows older than 30 days. Registered in
`MarketplaceWorkerModule`, imported by `WorkersModule` only.

## Listings audit (2026-10-17): features with no Marketplace listing

An audit found the catalogue (14 listings: Appointments, Forms, Email, the Chrome extension, the Google Sheets add-on, the generic Webhook and the 8 lead
portals) missing the optional, add-on style features that exist in the product or in Reference. This section is the survey, the decision per feature and
what was built. Owner decisions applied: a **built** feature gets a first-party listing that is gated by install like Forms, Email and Appointments, seeded
as a draft with the price unset (the operator prices it; publishing is refused with `price_not_set` until then), granting the plan feature that gates it; a
feature that is **core** to every workspace is not gated and gets an information listing (connector `client`, free, grants nothing); an **unbuilt**
feature is a draft that cannot be published (connector type `oauth`, framework-only: `409 MKT_CONNECTOR_NOT_AVAILABLE`; no recipe, so a version cannot be
approved either) and is recorded here as `blocked` with an id. **No Reference feature may be lost for any existing workspace**, so no gate here changes what
a workspace has today (see "How nothing is lost"). Reference's "More features" page
(`reference/app/resources/views/user/more/index.blade.php`) and its plan flags (`plans-subscriptions-trials` inventory, TW-PLAN-007) were read for the list.

### How nothing is lost

Three situations, one rule each. In every one an existing workspace keeps what it has, without buying, installing or noticing anything.

1. **A feature whose plan flag is already off by default** (every `T` listing). A workspace has such a feature only through its plan or an override, and an app
   adds a way to get it on top (`app-grants.ts`: the app's grant is merged beside the plan's, the plan's own is never touched). So the migration changes **no
   plan row, no permission key and no gate**. A workspace on a plan that grants the feature keeps it with no purchase and no install; set `includedPlanFeature`
   on the listing so the app is shown to such a workspace as included instead of for sale.
2. **A feature that was open to every workspace and now needs the app** (only AI lead scoring: it had no plan gate, only the workspace's own opt-in). The key is new
   and off, so migration `..090000` gives every workspace that **uses** it an override `features.lead_scoring = true` on its plan state, in the same transaction
   (the Appointments recipe leaves a window between the deploy and the operator's comp; this does not). "Uses" is the same probe the operator's comp action
   runs (`USAGE_PROBES.lead_scoring` in `operator-pricing.service.ts`): the workspace switch is on, any run is in its log, or the growth pilot has a row. An
   override an operator already set (true or false) is never touched; other overrides are kept; re-running the migration touches no row. The operator then
   runs **Comp existing users** (dry run first) so there is a lasting subscription record; a workspace that has not been comped keeps working on its override.
3. **A feature that is core** (devices, Meta lead forms): not gated at all. The listing only describes the feature and installing it changes nothing.

What a workspace without the feature sees: every lead scoring route answers `422 PLAN_FEATURE_LOCKED` (reads included, `reason: feature_disabled`, or
`app_not_installed` with `installUrl` when it has paid but not installed); `/growth` answers `available: false`; the Settings tiles `lead-scoring` and `growth` are
removed and their routes are closed in the shell with "isn't part of your workspace" and a link to the app's page; a contact's Lead score card keeps the number a
person typed and drops the AI button and history; the chat insight, the growth card and the AI stage-change undo are not shown. Background work (automatic
scoring, the backfill, the chat reading, every growth sweeper and listener) does nothing for such a workspace.
