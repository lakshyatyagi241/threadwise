# Wiring map: calling-voice (CALL)

Read with [the inventory entry](../inventory/calling-voice.md). `built` = in this repo and tested; `intended` = deliberately different (reason in
[parity/calling-voice.md](../parity/calling-voice.md)); `not ported` = dead code in Reference; `not built` = outside the 21 tracked features, listed so it
is not lost. The inventory details 001 to 021; 022 onward (call logs, assistants, the Node bridge, voice notes, voicemail) are index rows. Rows 022 and 036
(the call log and its detail with playback) are built from Reference's `CallLogsController`, `CallRecordingController` and the two `call-logs` views.

## How a call moves

| Step                 | Reference                                                                       | Ours                                                                                                                                                                                                              |
| -------------------- | ------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Meta tells us        | its own `webhooks/wa-calling` handler, plus a forward from the messages webhook | one WhatsApp callback (`/v2/public/webhooks/whatsapp`) already carries the `calls` field; `/v2/public/webhooks/wa-calling` is the same door under Reference's name (same token, same signature check, same queue) |
| Route to a workspace | scan and decrypt every WABA config                                              | `waba_route_lookup` (indexed), already used by every other field                                                                                                                                                  |
| Handle it            | inline in the controller                                                        | `WabaIngestService` hands `calls` to `WABA_CALLS_SINK`; the calling domain binds it (`CallingWabaSink` to `CallEventsService`)                                                                                    |
| Place a call         | `WaCallingService`                                                              | `CallActionsService.dial`: permission first, row written before Meta, marked `failed` when Meta refuses                                                                                                           |
| Answer               | transaction with a row lock, Meta pre_accept then accept                        | one atomic `UPDATE ... WHERE status = 'ringing'` claims it; pre_accept, 900 ms, accept with the same SDP; a Meta refusal puts it back to ringing                                                                  |
| End                  | Meta's terminate webhook                                                        | the same; the row is closed with Meta's status and duration, and one bubble is written in the customer's thread                                                                                                   |

## Quiet hours and calling windows (BL-177, product extension)

Not in Reference. `CallActionsService.dial` asks `SendWindowService` (kind `call`) before the permission request and before Meta is called: outside the workspace's calling window (days and hours, on the contact's clock) it answers 422 `CALL_OUTSIDE_WINDOW` with `opensAt`, `zone` and `zoneSource` in the details. A live call cannot wait, so this is the one place the window refuses. A call back to someone who messaged (`conversations.last_inbound_at`) or called (`wa_calls`, `USER_INITIATED`) in the last 24 hours is service and is not refused. The web shows `calling-voice.errors.CALL_OUTSIDE_WINDOW` with the opening time in the reader's locale.
