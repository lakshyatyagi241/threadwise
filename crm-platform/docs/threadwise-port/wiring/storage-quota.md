# Wiring map: storage quota, phases S0 and S1 (STQ, observe mode)

Not a Reference feature: Reference has no storage meter. Requested by the project owner (backlog BL-300, spec approved with the recommended defaults for O1 to O13 on 2026-10-18).
Lives in the STORAGE domain (`modules/storage-quota`, `common/storage-meter`). Read with [specs/storage-quota-and-archival.md](../../specs/storage-quota-and-archival.md),
[api/storage-quota.md](../../api/storage-quota.md), [inventory/storage-quota.md](../inventory/storage-quota.md), [ADR-0030](../../adr/0030-workspace-closing-state.md) and
[runbooks/storage-quota.md](../../runbooks/storage-quota.md). New ids: `WIRE-STQ-*`.

**What is built (S0 + S1):** the four tables, the `storage_gb` plan limit key, the error code, the closed list of categories, the permission keys, the guard (reserve, write,
commit, release, remove) wired into every counted writer, the backfill and the nightly counter check as BullMQ jobs, the reservation reaper, and the operator's read-only fleet
view. **OBSERVE MODE ONLY: nothing is ever refused, nothing is deleted, no user sees a difference.** Enforcement, warnings, packs, archival and Settings > Storage are phases S2 to S7.

## How a file gets metered

The protocol is `reserve -> write -> commit` (`common/storage-meter/storage-meter.port.ts`). Every step is fail-open: a metering fault is logged and counted
(`crm_storage_meter_failures_total{step}`), the file operation goes on, and the nightly counter check corrects the drift.

| Door (the only code that may put bytes on a store or a disk)                                                              | Category                                                                                                  | Metered by                                                   | Delete path                                                                          |
| ------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------ | ------------------------------------------------------------------------------------ |
| `ChatMediaStore.store` (agent inbox upload, widget visitor, developer API, flow-sent file, mail composer, call recording) | `inbox_media` (default), `call_recording` (call-recordings.service), `email_attachment_staged` (outbound) | `meteredWrite` around gateway put / local put                | `ChatMediaStore.remove` -> `recordRemovedOn`                                         |
| `ChatMediaStore.storeInbound` (every channel adapter, inbound WhatsApp fetch, email attachments)                          | `inbox_media_inbound` (default), `email_attachment_inbound` (mail-ingest.service)                         | via `store`                                                  | same                                                                                 |
| `ChatMediaStore.storeInboundStream` (large inbound files, spooled)                                                        | `inbox_media_inbound`                                                                                     | `meteredWrite` after the size is known                       | same                                                                                 |
| `MediaStorageService.put` for `marketing/`, `scheduled/`, `telegram/`, `ai-training/` keys                                | `campaign_media`, `scheduled_media`, `channel_profile_media`, `ai_training_file` (by key area)            | `reserveOn` + commit once the bucket took the object         | `MediaStorageService.remove` -> `recordRemovedOn` (all keys)                         |
| `LocalTrainingFileStore.put` (`TRAINING_FILE_STORE`, knowledge files)                                                     | `ai_training_file`                                                                                        | `meteredWrite`                                               | `remove` -> `recordRemovedOn`                                                        |
| `MessagesService.post` (team chat attachment, a Postgres blob `team_chat_attachment_blobs`)                               | `team_chat_attachment`, key `pg:team_chat_attachment_blobs:<message id>`                                  | reserve before the transaction, commit inside it (savepoint) | none per file: the blob cascades with its message; the nightly check syncs the table |

`chat/` keys are metered by `ChatMediaStore` only (it also covers local disk); `MediaStorageService.put` skips them so a file is counted once. A key with no workspace id
(`site/` marketing-site images) is platform data and never metered.

## Every writer, classified (the coverage test)

`apps/api/test/unit/storage-quota/storage-writes-guarded.spec.ts` lists every file that puts an object on a store, writes a file to disk or signs a bucket write, and every Postgres
table with a `bytea` column. A new writer that is in neither list fails the build. Findings of this pass that the spec's section 2 did not list:

| Writer                                                                       | Class                   | Note                                                                                                                                                       |
| ---------------------------------------------------------------------------- | ----------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Telegram profile pictures (`channel-telegram/_shims/storage-media-store.ts`) | metered (new category)  | `telegram/<org>/...` through `MediaStorageService.put`; category `channel_profile_media`, customer origin (grace, then metadata only in S2).               |
| Flow builder media (`flow-builder-editor/flow-media.service.ts`)             | **gap**                 | `FLOW_MEDIA_STORE` is a local-disk adapter keyed by the workspace UUID; not metered in S1. Follow-up with its production adapter (phase S7).               |
| `calling-voice/cli/demo-calls.ts`                                            | **gap** (dev tool)      | Seeds demo recordings straight onto a store; the backfill and the nightly check pick them up.                                                              |
| Campaign / broadcast media rows                                              | not backfilled          | The owner row keeps a URL, not a key, so the backfill cannot find them; going forward the door meters them. The weekly bucket verify (S5) adopts the rest. |
| Email attachments received before the meter                                  | not backfilled          | The key lives inside `messages.meta`; same S5 bucket verify.                                                                                               |
| Exports, privacy export, avatars, logos, widget pictures, payment proofs     | exempt (spec section 3) | Classified by table in the coverage test with the spec's reason; never counted, never blocked.                                                             |

## Decisions taken without asking (defaults, all reversible)

| #   | Decision                                                                                                                                                                                                                                                                | Why                                                                                                                                                                                                |
| --- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| D1  | The default mode is `observe` (the task's instruction), not `off` as spec section 15 step 1 says. `off` still exists and is honoured everywhere.                                                                                                                        | Observe changes nothing a user can see and is what fills the fleet view; the spec's staged rollout still holds (observe before enforce).                                                           |
| D2  | A registry row written by a door has no owner yet, so it is `pending`; the nightly check links it to its owner row through the owner map (`storage-owners.ts`) and flips it to `live`. A `pending` row is NOT an orphan sign by itself in S1: nothing deletes anything. | The doors do not know the owner row (it is written by a later statement in the caller). S5 must treat "pending and not linkable by the owner map for an hour" as an orphan, never "pending" alone. |
| D3  | `storage_org_state` is keyed by `org_id` alone (one row per workspace), like the other one-row-per-workspace tables; the other three are keyed `(org_id, id)`.                                                                                                          | The schema invariants test requires `org_id` first; a surrogate `id` on a one-row table adds nothing.                                                                                              |
| D4  | Contact files are backfilled by measuring the object (stat or HEAD), never from `file_size_bytes`.                                                                                                                                                                      | Spec section 14: do not trust client sizes.                                                                                                                                                        |
| D5  | The operator view reads `PlanEntitlementService.limit` for the cap. Packs (S4) will have to be merged by that service (or a sibling); until then the displayed cap is the plan's.                                                                                       | Spec 5.3 refers to `entitlement-merge.ts` / `addon-grants.ts`, which are not on `main`.                                                                                                            |
| D6  | The platform mode is changed by editing the `platform_settings` row; there is no screen or endpoint for it in S1.                                                                                                                                                       | The mode switch for operators is an S2 action (spec 11.1); a hand-edited row is enough for an observe-only release and avoids a second write path to audit.                                        |

## Not verified

- Behaviour against a real S3-compatible bucket (the HEAD size check, the PUT/commit order) was not run: unit tests stub `fetch`; the integration tests use Postgres and local disk only.
- Backfill throughput on a large workspace and the hot-row contention of `storage_org_state` at 100 inbound files per second were not load-tested (spec 17, "Load").
- The operator fleet view has no screen; it was exercised through the service and unit tests, not a browser.
