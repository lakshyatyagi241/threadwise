# Wiring map: flow-runtime-engine (FLR)

Read with [the inventory entry](../inventory/flow-runtime-engine.md). `built` = in this repo and tested; `intended` = deliberately different
(reason in [parity/flow-runtime-engine.md](../parity/flow-runtime-engine.md)); `blocked:<domain>` = waits on a domain that does not exist yet;
`not built` = outside the 20 tracked features, listed so it is not lost. The inventory details 001 to 020; 021 to 071 are index rows, read from
the reference source directly.

## How a run moves

| Step              | Reference                                                                        | Ours                                                                                                                                                                            |
| ----------------- | -------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Decide who enters | Laravel hooks call `FlowEnrollmentService`; Node decides the keyword path itself | one door, `FlowLaunchService.start`; every path writes a `flow_runs` row with its `source`                                                                                      |
| Hold a run        | one JavaScript object in Node's memory, keyed `<sender>_<customer>`              | a row in `flow_runs` (graph snapshot, variables, visits, wait, step counter); one live run per (channel, customer) by a partial unique index                                    |
| Walk it           | recursive awaits, 1.5 s timers                                                   | one BullMQ job per step on queue `flow-run`; the job id is `flr-<org>-<run>-<step>` and the worker writes only if the run is still at that step (compare-and-set on `step_seq`) |
| Wait for a reply  | `waitingForInput` in memory                                                      | `flow_runs.wait` and `expires_at`; the inbox's inbound message resumes it                                                                                                       |
| Sleep (Delay)     | `setTimeout` inside the call stack                                               | `status = sleeping`, `resume_at`, a delayed job; the sweeper backs it up                                                                                                        |
| End               | `endFlowSession`, never marks the subscriber                                     | `completed` / `failed` / `expired` / `cancelled` with an `end_reason`; the subscriber follows                                                                                   |

Instagram and Messenger editor nodes (TW-FLR-010 rule 6, 061, 062): `ig_send_dm`, `ig_ask`, `ig_quick`, `ig_buttons` and `ig_ai` compile onto the shared Message, Question, buttons, call-to-action and ChatGPT executors (`TYPE_MAP` and `shapeNode` in `compile-graph.ts`); only link buttons of `ig_buttons` are kept. `ig_to_whatsapp` and `fb_to_whatsapp` run `SocialHandoffNode`: deep-link mode sends a `wa.me` link; direct mode says the intro and announces `flow.whatsapp_handoff_requested`, which the worker's `SocialHandoffConsumer` turns into a contact for the captured number (named "WhatsApp <digits>") and `FlowLaunchService.start` with source `handoff` (the node cannot call the launch service: it needs the engine, which needs the node).

## Producers of flow triggers (TW-FLR-005, 006, 010)

Every producer writes an outbox event in the transaction of its cause; a worker consumer turns it into `FlowLaunchService.start`. Start is idempotent per (flow, reason); the loop guard and the 24 hour window rule below apply to all.

| Trigger                | Producer (event)                                                                                                                                                                                                                                                                                                                | Consumer                                           | Reason / idempotency                                                                                                                 | Data on the run                                                                                                               |
| ---------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------- |
| `order_placed`         | storefront checkout and AI ordering (`store.order_placed`), WhatsApp catalog cart (`whatsapp.order.received`), Shopify/WooCommerce order created by its own webhook (`order.placed`, `ShopifyWoocommerce` `announceOrder`; imports and later updates announce nothing, an intended difference: Reference fired for imports too) | `FlowTriggerEventsConsumer`                        | `order:<order uuid>`, a repeat buyer runs again                                                                                      | name, first_name, email, order_number, order_name, total, total_price, currency, status, invoice_url, order_url, payment_link |

**Loop guard.** Events written while a run's step executes carry its request id `flr-<run>-<seq>`; the consumer reads that run's `__trigger_hops` and the next run gets +1. At 5 the start is refused: no run, the subscriber shows `failed` ("flows started each other"). **24 hour window.** A run that was not started by a customer message (everything above) whose free-form messages were all refused ends `failed` with code `SERVICE_WINDOW_CLOSED`; a template that got through keeps it `completed`. **Plan:** the `automation` flag gates editing only, never a start (Reference parity); routing keeps `inbox_routing`.

## Order events (TW-FLR-006)

The order trigger starts on three events, all read back by the order's uuid from `wa_orders` and handled as `order.placed`, so a repeat is the same enrolment (`order:<uuid>`):
`order.placed` (the commerce contract), `store.order_placed` (the storefront checkout) and `whatsapp.order.received` (a catalog cart on WhatsApp, TW-WABA-042).
Before this, the storefront emitted `store.order_placed` and nothing turned it into a flow trigger. Evidence: `flow-runtime.e2e.spec.ts` (store checkout and catalog cart, once per order).

## Wired to the catalog and the inbox (this change)

- A WhatsApp catalog cart captured by the WABA domain (`whatsapp.order.received`) resumes a shop node waiting on `purchased`: the cart is no longer a chat bubble, so `CatalogCartResume`
  (an outbox consumer) finds the customer's live run on the number's channel and calls `CommerceResume.catalogCart`.
- The catalog concierge answers a free-text product question after the flows had their turn: `CatalogConciergeListener` is an inbound listener marked `after`, and the inbound hooks now
  run those last and tell them through `prior.consumed` whether a flow already took the message.

## Quiet hours (BL-177, product extension)

Not in Reference. A flow message that is MARKETING (a MARKETING template, or a free-form message of a run the business started: `PROACTIVE_FLOW_SOURCES`) goes through `ChannelDispatcher.send`, which asks `SendWindowService` after the ConsentGate. Inside the workspace's quiet hours it throws `SendHeldError`; `FlowSender.outcomeOf` turns that into a halt (`SEND_HELD`), so the run waits and the same step runs again on the engine's 5 minute halt retry (inside the run's seven day limit). Nothing is skipped or failed. Replies of a reply run and notes to a colleague's number are service and are never held. An exact wake-up at the opening is BL-192.

## Age question (BL-212, product extension)

The Ask node's `age` / `date_of_birth` validation (`ask-input-node.ts` `answerAge`) calls `MinorDetectionService.applyAnswer` (contact date of birth, minor flag) and `ContactPrivacyService.minorAge` (the workspace's age). Variable `<var>_age_gate`. See [contact-consent.md](contact-consent.md).
