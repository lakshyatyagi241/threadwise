### 3.2 Channel port (replaces "send methods throw")

```
interface ChannelAdapter {
  readonly kind: 'simulator' | 'whatsapp_cloud' | 'whatsapp_qr' | 'webchat' | ...;
  capabilities(channel): { windowHours: number | null; templates: boolean; media: MediaKind[];
                           reactions: boolean; editDelete: boolean; receipts: ('sent'|'delivered'|'read')[]; typing: boolean };
  send(channel, envelope: OutboundEnvelope): Promise<{ providerMessageId: string; acceptedAt: Date }>;   // throws ChannelError{retryable, code}
  verifyInbound(channel, rawBody, headers): boolean;                    // never skipped, never "dev mode"
  parseInbound(channel, payload): { messages: NormalisedInbound[]; receipts: NormalisedReceipt[] };
  fetchMedia?(channel, mediaRef): Promise<{ bytes: Buffer; mime: string }>;
}
```

`OutboundEnvelope` = `{ to (peer_key), kind: text|media|template|reaction|location, body, media {key,mime,name}, template {name,language,vars}, replyTo, clientReference }`. The
guard (`OUTBOUND_SEND_GUARD`), plan check and window check live in one `ChannelDispatcher`, so every adapter is covered once.

**Simulator adapter (dev and test only, `CHANNEL_SIMULATOR_ENABLED=true` and `NODE_ENV !== 'production'`, refused at boot otherwise):**

- Inbound: `POST /dev/simulator/channels/:id/inbound` runs the same normalised path as a real webhook (it calls `parseInbound` on a simulator payload and enqueues on `webhook-ingest`), so the whole pipeline is exercised, not bypassed.
- Outbound: `send()` accepts, returns a fake id, then a BullMQ delayed job posts receipts `sent` (0 s), `delivered` (1 s), `read` (3 s), configurable per channel (`settings.latencyMs`).
- Fault injection by magic prefixes in the outbound body or by buttons in the dev panel: `/fail` (permanent failure, code `SIM_REJECTED`), `/flaky` (retryable error twice then success), `/slow` (10 s), `/dup` (deliver the inbound webhook 3 times), `/ooo` (receipts out of order: `read` then `delivered` then `sent`), `/window` (toggle the 24 h window capability to exercise the template-only UI).
- Capabilities default to a WhatsApp-like profile (24 h window, templates, image/document/audio/location, reactions, receipts all three) so Phase 1 UI is the real shape.
- Never charges the wallet, never counts toward plan messages (flag on the channel row), never reachable from `/webhooks`.

### 3.4 Pipelines

**Inbound** (webhook or simulator -> worker; all stages in one transaction unless noted):

1. Public controller `POST /webhooks/channels/:channelUuid` (and `GET` for Meta's verify challenge): look up the channel by uuid, verify the signature on the raw body with that channel's secret, persist nothing, enqueue on `webhook-ingest` (`jobId = ingest:{channel}:{providerMessageId}`), answer 200. Unknown channel or bad signature: 404/401 with no detail.
2. Worker `ingest.inbound`: `INSERT INTO message_ledger ... ON CONFLICT DO NOTHING RETURNING`; no row means duplicate, stop (idempotent).
3. Resolve the peer to a contact: `ContactsService.resolveOrCreateByIdentity(kind, value, name)`. Quota reached: continue with `contact_id NULL` and a `needs_contact` flag; **an inbound message is never dropped**.
4. Find or create the conversation: `pg_advisory_xact_lock(hashtextextended('conv:org:channel:peer'))`, `INSERT ... ON CONFLICT DO NOTHING`, then `SELECT ... FOR UPDATE`. Allocate `msg_seq = msg_seq + 1`.
5. Insert the message (`status received`, `provider_ts`), update the conversation: `last_message_at`, `last_inbound_at`, `unread_count + 1`, preview, `window_expires_at = provider_ts + windowHours`, `waiting_since = coalesce(waiting_since, now)`, reopen when resolved or snoozed (Reference: a customer reply reopens; verified at `WaInboundController`, the `inbox_status => 'open'` update on inbound).
6. Phase 2+ stages, in this order (copied from Reference's order, verified): routing (assign, tag, priority), opt-out STOP/START (stored first, then handled, before any bot), auto-reply, AI.
7. Outbox: `conversation.created` / `conversation.reopened` in the same transaction.
8. After commit: realtime emit (section 3.6). Best effort; the database is the truth and clients resync by cursor.

Per-conversation ordering comes from the row lock plus `seq`, not from the queue: BullMQ cannot order per key, and a single concurrency-1 queue would serialise the whole tenant.

**Outbound:** `POST .../messages` (Idempotency-Key header is mandatory, plus `clientMessageId`) -> permission, window check, plan cap, no send yet -> insert `queued` + ledger `client_id` + conversation update in one transaction -> after commit enqueue on `message-dispatch` (`jobId = msg:{id}`) and emit -> `202` with the message. Worker: guard (`OUTBOUND_SEND_GUARD.beforeSend`), adapter `send`, on success set `sent` + `provider_message_id` + ledger `provider_id`; `ChannelError.retryable` rethrows to BullMQ (5 attempts, exponential); permanent error sets `failed` with `failure_code` (for Meta: 131047 window closed, 131026 undeliverable, 131048 spam rate) and a retry button. **Residual risk, documented:** if the process dies after the provider accepted and before the status commit, the retry may send twice (the Cloud API has no idempotency key). Mitigation: mark `attempt` in `message_events` before the call and, on retry, refuse to re-send an attempt that has no recorded outcome unless the receipt webhook has not named the `clientReference` within 2 minutes.

First response is stamped **when the provider accepts**, not on request (Reference stamps it even when the send failed, verified at `TeamInboxController.php:3225`, in `reply()`).

**Receipts:** webhook or simulator -> ledger lookup by provider id -> `UPDATE messages SET status = $new WHERE ... AND rank(status) < rank($new)`; rank queued 0 < sent 1 < delivered 2 < read 3; `failed` only from queued or sent and never over delivered or read; always append to `message_events`. (Reference's `shouldAdvance` is the reference; verified.)

### 3.5 Corrections to the architecture doc

1. `UNIQUE (org, channel_id, contact_id)` becomes `(org, channel_id, peer_key)` with `contact_id` a nullable link, because a conversation must exist before (or without) a contact (quota, groups, web visitors).
2. Message-level realtime does not use the outbox (it polls every 2 s). Lifecycle events use it; message and receipt signals go straight to the redis emitter after commit.

### 3.6 Realtime

- Library: Socket.IO 4.8 as built, plus `@socket.io/redis-emitter` so the API, the ingest worker and the dispatch worker all publish through one `RealtimeEmitter` (decision D3). New dependency lines go in their own `chore(deps)` PR (seam rule).
- Browser auth: `POST /v2/realtime/ticket` through the same-origin BFF (it attaches the cookie token) returns a 60 s one-time ticket; the socket connects to `NEXT_PUBLIC_REALTIME_URL` with `auth:{ticket}`; the gateway accepts a ticket type in addition to the bearer token. Reconnect mints a new ticket.
- Rooms: `user:{org}:{user}` (already auto-joined) and `conv:{org}:{id}` (explicit `room:join`, authorised by the same visibility check as the REST read). **No `org:` or per-team rooms for conversation traffic.** Emits are fan-out to the computed audience (assignee, members of the assigned team, holders of `read` scope `all`), which for a small business is at most a few dozen user rooms, resolved from a 30 s per-org cache. This avoids Reference's flaw where the `workspace.{id}.inbox` channel authorised every member for every conversation (verified in `routes/channels.php`).
- Events (names prefixed `inbox.`): `conversation.upsert` (id, version, fields that changed, no body), `message.new` (to the `conv:` room, with the message), `message.status`, `unread` (to `user:`), `assignment`, `typing`, `presence`. List events are signals; the client refetches the row through REST (scope and RLS enforced there).
- Gap handling: every message carries `seq`. A client that sees `seq` jump, reconnects, or regains focus calls `GET .../messages?afterSeq=` (the gap-free pattern from tchat). A 60 s safety poll of `GET /inbox/counts` replaces the bell's minute poll.
- tchat: swap its 3 s poll for the same emitter in Phase 8 (2 days).

### 3.7 Permissions and visibility

Map Reference's keys onto our scope model instead of copying 13 keys: `inbox.conversation.read` with scope `all` (every conversation, including unassigned), `team` (assigned to me or to one of my teams, plus unassigned), `own` (assigned to me). New keys: `inbox.conversation.note`, `.tag`, `.snooze`, `.bulk`, `.priority`, `.claim` (assign to myself only, Reference's `assign_self`), `inbox.routing.manage`, `inbox.sla.manage`, `inbox.savedreply.manage`. Defaults: Admin all; Counsellor/agent `read` at `all` (a shared inbox: Reference's Agent also got `view_all_teams`, with a comment explaining that withholding it made the list and the thread disagree), `claim` only; viewer `read` at `team`, no reply. Granting uses the locked-role unlock pattern from `20261005100100_tchat_permissions.sql`.
