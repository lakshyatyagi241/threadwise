# whatsapp-personal-groups build plan

Spec: `inventory/whatsapp-personal-groups.md` (TW-WAGRP-001..036). Related: `docs/specs/waba-groups-management.md` (the official feature to mirror), `docs/specs/personal-whatsapp-connect.md`.
Goal: groups on PERSONAL numbers (unofficial Baileys, channel kind `whatsapp_qr`) work end to end: group messages arrive as inbox threads, agents reply into groups, and a management screen
lists, creates and edits groups and their members, like the official `/waba-groups` feature but over the lease-owning worker's socket.

## Decisions (owner may overrule; D numbers are the spec's)

- D1 no new plan feature: gated by the existing two-level unofficial gate (platform switch + per-workspace allow list) like every personal-number action.
- D2/D3 group messages become inbox threads (peer key `g:<bare group id>`), STORAGE ONLY: no flows, keyword, AI, routing or commerce listener runs on them, no contact is created per speaker, a message typed on the phone in a group is mirrored as outbound. Sender name = participant pushName; LID-only speakers have an empty `participant`.
- D4 permissions `wa.groups.read`, `wa.groups.create`, `wa.groups.manage`, `wa.groups.leave` (category whatsapp, no scope; Owner/Admin baseline).
- D5 a group the number left or was removed from is kept, marked `left_at`, and its thread becomes read-only.
- D6 a management screen (Reference has none): a third tab "Groups" next to Numbers and Warmer on /devices.
- D7 additions included: join approvals (list/approve/reject), invite link get/reset, group picture, join by invite link (own cap, highest ban risk, off by default via env).
- D8 composer in a personal group thread: text, media, location, contact, reactions, @mentions (typed @ picks a member), replies.
- D9 not metered per member: a group send counts as ONE message, no wallet charge.
- D10 scheduling and broadcasts to groups stay refused.
- D11 ban-safety: per-device group-op limiter (Redis, default 20 ops/min and 200/day), max 20 participants per add call, create limited to 5/day/device, join-by-link 5/day/device, a 10 min cooldown after a refusal that looks like a ban/limit signal; env overrides.
- D12 subject max 60, description max 512 (Reference).
- Own table `wa_device_groups` (+ `wa_device_group_members` only if needed): NOT the legacy `wa_groups`/`wa_group_members` (device-agnostic, unique on jid alone); the storefront's group-code ordering keeps reading the legacy tables and a small sync keeps `wa_groups` filled from the new directory so `/store/groups` keeps working (decide in the build and document).
- Group id convention: bare id without `@g.us` everywhere (`g:<id>` thread key, `group_jid` column stores the bare id; `groupJid()` re-adds the suffix).

## Work split

Phase A (one agent): shared contracts, migrations (table, permissions), socket/port types and Baileys calls, limiter, events/realtime contract. Then in parallel:

1. inbox integration (api): bridge, ingest, peer-key, dispatcher, qr adapter group send, retitle, read-only when left, tests that currently assert the old behaviour flip.
2. groups API (api): controller, service, repository, directory sync sink, events, realtime consumer, notifications, limits.
3. web: the Groups tab and screens, inbox composer/thread changes, i18n 21 locales, help, tests.

## Phase A seams (as built)

Everything below exists in the branch `lakshya/wa/personal-number-groups`. The three later agents code against THIS section only. Paths are relative to `crm-platform/`. Nothing is committed.

### Conventions fixed by Phase A

- Group id: BARE everywhere (no `@g.us`): `wa_device_groups.group_jid`, the thread key `g:<id>`, `GroupSnapshot.groupId`, `WaDeviceGroup.groupId`. The socket layer takes either form (`toGroupJid()` re-adds the suffix); `GroupSnapshot.jid` keeps WhatsApp's full `...@g.us` id.
- Phones: the runtime reports DIGITS (no `+`); the API contracts speak E.164 (`+digits`). Convert at the API edge (`'+' + digits`; the number input to the socket may be E.164 or digits, `jidOf` strips non-digits).
- A member is addressed by its WhatsApp id (`jid`, may be `...@lid`); the participants jsonb stores `{jid, phone, lid, name, admin}` (`phone`/`lid` digits). Mentions, join-request handling and removals by id use `jid`.
- Unofficial gate: `DeviceControlService.groupAction/sendMessage/messageAction` all call `UnofficialWhatsappGate.assertEnabledFor(orgId)` first (throws WA_UNOFFICIAL_DISABLED). The groups API must also call it before touching its own tables' write paths (it is the same gate used by the devices routes).
- Deleting a device CASCADE-deletes its `wa_device_groups` rows (documented in the migration; threads are separate rows and stay).

## Inbox seams (as built)

Inbox integration (api). Paths relative to `apps/api/src/` unless noted. Nothing is committed. The web agent codes against THIS section.

### Messages in

- `modules/node-bridge-runtime/inbox/inbox-bridge.service.ts`: a `kind:'group'` message is no longer dropped. Thread key `g:<bare group id>` (the ingest prefixes `g:`; the bridge passes the bare id from `chat.jid`). `group = {title, participant, participantName?, participantLid?}`: `title` = `wa_device_groups.subject` of that device and group (cached 60 s), else `WhatsApp group`; `participant` = the speaker's phone digits, or `''` for a LID-only speaker, whose anonymous id travels in `participantLid` and is stored as `meta.group.senderLid`; `participantName` = pushName. The thread has no peer name, no contact (`contact_id` null), no per-speaker contact.
- Phone-typed or other-linked-device group messages (`fromMe`): mirrored as OUTBOUND through `recordOutbound` (`source: 'phone'`, `threadTitle` = subject when it creates the thread), once (provider-id ledger). A message whose id is already in the sent marker (`inboxKeys.sent`, which `QrChannelAdapter.send` writes after every send) is skipped: it is our own send echoed back. Residual race: if WhatsApp echoes our own send before the adapter has written the marker AND before the dispatch worker stored the provider id on the row, one duplicate outbound bubble is possible (same race the 1:1 echo path has). Our own reactions are not bubbles.
- Media goes through the existing inbound path (Redis hand-off, `fetchMedia`); the socket's 25 MB cap and 60 s timeout apply, a file over the cap or that failed arrives as `[Photo not available]`-style text (kept, not lost). Group media of `fromMe` messages is not downloaded (described, as for a 1:1 echo). Reactions, locations, contact cards and unsupported kinds use the 1:1 mapping. `mentionedJids` of an inbound message are stored as `meta.mentions = [{jid}]`.
- `infra/providers/chat-conversations/channel-ingest.job.ts` + `channel.port.ts`: `group.participantLid?` added; `participant` may be `''`.
- No listener runs on a group message: `InboundIngestService` never calls `InboundMessageHooks.run` for `m.group` (that covers every listener, including FAQ, routing, concierge, commerce resume, flow inbound and translation, all registered on the hooks), and `InboundMessageHooks.run` itself now answers `consumed: true` for any `g:` peer key (defence in depth). Regression: e2e `inbox-bridge.e2e.spec.ts` registers a spy listener, sends group messages, then a 1:1 message, and asserts the spy saw only the 1:1. Notifications follow the existing group rule (`message.received` carries `group: true`); the unread nudge already excludes `g:`.

### Keys and titles

- `modules/chat-conversations/peer-key.ts`: on phone channels (`whatsapp_qr`, `whatsapp_cloud`, `simulator`) a `g:<id>` key bypasses the canonicaliser in every path (`recordOutbound`, `findThread`, ingest). `identityOfPeer` returns null for it; `defaultTitle` gives `WhatsApp group`.
- `RecordOutboundInput.threadTitle?` (facade): the title of a thread this call creates.
- Retitle: `chat-conversations/device-group-retitle.consumer.ts` (`DeviceGroupRetitleConsumer`, registered in `ChatConversationsWorkerModule`) subscribes to `whatsapp.device_group.created` and `.updated`; it reads the subject from the `wa_device_groups` row named by the event's `aggregateId` (the event carries ids only) and updates the `g:<group_jid>` thread of the `whatsapp_qr` channel whose `external_id` is the device uuid (`DeviceGroupThreadTitleService.retitle(orgId, groupRowId)`, idempotent, nudges realtime `conversation changed: title`). The groups API must therefore emit these events with `aggregateId = wa_device_groups.id` when the subject is written.

### Sending

- Dispatcher (`channel-dispatcher.service.ts`): `whatsapp_qr` is no longer refused for group peers. Kinds allowed into a group: `text`, `media`, `location`, `contacts`, `reaction`; `template` and `interactive` fail `CHANNEL_CAPABILITY_UNSUPPORTED` (422). A disconnected number fails `CHANNEL_DISCONNECTED` like any send. The group-op limiter is NOT in the message path.
- `outbound.service.ts` `assertGroupSendable` (enqueue and retry): for a `whatsapp_qr` group thread, no wallet (D9, one send is one message; `channel.settings.metered` is false for device channels, so no monthly cap either), but `wa_device_groups.left_at` set -> 409 `WA_GROUP_LEFT`; `announce` and not `is_admin` -> 422 `WA_GROUP_ANNOUNCE_ONLY`. A group with no directory row yet is not refused. `QrChannelAdapter.send` repeats the check at send time (non-retryable `ChannelError`), and a WhatsApp refusal of a group send (`not-authorized`, `forbidden`, ...) maps to non-retryable `WA_GROUP_LEFT`. Unofficial gate stays first.
- Mentions: `sendMessage` text `mentions[{jid,name?}]` -> `OutboundContent.text.mentions` (dropped for any thread that is not a `whatsapp_qr` group) -> stored on the message as `meta.mentions` -> envelope `mentions` -> `SendCommand` `{type:'group_text', groupJid, body, mentions:[jid]}`. The adapter swaps a typed `@<name>` for `@<user part of the jid>` (what WhatsApp needs in the body to draw the tag, `mentionedBody`); a mention whose token is not in the body is still sent (the member is notified). The web composer may therefore insert either `@Name` or `@<digits>`; with `name` set both work.
- Other kinds go as `{type:'text'|'media'|'location'|'contact', to:<bare group id>, toGroup:true}`; a reply (`replyToMessageId`) sends `quote {providerMessageId, fromMe, participant?, text?}` resolved from the stored message (a member's message: `<phone>@s.whatsapp.net`, else `<lid>@lid`); a reaction in a group is `MessageAction react` with `to:'<id>@g.us'` and the new optional `participant` (WhatsApp needs the author of the message reacted to). Socket factory: the react key carries that `participant`.

### What the web reads

- `GET /v2/inbox/conversations/:id` (detail, `ConversationDetail`) gains optional `personalGroup` (contracts `conversationPersonalGroupSchema`, `packages/contracts/src/chat-conversations/conversation.ts`), present only for a `whatsapp_qr` thread keyed `g:<id>`: `{groupId, left, announce, isAdmin, announceOnly, canSend, memberCount}`. `left`: number left or was removed, thread read-only. `announceOnly` = `announce && !isAdmin` (admins-only group and we are not one). `canSend` = `!left && !announceOnly`. Use `canSend` to disable the composer and `left` / `announceOnly` to pick the banner. Absent/unknown directory row -> `canSend:true`, `memberCount:0`.
- `GET /v2/inbox/conversations/:id/group-members?q=&limit=` (permission `inbox.conversation.read`, same visibility as the thread): `{members:[{jid, name|null, phone|null (E.164), admin:'admin'|'superadmin'|null}], total}`; admins first, then by name, members known only by an anonymous id last with `phone:null`; `q` matches name or digits; `limit` default 50, max 200. Empty for any other thread. Use `jid` as `mentions[].jid`. Contracts: `conversationGroupMemberSchema`, `listConversationGroupMembersQuerySchema`, `conversationGroupMembersSchema`. Service: `PersonalGroupThreadReader` (exported from the chat-conversations barrel; reads `wa_device_groups.participants`, no WhatsApp call).
- Messages (`MessageResponse`): `group.participant` (phone digits, `null` when LID-only), `group.senderName`, new `group.senderLid` (anonymous id when there is no phone), `mentions: [{jid, name?}]` on both directions (inbound: jids only). `group.senderIsAdmin` is not filled (not stored per message). A phone-typed message is a normal outbound bubble (`meta.source = 'phone'`), no author.

## Groups API seams (as built)

Full route table, errors and rules: [docs/api/whatsapp-devices-baileys.md](../../api/whatsapp-devices-baileys.md#groups-of-a-personal-number-v2devicesidgroups). What the web must know:

- **The final base path is `/v2/devices/:id/groups`** (`:id` = `devices.uuid`, `:gid` = `wa_device_groups.uuid`), NOT the flat `/v2/wa-groups` the contract comments in `groups.ts` name. The number is in the path, so the device-scoped bodies and queries drop `deviceId`: use `waDeviceGroupListByDeviceQuerySchema`, `createWaDeviceGroupBodySchema`, `waDeviceGroupJoinPreviewBodySchema`, `waDeviceGroupJoinBodySchema` (added to `groups.ts`, derived with `.omit`). Mapping from the contract's comments:

  | Contract comment                                 | Built                                                                                                                                      |
  | ------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------ |
  | `GET /v2/wa-groups/state?deviceId=`              | `GET /v2/devices/:id/groups/state`                                                                                                         |
  | `GET /v2/wa-groups?deviceId=...`                 | `GET /v2/devices/:id/groups?q&status&limit&cursor`                                                                                         |
  | `POST /v2/wa-groups`                             | `POST /v2/devices/:id/groups` (201)                                                                                                        |
  | `PATCH /v2/wa-groups/:id`                        | `PATCH /v2/devices/:id/groups/:gid` (200 with the group, synchronous)                                                                      |
  | `PUT .../:id/picture`                            | `PUT .../:gid/picture` (multipart `file`), plus `DELETE .../:gid/picture`                                                                  |
  | `GET .../:id/participants`                       | `GET .../:gid/participants?q&limit&cursor`                                                                                                 |
  | `POST .../:id/participants/{add,promote,demote}` | ONE route `POST .../:gid/participants` with `{ action: 'add' \| 'promote' \| 'demote', numbers }` (`changeWaGroupParticipantsInputSchema`) |
  | `POST .../participants/remove`                   | `DELETE .../:gid/participants` with `{ numbers }` (as the official groups)                                                                 |
  | `GET/POST .../:id/join-requests`                 | `GET .../:gid/join-requests[?fresh=1]`, `POST .../:gid/join-requests`                                                                      |
  | `GET .../:id/invite-link`, `POST .../reset`      | same under `/v2/devices/:id/groups/:gid/`                                                                                                  |
  | `POST /v2/wa-groups/join-preview`, `/join`       | `POST .../groups/join-by-link/preview`, `POST .../groups/join-by-link`                                                                     |
  | `POST .../:id/leave`                             | `POST .../:gid/leave` with `{ confirm: true }` (answers the group, `left: true`)                                                           |
  | (new)                                            | `GET .../:gid` (detail), `POST .../:gid/refresh`, `POST .../groups/sync` (`waDeviceGroupsSyncResultSchema`, once a minute)                 |

- Every mutation needs an `Idempotency-Key`. A participants call is a 200 with per-number `results` even when nobody could be added (the reasons are the point); refusals before WhatsApp
  are 4xx. 429 `WA_GROUP_RATE_LIMITED` carries `errors[]` `retryAfterS` and `scope`; there is no `Retry-After` header.
- A group the number left stays in the list (`left: true`, `leftAt`); `status=left|active|all` filters. `hasInviteLink` only says a code is held. The member list, join requests and invite
  link need `wa.groups.manage`; the list and `stats` need only `wa.groups.read`.
- `pictureUrl` is always `null` (WhatsApp re-encodes the picture and no copy is stored); show a placeholder, refresh after `PUT picture` from the response.
- Realtime `whatsapp.device_group.changed` `{ groupId, deviceId, kind }` (to `wa.groups.read` holders); bell rows `device_group_join_request` (collapsing, `data.count`) and `device_group_removed` link to `/devices/groups?device=<device uuid>`.
- Worker side: `WhatsappDevicesBaileysWorkerModule` (sink, realtime consumer, sweep), `DeviceGroupNotificationConsumer`. The legacy `wa_groups` / `wa_group_members` are kept filled one way from the directory
  (never `group_code`); a group left keeps its legacy row. Env: `WA_GROUPS_SWEEP_HOURS` (6; 0 = off) joins the limiter's `WA_GROUPS_*` list.
- Events (aggregate module `whatsapp-devices-baileys`, id the row): `created` (`changed: ['rejoined']` when the number came back; `bulk`/`lead` on a first import of more than 25 groups), `updated`
  (`changed`: `subject|description|settings|admin|picture|invite_link`), `participants_changed` (`added`, `removed`, `roles`, `size`), `join_request` (`added`, `pending`, or `handled: 'settled'`), `left` (`removed`).
- Tests: `test/e2e/whatsapp-devices-baileys/device-groups.e2e.spec.ts` (47), `test/unit/whatsapp-devices-baileys/device-groups-{rules,mapper,sweep}.spec.ts`, `test/unit/notifications/device-group-notification-rules.spec.ts`.
