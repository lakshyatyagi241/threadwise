# whatsapp-personal-groups build plan

Spec: `inventory/whatsapp-personal-groups.md` (TW-WAGRP-001..036). Related: `docs/specs/waba-groups-management.md` (the official feature to mirror), `docs/specs/personal-whatsapp-connect.md`.
Goal: groups on PERSONAL numbers (unofficial Baileys, channel kind `whatsapp_qr`) work end to end: group messages arrive as inbox threads, agents reply into groups, and a management screen
lists, creates and edits groups and their members, like the official `/waba-groups` feature but over the lease-owning worker's socket.

## Decisions (owner may overrule; D numbers are the spec's)

- D1 no new plan feature: gated by the existing two-level unofficial gate (platform switch + per-workspace allow list) like every personal-number action.
- D2/D3 group messages become inbox threads (peer key `g:<bare group id>`), STORAGE ONLY: no flows, keyword, AI, routing or commerce listener runs on them, no contact is created per speaker, a message typed on the phone in a group is mirrored as outbound. Sender name = participant pushName; LID-only speakers have an empty `participant`.
- D4 permissions `wa.groups.read`, `wa.groups.create`, `wa.groups.manage`, `wa.groups.leave` (category whatsapp, no scope; Owner/Admin baseline).
- D5 a group the number left or was removed from is kept, marked `left_at`, and its thread becomes read-only.
- D6 a management screen (Reference has none): a third tab "Groups" next to Numbers and Warmer on /devices.
- D7 additions included: join approvals (list/approve/reject), invite link get/reset, group picture, join by invite link (own cap, highest ban risk, off by default via env).
- D8 composer in a personal group thread: text, media, location, contact, reactions, @mentions (typed @ picks a member), replies.
- D9 not metered per member: a group send counts as ONE message, no wallet charge.
- D10 scheduling and broadcasts to groups stay refused.
- D11 ban-safety: per-device group-op limiter (Redis, default 20 ops/min and 200/day), max 20 participants per add call, create limited to 5/day/device, join-by-link 5/day/device, a 10 min cooldown after a refusal that looks like a ban/limit signal; env overrides.
- D12 subject max 60, description max 512 (Reference).
- Own table `wa_device_groups` (+ `wa_device_group_members` only if needed): NOT the legacy `wa_groups`/`wa_group_members` (device-agnostic, unique on jid alone); the storefront's group-code ordering keeps reading the legacy tables and a small sync keeps `wa_groups` filled from the new directory so `/store/groups` keeps working (decide in the build and document).
- Group id convention: bare id without `@g.us` everywhere (`g:<id>` thread key, `group_jid` column stores the bare id; `groupJid()` re-adds the suffix).

## Work split

Phase A (one agent): shared contracts, migrations (table, permissions), socket/port types and Baileys calls, limiter, events/realtime contract. Then in parallel:

1. inbox integration (api): bridge, ingest, peer-key, dispatcher, qr adapter group send, retitle, read-only when left, tests that currently assert the old behaviour flip.
2. groups API (api): controller, service, repository, directory sync sink, events, realtime consumer, notifications, limits.
3. web: the Groups tab and screens, inbox composer/thread changes, i18n 21 locales, help, tests.

## Phase A seams (as built)

Everything below exists in the branch `lakshya/wa/personal-number-groups`. The three later agents code against THIS section only. Paths are relative to `crm-platform/`. Nothing is committed.

### Conventions fixed by Phase A

- Group id: BARE everywhere (no `@g.us`): `wa_device_groups.group_jid`, the thread key `g:<id>`, `GroupSnapshot.groupId`, `WaDeviceGroup.groupId`. The socket layer takes either form (`toGroupJid()` re-adds the suffix); `GroupSnapshot.jid` keeps WhatsApp's full `...@g.us` id.
- Phones: the runtime reports DIGITS (no `+`); the API contracts speak E.164 (`+digits`). Convert at the API edge (`'+' + digits`; the number input to the socket may be E.164 or digits, `jidOf` strips non-digits).
- A member is addressed by its WhatsApp id (`jid`, may be `...@lid`); the participants jsonb stores `{jid, phone, lid, name, admin}` (`phone`/`lid` digits). Mentions, join-request handling and removals by id use `jid`.
- Unofficial gate: `DeviceControlService.groupAction/sendMessage/messageAction` all call `UnofficialWhatsappGate.assertEnabledFor(orgId)` first (throws WA_UNOFFICIAL_DISABLED). The groups API must also call it before touching its own tables' write paths (it is the same gate used by the devices routes).
- Deleting a device CASCADE-deletes its `wa_device_groups` rows (documented in the migration; threads are separate rows and stay).

- Errors (`WA_GROUP_ERROR_CODES`, spread into `ERROR_CODES` via `WADEV_ERROR_CODES`): `WA_GROUP_NOT_ADMIN` (403), `_NOT_FOUND` (404), `_DEVICE_NOT_READY` (409), `_RATE_LIMITED` (429, `errors[]` `retryAfterS` + `scope` of `WA_GROUP_RATE_SCOPES`), `_LIMIT_REACHED` (422), `_LEFT` (409), `_INVALID_NUMBER` (422), `_JOIN_LINK_INVALID` (422), `_JOIN_BY_LINK_DISABLED` (422), `_ANNOUNCE_ONLY` (422, send guard), `_UNAVAILABLE` (502). ### 3. Runtime and socket (`apps/api/src/infra/providers/node-bridge-runtime/*`, `apps/api/src/modules/node-bridge-runtime/*`)

- `inbound.port.ts`: `GroupSnapshot {jid, groupId, subject, description, size, isAdmin, announce, restrict, joinApproval, memberAddMode, owner, creation (ISO), addressingMode, inviteCode (usually null: only `invite` reads it), participants[GroupParticipantSnapshot {jid, phone, lid, name, admin}] (cap 1024)}`; `GroupPatch`; `GroupEvent = {kind:'update'|'participants'|'join_request', groupId (bare), author, ...}` (`participants` carries `selfAffected`).
- `socket.port.ts`: `SocketEvent` adds `{type:'group_event', event}` and `groups` gains `complete?: boolean` (default true = every group the account is in, so a missing one was left; false = only these were re-read). `GroupAction` (all `groupJid` bare or full): `list, metadata, create{subject, participants, description?}, participants{change add|remove|promote|demote}, subject, description, settings{announcement|not_announcement|locked|unlocked}, member_add_mode{mode}, join_approval{enabled}, join_requests, join_request_update{participants(jids), action approve|reject}, leave, invite, revoke_invite, picture{data|bufferKey|remove}, get_invite_info{code}, accept_invite{code}`. `GroupResult` by action (tell apart with `in`): list `{groups}`, metadata `{group}`, create `{group, participants[{jid,status}], descriptionSet}`, participants and join_request_update `{participants: [{jid, status}]}` (WhatsApp status codes `'200'`, `'403'`, ...), join_requests `{requests: GroupJoinRequestSnapshot[]}`, invite and revoke_invite `{code}`, get_invite_info `{invite: GroupInviteInfo}`, accept_invite `{joined: {groupId|null, requested}}`, rest `{ok:true}`.
- `group-mapping.ts` (pure, exported via the module index): `participantOutcome(change, status)` (status code -> `ParticipantOutcome`, same strings as the contract), `classifyGroupError`, `COOLDOWN_REASONS`, `inviteCodeOf`, `mentionToken(jid)` (`'@' + user part`: the BODY must contain this token for WhatsApp to draw the mention), `toGroupJid`, `bareGroupId`, `jidUser`, `toSnapshot`.
- Sends: `SendCommand` variants `text|media|location|contact` take `toGroup?: true` (`to` = bare group id or `...@g.us`); `{type:'group_text', groupJid, body, mentions?: string[] (member jids)}` stays; every command takes `quote?: {providerMessageId, fromMe, participant?, text?}` (a reply; in a group give the quoted author's jid as `participant`). A bare id of 16+ digits or digits-with-dash is recognised as a group id even without `toGroup`, so it can never be turned into a person's address. Group media download is allowed (`downloadMedia` keeps files of `kind:'group'` messages that are not `fromMe`).
- Events: the factory listens to `groups.upsert` (full read, debounced 5 s, `complete:true`), `groups.update` and `group-participants.update` (emit `group_event`, then re-read ONLY that group after a 5 s debounce, `complete:false`; more than 5 pending groups become one full read; a `remove` of our own number is not re-read), `group.join-request` (emit `group_event`). `InboundSink` gains `groups(ctx, groups, {complete})` (signature changed: third arg) and `groupEvent(ctx, event)`; `InboundRouter.groupEvent` fans out.
- Control (`DeviceControlService`, provided by `NodeBridgeRuntimeModule`): `groupAction(orgId, deviceId, action): Promise<DeviceCommandResult>` (never throws except the gate). Order: gate, `participants.length > 20` -> `{ok:false,status:'error'}`, join-by-link off -> `{ok:false,status:'disabled'}`, limiter -> `{ok:false,status:'rate_limited', retryAfterSeconds, scope}`, then local socket or the owning worker (`not_ready` when no lease). A WhatsApp refusal returns `{ok:false, status:'group_failed', reason: not_admin|not_found|limit_reached|bad_invite|forbidden|whatsapp_rate_limited|unknown, message}`; `forbidden` and `whatsapp_rate_limited` start the cooldown (a plain not-admin never does). Success is `{ok:true, status:'group', result: GroupResult}`. Map: `rate_limited|whatsapp_rate_limited` -> `WA_GROUP_RATE_LIMITED`, `disabled` -> `WA_GROUP_JOIN_BY_LINK_DISABLED`, `not_ready` -> `WA_GROUP_DEVICE_NOT_READY`, `timeout|not_found` -> `WA_WORKER_UNAVAILABLE`-style 503/`WA_GROUP_UNAVAILABLE`, `group_failed.not_admin` -> `WA_GROUP_NOT_ADMIN`, `not_found` -> `WA_GROUP_NOT_FOUND`, `limit_reached` -> `WA_GROUP_LIMIT_REACHED`, `bad_invite` -> `WA_GROUP_JOIN_LINK_INVALID`, the rest -> `WA_GROUP_UNAVAILABLE`.
- Picture: pass `{type:'picture', groupJid, data: Buffer}` to `groupAction`; it travels through Redis (`wa:out:...`, 300 s) between processes. Baileys re-encodes it (sharp is installed); the API still checks type and the 5 MB cap.
- Limiter (`runtime/group-limiter.ts`, `DeviceControlService.groupLimiter`): `GroupOpLimiter.acquire/startCooldown/cooldownRemaining/peek(orgId, deviceId)`; `peek` returns the numbers behind `WaGroupLimits` (`opsPerMinute, opsPerDay, createsPerDay, joinByLinkPerDay` as `{limit, remaining, resetsAt}`, `cooldownUntil`, `participantsPerCall`, `joinByLinkEnabled`) for the state endpoint. Counted per org+device in Redis (`wa:grp:<org>:<device>:<scope>:<bucket>`, cooldown `wa:grpcool:<org>:<device>`); minute window, day windows reset at 00:00 UTC; a refused call is refunded; fail-open on a Redis error. Costs: every action 1 op; `create` also 1 create; `accept_invite` and `get_invite_info` also 1 join. Env (all optional): `WA_GROUPS_OPS_PER_MINUTE` (20), `WA_GROUPS_OPS_PER_DAY` (200), `WA_GROUPS_CREATES_PER_DAY` (5), `WA_GROUPS_JOIN_BY_LINK_PER_DAY` (5), `WA_GROUPS_JOIN_BY_LINK_ENABLED` (off), `WA_GROUPS_COOLDOWN_SECONDS` (600), `WA_GROUPS_PARTICIPANTS_PER_CALL` (20). NOT done here (the groups API owns it): the list refresh min interval / roster cache TTL, and whether the API pre-checks `isAdmin` from the row before calling (it should, so a plain member never reaches WhatsApp).
- Module exports (`apps/api/src/modules/node-bridge-runtime/index.ts`): types `GroupEvent, GroupParticipantSnapshot, GroupPatch, GroupSnapshot, GroupAction, GroupResult, GroupInviteInfo, GroupJoinRequestSnapshot, GroupParticipantStatus, GroupFailureReason, ParticipantOutcome, GroupLimits, GroupLimitsView, GroupRefusal`; functions `participantOutcome, classifyGroupError, COOLDOWN_REASONS, inviteCodeOf, mentionToken, toGroupJid, bareGroupId, jidUser, loadGroupLimits, opKindOf`; classes `GroupOpLimiter`.
- Test support (`apps/api/test/e2e/node-bridge-runtime/support.ts`): `fakeGroupSnapshot(over)`, `FakeSocket.groupReplies[actionType] = result | Error | fn` (an Error with `isBoom: true` and numeric `data` reads as WhatsApp's refusal), `FakeSocket.groupCalls`, `groupResult` fallback.
