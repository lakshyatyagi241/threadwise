# Google Calendar, Sheets and the flow Google nodes: audit, build and manual test

Walkthrough item 30, "Calendar and Sheets": "Calendar: API done, never run against real Google. Sheets: partial. The Sheets add-on is built but never run in a real
Sheet. Flow Google nodes are bound to `NoGoogleAccount`, so they do nothing." This file is the audit, what was built, the decisions, and the checklist for the first
real Google account. **No real Google account was used for any of it**: every Google answer in the tests comes from a local stand-in written from Google's documentation
(`apps/api/test/e2e/appointments-booking/fake-google.ts`) and the Apps Script add-on runs under an emulator of Apps Script's globals. What that proves and what it cannot
is stated in each section.

Owners of the domains touched (`ownership.json`): Punya (appointments-booking), Vedant (flow-runtime-engine, flow-builder-editor); the new `google-account` domain (code `gacc`) is Lakshya's. This work crosses those zones: the owners should review the files listed by `ownership_check.py --as lakshya` (FOREIGN). Branch: `lakshya/google/calendar-sheets-flows`. Runbooks:
[google-workspace-setup.md](../../runbooks/google-workspace-setup.md) (Google Cloud, operator), [google-sheets-addon-real-sheet-test.md](../../runbooks/google-sheets-addon-real-sheet-test.md)
(a human in a real Sheet). API: [google-account.md](../../api/google-account.md). Wiring, parity: [wiring](../wiring/google-account.md), [parity](../parity/google-account.md).

### Calendar (appointments) against real Google: what is built and what would break

Built and tested against the stand-in: consent, refresh, free/busy with a 30 s cache and a back-off after an outage, event insert with a fixed id (409 turns into an update),
patch, delete (404/410 are success), Meet creation with a recheck, own-event filter for group types, `invalid_grant` handling, disconnect with revoke.

Findings, in priority order:

1. **No retry or backoff inside a call, and no `Retry-After`.** One 429 or 503 failed the outbox attempt (it retries with backoff) or tripped the 20 s free/busy back-off. Real Google
   returns 429 `rateLimitExceeded` / `userRateLimitExceeded` routinely on calendars. Fixed: `googleRequest` (below).
2. **Failure reasons were free text from Google's body.** `googleReason` put whatever a response said into error messages and logs. Fixed: only short identifiers pass.
3. **A 403 was only `forbidden` or rate limit.** Real Google answers 403 for three different things: the token lacks the scope (`ACCESS_TOKEN_SCOPE_INSUFFICIENT`), the API is not
   enabled in the Cloud project (`SERVICE_DISABLED`, `accessNotConfigured`) and "this account may not". They need three different fixes (workspace, operator, share the file). Fixed.
4. **A grant could be calendar-only or not, with no way to tell.** The adapter treated any active grant as a calendar. Now it checks the stored scopes cover the calendar capability, so
   a workspace connected for Sheets only is "disconnected" for the calendar and nothing is written or read.
5. **`include_granted_scopes` and `login_hint` were absent**, so an incremental consent would have replaced the grant and could land on a different Google account. Fixed.
6. **The first insert after a lost answer relied on the outbox only.** Still correct (409 becomes an update); now the same call recovers inside itself when a repeat is allowed.
7. **Free/busy failing means slots are offered without it** (`SlotsService.busyFor`). This is Reference's behaviour and an agreed decision, but it is the one place real Google trouble can
   produce a double booking; it is logged as `calendar free/busy failed`. Not changed.
8. Not exercised against real Google, and could not be here: Meet creation timing (the adapter rechecks once after 600 ms), the `privateExtendedProperty` filter, free/busy range limits for
   very long booking windows, behaviour of an app in Testing (grants end after 7 days, handled as needs-reconnect), all-day events (Google counts them as busy in free/busy unless
   marked free; the adapter does not filter them), recurring events (free/busy expands them), attendees and invitations (`sendUpdates=all` only when there is an attendee address).

**Not built, on purpose: incremental sync tokens (410 reset), watch channels with renewal, a push webhook, echo dedupe.** The calendar is one-way (we write bookings, we read busy time when a
slot list is built). Reference has no read-back either, and there is no rule for what an appointment should do when someone moves or deletes its event in Google (cancel it? reschedule it? ask
a person?). Building a sync would add behaviour Reference does not have and needs that rule first. See open decision 1. What a watch channel would buy without the rule is a fresher busy-time
cache, which the 30 s cache already approximates.

## 2. What was built

**Contracts** (`packages/contracts/src/google-account/`): the capability table (`calendar`, `sheets`, `docs`, `forms`, `drive_listing`) with the scopes of each and which are restricted;
`googleScopesFor`, `googleCapabilitiesOf`, `googleMissingScopes`; status, connect and summary schemas; ten `GOOGLE_*` error codes.

**Database** (`20261207090000_gacc_google_account.sql`): four columns on `appointment_calendar_connections` (`last_error_code`, `last_error_at`, `last_error_capability`, `last_used_at`, with a check that the first two go together) and two permission keys (`google.account.read`, `google.account.manage`, admin presets via the baseline table). **No new table**: the grant table already satisfied the tenancy
rules (composite key, forced RLS with USING and WITH CHECK, touch trigger) and renaming it would have churned the appointments code for nothing.

**API**

- `infra/providers/appointments-booking/google-transport.ts`: one HTTPS transport for every Google call: timeout, no redirects (a bearer token must not follow one), typed errors, and retries
  with full jitter. Repeats only transient failures; a `Retry-After` longer than the cap is handed to the caller instead of slept on; a sheet append and a document copy repeat only after a 429
  (a 5xx may have happened after the work); the busy-time lookup and the one-time code exchange never repeat.
- `google-calendar.errors.ts`: kinds `scope` and `api_disabled`, `Retry-After` parsing, `googleFailureCode` (one stable `GOOGLE_*` per kind), identifier-only reasons.
- `google-calendar-tokens.service.ts`: `withToken(orgId, fn, { capability })` stops at once with `scope_missing` when the grant lacks the capability; the operator's switch is checked before
  anything else; last error / last used are recorded (only account-level failures, only on change, at most once a minute, fire-and-forget).
- `google-calendar-connect.service.ts`: `begin(capabilities, returnTo)` and `account()`; the callback checks the grant against the capabilities this consent asked for (the signed state
  carries them); a shorter grant on an account that is already connected is kept (it is a superset of what was stored), on a first connection it is withdrawn.
- `modules/google-account/` (new): `GoogleAccountController` (`GET /v2/google-account`, `POST .../connect`, `GET .../calendars`, `POST .../disconnect`), `WorkspaceGoogleAccessTokens` (the real
  `GOOGLE_ACCESS_TOKENS`), `GoogleFilesService` (the pickers and the summary), `GoogleAccountModule` (binds `GOOGLE_ACCESS_TOKENS` and `GOOGLE_WORKSPACE`; replaces `NoGoogleAccount`).
- `HttpGoogleWorkspace` rewritten on the shared transport: capability per call, `GoogleAccountError` with a stable code, `listFiles`, the workspace's chosen calendar for Meet, an event id derived
  from the flow step (a repeated step reads back its own meeting), `{key}` as well as `{{key}}` in Docs (Reference did both; the first port only did one), a Docs fill or share that fails after
  the copy exists no longer loses the link (Reference carried on), and customer-typed text that Sheets would run as a formula is written as text.
- Flow builder: `GET /flows/builder-context/google/:kind` now lists files; `GET /flows/builder-context/google/status` for the notices.
- Flow nodes write `[GOOGLE_*]` and what to do into the run log (`google-failure.ts`).

**Web**: `/google-account` page (status, account, capability list with a tick per permission, Connect / Add permissions / Reconnect / Disconnect, last problem, used by, privacy note), the
Settings tile, a help guide, 21 locales; a yellow notice above each Google step in the flow inspector when the account is not usable for that step; the picker says "the file list permission
was not given" instead of "not connected" when that is the case; the calendar card's disconnect confirmation says the Google steps stop too.

## 3. Decisions (made without asking, listed for the owner)

1. **One connection, extended; no second OAuth stack and no table rename.** Reference had exactly one Google grant per workspace shared by Calendar, Meet, Sheets, Docs and Forms. The calendar
   connection already is that, with better storage than Reference's. Reusing the Gmail OAuth was rejected: different client, different (restricted) scopes, per mailbox.
2. **Capabilities instead of one big consent; all of them shipped (owner decision, round 2).** Reference asked for `drive` (restricted) from everyone on the first click. Here the admin ticks what they
   want and can add more later. Calendar, Sheets and Forms are ticked by default, **Docs and Drive** and **Drive file list** (restricted by Google) start unticked but are selectable, and **nothing is gated in code**:
   what limits a customer before verification is Google (an unverified app is limited to its test users), and the runbook says so, with the exact verification submission checklist (section 9 of
   [google-workspace-setup.md](../../runbooks/google-workspace-setup.md)). Without the file list the builder falls back to "paste the link", which Reference also supported.
3. **A Google node that cannot run FAILS visibly (owner decision, round 2; the first build kept Reference's "flow goes on" and listed it as open).** The step fails with its stable `GOOGLE_*` code and a
   sentence that says what to do (`GOOGLE_ACCOUNT_NOT_CONNECTED`: choose "Connect Google" ...). If the node has an error output the run leaves by it; **none of the Google nodes has one** (Form's two exits are
   timeout and continue), so the run fails at that step: the run log and the run view show the code and the fix text, and a failed run can be retried from the run after the account is fixed.
   Customers still get Reference's apology for Docs, Meet and Form. What is not a failure (Reference behaviour kept; corrected in round 3, R5): a step the author left half empty (no sheet, no columns, no template, no form) is noted in the run log and skipped, and the checks take their "no" branch; and a lookup that
   found no row is an ordinary empty result. A Docs fill or share that fails after the copy exists is still a note: the link is sent (the document exists), the step does not fail.
4. **Not configured is reported before not connected.** With no platform client nobody can connect, so "Connect Google" would be no help (Reference: 503 while the master switch is off).
5. **Security hardening deviations** (written in the parity file): formulas typed by customers are stored as text; reasons from Google bodies are reduced to identifiers; no redirects on Google calls;
   a sheet row or document copy is never repeated after an ambiguous failure.
6. **Plan gate.** Reference gated `/google-account` on a plan feature with no counterpart in the plan registry. The page and routes are gated by the two permissions only; flows keep `automation` and
   appointments keep `appointment_booking`.
7. **Operator console keeps the name "Google Calendar"** (settings group `googleCalendar`, env `GOOGLE_CALENDAR_*`) so the redirect address operators registered stays valid. Its texts and the
   runbook now say it serves every Google permission.
8. **Signing the Sheets add-on's payloads with HMAC** is not possible with this design (the server stores only a hash of the member's key), and the add-on's webhook is an idempotent upsert; see section 5.

## 5. The Sheets add-on: verification harness, findings and fixes

Nothing in this section ran inside a real Google Sheet. What was built is an **emulator of Apps Script's globals** (`apps/api/test/support/apps-script-harness.ts`, with `apps-script-addon-kit.ts`,
`apps-script-fake-crm.ts` and `apps-script-remote.ts`) that runs the **unchanged** `Code.gs` and the dialogs' server calls under Node: `SpreadsheetApp` with a real in-memory grid,
`PropertiesService`, `CacheService`, `LockService`, `ScriptApp` triggers (with the documented limit of 20 per user per script), `HtmlService`, `UrlFetchApp` (pluggable; a real HTTP bridge on a worker
thread, because a synchronous fetch on the test thread would deadlock the in-process Nest server), `Utilities`, `Session`; scope enforcement from `appsscript.json`; edit and time-driven event objects;
the documented execution-time budget and 10,000-row sheets; virtual time. A method the emulator does not model throws, so a gap shows up as a failing test, not a silent pass.

| Test                                                                | What it covers                                                                                                                                                                                                                                                                                                                           |
| ------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `test/unit/chrome-extension-sheets-addon/addon-runtime.spec.ts`     | menu, Initial Setup, Send Test, Submit, edit trigger install/removal, error messages for 401/403/413/429 and network failures, URL parsing edge cases, key never in document properties or logs                                                                                                                                          |
| `addon-sweep.spec.ts`                                               | the hourly sweep: new and changed rows, the hidden state sheet, headers, trigger column, chunking, partial failure, the time guard (resumes next hour), a 10,000-row sheet                                                                                                                                                               |
| `addon-static.spec.ts`                                              | every `google.script.run` function the dialogs call exists, no `innerHTML` or `eval`, the manifest (V8, valid time zone, exactly the scopes the code needs, each justified by an API use)                                                                                                                                                |
| `apps-script-harness.spec.ts`                                       | the emulator itself, so its rules are tested and not assumed                                                                                                                                                                                                                                                                             |
| `test/e2e/chrome-extension-sheets-addon/addon-real-api.e2e.spec.ts` | the unchanged `Code.gs` against the real Nest app and Postgres: Initial Setup with a real Webhook URL, Send Test records the columns, an edit becomes a contact, re-sending is "unchanged" (no duplicate), a changed row updates the same contact, 600 rows in chunks, a revoked key reads clearly, a per-key 429, pull and product sync |
| `sheets-webhook-hardening.e2e.spec.ts`                              | idempotency per row and of the consent ledger, concurrent identical posts, 500-row and 2 MiB limits, the key stored only as a hash (a scan of every table and every Redis key found no raw key)                                                                                                                                          |

**Bugs the emulator found in `Code.gs`, each fixed with a test that failed first (14):** the status column the add-on writes itself was part of the row hash, so every row was re-sent every hour;
Send Test and Submit failed when the settings box was left empty ("keep the saved one"); writes past the default 1000 x 26 grid threw; hash text such as `12e4` was stored by Sheets as a number so the row
looked changed for ever; the sweep read the sheet one row at a time (thousands of calls) instead of in bulk; no time guard (now stops at 4.5 minutes and resumes next hour); a 413 could not be fixed by
retrying (requests are now split by size, an oversize row is marked, long cells trimmed to 500 characters); Pull wrote with `setValues`, so a name like `=HYPERLINK(...)` became a formula and `+91...`
lost its plus (now plain text); edit triggers were not scoped per spreadsheet; no lock around concurrent sends and a second "CRM status" column could be created; the sweep read whatever sheet was active
after the chosen one was renamed; a heading such as "Age" or "ID" was read as column letters; Send a test row failed on a non-https server; the Google daily fetch quota had no message of its own.
`Settings.html` "Remove connection" used `window.confirm()`, which Google's sandbox may ignore, so it is now an inline confirmation (unverified: manual checklist C11).

**Server side**: ten simultaneous posts of one new person created ten contacts, because `ContactsService.create` looked up and inserted in two steps. First fixed with a Redis lock in the Sheets webhook; **now
fixed where it belongs, in `ContactsService.create`** (section 8, decision 5), and the Redis lock is gone from the webhook path. A re-sent consent row now reports "unchanged" when the ledger already holds that
consent. 422 above 500 rows and 413 above 2 MiB were already right.

**Payload signing and replay protection: not implemented, on purpose.** The server stores only a hash of the member's key, so an HMAC with the key as secret cannot be verified, and a redesign of the add-on's
authentication is not in scope. A replayed body is the same idempotent upsert (the replay test shows "unchanged", one contact, one consent entry) and cannot reach another workspace; a timestamp or request-id
header would add nothing without a signature.

**What the emulator cannot prove** (the human checklist in [google-sheets-addon-real-sheet-test.md](../../runbooks/google-sheets-addon-real-sheet-test.md) does): Google's real runtime, the authorization and consent
screens (the four permission lines; whether `LockService` needs a fifth), which menu appears (add-on menu or the plain fallback), real trigger delivery timing, real quotas, the sandboxed dialog iframe, the mobile app.
Two things to look at first: **whether the hourly trigger of the Marketplace editor-add-on version can read the spreadsheet at all** (the author suspects not, and the emulator assumes it cannot; if so
"Send on schedule" needs a design change), and whether `exceptionLogging: NONE` is what you want (Reference used STACKDRIVER; NONE was kept for privacy).

Left as reported, not changed: one paste sends at most 50 rows, so with only "Send on event" on the rest wait for a sweep; `consent` and `consent_note` are not mapped by `Code.gs`, so consent cannot be sent from a sheet.

## 8. Round 2: the owner's decisions, and what was built

### Decision 1: calendar drift is looked for, never auto-applied

Google is not the source of truth. **What exists**: a bounded reconcile that reads, never writes an appointment.

- **Schedule**: BullMQ queue `calendar-reconcile`. `CalendarReconcileScheduler` (every 60 s, worker process) claims up to 10 workspaces whose `next_reconcile_at` is due (`FOR UPDATE SKIP LOCKED`,
  the claim moves the time 30 minutes ahead so a dead worker's workspace comes back) and enqueues one job each (`jobId` per workspace and minute, 3 attempts, exponential backoff from 60 s).
  `CalendarReconcileProcessor` takes a Redis lock `calendar-reconcile:lock:<orgId>` (a second worker or an overlapping retry skips), then runs the pass under that workspace's own context (RLS).
- **Pass**: confirmed appointments with a Google event id that start in the next **60 days** and were not looked at in the last 50 minutes, at most 100 per pass (least recently looked at first), one
  event read each (`events.get`, 150 ms apart), no watch channels or sync tokens. So each appointment is read about once an hour, not continuously. Next pass in an hour (5 minutes when 100 were taken);
  after Google failures 5, 10, 20 ... minutes up to six hours (`reconcile_failures`).
- **Verdicts** (`calendar-drift.rules.ts`, pure): `in_sync`, `pending`, `drifted`. The event is compared with **what we last wrote** (`google_pushed_*`: start, end, guest, etag), never with the
  appointment. So our own move that has not been pushed yet is `pending` (an echo), our own push changes the etag but matches the snapshot (not drift), and a guest answering or Google filling in the
  Meet link is `in_sync`. Drift reasons (contract `CALENDAR_DRIFT_REASONS`): `event_deleted` (410 or status `cancelled`), `event_missing` (404), `time_changed`, `attendees_changed`.
- **When Google cannot be asked** (5xx, quota, timeout, a grant that died mid-pass): the pass stops, **nothing** is claimed about any appointment ("could not look" is never "gone"); a dead grant ends as
  `needs_reconnect` through the existing token path; the workspace backs off.
- **Stored**: migration `20261208090000_gacc_drift_and_consent.sql`: `appointments.google_sync_state|reason`, `google_drift_detected_at`, `google_drift_starts_at|ends_at` (what Google shows), the push
  snapshot, `google_event_etag`, `google_checked_at`; `appointment_calendar_connections.next_reconcile_at|last_reconcile_at|reconcile_failures`. Reasons are check-constrained, stable and in
  `@crm/contracts` (`google-account/drift.ts`); the appointment response carries `calendar.sync`.
- **Shown**: "Calendar out of sync" in the booking list's status cell and, in the booking drawer, a panel with the reason, what Google shows, "This booking has not been changed" and, for people with
  `record.appointments.update` for that appointment, two buttons.
- **Actions** (`POST /v2/appointments/:id/calendar/push|accept`, 409 `GOOGLE_SYNC_NOT_DRIFTED` when there is nothing to decide): **push** writes the event again from the appointment through the same code as every
  automatic write (a deleted event returns under its id); **accept** reads the event again and applies it through the usual rules: a deleted or missing event cancels (customer told), a moved event reschedules to
  Google's start (availability is not re-checked; the customer is told), changed guests are acknowledged (the invitee is the appointment's contact and cannot be edited from Google).
- **One notification**: the first detection writes an audit row and the outbox event `appointment.calendar_drifted`; `AppointmentDriftNotificationConsumer` writes one in-app notification (`appointment_calendar_drift`)
  to the appointment's host, else whoever booked it, linking to the appointment. A different reason later is a quiet update.
- **Tests** (fake Google): deleted, moved, guests changed, our own echo (pending and after the push), churn that is not drift, 404, 410, an outage claiming nothing and backing off, a token revoked
  mid-run, the 60-day horizon, put back by hand clears the badge, push and accept for every reason, permission and tenant checks, scheduler claims once, processor lock. Unit tests of the verdict rules and the back-off.

### Decision 4: consent bound to the person who pressed Connect

Table `google_consent_requests` (forced RLS, `nonce_hash` unique, composite FK to the user, status check, expiry index): **Connect** creates a record bound to the user, the workspace and the capabilities, and the signed
state names it by nonce (the nonce is stored only as a hash). Google's redirect (the public callback, which cannot see a session) **claims** the record atomically (once), exchanges the code, checks the grant
and **parks** the sealed tokens, then redirects to **`/google-account/confirm?request=<uuid>`**. That page (signed in, `GET/POST /v2/google-account/consent/:id[/confirm|/cancel]`, no permission key: the same
person decides) shows "Connect <google email> to <workspace> for <capabilities>?" with **Confirm** and **Cancel**; only Confirm stores the grant (one transaction, row locked, audit, outbox).
Another signed-in user gets `403 GOOGLE_CONSENT_NOT_YOURS` (and the parked grant is withdrawn at Google unless it could be the stored account's), another workspace gets 404, an expired record `410
GOOGLE_CONSENT_EXPIRED`, a used, cancelled or refused one `409 GOOGLE_CONSENT_USED`. A worker sweep forgets and withdraws records nobody finished. Tests: confirmation shows who and what, forwarded link, expired,
replayed (twice and at once, and a replayed Google redirect), wrong workspace, cancelled (and a cancelled top-up keeps the working connection), replaces-account notice, the sweep, plus the schema test.

### Decision 5: duplicate contacts fixed where they come from

`ContactsService.create` now takes a transaction-scoped advisory lock (`pg_advisory_xact_lock(hashtextextended('contact-identity:<org>:<email|phone>', 0))`) on the normalised email and phone of the
request before it looks for an existing contact, keys sorted so two requests never deadlock; the second concurrent request waits, then sees the first's contact and matches it (the existing "matched" path). `createOrMatch` returns
whether it created, so the Sheets webhook reports "unchanged" for a matched row. **The Redis lock in the Sheets webhook path is removed.** Behaviour is otherwise unchanged. Test:
`test/e2e/contacts-attributes-tags/contact-create-concurrency.e2e.spec.ts` (real Postgres: ten parallel creates of one email, phone against phone plus email, different people, another workspace).
**Note for the CRM owners:** this touches `modules/crm/contacts/contacts.service.ts`, their zone; please review it (the diff is the helper `lockIdentities`, its call at the top of the create transaction and
the `createOrMatch` split).
