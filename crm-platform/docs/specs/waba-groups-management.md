## 1. Problem

A business on a Cloud API number that Meta has granted Groups can run WhatsApp groups from its business number: create a group, hand out the invite link, approve who joins and talk to the members. WaDesk has a screen for this ("Meta Groups", `/waba-groups`). In our repo only the plumbing under that screen exists: Meta's four Groups webhooks are mirrored into `waba_groups`, and messages posted in a group show up as an inbox thread. There is no way to create or manage a group, no screen, and sending a reply to a group thread is unsafe (section 4).

Not to be confused with `wa_groups` and `wa_group_members` (the forms-links-groups schema). Those are WaDesk's **unofficial** (Baileys, personal number) group directory, keyed by a `...@g.us` jid. The owner switched that engine off (`docs/runbooks/whatsapp-unofficial-switch.md`). The two share nothing but the word "group".

## 2. Goals and non-goals

### Goals

1. Port every capability of WaDesk's `WabaGroupsController` with the same rules (section 3), on our stack.
2. Make a group thread a first-class inbox thread: send to it safely, show who wrote each message, and refuse a suspended group.
3. Keep the mirror (`waba_groups`) as the one source the screens read; Graph is called only to act or to refresh one group.
4. Make "not eligible" a normal state of the screen, not an error (WaDesk does the same).

### Non-goals

| Not in this spec                                                                      | Why                                                                                                                                                            |
| ------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Adding a participant directly                                                         | WaDesk has none and Meta does not offer it: groups are invite-only (reference code comment; **Meta docs** list no add endpoint).                               |
| Group profile picture upload                                                          | Meta supports it (5 MB, **Meta docs**); WaDesk has no UI or call for it, and the PORTING_RULES forbid new behaviour. Phase 4 candidate.                        |
| Ordering codes and "ORDER G:<code>" links for Cloud API groups                        | They exist only for `wa_groups` (section 5). Group messages deliberately never run automation (WD-WABA-039), so an ordering bot cannot read a Cloud API group. |
| Flows, keyword replies, AI or routing on group messages                               | WD-WABA-039 stores only; a 100-member group would bill per member for every automated reply.                                                                   |
| Groups on Interakt or on a registry provider                                          | Unverified that those routes expose the Groups API (section 9). Phase 1 refuses them with a clear code.                                                        |
| Group calling, interactive and commerce messages, edit/delete of a sent group message | **Meta docs**: unsupported on groups.                                                                                                                          |

**Verified gaps inside WaDesk itself** (they matter for "no feature lost"):

1. `POST /waba-groups/{group}/settings` (edit subject and description) and `DELETE /waba-groups/{group}/participants` (remove up to 8) have **no control on the page and no JS caller**. 2. The pending queue is fed **only by the webhook** (`group_join_request_created`). Meta's `GET join_requests` is coded (`GroupClient::joinRequests`) but nothing calls it, so a request made while the webhook was down is never shown. Likewise `GroupClient::list` is used **only** as the eligibility probe: there is **no "sync all groups from Meta"** action. A group appears in WaDesk only by being created there or by a lifecycle webhook. Refresh is per group.
3. `WabaGroup::hasConnected()` and the `usable` scope are defined and never called (dead code).

### 3.4 Eligibility

Meta has no capability flag in WaDesk's view, so `isEligible()` probes `GET /{phone}/groups?limit=1` and treats **only error 131215** as "not eligible"; any other failure (network, rate limit) is **not cached** as a "no". A definite answer is cached for one hour per number (`waba_groups_eligible_<config id>`). A missing token or phone id returns "This WhatsApp number is missing its Meta credentials. Reconnect it and try again." **Reference.**

### 3.5 Error text

`GroupClient::ERROR_TEXT` replaces Meta's developer wording for 15 codes (**reference, not re-verified**; Meta's reference page did not list them): 131020 needs more than one member; 131041 group gone or number not a member; 131059 cursor expired; 131201 some participants could not be processed; 131202 duplicate participant; 131204 participant limit; 131207 suspended for policy; 131208 too many group operations; 131209 picture must be square; 131210 picture at least 192 by 192; 131211 created-group limit reached; 131212 not a member; 131213 join request gone; 131214 creation temporarily disabled; 131215 not eligible. Anything else shows Meta's message or `HTTP <status>`.

### 3.6 Webhooks and inbox (already ported, listed for completeness)

- `group_lifecycle_update`, `group_participants_update`, `group_settings_update`, `group_status_update` mirror into `waba_groups` (WD-WABA-040); `group_delete` deletes the row.
- A message with `group_id` is stored on a thread keyed on the group id, no contact, no automation, unread incremented (WD-WABA-039); statuses with `recipient_type=group` fold into `meta.group_delivery`.
- **Sending**: the inbox dispatcher, for a WABA thread whose `raw_jid` is non-numeric, sends to that id verbatim with `recipient_type=group`; text, media and template payloads are otherwise identical. It has **no reference to `WabaGroup`**, so a suspended group is **not** blocked on send (the "cannot message it" line on the page is advice, not a check). **Verified by grep.**
- There is no "send the invite as a template" feature (the code comment says that is how a link is shared; the page only offers Copy).

### 4.3 Sending to a group: **not built, and the current path is unsafe**

Fact, from reading (not executed):

1. A group thread's key is `g:<group id>` (`inbound-ingest.service.ts` line 109); the thread is created with no contact.
2. A reply goes `OutboundService` -> `envelopeOf(row, conv.peerKey, ...)` (`outbound-envelope.ts`, `to: peerKey`) -> `buildMessageBody` in `apps/api/src/infra/providers/whatsapp/meta-outbound.ts`, which hard-codes `recipient_type: 'individual'` (line 129) and passes `to` through `metaRecipient()` (line 17): that **strips every non-digit** and accepts 4 to 20 digits.
3. Result: a Cloud API group id is long base64 text with embedded digits. If its digits number more than 20 the send fails `RECIPIENT_NOT_ALLOWED`; if they number 4 to 20 the message is **sent as an individual to an unrelated phone number made of those digits**. No branch handles `g:`; `recipient_type: 'group'` appears nowhere in the outbound code (only the inbound status filter in `meta-inbound.ts`). The other outbound builders (`meta-cloud.provider.ts`, catalog, OTP) are individual-only by design.

The web inbox also has no group rendering: nothing in `apps/web/src` reads `meta.group` (sender name and number), so a group thread shows messages with no author. This is why phase 0 is a guard, not a feature.

## 5. Ordering codes: the relation, if any

None. Ordering codes (`wa_groups.group_code`, the "ORDER G:<code>" `wa.me` link, the Store > Groups screen) live in `storefront-builder/admin/store-groups.service.ts` and `checkout-orders-merchant-payments/lib/group-code.ts`, read and write **only `wa_groups`** (the unofficial directory), and the inbound bot that reads such an order runs on that engine. A Cloud API group has an opaque id, no code column, and never reaches an ordering flow. Do not add a code column to `waba_groups` (decision D7 records this).

## 8. Data model

`waba_groups` already holds every column WaDesk uses; **no change is needed for parity**. Needs and options:

| Item                                             | Decision                                                                                                                                                                                                                          |
| ------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Join requests                                    | Keep in `meta_json.join_requests` (the webhook rules already write it). A table is only worth it if D5 (list from Meta) is chosen. Not recommended for v1.                                                                        |
| Participants                                     | WaDesk stores none. v1: none. If D3 gives a remove-participant screen, show the members from `GET /{group}?fields=participants` **on demand** (not stored: it is personal data and Meta is the source). No participants table.    |
| `created_by_user_id`, `source` (`api`/`webhook`) | Optional additive columns so the list can say who created a group. Recommend adding `created_by_user_id bigint NULL` with a composite FK to `users`; cheap, and audit already records the actor.                                  |
| Deleted-by-us marker                             | Not needed: delete removes the row, and `group_delete` re-delivers the same removal idempotently.                                                                                                                                 |

## 9. API surface

Base `/v2/waba/numbers/:id/groups` (the number is the owner; `:id` is the connection uuid, the same shape as `waba/numbers/:id/username` in `waba-extras.controller.ts`). Controller `waba-groups.controller.ts`, service `waba-groups-admin.service.ts` (a new file: the existing `WabaGroupsService` stays the webhook mirror), all through `DatabaseService.tx()`; mutations take `Idempotency-Key` (`common/interceptors/idempotency.interceptor.ts` exists) and updates carry `rowVersion`.

| Route                                 | Does                                                                | Permission                              |
| ------------------------------------- | ------------------------------------------------------------------- | --------------------------------------- |
| `GET /groups/state`                   | `{eligible, reason, provider}` (cached probe; `?fresh=1` re-probes) | `waba.groups.read`                      |
| `GET /groups`                         | keyset list + the four KPIs; number switcher uses the numbers list  | `waba.groups.read`                      |
| `POST /groups`                        | create (`subject` 1-128, `description` 0-2048, `joinApprovalMode`)  | `waba.groups.create`                    |
| `POST /groups/:gid/refresh`           | refresh row and link from Meta                                      | `waba.groups.read` (it only reads Meta) |
| `POST /groups/:gid/invite-link/reset` | new link                                                            | `waba.groups.manage`                    |
| `PATCH /groups/:gid`                  | subject, description (answers 202: confirmed by webhook)            | `waba.groups.manage`                    |
| `POST /groups/:gid/join-requests`     | `{action: approve\|reject, ids[1..]}`                               | `waba.groups.manage`                    |
| `DELETE /groups/:gid/participants`    | `{participants[1..8]}`                                              | `waba.groups.manage`                    |
| `DELETE /groups/:gid`                 | delete on Meta, then the row                                        | `waba.groups.delete`                    |

- **Permission keys.** The convention in this repo's skill is `<category>.<resource>.<action>`, with `record.*` for CRM entities. The WABA domain already uses `waba.<resource>.<action>` (`waba.numbers.read|connect|manage`, `waba.customers.*`), so groups follow the domain: `waba.groups.read`, `.create`, `.manage`, `.delete`, category `whatsapp`, **`supports_scope = false`** (a group belongs to a number, not to a record owner; the same as `waba.numbers.*`). Granted to Owner and Admin like WaDesk's admin-only access (unlock, grant, relock pattern in migration `20261014090000`). If the owner wants the literal `record.` prefix, see D2.
- **Contracts** (`packages/contracts/src/whatsapp-cloud-api-waba/groups.ts`, exported from the barrel): `wabaGroupSchema` (uuid, `groupId`, subject, description, `inviteLink`, `joinApprovalMode`, `participantCount`, `suspended`, `awaitingInviteLink`, `pendingJoinRequests[{id, waId, createdAt}]`, `lastError`, `syncedAt`), request schemas with the limits above, `WABA_GROUP_ERROR_CODES`. Error codes in `errors.ts` (problem+json): `WABA_GROUPS_NOT_ELIGIBLE`, `WABA_GROUPS_PROVIDER_UNSUPPORTED`, `WABA_GROUP_NOT_FOUND`, `WABA_GROUP_SUSPENDED`, `WABA_GROUP_LIMIT_REACHED`, `WABA_GROUP_RATE_LIMITED`, `WABA_GROUP_META_REJECTED` (with Meta's code in `meta`). The web branches on `code`, never on text.
- Phone numbers of join requests and members are personal data: returned only to a holder of `waba.groups.manage`.

## 10. The Meta client port

- **Where**: a new port `waba-groups.port.ts` and adapter `waba-groups.client.ts` next to `waba-admin.client.ts` in `apps/api/src/infra/providers/whatsapp-cloud-api-waba/`, registered in `waba-providers.module.ts`. It uses `WabaHttp.call(auth, {method, path, json})` (DELETE with a JSON body is supported: `WabaRequest.json` is sent for any method) so base URL, version (`META_API_VERSION`), timeout (`WABA_HTTP_TIMEOUT_MS`) and error normalisation are the existing ones. Nothing builds a URL elsewhere.
- **Provider selection**: groups belong to **one number** (`provider_config_id`), resolved with `WabaConnectService.resolveConnection` like the other number-level calls. A connection on `interakt` or a `registry` route returns `WABA_GROUPS_PROVIDER_UNSUPPORTED` in phase 1 (not verified that those routes pass the Groups API through; WaDesk always went to Meta directly). A manual or Embedded Signup connection with a Meta token is the supported case. A follow-up task: ask Interakt and each registry provider.
- **Eligibility**: probe `GET /{phone}/groups?limit=1`, treat only 131215 as definitive (WaDesk's rule). Also read `is_official_business_account` already stored by connect/health as a cheap pre-check and a message, but the probe is the authority (the flag's agreement with 131215 is unverified).
- **Error mapping**: add the group codes of section 3.5 to a `waba-group-errors.ts` that returns our `code` plus an operator sentence (English now, i18n keys in the web; the web owns the wording). `WabaApiError.retryable` already classifies transient failures.
- **Idempotency and retries**: Meta's create is **not idempotent**, so create is never retried by us. The request is called with a client-supplied `Idempotency-Key`; if the Graph call succeeded and our write failed, the `group_create` webhook upserts the row anyway (`waba-groups.service.ts` `apply`). Approve, reject, reset, update, delete may be retried once on a transient error; remove is not retried.
- **No database transaction is held across a Graph call** (the rule already recorded in the parity notes): call Meta, then open one tx that writes the row, the audit record and the outbox event.
- **Rate limiting**: Meta's limit is not documented on the pages read (131208 is the signal). Add a per-org, per-number throttle on mutations (proposal: 30 per minute per number, Redis, fail-open like `LeadHookThrottle`) and map 131208 to `WABA_GROUP_RATE_LIMITED` with a "wait and retry" message. The 30 is a proposal, to be tuned.
- **Timeouts**: the existing 20 second WaDesk value is a reasonable default; use the env value already there.

## 11. Worker and outbox events

Existing names are `whatsapp.connection.connected|disconnected|removed|primary_changed`, `whatsapp.order.received`, `whatsapp.form.submitted`, so groups use **`whatsapp.group.*`** (not `waba.group.*`), via the `outbox-event` skill, in the same transaction as the write:

| Event                         | When                                                                                  | Consumers                            |
| ----------------------------- | ------------------------------------------------------------------------------------- | ------------------------------------ |
| `whatsapp.group.created`      | our create succeeded, and also when a `group_create` webhook creates a row we did not | notifications, realtime refresh      |
| `whatsapp.group.updated`      | settings, link reset, refresh changed something                                       | realtime                             |
| `whatsapp.group.deleted`      | our delete, and the `group_delete` webhook                                            | realtime                             |
| `whatsapp.group.join_request` | a join request is created (webhook), and when handled (`handled: approved\|rejected`) | notification "N people want to join" |
| `whatsapp.group.suspended`    | `group_status_update` changes the flag (both directions)                              | notification to admins               |

The webhook path (`WabaGroupsService.apply`) today emits nothing; adding the events there is part of phase 2. No new worker job is required: Meta calls are made in the request. An optional repeatable job `waba-group-sweep` (D4) would list groups per eligible number to catch missed webhooks.

## 12. Inbox integration

1. **Phase 0 guard (no decision needed).** A thread whose key starts with `g:` must never reach `metaRecipient()`. Until phase 3, `OutboundService` refuses with a typed error (`WABA_GROUP_SEND_UNAVAILABLE`) and the web composer is disabled on a group thread with a line explaining it. This closes the wrong-number send of section 4.3.
2. **Sending (phase 3).** `OutboundEnvelope` gets an optional `recipient: {kind: 'individual'|'group'}`; `buildMessageBody` sets `recipient_type` accordingly and uses the group id **verbatim** (without `g:`, without stripping). Allowed kinds: text, media, template; refuse reaction, interactive, location, order, flow, contacts with `WABA_GROUP_KIND_UNSUPPORTED` (**Meta docs**: interactive and commerce are unsupported). Refuse when `waba_groups.suspended` is true (`WABA_GROUP_SUSPENDED`), which WaDesk does not do (an improvement, recorded as `intended`). The 24 hour window, wallet debit and per-participant billing are checked with the billing owner: today's `assertCanQueue` assumes one recipient, and a group send bills per participant (reference text, **not re-verified**), so the pre-send balance check must use `participant_count` (D8).

4. **Mentions** are not part of the Cloud API pages read; not in scope.
5. **Threads** stay keyed `g:<group id>`; the title follows the subject (a rename from `group_settings_update` should also retitle the thread: small addition in phase 2, today the title is set at first message only).
6. **Contacts**: still none. A participant's number is not made a contact (WD-WABA-039 rule).

## 16. Security, abuse and compliance

- **Tenancy**: a group is addressed only by `(org, number, group)`; the webhook already scopes by the receiving number, the new routes load the row by uuid under RLS, so a guessed id from another workspace is "not found".
- **Who can create**: Owner and Admin by default (WaDesk: admin). Creating a group and sharing a link is a way to message people at scale: the product should not let a low-trust role do it; `waba.groups.create` is separately grantable.
- **Opt-in and spam**: groups are invite-only and the person chooses to join, which is Meta's consent model; we add **no** add-by-number feature (non-goal) and no bulk "send my invite template to a list" in v1 (a possible later feature; it would need the template opt-in rules and the wallet checks of broadcasts). A suspended group (Meta policy action) is shown and blocks sends.
- **Invite link** is a bearer secret: shown only to `waba.groups.read`, never written to audit or logs, never in a URL parameter; a reset invalidates all older links (Meta).
- **PII**: member and join-request numbers are personal data; they are not stored in `waba_groups` beyond the pending-request map the webhook already writes (retention: removed when handled or revoked) and are not copied into contacts.
- **Cost**: a send bills per participant (reference text); show the member count next to the composer and check the wallet against it.
- **Webhook trust** is unchanged (signature or platform key, then routing by `phone_number_id`).
- **Data export / deletion**: deleting a workspace cascades the rows; a "forget a participant" request is a remove action plus the stored message text, handled by the inbox's existing deletion path (not new here).
