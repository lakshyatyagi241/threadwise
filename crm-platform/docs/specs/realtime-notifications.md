## 0. How to read this, and the evidence behind it

Everything marked **verified** was read in this working tree (branch `lakshya/whatsapp/personal-connect-phase1`) or in `reference/app` (read-only), with the path next to it. **Inferred** means reasoned from code, not run. Nothing was run: no app, no browser, no test, and no code was changed to write this.

## 1. Problem, in one paragraph

The platform already has everything needed to push a live signal to one person on any page: one Socket.IO connection per signed-in session, mounted once in the app shell, already joined to that person's private `user` room. But (a) nothing on the server ever creates a bell row for a message, an assignment or a mention, so the bell has nothing to show, (b) the bell has no socket subscription at all and polls once a minute, and (c) the only code that listens to the inbox events (`inbox.unread`, `inbox.conversation.upsert`, `inbox.assignment`) lives inside the Inbox page's list hook, so on any other page the events arrive at the browser and are dropped. Fixing it is therefore mostly a **producer** problem (new notification rows and one new socket event) plus a **global listener** on the web; the transport does not change.

### 2.3 Server: the notifications module (verified)

- **Table** `inbox_notifications` (`packages/db/src/schema/notifications-activity-audit/tables.ts`): `org_id, id, uuid, user_id, type, title, body, data jsonb, link, dedupe_key, read_at, created_at, updated_at, row_version`. Forced RLS; unique partial index `(org_id, user_id, dedupe_key)`; feed index `(org_id, user_id, id desc)`; partial index on unread. (A second table, `notifications`, is the Reference workspace feed; unused by the bell. `push_subscriptions` exists, see 2.5.)
- **API** (`notifications.controller.ts`): `GET /v2/notifications`, `GET /v2/notifications/unread-count`, `POST /v2/notifications/:id/read`, `POST /v2/notifications/read-all`. Staff only, pinned to the caller, no permission key. Cursor is the row id.

### 2.4 Web (verified)

- **One socket per session already exists globally.** `apps/web/src/app/(app)/layout.tsx` mounts `RealtimeProvider` (keyed by org and user) around the whole shell. `RealtimeClient` is connected on every page; the `user` room is joined by the server at connect. The URL comes from `REALTIME_URL` / `NEXT_PUBLIC_REALTIME_URL` (`.env.example` line 159, `deploy/hostinger/docker-compose.yml` line 370).
- **Subscribers**: `useRealtimeEvent` / `useResync` / `useRoom` are used only in `features/team-inbox-conversations/api/{use-list,use-thread,hooks}.ts`, `inbox-screen.tsx` (presence), `thread-pane.tsx` (typing), and the wallet balance hook. The client calls handlers only for event types somebody subscribed (`realtime-client.ts` `eventHandlers` lookup), so everything else is silently dropped.
- **Why the inbox counter changes only on the Inbox page.** The "unread" tab count lives in a `useReducer` inside `useConversationList` (`use-list.ts`), which exists only while the Inbox screen is mounted. Its handlers for `inbox.unread` / `inbox.conversation.upsert` / `inbox.assignment` die with it. There is no app-level store, no react-query key and no nav badge for the inbox (`nav-rail.tsx` supports only the `'new'` / `'soon'` / `'upgrade'` text pills; `_registry/types.ts` `badge?: 'new'`).
- **Why the bell does not react.** `features/notifications-activity-audit/components/notification-bell.tsx` + `api/hooks.ts`: react-query keys `['notifications','unread']` and `['notifications','feed']`, `refetchInterval: 60_000`, `refetchOnWindowFocus`, no `useRealtimeEvent`. Even a perfect socket would not help, because the server never writes a row for a message (2.3) and never emits a notification event.
- **Toasts**: `@crm/ui` `ToastProvider` / `useToast` (success and info 5 s, danger 9 s, max 4 visible, message is a `ReactNode`, no action API). It is mounted **per feature page** (about 50 `providers.tsx` files), **not** in the `(app)` layout, so there is no way to toast from a global listener today. Whether the region has `aria-live` was not checked; verify (section 8).
- **Not present anywhere in `apps/web/src`** (grep): document-title badge, favicon badge, notification sound, `Notification.requestPermission` / `new Notification`, service worker. `push_subscriptions` and a VAPID key service exist on the API (`platform-settings-branding-storage/vapid.service.ts`) but no subscribe route, no sender and no service worker were found.
- **Copy**: bell wording is by `type` in `apps/web/messages/{en,ar}/notifications-activity-audit.json` `types.*`, falling back to the server's English `title` / `body` for unknown types (`lib/copy.ts`).
- Unread-count semantics: `GET /v2/notifications/unread-count` is a true count; `meta.unread` on the list is the same.

## 3. Goals and non-goals

### Goals

1. A person who may see a conversation is told, wherever they are in the app, within about 3 seconds of a new chat, a new message on a chat they own, an assignment to them, or a mention of them.
2. The bell shows those items as rows, with a live badge and no 60-second wait; opening the row opens the conversation.
3. A calm experience: one row per chat (with a count), no notice for the chat you are reading, none for your own actions, throttled toasts and sound, no flicker.
4. Works in several tabs and across several API pods; degrades to polling when the socket is down.
5. Existing notifications (task, lead, form, sales doc, wallet) keep their rows and behaviour and gain the live push for free.
6. Respect tenant isolation, permissions and plan gates exactly like the REST reads do.

### Non-goals

| Not in this spec                                                 | Why                                                                                                                                                    |
| ---------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Changing the transport (Socket.IO, ticket handshake, room model) | It works and is tested; the problem is above it.                                                                                                       |
| Moving team chat or incoming calls onto sockets                  | Own plans (`docs/api/realtime.md` "Not built here"); this spec only adds a team chat **mention** notification (phase 2) from an existing outbox event. |
| Email, Slack, mobile push                                        | TW-NOTIF-002, 022 to 025, own work. The prefs model below leaves room for them.                                                                        |
| Operator (platform admin) bell                                   | Separate feed (`admin-console-shell/header/notification-bell.tsx`); not touched.                                                                       |

## 4. Design overview

```
inbound message commit ──► outbox `message.received` ─┐
assignment commit ───────► outbox `conversation.assigned` ─┤  (worker)            ┌─ insert/collapse row (RLS, dedupe)
note commit ─────────────► outbox `conversation.note_added` ┤  NotificationConsumers ─┤
task/lead/form/wallet... ► (existing outbox events) ───────┘                      └─ AFTER commit: NotificationPublisher
                                                                                        │  RealtimeEmitter.emitToUsers(user rooms)
                                                                                        ▼  Redis ► API pods ► sockets
browser (any page): RealtimeProvider ► LiveNotifications (mounted once in (app) layout)
   notification.created / .read / inbox.unread / inbox.assignment / resync
        └► react-query: setQueryData(unread) + debounced invalidate(feed, unread, inbox counts)
        └► toast (deep link) · sound · desktop notification · tab title · aria-live
```

Principles: the **row is the truth** (the bell is built from the table); the **socket event is a hint** (`notification.created` carries ids and the new unread total, never message text, same rule as `docs/api/realtime.md`); every producer goes **through the outbox** and publishes **after the commit**.

Rules that apply to every row of the catalogue:

- **Never notify the actor** of their own change (assignee == `byUserId`, author of the note, the person who started the broadcast when it succeeds).
- **Never notify the person looking at it.** The client suppresses toast, sound and desktop alert when the visible tab shows that conversation, and marks the row read (section 8.4). The server also marks matching unread rows read in the same transaction as "mark conversation read" (section 7.3), so a second device or a reload agrees.
- **Muted conversation** (`conversations.muted_at`, verified): no rows 1 and 2.
- **Only people who may see the record** (`AudienceResolver` / `conversationVisible`) get a conversation notification, recomputed at the moment of the event, so a role change applies at once (same guarantee as the live inbox signals).
- **Plan and module gates**: a conversation notification is written only when the workspace has the inbox on its plan (use the same feature check the inbox REST routes use, found at implementation time), so a downgraded workspace stops getting them. Domain notifications keep their own domain's gate.
- **Workspace preferences** (the owner's table that exists today) gate **new** types in the catalogue through one resolver, `NotificationPrefsResolver`, extracted from `workspace-settings.service.ts` and `defaultEventFlags`; `inapp=false` suppresses both the row and the live push. Rows 5 to 7 stay ungated in phase 1 (no behaviour change for what already works). See D3.
- **Per-user preferences** (bell / toast / sound / desktop per type, DND) are phase 2, in a new table; phase 1 keeps per-browser conveniences (sound on or off, desktop on or off) in `localStorage`, which is exactly what browser storage is for.

## 6. Data model (one migration, phase 1; use the `add-migration` skill and run its RLS checker)

`inbox_notifications` gains, all nullable or defaulted so every existing row and writer keeps working:

| Column         | Type                     | Use                                                                                                     |
| -------------- | ------------------------ | ------------------------------------------------------------------------------------------------------- |
| `collapse_key` | `text`                   | Non-null only for collapsing types (`msg:<convUuid>`).                                                  |
| `event_count`  | `int not null default 1` | How many events the row stands for ("3 new messages").                                                  |
| `subject_kind` | `text`                   | `conversation`, `channel`, `team_chat_channel`, ...; lets "mark read" find rows by what they are about. |
| `subject_uuid` | `uuid`                   | The conversation / channel uuid.                                                                        |

Indexes: unique partial `(org_id, user_id, collapse_key) WHERE collapse_key IS NOT NULL AND read_at IS NULL` (one unread collapsed row per person and chat; a unique-violation retry loop handles a race); `(org_id, user_id, subject_kind, subject_uuid) WHERE read_at IS NULL` for mark-by-subject. No change to RLS (same table). `type` stays free text; add the new values to `NOTIFICATION_TYPES` in contracts.

Collapse is "delete the unread row for this key and insert a new one carrying `event_count + 1`" in one transaction, not an in-place update, so `id` (the keyset cursor) keeps growing with time and the bell order is right. It is idempotent per outbox event because the new row also carries `dedupe_key = message.received:<outboxEventId>` and a redelivered event hits that unique index and does nothing.

Phase 2 adds `notification_user_prefs (org_id, user_id, type, bell bool, toast bool, sound bool, desktop bool, dnd_from, dnd_to)` with the usual composite key, forced RLS and `touch_row`. Phase 2 also adds a retention job (D5).

## 7. Server design

### 7.1 Events and contracts (`packages/contracts`, `contracts-change` skill)

Add to `REALTIME_EVENT` and `realtimeEventSchemas` (`packages/contracts/src/realtime/events.ts`):

| Event                  | Room   | Payload                                                                                                                                          |
| ---------------------- | ------ | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| `notification.created` | `user` | `{ notificationId: uuid, type: string, unread: int, subjectKind: string \| null, subjectId: uuid \| null, collapsed: boolean, silent: boolean }` |
| `notification.read`    | `user` | `{ unread: int, notificationIds: uuid[] \| 'all' }` (multi-tab and multi-device sync after mark read)                                            |

`silent=true` means "update the bell but do not toast or ping" (a collapsed bump inside the throttle window, a team-wide assignment, a muted type). No title, body, name or phone number travels in the event: the client refetches the feed (it needs it for the bell anyway) and renders the toast from the fetched row. Add the new `NOTIFICATION_TYPES` and a `data` schema per type (conversationId, contactName, channelKind, preview of at most 80 characters, count).

### 7.2 Producers and the publisher

- New `NotificationPublisher` in `apps/api/src/modules/notifications/` (pattern of `wallet-realtime.publisher.ts`): `created(orgId, userId, row, opts)` and `read(orgId, userId, ...)`. It computes `unread` with `repo.countUnread` (served by the partial unread index) and calls `RealtimeEmitter.emitToUsers`. Never throws; called **after** the consumer's transaction resolves, never inside it. The worker already imports `RealtimeEmitterModule` (`worker.module.ts` line 50) so consumers can inject the emitter without hosting sockets; the API process has it through `RealtimeModule`.
- `NotificationsRepository`: `insertOnce` returns the new row (id, uuid) instead of a boolean (callers that use the boolean keep working through a wrapper), plus `collapseOrInsert(tx, orgId, n)`.
- Existing consumers (task, salesdoc, lead, form, wallet): after a row is actually written (`written === true`), call `publisher.created`. This is the only change to them.
- New consumers in `NotificationsWorkerModule` (registered with `OutboxSubscriberRegistry`, `txAs({ orgId })`, RLS applies, idempotent, same shape as `TaskNotificationConsumer`):
  - `ConversationNotificationConsumer` for `message.received`, `conversation.assigned`, `conversation.note_added`. It reads the conversation fresh at delivery time (assignee, team, `muted_at`, visibility) and drops what is no longer true, like the task consumer does. Recipients come from `AudienceResolver` / `MemberDirectory` (already usable from the worker: `realtime.md` says so). A hard cap on recipients per event (`NOTIFY_MAX_RECIPIENTS`, default 50) with a warning log when truncated.
- **New outbox event `message.received`** emitted by `chat-conversations/inbound-ingest.service.ts` inside the same transaction as the message insert (skipped for `m.history` and for outbound), payload `{ conversationId, messageId, channelId, channelKind, firstInbound, preview(<=80), contactName }`. The `outbox-event` skill governs this. Why not call the notifier directly after commit like the realtime publisher does: a crash between commit and call would lose the bell row for ever, while the outbox retries; the cost is up to 2 s latency, which the immediate `inbox.unread` signal (which fires at once, today, to the same user room) covers for the badge. **Risk** R2 (drain throughput) applies.
- No other module is imported across a boundary: the consumer reads conversations through `realtime/audience` (already exported) and the chat barrel; `pnpm arch:check` must stay green.

### 7.3 API changes (all additive)

- `GET /v2/notifications` and the unread count: unchanged shapes; list items gain `count` (from `event_count`) and `subject` (`{kind, id}`), both optional in the schema.
- `POST /v2/notifications/read-subject` `{ kind, id }`: marks the caller's unread rows for that subject read; used by the web when the thread opens.
- Server-side too: `InboxConversationsService.markRead` (`team-inbox-conversations/inbox-conversations.service.ts` line 190, which calls the chat core) additionally calls `NotificationsService.markSubjectRead` for the caller, in the same request, then publishes `notification.read`. This is the single place the thread is "read", so another device or tab clears the bell row too. (Confirm the exact call site during implementation.)
- `POST /v2/notifications/:id/read` and `read-all` also publish `notification.read` so other tabs update.
- Phase 2: `GET/PUT /v2/notifications/preferences` (per user).

### 7.4 Scaling, backpressure, failure modes

- Fan-out is one Redis publish per recipient room per event (`emitToUsers`), the same cost class as the inbox signals already sent for every inbound message. The member list is cached 30 s per workspace.
- A burst of 500 messages in one chat produces 500 outbox events, one live row per assignee (collapse), and at most one socket event per 5 s per (user, chat) thanks to a Redis `SET NX PX 5000` guard on `rt:nc:<org>:<user>:<conv>`; guard failures fall back to emitting (never lose a signal). The row count is still exact.
- Several API pods: nothing new, the Redis adapter already routes. Worker pods: the outbox drain claims rows (existing); consumers are idempotent by `dedupe_key`.
- Redis down: emits are dropped with a warning (existing behaviour); rows are still written; the web falls back to polling and a reconnect triggers a resync (section 8.5).
- Socket event lost or reordered: the client reconciles on `useResync` and by a safety poll; the number in the badge always comes from the server count.

## 8. Web design

### 8.1 The one global provider

`apps/web/src/features/notifications-activity-audit/live/` (new): `LiveNotifications` (client component) mounted **once** in `apps/web/src/app/(app)/layout.tsx` directly inside `RealtimeProvider` and above `WalletAppShell`, together with a layout-level `ToastProvider` (from `@crm/ui`) so a global listener can toast on every page. It reuses the existing socket (no second connection): `useRealtimeEvent` and `useResync` from `@/lib/realtime`. Authentication and reconnect are already handled by `RealtimeClient` (ticket per attempt, backoff, foreground resync after 30 s hidden, online event). The existing `key={org:user}` restarts everything on user or workspace switch.

Because inbox screens have their own nested `ToastProvider`, a global toast shown while the Inbox page is open would render in the layout host; check that the two hosts do not overlap (R5) and, if they do, route all `LiveNotifications` toasts to the layout host and keep page toasts where they are.

### 8.2 Events to cache updates (react-query, no new state library)

| Event                                                                                           | Effect                                                                                                                                                                                                                                                                             |
| ----------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `notification.created`                                                                          | `setQueryData(['notifications','unread'], payload.unread)` at once (monotonic server value, so no flicker); add the id to a pending batch; flush after 400 ms: `invalidate(['notifications','feed'])`, `invalidate(['inbox','counts'])`, then toast/sound/desktop per section 8.3. |
| `notification.read`                                                                             | `setQueryData` unread; invalidate feed. Other tabs and devices converge.                                                                                                                                                                                                           |
| `inbox.unread`, `inbox.conversation.upsert`, `inbox.assignment` (already sent to the user room) | Invalidate `['inbox','counts']` (debounced 400 ms, the same number the Inbox tabs use, served by the existing `/inbox/counts`). This alone makes an inbox nav badge live on every page.                                                                                            |
| `useResync` (reconnect, gap, foreground, server request)                                        | Invalidate unread, feed, inbox counts.                                                                                                                                                                                                                                             |

Safety nets: the bell polls every 5 minutes while the socket is `connected` and every 30 seconds while it is not (read `useRealtimeStatus()`), only while the tab is visible, plus the existing refetch on window focus. The Inbox list keeps its own handlers and its 60 s count poll untouched (no regression); the global handler only adds.

### 8.3 What the person sees and hears

- **Bell**: badge updates from the event (no wait); rows use `types.*` copy with an ICU plural for the count ("3 new messages from Ada"); a collapsed row moves to the top. Row text for message types comes from `data` (`contactName`, `preview`) rendered as text (React escapes), never HTML. Footer toggles: "Sound", and "Desktop alerts" (shown only when the browser permission is `default` or `granted`).
- **Toast** (tab visible, not looking at that conversation): "Ada: Hello, I need help with..." with a link to the conversation (`safeLink` rule: app paths only). Info tone, 5 s. Danger tone for disconnects and failures (9 s). Throttle: at most 3 toasts per 10 s; beyond that a single summary "5 new notifications" linking to the bell; one toast per chat per 30 s.
- **Sound**: the Reference two-tone ping (880 then 1175 Hz, about 0.34 s, WebAudio, no asset), at most once per 3 s, only for types marked sound in the catalogue, only after a first user gesture unlocked audio (browsers require it; same as Reference). Default on for chat types (Reference parity), toggle in the bell footer, stored in `localStorage` with try/catch.
- **Desktop notification** (tab hidden): browser `Notification` with the contact name only (no message text, because it appears on lock screens) unless the person opts into previews; `tag = notification type + subject` so a chat replaces its own earlier alert; click focuses the window and navigates. Permission is requested only from the explicit "Desktop alerts" control, never on the first click (Reference's behaviour is hostile to browser heuristics).
- **Tab title**: `(3) <page title>` using the bell's unread total; re-applied through a `MutationObserver` on `<title>` because Next rewrites it on navigation. Favicon badge: phase 2.
- **Inbox nav badge**: phase 2 (needs a numeric badge in the shared nav rail, a shell-owner change); until then the live bell and the title cover it.

### 8.4 Not notifying the person who is looking

A small `openConversationStore` (module-level, `useSyncExternalStore`) is written by the Inbox screen with the id of the thread that is open and visible. `LiveNotifications` checks it plus `document.visibilityState === 'visible'`: match means no toast, no sound, no desktop alert, and the row is marked read through `POST /notifications/read-subject` (debounced), so the badge does not tick up and down.

### 8.5 Multiple tabs, background tabs, accessibility, i18n, volume

- **Multi-tab**: each tab has its own socket and its own cache. To avoid N pings and N desktop alerts for one event, tabs coordinate over `BroadcastChannel('crm-notify')`: on each event id a visible tab claims it immediately, a hidden tab after 150 ms; the first claim plays the sound and shows the desktop notification, the others skip. Toasts are shown by every visible tab (only one tab is normally visible). `BroadcastChannel` absent (old Safari): every tab acts, acceptable.
- **Background tab**: sockets survive (timers are throttled by the browser); a long-hidden tab reconnects and the existing `notifyForeground()` resync fires on return, so the bell is correct when the person comes back. Desktop alerts cover the hidden case when allowed; the title badge always works. Closed-tab alerts need Web Push (phase 3).
- **Accessibility**: a visually hidden `aria-live="polite"` region in `LiveNotifications` announces the same text as the toast, rate-limited to one announcement per 3 s with batching ("3 new notifications"), because `@crm/ui` toast announcement behaviour is unverified (check `toast.tsx` for `role`/`aria-live`; fix there if missing, it benefits every page). The bell button keeps `aria-label` with the count (exists). Toasts never steal focus; the link inside is focusable; Escape dismisses.
- **i18n en/ar**: new keys under `types.*` and `live.*` in `apps/web/messages/{en,ar}/notifications-activity-audit.json`, plural forms for Arabic via ICU; RTL: toast and badge positions use logical properties (`end-*`, as the bell already does); contact names and previews are wrapped with `dir="auto"`. Unknown types fall back to the server's English `title` / `body` (existing rule).
- **Volume**: handlers are O(1): they push into a ref and a single 400 ms flush coalesces any number of events into one invalidate and at most one summary toast; the client already drops repeated event ids (`seen`). No per-event fetch, no per-event render.

## 18. Phase 3 (BL-097): browser notifications (Web Push), as built

| #   | Question                                      | Decision                                                                                                                                                                                                                                                                        |
| --- | --------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | Where does the push hook in?                  | `NotificationPublisher.created`, which every producer already calls after commit. No consumer changed, so a push obeys exactly the rules that made the row (audience, mute, workspace toggle, bell choice) and cannot reach someone the bell would not.                         |

English text (a service worker has no access to the person's language files).                           |
| 4   | When is a push skipped?                       | Deployment unconfigured; silent row; row gone or read; no live device; **the person has a visible tab** (tabs report `{ visible }` over the socket every 15 s, remembered 35 s). ## 19. BL-098: the "waiting for a reply" nudge for unassigned chats, as built

Added 2026-10-08, owner-approved. A product extension (Reference has no equivalent; it has no unassigned-chat alert beyond the first message). The rule of section 5 row 2 stays: a later customer message on an unassigned chat tells nobody,
because everyone who can answer was told at the first message. The gap it leaves is a chat nobody owns that nobody answers. API, settings and operations: [docs/api/notifications.md](../api/notifications.md) ("Waiting for a reply").
Recorded in [product-extensions.md](../threadwise-port/parity/product-extensions.md) ("Waiting for a reply").

| #   | Question                         | Decision                                                                                                                                                                                                                                                                                                                                    |
| --- | -------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | What triggers it?                | A sweep, not an outbox event: nothing happens when a customer is ignored, so there is no event to react to. A delayed job per message would need cancelling on every reply, assignment, read, mute and resolve; a sweep re-reads the truth each minute and cannot be left stale.                                                            |
| 2   | When does a chat qualify?        | Open, not archived, not muted, unassigned (no person, team or AI agent), not a group, no human answered (`waiting_since` set), unread (`unread_count > 0`), latest live customer message at least N minutes old (default 5, `NOTIFY_WAITING_MINUTES`) and at most 24 hours old. Snoozed and closed chats are excluded by `status = 'open'`. |
| 3   | Who is told?                     | Everyone who may read AND reply, as for a new unassigned chat (D1), capped at `NOTIFY_MAX_RECIPIENTS`. Not managers only; business hours do not apply (open question left to the owner). A person who just had the chat open is skipped.                                                                                                    |
| 4   | Does a bot or auto-reply answer? | No. Only a human reply clears `waiting_since` (`applyOutboundSent`), so a chat an auto-reply answered still counts as waiting for a person.                                                                                                                                                                                                 |
| 5   | How often?                       | Once per waiting episode. Dedupe key = conversation uuid + the latest customer message uuid; a chat is also left out while a `chat_waiting` row exists since `waiting_since`, so further customer messages in the same unanswered stretch do not repeat it. A new message after a human answer is a new episode.                            |
| 6   | Which channels?                  | The same fan-out as every producer (`NotificationFanout`): bell row, live `notification.created` with a toast, and Web Push. Defaults: bell on (gated by the owner's `new_customer_reply` toggle), pop-up on, sound off, push on (owner confirmed; `task_assigned` push also stays on).                                                     |
| 7   | What does it say?                | Bell and toast: "No one has answered <contact> yet" and the 80-character preview, in the person's language (en, ar). Push (D4): the contact name as title and "Waiting for a reply" as body, never the message text.                                                                                                                        |
| 8   | Cost and safety                  | One indexed cross-tenant read of ids per minute (partial index `idx_conversations_waiting_nudge`), capped at 100 chats; per-workspace work under RLS with one facts query and a LATERAL probe of the latest message, no query per chat. Worker only. Idempotent across sweeps and pods.                                                     |
| 9   | A workspace setting for N?       | Not built: one env default is enough until an owner asks, and a per-workspace value would put a settings join in the sweep. The default (5 minutes) is documented; N is an env value.                                                                                                                                                       |
| 10  | Groups and unofficial threads    | Group threads (`peer_key` starting `g:`) are excluded. Threads on the unofficial WhatsApp channel are **included**: the first-message notification does not exclude them either (the brief assumed the existing consumer did; it does not, and a group's first message does notify today).                                                  |

Not built: business hours, managers-only recipients, a chat assigned to someone who has not answered (SLA, BL-004), a repeating reminder.
