## 1. Problem

A workspace that advertises on its own site, at an event or by QR code needs a page where a stranger types name, phone, email, what they want, sometimes pays a deposit, and lands in the CRM as a contact (and company, and deal) with the right owner and an automation fired. Today the product has:

- **Lead doors for other people's forms** (`POST /v2/public/lead-hooks/:token`, Zapier, ad platforms, portals). They accept a payload; they do not **render** a form, collect payment, or let the user choose fields.
- **A chat bubble** (chatbot-widget) that captures leads through conversation.
- **WaDesk's "forms"**: these are **WhatsApp Flows forms** (`wa_forms`, `wa_form_submissions`; domain `forms-links-groups`, owner Vedant, pending, schema only in our repo). WaDesk has **no web form builder and no public form URL**. So Forms is **not a port**: it adds a feature, and the WaDesk "no feature lost or changed" rule is met by not touching the WhatsApp Flows forms at all (section 3, naming rule).

Competitors (HubSpot, Typeform, Jotform, Zoho Forms) set the expectation: build in minutes, theme it, drop a snippet on a site, take payment, land in the CRM.

## 2. Goals and non-goals

### Goals

1. A workspace member builds, styles and publishes a form in under 5 minutes, from a template or from a description (text or voice).
2. A **hosted** public URL and an **embed** (script and iframe) on the customer's site, with a per-form origin allow-list.
3. One submission creates or updates **Contact, Company and Deal** from mapped CRM properties (built-in and custom), de-duplicated, owned, tagged, attributed, audited and announced to automations.
4. Optional **payment** inside the form on the workspace's own gateway; the submission becomes "paid" only from a verified gateway webhook, never from a redirect.
5. Nothing is visible or reachable until the workspace subscribes (menu, route, Settings tiles, permissions, public URLs).
6. Safe by default on a public, unauthenticated, cross-origin surface (rate limit, spam, CAPTCHA option, no stored XSS, frame rules, PII retention).

## 4. Product shape

```
Forms (menu, only with the app)
 ├─ Forms         list: status, views, submissions, conversion, last submission; New form (blank / template / Describe it)
 │   └─ a form    Build · Design · Settings (what happens next) · Share · Submissions · Analytics
 ├─ Templates     gallery (lead capture, contact us, event registration, order and payment, survey)
 └─ (Settings > Forms: defaults, CAPTCHA, retention, notification defaults)
```

Lifecycle of a form: `draft` -> `published` (a frozen **version** is what the public sees) -> `paused` (public URL shows "closed") -> `archived`. Editing a published form edits the **draft**; **Publish** snapshots a new version. A submission stores the version it was made against, so a changed form never reinterprets old answers.

## 5. The form definition (one JSON schema, used by the editor, the renderer, the server and the AI)

The form is a document validated by a Zod schema in `@crm/contracts` (`packages/contracts/src/forms-builder/form.ts`). The same schema validates a submission server-side, drives the renderer and is the **output schema of the AI builder** (section 11).

```ts
FormDefinition = {
  schemaVersion: 1,
  title, description?: richTextLite,
  steps: [{ id, title?, blocks: Block[] }],           // one step = a plain form; more = multi-step
  settings: { submitLabel, successMode: 'message'|'redirect', successMessage, redirectUrl?, locale: 'en'|'ar', dir?: 'ltr'|'rtl' },
  theme: ThemeTokens,                                  // section 8
  rules: Rule[],                                       // conditional logic
  mapping: Mapping, payment?: PaymentConfig, after: AfterSubmit
}
Block = Field | Heading | Paragraph | Divider | Hidden | PaymentSummary
Field = { id, kind, label, help?, placeholder?, required, width: 'full'|'half',
          validation?: { min?, max?, pattern?, minLen?, maxLen?, options? },
          bind?: { object: 'contact'|'company'|'deal', property: string },  // section 9.3
          options?: [{ value, label }] }
```

Field kinds in v1.0: short text, long text, email, phone (with country picker), number, currency amount, date, dropdown, radio, checkbox group, single checkbox (also the consent box), rating (1 to 5), hidden (UTM, referrer, a constant), and heading/paragraph/divider. These map to the existing `fieldTypeSchema` values so a bound field inherits type, options and validation from the CRM property (a CRM field of type `radio` becomes a radio block with that property's options). Later: file, signature, matrix, address, scheduling.

Conditional logic (v1.0, small): `show`/`hide` a block or skip a step when `field op value` (`equals`, `not_equals`, `contains`, `is_empty`, `gt`, `lt`), `all`/`any`. Evaluated in the browser **and** on the server (a hidden required field is not required; a hidden field's value is dropped), so the server never trusts the client's idea of visibility. Rules form a DAG over earlier fields only (validated at publish: no cycles, no reference to a later field).

Limits (validated at save): 100 blocks, 10 steps, 50 options per field, 200 characters per label, 5,000 for rich text, definition at most 256 KB.

## 6. Data model

All tables are tenant tables: `org_id`, composite `(org_id, id)` primary keys, composite foreign keys, RLS enabled **and forced** with the `tenant_isolation` policy (`USING` and `WITH CHECK`), `touch_row` for `row_version`, `uuid` for the wire. Written through the `add-migration` skill and its RLS checker. Migration series `2026xxxx_forms_*`.

```
organizations 1─* web_forms 1─* web_form_versions
                     │              ▲
                     │              └─ web_form_submissions *─1 (version_id)
                     ├─* web_form_events          (views, starts, step reached, completions; partitioned monthly)
                     ├─* web_form_submissions 1─* web_form_payments
                     │                        1─* web_form_files          (phase 4)
                     └─* web_form_deliveries      (outbound webhooks, phase 2)
web_form_lookup (SECURITY DEFINER function, no table)   web_form_usage_monthly (counters)
```

## 7. API surface

Base `/v2`. Errors are problem+json with stable `FORMS_*` codes in `packages/contracts/src/forms-builder/errors.ts`. Every mutation takes `Idempotency-Key`; updates take `rowVersion`. Shapes live only in `@crm/contracts` (`contracts-change` skill).

## 8. Styling and theming

Tokens, not CSS: `ThemeTokens` (reusing and extending the storefront's `themes.ts` shape and its 8 themes): `primary`, `background`, `surface`, `text`, `mutedText`, `border`, `error`, `radius` (0/4/8/16/pill), `density` (compact/comfortable/spacious), `fontFamily` (a curated list of 10 web-safe and Google Font stacks; the Google font is loaded by the renderer only when chosen), `fontScale`, `labelPosition` (top/left/floating), `buttonStyle` (filled/outline), `buttonWidth`, `shadow`, `backgroundImage` (workspace media, validated URL), `logo`, `coverImage`, `maxWidth`, `mode` (light/dark/auto). The renderer turns tokens into CSS custom properties on one wrapper element; a server-side validator accepts only the token keys and value shapes (hex colours, a closed set of enums, bounded numbers, https image URLs from the workspace's media storage). That makes theming safe by construction (no CSS parser needed). **Layout presets**: classic card, full-width, split with cover image, minimal (embed, no chrome), conversational (one question at a time, Typeform-style, phase 2). Custom CSS is phase 5 and only with a real sanitiser.

Accessibility: every control has a visible label tied by `for`; errors are linked with `aria-describedby` and announced (`role="alert"` on the summary); focus moves to the first error; colour contrast is checked live in the Design tab (warn under 4.5:1); keyboard-complete; `prefers-reduced-motion` respected; `lang` and `dir` set from `settings.locale` (en, ar RTL). Mobile: single column below 640 px, 16 px minimum input size (no iOS zoom).

## 9. The submission pipeline

### 9.1 Steps (one request, one transaction after the cheap checks)

1. **Edge checks (no DB write yet):** body-size class; content type JSON; `Origin` matches (browser) ; rate limit (per IP, per form, per normalised email/phone: e.g. 20/min/IP, 120/min/form, 5/hour per email); honeypot (silent success, status `spam`, not stored beyond a counter); CAPTCHA when the form or workspace turns it on (`CaptchaService.assert(token, 'form')`); minimum fill time (a submit under 2 seconds after the page's `start` event is scored as bot); link/URL count and keyword heuristics produce `spam_score`; over threshold -> status `spam`, no CRM write, visible in a "Spam" filter, never an error to the sender.
2. **Resolve** the form through `web_form_lookup`; load the frozen **version**; refuse if not `published`; open `db.txAs({ orgId, userId: null })`.
3. **Claim** the submission: `INSERT ... ON CONFLICT (org_id, form_id, idempotency_key) DO NOTHING`; a repeat returns the stored outcome (`201`, same token, nothing written twice). A stored `received` older than 5 minutes is taken over, as the lead pipeline does.
4. **Validate** answers against the version: unknown field ids dropped, hidden-by-rule fields dropped, required, type, min/max, pattern, option membership, email shape, phone to E.164 through `canonicalizeLocalPhone` (with the form's default country), values capped in length, NUL removed, text normalised. Failure: `422 FORMS_VALIDATION` with `{ fieldId, code }[]` (the one case the sender learns specifics, because it is the visitor's own input).
5. **Map and write CRM** (9.2 to 9.4), in this same transaction.
6. **Payment** (section 10): when the form takes payment, create the `web_form_payments` attempt and status `awaiting_payment`; the pay link is minted **after commit** (the gateway call is network I/O and must not sit in a transaction, as `GatewayLinkService.mint` is "outside tx").
7. **Outbox** in the same transaction: `form.submitted` (always), `form.submission_failed`, `form.payment_pending`; and the CRM events the existing writers emit (`contact.created`/`contact.updated`, `company.created`, `deal.created`) with `origin: 'form'`, `formId`, `submissionId`.
8. **After commit, by outbox consumers in the worker** (`worker-job`, never inline): in-app notification to owner and listed users (`insertOnce`, deduplicated on the submission), notification email, submitter confirmation (email or WhatsApp template, opt-in, phase 2), outbound webhook delivery (phase 2), automation trigger, counters.

### 9.2 Hybrid: reuse the lead pipeline's rules, not its entry point

Option A, add a `form` kind of lead source and call `LEAD_INGEST`: gets dedupe, quota, owner round robin, tag, attribution, deal and notify for free, and reuses the events screen. But it **cannot create or link a company, cannot write company or deal properties, cannot touch an existing deal, has no payment state and no frozen-version link**, and a form is not a "source token" an admin creates per form.
Option B, a dedicated service on tx-aware primitives: everything the form needs, but it re-implements what the lead pipeline already settled.

**Recommendation: the hybrid.** A dedicated `FormSubmissionService` (Option B) composes, in one `db.txAs`, the **same primitives and rules** the lead pipeline uses: `resolveOrCreateByIdentity` (email first, then phone, then legacy normalised values; advisory lock; contact quota -> `needs_review: plan_limit_reached`), fill-blank-only update of an existing contact (never overwrite curated data), `coerceCustomValue`, `assertRequiredProperties`, tag, owner (`fixed` / `round_robin`, reusing the cursor logic), attribution (`contact_attributions` row with platform `form`, campaign from `utm_campaign`, form id), deal through `DealsRepository.insert` + `DealEngine.recordCreated` with source `'form'`. The shared pieces move to a leaf in `leads/` (or `crm/`) exported through the barrel so `arch:check` stays green; the leads module keeps its behaviour. A form later also gets a **lead source of kind `form`** only as a record for Attribution reports, if wanted. Reason: the product value is the multi-object write, which the lead pipeline structurally lacks; the safety value is not diverging on dedupe and quota rules.

### 9.3 Binding fields to CRM properties ("mix and match")

Each field has `bind: { object, property }`. The picker (`GET /forms/meta/properties`) lists:

| Object      | Properties offered                                                                                                                                                                        | Write path (v1.0)                                                                                                                                                                                                                                                                     |
| ----------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Contact** | built-in columns (first/last/full name, email, phone, source note, lifecycle is **form-level**, not visitor-set) and every active custom field (`contacts.data`), typed from the registry | create or fill-blank update, as above; custom values pass `coerceCustomValue`                                                                                                                                                                                                         |
| **Company** | name (the match key), domain, phone, address parts, industry, size ... as the Companies contract has them, and company custom fields from the registry (`module_key` `companies`)         | **new**: the Companies domain has no find-by-name/domain and **no custom-value write path** (`createCompanySchema` has no `customFields`; `data jsonb` exists). Add `CompaniesRepository.findByDomainOrName` and `setCustomValues` through the Companies barrel (small, owner review) |
| **Deal**    | title (template `{{name}} from {{form}}`), amount, close date, pipeline and stage (**form-level**, set by the admin), and deal custom values                                              | Deals have **no custom fields today**; v1.0 exposes only title, amount, expected close date, notes. Deal custom fields are a Deals-domain change (decision D5)                                                                                                                        |

Rules: a field not bound is kept only in the submission (`answers`) and shown on the submission and the contact timeline. Required CRM properties (`assertRequiredProperties`) must be bound and required in the form, checked at **publish** (422 `FORMS_PUBLISH_INVALID: crm_required_unbound`), not at 2 a.m. on a visitor. **A visitor can never set**: owner, lifecycle stage, tags, pipeline, stage, any "system" or formula/lookup property (the picker does not offer them; the server ignores a hand-crafted bind). Those are decided by the form's **After submission** settings.

**Match and merge**: contact by email, then phone (the identity order above). Company by `domain` (derived from the visitor's email domain when the form says "match by email domain" and the domain is not a free-mail provider, a built-in blocklist) else by exact case-insensitive name; a match **links** the contact to that company and fills blanks, never overwrites; no match creates one. Deal: `create` (always), `create if none open` (default, the lead-pipeline rule: a returning contact with an open deal gets no second one), or `none`. A returning contact with an open deal gets an activity note and a task option instead.

### 9.4 After submission (admin settings of a form)

Owner (unassigned / fixed / round robin over active users); tag(s); lifecycle stage; deal on/off with pipeline, stage, title template, amount source (fixed, a field, or the payment total); a task for the owner (title, due in N days); group add (when Contact groups are ours to write: through the barrel); notify (owner, users, email addresses); submitter confirmation (phase 2); thank-you (message with a safe subset of rich text, or redirect URL, https only); outbound webhook (phase 2). The contact's **activity timeline** gets an entry `Submitted <form>` with a link to the submission (through `ContactActivitiesRepository.insert`).

### 9.5 Consent, double opt-in, GDPR

There is **no consent table and no DND flag** today (contacts have `is_unsubscribed` and `*_subscription_status` text columns, and nothing emits `contact.opt_in`). v1.0: a **consent block** (checkbox + the exact text + a privacy-policy link, required when the form is marked "collect consent"); the text shown, its version and the time are stored on the submission (`consent jsonb`); a ticked marketing consent sets the contact's subscription status to the value the channel code already uses for "subscribed" and emits `contact.opt_in` (one event, defined here, so a flow can react; this is the first emitter, flagged for the Contacts owner). Unticked consent never flips a subscription. **Double opt-in** (email confirm link before the contact is "subscribed") is phase 2. **Erase** (`DELETE` a submission) wipes `answers`, `utm`, files and nulls the submitter's address from the submission; the contact is an ordinary CRM record erased by the existing contact delete. **Export** of one person's submissions is the CSV export filtered by contact. **Retention**: `retention_days` (default 365, 30 to 3650, or "forever" by the owner) purges `answers` on a daily worker sweep exactly like `LeadRetentionSweepService`; the submission row, outcome and links stay.

### 9.6 Files (phase 4)

No public upload endpoint, no virus-scan hook exist. Design: an upload ticket from `submit-prepare` (signed, 10 minutes, bound to form, field and size), direct-to-storage via `MediaStorageService` with a **private** bucket, allow-listed MIME and extension, per-file 10 MB and per-submission 25 MB caps (`UploadPolicyService.validate`), content sniffing, files stored with `scan_status = 'pending'`, a worker job calls a scan port (`FILE_SCAN` with a ClamAV adapter, `provider-adapter` skill), files are downloadable by staff only after `clean`, through short-lived signed URLs, `Content-Disposition: attachment`. Until then v1.0 has **no file field** and the AI builder is told not to generate one.

### 9.7 Failure handling

| Failure                                                         | Behaviour                                                                                                                                                                                                               |
| --------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Validation                                                      | 422 with field codes; nothing stored (the claim row is not created before validation passes)                                                                                                                            |
| No usable email or phone                                        | `needs_review: no_contact_point`; the answers are kept; admin sees it in "Needs attention" with a retry                                                                                                                 |
| Contact quota reached (new contact)                             | `needs_review: plan_limit_reached`; an existing contact still updates                                                                                                                                                   |
| Plan feature lost, form limit or monthly submission cap reached | Cap reached: the visitor still gets a friendly "received"; the submission is stored `needs_review: submissions_cap` and the admin is notified once per day (never silently drop a lead). Workspace without the app: 404 |
| Deal cannot be made (pipeline deleted, no sales pipeline)       | The contact stays; `error: deal_skipped: ...` on the submission, as in leads                                                                                                                                            |
| Unexpected error                                                | Roll back, record `failed` (`internal_error`) in a transaction of its own, `form.submission_failed` on the outbox; the visitor sees a generic error and the client may retry with the **same** idempotency key          |
| Redis down                                                      | Throttle fails open (as the lead hook does) but CAPTCHA and the honeypot still run; an alert is logged                                                                                                                  |

## 10. Payments in a form

### 10.1 Choice: payment link first, inline later

**Phase 3 settles through a hosted payment link** (`GatewayLinkService.mint`) opened after the submission is stored. Inline card entry (Stripe Elements, Razorpay Checkout in-page) is **phase 5** because it needs per-gateway client SDKs and PCI-scope review. Link flow works for every gateway that `supportsPaymentLinks(slug)`; that is false for offline, Cashfree, PayU, Braintree, HyperPay, Skrill and Authorize.net, so the builder's Payment panel lists only the gateways the workspace has **and** that support links, and says why the others are missing. Razorpay and Stripe are the only two **truly verified** drivers today; the owner should treat the others as untested (decision D6).

### 10.2 Amount types

| Type                  | Definition                                                                                                                                                                           |
| --------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Fixed                 | `amountMinor` set by the admin (registration fee, deposit)                                                                                                                           |
| Per item (order form) | Product lines: each line has a fixed price and a quantity field (a number or dropdown block) or a checkbox; total = sum. Prices live in the **frozen version**, never in the browser |
| From a field          | A choice field whose options carry amounts (a dropdown "Plan A 500 / Plan B 900")                                                                                                    |
| Pay what you want     | A currency field with `min` and optional `max` set by the admin (donation)                                                                                                           |
| Deposit               | Fixed amount or a percent of the computed total, with the balance noted on the deal (not collected)                                                                                  |

**The server computes the amount** from the frozen version and the validated answers. Any amount the browser sends is ignored (a visitor cannot pay 1 for a 500 item). The result is `bigint` minor units using the currency's exponent (`@crm/tax` `parseMoney` / `minorToMajorString`; no float). Currency: one per form, from the gateway's per-gateway whitelist in `catalogue.ts` (the builder refuses a currency the gateway cannot take; multi-currency by visitor choice is later). **Coupons** (a coupon field using the existing coupons domain) are phase 5.

### 10.3 Tax

Optional tax block uses `@crm/tax` with `taxMode: 'auto'` for the workspace's country preset (`docs/tax-engine.md`): the form shows "subtotal, tax, total" computed by the same engine in the browser for display and **recomputed on the server** for the charge. The tax disclaimer from the engine is shown to the admin where a preset is applied. Tax-inclusive vs exclusive is a form setting.

### 10.4 Flow

```
visitor submits ──> validate + write CRM (status awaiting_payment, payment row `pending`, reference FRM-…)
        │ commit
        ▼
mint link (GatewayLinkService.mint(gateway, { reference, amountMinor, currency, callbackUrl: /f/<key>/pay-return?s=<token> }))
        │ answer { next: { type: 'pay', url } }  (client redirects, or opens in the iframe's top window)
        ▼
gateway webhook  POST /v2/store-public/webhooks/gateway/:gatewayId  (signature verified by the existing handler)
        │ settler found by reference prefix `FRM-`
        ▼
FormPaymentSettler.settle(ctx): idempotent  → payment `paid`, submission `paid`, deal amount/stage, contact timeline "Paid 500 INR",
        receipt (phase 3b: invoice + payment recorded), outbox `form.payment_succeeded`, notification
```

`GatewayPaymentRegistry.register({ prefix: 'FRM-', settle })` sits next to the `WAORD-` and `INV-` settlers. **The redirect back is never proof**: `pay-return` only reads the submission's status (set by the webhook) and shows "confirming" with a short poll. If the webhook is late the page says so; the admin sees `awaiting_payment`.

### 10.5 Idempotency and double pay

The reference is unique per attempt; the settler locks the `web_form_payments` row, and a second "paid" for the same reference is acknowledged and writes nothing. The webhook layer has **no event-dedupe table** today, so idempotency is the settler's own (attempt status plus the ledger's `gatewayPaymentExists` check). A visitor who pays twice on two attempts: the second paid attempt is recorded, flagged `duplicate_payment` on the submission, and surfaced for a manual refund (no auto refund). A resubmission with the same idempotency key returns the existing attempt's link (re-minting if expired).

### 10.6 Failed, expired, refunded

The webhook handles only "paid" today; there is **no failed or refund path**. v1.0: an attempt stays `pending` until paid or until a 48-hour worker sweep marks it `expired`; the admin sees "awaiting payment" with a "Resend payment link" action (email/WhatsApp to the contact) and "Mark as paid manually" (an audited staff action, `record.form-submissions.update`, for offline payments). **Refunds are ledger-only** in the repo (no gateway refund call), so v1.0 records a refund note against the payment and the invoice credit note; gateway refund calls and failed-payment webhooks are a Payments-domain follow-up (listed in section 18) and not promised by this app.

### 10.7 Invoice and receipt (phase 3b)

For a paid submission, optionally create a draft **invoice** and record the **payment** (`InvoicesService.createDraftIn/issueIn`, `PaymentsService.recordIn`) linked to the contact and deal, with its own idempotency key `FRM-<payment id>` (`ExternalOrderBillingService` is keyed to `wa_orders` and cannot be reused as is). Off by default; needs the Sales documents plan feature (and decision A of the menu spec may make that an app too: read it at build time, the Forms app must degrade to "no invoice" when sales documents are not owned).

## 11. The AI builder

### 11.1 Flow

1. Admin clicks **Describe it** (or "Ask AI to change this form" in the editor). Types or **speaks** a description in any language: "A registration form for my yoga retreat, collect name, phone, email, which dates, dietary needs, and take a 2000 INR deposit".
2. `POST /forms/ai/generate` -> the server returns a **`FormDefinition`** (section 5) plus short `notes` ("I bound Name and Phone to the Contact, created a deal in Retreats").
3. The UI shows a **review screen** (the form preview beside a change list); nothing is saved or published until the admin clicks **Use this form**. For a revision the screen shows a diff (added, removed, changed fields) with **Apply** and **Discard**. The AI never publishes and never enables payment by itself: payment blocks come back **proposed and disabled** with a note, because money must be a human decision.
4. The result opens in the normal builder, fully editable.

### 11.2 Prompt, schema and guardrails

- **Output = the form JSON schema.** The system prompt gives the schema (a compact rendering of the Zod definition), the closed list of field kinds, the **catalogue of the workspace's real CRM properties** (names, types, options, from `GET /forms/meta/properties`: so "company size" binds to an existing field or is created as an unbound field, never invented as a bind) and the theme token names. The model must answer with JSON only.
- **Validate, repair once.** A new helper `generateStructured(schema, messages)`: call `FlowAiPort` (JSON mode where the provider supports it), `tryParseJson` / `extractionSuffix` from `ai-rules.ts`, validate with the Zod schema; on failure one repair call that includes the validation errors; second failure -> `422 FORMS_AI_INVALID_OUTPUT` and no charge beyond the tokens used. No streaming of partial JSON to the user in v1.0 (a progress state "Building your form..." with a skeleton; the streamed-fields effect is phase 5).
- **Guardrails.** The user's text is data inside a delimited block, never instructions (prompt injection through a pasted description cannot change the schema: the output is validated anyway and never executed); max 4,000 characters in, max output tokens capped; the model is told it cannot create files, scripts, HTML, CSS, webhooks or URLs (the schema has no place for them, and a post-validation pass strips any `redirectUrl` and image URL it invented); a content filter refuses collection of sensitive categories the product does not permit (card numbers, passwords, government ids, health details) by turning such a field into a `Heading` warning rather than a field. Revisions send the current definition and ask for the **full** new definition (simpler to validate than patches), and the server computes the diff for the UI.
- **Languages.** The prompt asks the model to write labels in the language of the description (or `locale`), and set `dir` for Arabic.

### 11.3 Keys, metering, limits, no key

Follow `AiCallService` (`flow-runtime-engine/runtime/nodes/ai/ai-call.service.ts`): `AiKeyResolver.resolve(orgId, provider)` -> `{ key, source: 'workspace' | 'admin' | 'none', model }`; `AiTokenMeter.guard` **only when the source is the platform's key** (the existing convention: `ai_token_limit_monthly` is enforced for admin keys only), cap the max tokens, call, `AiTokenMeter.record`. On top, the new plan limit `ai_form_generations_monthly` counts **generations** (one per accepted request, including its repair retry) in `web_form_usage_monthly`, so a customer cannot burn the platform's tokens with the cheap forms feature; reaching it is `422 PLAN_LIMIT_REACHED`. **Do not copy** the chatbot widget's AI, which uses environment keys and is unmetered.
**No key** (source `none`): `422 FORMS_AI_NO_KEY` (mirrors the flow builder's `FLB_AI_NO_KEY` pattern) and the UI **falls back** to the template gallery and a "Start from a template" card, with "Connect an AI key in Settings > AI" for admins who may. The builder is fully usable without AI.

### 11.4 Voice

Works in Chrome, Edge and Safari; the mic button is **hidden** where unsupported, with the typed box always present                                              | `MediaRecorder` (webm/opus), 60-second cap, sent to `POST /forms/ai/transcribe`                                                                 |
| Transcribe          | In the browser (the browser vendor's service)                                                                                                                                                                                                                                                                               | Server: Deepgram nova-2 via the admin or workspace key (`AiKeyResolver`), audio **not stored**, deleted after the response; transcript returned |
| Review              | The transcript lands in the text box; the admin edits it, then presses Generate (never auto-submits speech to the model)                                                                                                                                                                                                    | same                                                                                                                                            |

(v1.0 transmits **text only** to us); phase 2 notice says audio goes to our transcription provider and is deleted at once; microphone permission is the browser's own prompt; no recording is ever kept | Add the provider to the privacy page and the sub-processor list before enabling                                                                 |

### 12.2 Plan feature

`packages/contracts/src/plans-subscriptions-trials/catalogue.ts`: add `{ key: 'form_builder', group: ..., default: false }` to `PLAN_FEATURE_DEFS`, the label to `PLAN_FEATURE_LABELS` (the typed `Record` forces it), the key to `PLAN_CHIP_ORDER`. Default **off** is a hard rule for a granting listing (a default-on feature is rejected at publish: `409 MKT_VERSION_STATE`). Do **not** reuse `forms_and_links` (on by default, WaDesk's) or `chatbot_widgets`. A second flag, `form_payments`, is **not** added: payment collection is a form-level setting of the app, with an on/off plan switch only if the owner wants payments upsold separately (D2); if yes, add it as a limit-style toggle (a `0/1` limit key `form_payments`), because a second **feature** a plan would have to grant clashes with `grants_plan_features` simplicity.

### 12.3 Limits (the owner asked for forms, submissions_monthly, ai_form_generations_monthly, payment toggle)

Add to `PLAN_LIMIT_DEFS`: `forms` (max active forms, 0 = unlimited), `form_submissions_monthly`, `ai_form_generations_monthly`, and (D2) `form_payments` (0 = off, 1 = on). Defaults of the app's limits for an app grant are the operator's call (D1): suggested start **10 forms, 500 submissions per month, 50 AI generations per month**, all editable per plan and per workspace override.

### 12.4 Permissions

`record.forms.read|create|update|delete`, `record.form-submissions.read|update|delete|export`, `forms.settings.manage`, registered with the `rbac-permission` skill (`supports_scope` for the `record.*` keys, so a user can see only forms they own), tagged `UPDATE permission_defs SET plan_feature = 'form_builder' WHERE key LIKE 'record.form%' OR key = 'forms.settings.manage'`. Role defaults: Owner and Admin all; Manager read/create/update + submissions read/export; Agent submissions read only. Marketplace keys `market.apps.read|install|manage` already exist.

### 12.5 Menu, route gate, Settings tiles

`apps/web/src/features/forms-builder/nav.ts`: group Marketing or Campaigns (D7 recommends **Campaigns**, entry "Forms"), `gates: { permission: 'record.forms.read', app: 'form_builder' }`; the app gate removes (not locks) the entry and `AppGate` closes `/forms` and any depth with "Forms isn't part of your workspace" and a Marketplace link. Settings tiles under Settings > Integrations ("Forms defaults": CAPTCHA, retention, notification defaults) each carry `app: 'form_builder'`. The public `/f/*` pages are **outside** the app shell and not subject to the menu gate: their gate is server-side (`web_form_lookup` returns nothing when the workspace lacks the entitlement).

### 12.6 Entitlement lifecycle

Subscribing AND installing the app make the entitlement resolver (`PlanEntitlementService.forOrg`) include `form_builder` (owner decision 2026-10-08: a subscription alone only lets the workspace install; not installed, paused or uninstalled means menu entry gone, `/forms` closed, routes `422 PLAN_FEATURE_LOCKED` with `reason: app_not_installed`, Roles editor keys locked with the `app` badge): the menu appears, the routes open. **When the subscription lapses** the admin routes lock at once (`PLAN_FEATURE_LOCKED`) and the **public forms stop** (404 / "closed"), but **data is kept** (forms, submissions) so a renewal restores everything; a banner on the app page says so. No data is deleted on lapse. Uninstall with "delete data" is the Marketplace's BL-066 consumer: Forms registers a deleter that removes forms, versions, submissions and files, and the UI states plainly what is lost.

### 12.7 Dev setup and help

`seed:forms` (pattern of `seed:appointments`, after PR #89 lands): sets the price (default 499 INR monthly), publishes the listing, enables the add-on on every active plan through `plan_visible_addons`, comps a named workspace; refuses `NODE_ENV=production` and non-local databases; idempotent. Update `docs/runbooks/dev-seed-appointments-app.md` into a generic runbook or add `dev-seed-forms-app.md`. **Help guides** (the repo rule): one per screen in `apps/web/src/features/forms-builder/help/*.md` (forms list, builder, design, share and embed, submissions, analytics, payments, AI builder, settings), keywords on one line, gated like the screen so they show only to an owning workspace; coverage test fails without them; `help-center/pending.json` entries only as a temporary owned placeholder. API doc `docs/api/forms-builder.md` and wiring `docs/wadesk-port/wiring/forms-builder.md` (marked "not a WaDesk feature"), plus `product-extensions.md` rows.

### 12.8 Pricing (a recommendation; the owner decides)

Recommendation: **one paid add-on, per month, with generous limits**, no per-submission pricing in v1.0 (BL-075 usage-based pricing for apps does not exist). Anchor: Appointments is seeded at 499 INR/month on the dev script; Forms is a bigger value (lead capture + payments + AI) so **799 INR/month (about 9.99 USD)**, 7-day trial **only if** the owner enables trials for apps (`trial_days` exists on the listing; AI cost is the risk, so trial AI generations are capped at 10). Payment collection included (we do not take a cut; the customer's own gateway fees apply). Annual billing waits for BL-072.

## 14. Security checklist

| Area                   | Control                                                                                                                                                                                                                                                                                                                                                                 |
| ---------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Tenant isolation       | RLS forced on all tables; anonymous access only through `web_form_lookup` (`SECURITY DEFINER`, returns only what the public needs); integration test proves tenant A's key cannot read B's submissions                                                                                                                                                                  |
| Enumeration            | `public_key` 22 random chars; one 404 for unknown, archived, plan-locked; submit never reveals contact existence                                                                                                                                                                                                                                                        |
| Rate limiting          | per IP, per form, per email/phone, per visit; Redis fixed windows; limits returned as 429 `RATE_LIMITED` with `retryAfterSeconds`                                                                                                                                                                                                                                       |
| Spam                   | honeypot, minimum fill time, link/keyword heuristics, optional CAPTCHA (the existing provider options and `CaptchaService`), disposable-email list (warn, not block), per-form "spam" status and an admin "not spam" action                                                                                                                                             |
| CSRF / CORS            | no cookies on the public API (nothing to forge); CORS echo only for matched origins; same-origin relay on the web side; the admin API keeps its bearer-token model                                                                                                                                                                                                      |
| Clickjacking vs embed  | `frame-ancestors` per form from `allowed_origins`; hosted page keeps `'none'`; platform `FRAMEABLE` and `next.config.ts` extended only for `/f/*` and `/form-embed/*`                                                                                                                                                                                                   |
| XSS                    | output is rendered by React with escaping; rich text (intro, thank-you) passes `html-sanitizer.service.ts` on save **and** at render; no custom CSS or HTML in v1.0 (tokens validated); submission values are escaped in the staff UI, CSV export prefixes `=`, `+`, `-`, `@` cells with `'` (formula injection); redirect URLs `https:` only, no `javascript:`/`data:` |
| SSRF                   | outbound webhook goes through `guarded-http.ts` (no private ranges, no redirects to private ranges, timeouts, size caps)                                                                                                                                                                                                                                                |
| Payments               | amount computed server-side from the frozen version; paid only from a verified webhook; settler idempotent; no card data touches us (hosted link)                                                                                                                                                                                                                       |
| Files                  | none in v1.0; phase 4 rules in 9.6                                                                                                                                                                                                                                                                                                                                      |
| PII                    | raw IP never stored (salted hash), `answers` purged by retention, audit row whenever staff opens answers, secrets and webhook URLs not in audit diffs, privacy-policy link and consent text stored per submission                                                                                                                                                       |
| Abuse of our resources | caps on form size, submissions per month, AI generations per month; AI prompts length-capped; the AI output is data, never executed                                                                                                                                                                                                                                     |
| Email abuse            | submitter confirmation emails (phase 2) only to the address typed, at most 1 per submission, rate limited per address, and only when the form owner ticked it; the sender is the workspace's, never an open relay                                                                                                                                                       |
| Brand abuse            | forms show a small "Powered by" line unless the plan removes it (D8)                                                                                                                                                                                                                                                                                                    |
