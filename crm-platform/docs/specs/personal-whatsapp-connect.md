## 0. How to read this, and the evidence behind it

Everything marked **verified** was read in this working tree (branch `lakshya/whatsapp/unofficial-per-workspace`) or in `reference/app` (read-only). Marked **inferred** means reasoned from code, not run. Nothing here was run against a real WhatsApp account, the Reference reference was **not** running (no screen was compared live: screen text comes from the Blade view, its JS, the routes file and the inventory, which cites the same files), and no test was executed.

Two facts about the tree shape the plan:

- The per-workspace allow-list (`unofficial_whatsapp_workspaces`, `UnofficialWhatsappSwitch.isEnabledFor`, the operator panel, the `unofficial_whatsapp` entitlement key) is **uncommitted work of another agent in this same working tree**. This spec relies on its documented behaviour (the runbook) and on the files as they are now. The same uncommitted work already edits `runtime/device-runtime.service.ts` and `runtime/device-control.service.ts`, which phase 1 also needs to change: **sequence phase 1 after that branch merges**, or the two will conflict.
- WADEV has no wiring map (`docs/threadwise-port/wiring/` has `node-bridge-runtime.md` only) although PORTING_RULES section 7 requires one before port work. Writing `wiring/whatsapp-devices-baileys.md` is the first task of phase 1.

## 1. Problem

The owner decided (2026-10-05, 2026-10-06) that the official WhatsApp route is the supported one and the unofficial engine (personal numbers over Baileys, channel kind `whatsapp_qr`) is off unless a platform super admin allows a workspace. Now some small businesses ask to try it. Today an allowed workspace still cannot do anything with it: the **runtime is built** (sockets, leases, QR and pairing-code production, status, restore, sending, inbound, groups) but there is **no way for a person to reach it**:

- no API to add, list, rename, delete a device, or to start a pairing and read the QR;
- no web screen or menu entry (the web has dead links to `/devices`: `apps/web/src/features/flow-builder-editor/builder/inspector/forms-core/helpers.ts` lines 161 to 242);
- the only HTTP surface on `devices` is the read-only public API `GET /v1/devices` (`developer-rest-api-v1/resources/messaging/devices.controller.ts`);
- the three runtime commands that pair and unlink (`DeviceControlService.requestQr`, `requestPairingCode`, `terminate`) have **no caller** in `apps/api/src` (grep);
- nothing records that the user understood the ban risk (plan-inbox-chat decision 1 asked for "the ban warning shown at connect"; `parity/node-bridge-runtime.md` line 138 says it is not built).

## 2. Goals and non-goals

### Goals

1. In an enabled workspace, a member with the right permission connects a number by QR or pairing code in a wizard, sees its status, and can rename, disconnect and delete it, without an operator.
2. The ban risk is shown in plain words and **acknowledged and recorded** (who, when, which text version) before a device exists and before each pairing.
3. The number then works everywhere the engine already works: inbox, broadcasts, campaigns, scheduled messages, flows, warmer, WooCommerce "send from". Nothing in those consumers changes.
4. The QR and the pairing code reach only members of the device's own workspace who may pair, and are never logged or kept in the database.
5. Smallest slice first: a pilot workspace can connect and chat in phase 1.
6. Parity with WADEV where it is right; each deliberate difference is recorded as `intended` (PORTING_RULES 2.5).

### Non-goals

| Not in this spec                                                                                     | Why                                                                                                                                   |
| ---------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| Legal advice or a legal opinion on the wording or on WhatsApp's terms                                | The spec designs the guard (what is shown, recorded, enforced). Counsel reviews the text (D1).                                        |
| Making the unofficial engine safe from bans                                                          | It cannot be. The product reduces risk (warm-up, pacing, optional proxy) and tells the truth about the rest.                          |
| Turning the engine on for everyone, or any change to the allow-list design                           | Done and documented in the runbook; this spec only consumes `isEnabledFor`.                                                           |

### 3.1 Access, menu, limit

- Every `devices` route needs workspace role `admin` or above; lower roles are redirected to the team inbox. The six staff permission keys `devices.view|create|edit|delete|pair|disconnect` are seeded but **checked nowhere** (TW-WADEV-044, dead code). - The hub is "Omni channels" at `/devices`: Baileys numbers in a table with status tabs (All, Connected, Disconnected, plus Needs re-pair and Failed when non-empty), search (name or number, 220 ms debounce), KPI cards (channels live, accounts, routed 24h, health %), a "Check status" button, and a footer "Plan limit: used / limit numbers". Two silent loops run while it is open: a 15 s list refresh and a 10 s status check. Three static help cards (what is a device, keep it online, when to re-pair). Empty state: "No devices match the current filters. Try clearing filters or pair a new device."
- **Plan limit** (TW-WADEV-004): `packages.device_limit` (default 1; null, 0 or negative = unlimited, per-workspace override wins) caps **devices plus WABA and Twilio numbers together**. Checked as `used >= limit` before creating row N+1, **without a lock**, so two parallel adds can both pass (the inventory flags it). Refusal text: "You've reached your plan's limit of N devices. Upgrade your plan to add more, or delete an existing one to free up space."; the browser shows a toast "Your plan allows N WhatsApp number(s). Remove one or upgrade to add another." and blocks the modal. Platform admins bypass.

### 3.3 Status values, timeouts, reconnect

- **Row statuses** (`Device::STATUSES`): `connected`, `disconnected`, `needs_pair`, `failed`. The bridge reports free text; Laravel buckets it: connected only for exactly ready, connected, paired or open; disconnected when it names a logout, failed connection or pairing, or mismatch; **anything else is needs_pair** (so "Reconnecting" is "needs pairing" in the pill).
- **Bridge labels**: Connecting, Syncing data, Reconnecting, Qr generated, Code generated, Ready, Logged Out, Mismatch, Disconnected, "Pair failed: <reason>" (cut to 32 characters), "Pairing failed: <reason>".
- **QR**: the browser renders the QR string to an image (the `qrcode` library, client side, no image service). Baileys rotates it about every 20 s; events closer than 5 s are ignored; no scan within 90 s of the **first** QR aborts the pairing, deletes the session and reports "Pair failed: QR timeout"; the first credentials update after a scan cancels that timer (the 515 restart after a scan is normal).
- **Mismatch guard**: on open the linked number must equal the number typed when the device was added, else logout, wipe, "Mismatch".
- **Close handling**: first pairing that never opened and is not 515 or 500: stop, wipe, "Pair failed: <reason>". After having connected: 401 or 403 means logged out (stop, wipe, "Logged Out"); 500 bad session wipes and retries; **every other close retries for ever** with delay `min(base x min(1.5^retries, 10) + jitter, 30 s)` (base 2 s for 515, 4 s for 500 and 428, 6 s for 408 and 440, else 3 s). "Couldn't link" is the 4-linked-devices limit.
- **Heartbeat**: the bridge posts live numbers every 30 s; a connected device unheard of for 90 s becomes disconnected. Optional idle logout by a security policy (`device_logout_on_inactive_days`).
- **Restore at boot**: session folders with fewer than 3 files are not restored (reported Disconnected); healthy ones reconnect, 2 s apart. Shutdown keeps sessions.
- **Not in Reference**: no risk acknowledgement in the connect modal (the Blade view has no ban text beyond a hint that a banned device should not stall the queue; the ban guidance is in the documentation page `faqs/whatsapp-bans.html`, which says the unofficial channel "is not an approved automation method", that a number "can be temporarily or permanently banned at any time, with no appeal guarantee", and to treat such a number as expendable). No per-device rate limit on starting a pairing beyond the bridge's 60 s lock. No ownership proof of the number.

### 4.2 Answer to "can the runtime emit QR and pairing codes and accept commands today?"

**Yes.** The worker can open a socket for a device, produce the QR (rotating) and the 8-character code, report progress, finish on scan, restore after a restart, unlink on request and send and receive. All of it is covered by a fake-socket test, **none of it by a real WhatsApp session**. What does not exist is everything in front of it: device CRUD, the pairing endpoints that call `requestQr`, `requestPairingCode`, `terminate` and `status`, the consent, the permission keys, the screens, notifications, and a richer state than `connected | disconnected | needs_pair`.

## 6. Risk acknowledgement and honest copy (the guard)

This is the part the owner asked for. It designs **what is shown, recorded and enforced**; it is not legal advice, and the wording below is a **draft for counsel** (D1). The facts it states come from Reference's own ban guidance and from what the runtime does.

### 6.1 What the user must accept

A wizard step "Before you connect" with a short list and three separate checkboxes (all required; the button stays disabled until all are ticked; no pre-ticked box, no "agree to all"):

1. "I understand this connects my WhatsApp the way WhatsApp Web does. It is not an approved way to automate WhatsApp. WhatsApp can restrict or permanently ban this number at any time, including for normal use, and we cannot prevent it or get the number back."
2. "I will only connect a number I own or have the owner's permission to connect, and I can afford to lose it. I will only message people who expect to hear from me."
3. "I understand that from the moment it is linked, every private chat on this number (not only business chats) appears in this workspace's shared inbox for members who can read the inbox, and messages I type on my phone are copied there too."

Plain-language notes shown next to the list (not checkboxes): the official WhatsApp Business route is the lower-risk one for serious or long-term use; warm up the number slowly and keep volumes low; a ban is not covered by support; disconnecting here removes the link and the saved session but does not delete the chats from the inbox.

### 6.2 What is recorded (table `device_risk_acknowledgements`, section 9)

Who (user id and a name snapshot), when, the **policy version** (a string such as `2026-10-07.1`), a SHA-256 of the canonical English text of that version, the locale it was shown in, the workspace, the device it first led to (nullable, kept as a uuid copy after the device is deleted), and the request's user agent and a hash of the IP (not the IP). Append-only: updates and deletes are blocked by a trigger (the row goes only with its workspace). The canonical text lives in `@crm/contracts` next to the version constant; the web translates it (en, ar) keyed by version.

## 7. How the QR and the code reach the browser

### 7.1 What was read

- The API already hosts a **Socket.IO** namespace `/realtime` with a one-time-ticket handshake from the web proxy, rooms `org`, `user`, `conv:*`, `inbox:*`, a Redis adapter for several pods, and a rule written in `docs/api/realtime.md`: "an event is a hint, the database is the truth"; events are signals (ids, versions) and the client refetches over REST where scope and RLS apply (`apps/api/src/realtime/realtime.gateway.ts`, `realtime-emitter.service.ts`, `packages/contracts/src/realtime/events.ts`). **verified**
- There is **no SSE** anywhere (no `@Sse`, no `text/event-stream`, no `EventSource` in `apps/api/src` or `apps/web/src`). **verified**
- The web has a realtime client (`apps/web/src/lib/realtime/`) and the dependency `qrcode.react` for drawing a QR on the client. **verified**
- Today the QR sits in Redis (`wa:qr:<org>:<dev>`) and `DeviceControlService.status()` reads it, which is already a "poll over REST" shape.

### 7.2 Recommendation

**Fetch the QR and the code over an authenticated REST read; use Socket.IO only for signals that carry no secret.**

| Piece                 | Mechanism                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| --------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Start                 | `POST /v2/devices/:id/pairing/qr` answers when the first QR exists (the existing command waits up to 35 s) with `{ attempt, state, qr, qrAgeMs, deadlineAt }`. A "no QR in time" is a clean error, not a hang.                                                                                                                                                                                                                                                 |
| Rotation and progress | `GET /v2/devices/:id/pairing` every 2 s while the wizard is open (the same rate as Reference), `Cache-Control: no-store`, `Vary: Authorization`. Returns `{ state, label, progress, qr, qrAgeMs, code, codeExpiresIn, deadlineAt }`. One Redis read plus one indexed row read: negligible next to Reference's 2 s per modal.                                                                                                                                   |
| Status signal         | After commit, the consumer of `device.status_changed` publishes a new event `device.status` `{ deviceId, state, rowVersion }` to the **`user` rooms of members who hold `wa.devices.read`** (`RealtimeEmitter.emitToUsers`). The screens refetch. This replaces Reference's 15 s and 10 s polling of the list; the wizard still polls the pairing read because it needs the rotating QR (phase 2, optional: the same event also tells the wizard to read now). |

Why not push the QR through Socket.IO or SSE:

1. **The QR is a credential for 20 to 90 s.** Whoever scans it with a phone gets a linked session. A broadcast envelope carries a sequence number through a per-room counter and passes through Redis pub/sub to every pod; a REST read touches Redis once and returns to one caller.
2. **The authorisation is already exactly the REST one**: the caller's workspace (RLS on `devices`) and the permission `wa.devices.pair`. A socket room would need a new room kind and a new access rule in `RoomAccessService` for the same answer.
3. **No new transport.** SSE would be a new thing to deploy, proxy and authenticate; the platform has none.
4. A missed packet costs nothing: the next poll shows the current QR.

Cost: a polling request every 2 s per open wizard (one at a time per person; wizard closes on success, cancel, or after the 90 s deadline). If this ever matters, move the **read** to a signal-then-fetch without changing the secret's path. **Recommended: phase 1 poll only; phase 2 add the signal.**

### 7.3 Security of the secret

| Rule                                                                              | How                                                                                                                                                                                                                                                      |
| --------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Only members of the device's own workspace who hold `wa.devices.pair` may read it | The route runs `@RequirePermission('wa.devices.pair')`, resolves the device through `DatabaseService.tx()` under RLS (another workspace's uuid is a 404), and refuses when `assertEnabledFor(org)` is false (422).                                       |
| Never in a log                                                                    | The API logger (`pino-http`) logs requests and not bodies; no response body is logged; the runtime never logs `qr` or `code` (only `err` strings). A test greps the log output of the e2e for the fake QR string. **inferred** (config read, not tested) |
| Never in Postgres, outbox, audit or realtime payloads                             | `device.status_changed` carries status, label, progress only (verified); the pairing read is not `@Idempotent` (a stored response would keep a QR); the acknowledgement stores a text hash, not a QR.                                                    |
| Held in Redis only as long as needed                                              | QR 45 s (R6, rotation is about 20 s), code 180 s (its validity), command answer deleted on read (`GETDEL`); both removed when the attempt ends (already done in `applyStatus`).                                                                          |
| Not cacheable                                                                     | `Cache-Control: no-store` and the Next proxy must not cache `/api/v2/devices/*/pairing` (check `apps/web` proxy; **not verified**).                                                                                                                      |
| One pairing attempt at a time per device, from one person                         | Existing `wa:init` lock (60 s) plus the attempt record (section 8.2) keyed to the starter; a second person's start returns 409 with who started it and when.                                                                                             |

## 8. The state machine

### 8.1 Two fields, not one

Keep `devices.status` (`connected | disconnected | needs_pair`) exactly as it is: the sender resolver, dashboards, the operator counts, the warmer and the public API read it. Add **`connection_state`** (a closed set with a CHECK) plus `state_reason` and `state_changed_at`, written in the **same UPDATE** as `status` by the one writer, `applyStatus`.

| `connection_state`      | Meaning                                                                                                                                                                                 | `status` it carries | Shown as                                 |
| ----------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------- | ---------------------------------------- |
| `created`               | Row exists, never paired.                                                                                                                                                               | `disconnected`      | "Not linked yet" + Connect button        |
| `awaiting_qr`           | A QR is on screen and has not been scanned.                                                                                                                                             | `needs_pair`        | "Waiting for scan"                       |
| `awaiting_pairing_code` | A code is shown and has not been entered.                                                                                                                                               | `needs_pair`        | "Waiting for code"                       |
| `connecting`            | Scanned or restoring: Connecting, Syncing data, Reconnecting.                                                                                                                           | `needs_pair`        | "Connecting" (never "re-pair")           |
| `connected`             | Socket open, linked number matches.                                                                                                                                                     | `connected`         | "Connected" (green)                      |
| `disconnected`          | Closed by us (user disconnect, worker silent 90 s, restore skipped).                                                                                                                    | `disconnected`      | "Disconnected" + Reconnect               |
| `logged_out`            | WhatsApp ended the link (reason `unlinked_on_phone`, `forbidden`).                                                                                                                      | `disconnected`      | "Link ended by WhatsApp" + how to relink |
| `error`                 | A pairing or connection failed (reason: `qr_timeout`, `pair_failed`, `code_failed`, `mismatch`, `proxy_unreachable`, `session_conflict`, `device_limit_reached`, `worker_unavailable`). | `disconnected`      | The reason in words + Try again          |

`banned` is **not** a state: the runtime cannot tell a ban from an unlink (R8). `logged_out` with reason `forbidden` shows "WhatsApp refused the connection. This can mean the number was restricted." and nothing stronger.

### 8.2 Transitions and who drives them

| From                                             | To                               | Driver               | Trigger                                                                                 |
| ------------------------------------------------ | -------------------------------- | -------------------- | --------------------------------------------------------------------------------------- |
| (none)                                           | `created`                        | **API**              | `POST /v2/devices` (consent + limit + duplicate in one transaction)                     |
| `created`, `disconnected`, `logged_out`, `error` | `awaiting_qr`                    | runtime              | API start QR, runtime reports `qr`                                                      |
| same                                             | `awaiting_pairing_code`          | runtime              | API start code, runtime reports `code`                                                  |
| `awaiting_*`                                     | `connecting`                     | runtime              | creds update after the scan, then `connecting` or `syncing` (the 515 restart is normal) |
| `connecting`                                     | `connected`                      | runtime              | `open` and the linked number equals the device's number                                 |
| `awaiting_*`                                     | `error` (`qr_timeout`)           | runtime              | no scan 90 s after the first QR, or the code expired                                    |
| `awaiting_*`, `connecting`                       | `error` (`mismatch`)             | runtime              | linked number differs; the socket is logged out and the session wiped                   |
| `connected`                                      | `connecting`                     | runtime              | any close that is not 401 or 403: reconnect with backoff, indefinitely                  |
| `connected`, `connecting`                        | `logged_out`                     | runtime              | close 401 or 403 (session wiped)                                                        |
| `connected`, `connecting`                        | `disconnected` (`worker_silent`) | runtime sweep        | `last_seen_at` older than 90 s (`flipStale`)                                            |
| any live state                                   | `disconnected` (`user`)          | **API** then runtime | `POST .../disconnect`: terminate command, real logout, session wiped                    |
| `connecting`                                     | `error` (`proxy_unreachable`)    | runtime              | 3 failed starts through an unreachable proxy (R4)                                       |
| `connecting`                                     | `error` (`session_conflict`)     | runtime              | 5 closes with 440 in 10 minutes (R5)                                                    |
| any                                              | (row removed)                    | **API**              | `DELETE .../:id` after a confirmed terminate                                            |

The API never writes a state other than `created`; the browser can never assert "connected" (Reference's "Mark connected" is deliberately not ported, section 10).

A pairing may start only from `created`, `disconnected` **with fewer than 3 saved session rows**, `logged_out`, `error`, or from any other state with `relink: true` (R1). From `connected` the button is "Disconnect", then "Connect again".

### 8.3 Copy per reason (honest, no claims we cannot back)

`unlinked_on_phone` and `forbidden` both read "WhatsApp ended the link to this number. This happens when the device is removed in WhatsApp > Linked devices, and also when WhatsApp restricts a number. Your chats here are kept. You can link it again." `qr_timeout`: "The code was not scanned in time." `mismatch`: "The phone that scanned is not the number you entered. Check the number and try again." `device_limit_reached`: "WhatsApp allows 4 linked devices. Remove one in WhatsApp > Linked devices and try again."

### 8.4 Why the number is typed first

The runtime's mismatch guard (`isMismatch`, `close-policy.ts`) compares the scanning phone with the typed number, and the pairing code is requested **for** a number. Keeping the number first also protects the owner of a QR shown on a shared screen: someone else's phone scanning it ends in `mismatch`, not in a session for the wrong account. Reference works the same way. Parity kept.

## 11. Runtime changes needed (small, in NODE)

All in `node-bridge-runtime` and coordinated with the owner of the branch that is editing `device-runtime.service.ts` now:

1. `applyStatus` also writes `connection_state`, `state_reason`, `state_changed_at` in the same UPDATE and honours `activate_after_pairing` (R2, R3, R9).
2. Map runtime statuses to states (`qr` to `awaiting_qr`, `code` to `awaiting_pairing_code`, `connecting|syncing|reconnecting` to `connecting`, `open` to `connected`, `logged_out`, `pair_failed|code_failed|mismatch` to `error` with a reason, `disconnected`).

5. Proxy failure: report `error`/`proxy_unreachable` after 3 failures (R4); session conflict cap (R5).
6. Emit `device.status_changed` with `state` and `reason` (no secret). The consumer is part of phase 2.

## 16. Security

| Topic                                      | Design                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| ------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Who can pair                               | `wa.devices.pair`, Admin preset by default; the gate `assertEnabledFor`; one attempt at a time; audited with the user.                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| **Pairing a number the user does not own** | The product lets an admin type any number and ask for a code or QR, then hand it to someone. A pairing code entered on a victim's phone links **the victim's whole WhatsApp account** to our worker: it is a known social-engineering attack. Mitigations: the acknowledgement (item 2), the on-screen warning, rate limits (10.3), audit of every start with the starter, notification to all admins when a device is created, the operator allow-list (pilot clients are known to the operator), and the mismatch guard for QR scans. These reduce but do not remove the risk (D8). |
| Token handling between API and runtime     | There is no token on this path: the API and the worker talk over Redis pub/sub inside the platform. The old bridge token (`X-Node-Token`) only guards `GET /api/whatsapp-message-settings` (verified, `node-token.guard.ts`). Redis must not be exposed outside the private network (an existing requirement, restated in the operator runbook).                                                                                                                                                                                                                                      |
| Session material                           | Encrypted with `CryptoService` in `device_auth_state` (verified), under RLS. The probe runs from the worker.                                                                                                                                                                                               |
| Audit                                      | `device.created`, `device.risk_acknowledged`, `device.pairing_started` (method, relink), `device.connected`, `device.disconnected` (reason), `device.logged_out`, `device.renamed`, `device.deleted`, `device.proxy_saved`, through `AuditService.record(tx, ...)` in the same transaction as the change (the pattern in `whatsapp-cloud-api-waba/customer-profiles.service.ts`).
