# Storage quota, storage packs and archival (design only)

Status: **proposal, nothing built** (backlog BL-300). Written 2026-10-18 from a read-only investigation of `origin/main` (commit `d2e34babe`). Docs only: no code, no
migration, no behaviour change comes with this note. Every "today" statement below names the file it was read in.

Owner direction: charge for storage fairly while respecting privacy law. Three decisions are already made and are treated as fixed here:

| #   | Decision                                                                                                                                                                                                                                                                                                                                                           |
| --- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| D1  | A **storage quota** per workspace is included in the plan; more space is sold as an **add-on** (storage packs). Warnings at 80% and 100%. When full, **new** recordings and uploads are blocked with a clear message. **Nothing is silently deleted.**                                                                                                             |
| D2  | When a feature lapses (example: WhatsApp calling is no longer paid) the call list stays readable, recordings move to **cold storage** after about 30 days, an admin can **request a restore** (audited, optional fee), and the **privacy retention window** (default 90 days, 7 to 365) still applies: deletion at its end unless a **legal hold** says otherwise. |
| D3  | On **workspace cancellation**: an **export window** (30 days), then deletion. Holds win.                                                                                                                                                                                                                                                                           |

Related: [legal-hold.md](legal-hold.md) (branch `lakshya/next/legal-hold`, not on `main` yet; the guard, `is_subject_held` and `org_has_active_legal_hold` are defined there and only
referred to here), [privacy-and-data-governance.md](privacy-and-data-governance.md) (4.5 registry, 4.6 retention engine, BL-146 not built),
[../adr/0028-workspace-inactivity-lifecycle.md](../adr/0028-workspace-inactivity-lifecycle.md) (idle archive and erase, `storage_purge_queue`),
[persona-profiles.md](persona-profiles.md) (visibility versus entitlement), [call-logging.md](call-logging.md),

## 1. Goals and non-goals

| Goals                                                                                                                             | Non-goals                                                                                                              |
| --------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------- |
| One number per workspace: "storage used of storage allowed", the same in the meter, the banner, the 422 and the operator console. | Metering database rows (messages, contacts). Those have their own caps (contacts, messages, forms...).                 |
| Every path that writes a file asks one guard first, so no door is forgotten.                                                      | Changing per-file size limits (5 / 16 / 100 MB chat media, 50 MB recording, mail caps). The quota is an aggregate.     |
| Sell more space as a pack on the add-on mechanism that already exists (stackable, recurring, audited), no new billing engine.     | A new payment flow, proration engine or invoice type.                                                                  |
| Never lose data to a quota: block new writes, keep old ones, tell people early.                                                   | Deleting anything because a workspace is over quota, ever.                                                             |
| Cheaper cold tier for files nobody is paying to use, with a restore path that is audited and permissioned.                        | Hiding a retention or erasure duty behind the cold tier. Cold files obey retention, hold and erasure exactly like hot. |
| Retention, legal hold, erasure and cancellation stay consistent with the privacy registry and ADR-0028.                           | Duplicating the legal hold model (see [legal-hold.md](legal-hold.md)).                                                 |
| Rollout in observe mode first (meter and report, block nothing), enforce per workspace later.                                     | Per-user or per-team quotas (workspace level only in v1).                                                              |

## 3. What counts toward the quota

Rule of thumb: a file **a workspace's people or customers put there, that costs us storage and that the workspace controls**, counts. A file the platform needs to run the product, that is
small, capped by design and replaced in place, or that is a legal record, does not.

| Kind                                                                | Counts?              | Blocked at the limit?                          | Why                                                                                                                            |
| ------------------------------------------------------------------- | -------------------- | ---------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| Call recordings                                                     | Yes                  | Yes (before the call starts; see 6.3)          | The largest single file kind; the feature is paid.                                                                             |
| Inbox media sent by agents, widget visitor uploads, API uploads     | Yes                  | Yes                                            | Someone chose to store it.                                                                                                     |
| Inbox media received from customers (all channels)                  | Yes                  | **No**: grace allowance, then metadata only    | The workspace cannot refuse a customer's photo; see 6.2.                                                                       |
| Email attachments received                                          | Yes                  | **No**: grace allowance, then metadata only    | Same.                                                                                                                          |
| Email attachments staged for sending                                | Yes while staged     | Yes                                            | Agent action; freed by the expiry sweep.                                                                                       |
| Contact files (the object the row points to)                        | Yes, once per object | Yes, at the upload that stored the bytes       | Counted by object key, not by the client-supplied `file_size_bytes`, and never twice when a file is attached twice.            |
| Scheduled message media, broadcast / campaign media                 | Yes                  | Yes                                            | Agent action.                                                                                                                  |
| AI training files                                                   | Yes                  | Yes                                            | Agent action; today local disk only, counted from the day the object-store adapter lands.                                      |
| Team chat attachments (Postgres blob, 20 MB each)                   | Yes (`byte_size`)    | Yes                                            | Largest uncontrolled blob; the whole point of the quota is to cap it. Moving it to the object store is a separate step.        |
| Files restored from cold storage                                    | Yes, while restored  | The restore itself is refused without headroom | They are hot again for the availability window.                                                                                |
| Files in the **cold** tier                                          | **No** (shown apart) | n/a                                            | They are not being used; they obey retention and are bounded by it (8.5). Reported as "archived", never as free space to hide. |
| Order payment proof images                                          | No (system)          | Never                                          | Financial evidence tied to an order; 4 MB cap per order.                                                                       |
| Avatars, workspace logo and favicon, flow widget pictures           | No (system)          | Never                                          | One row per slot, replaced in place; blocking a logo upload would be absurd.                                                   |
| Generated exports (reports, message log, consent, audit, saved)     | No (system)          | Never                                          | Temporary (about 7 days), one at a time, and a data-subject or compliance duty. Listed under "temporary files" for sight.      |
| Privacy request export (`privacy_request_exports.file_zip`)         | No (system)          | Never                                          | A legal duty to deliver (GDPR Art. 15/20). Must work at 100% full.                                                             |
| CSV import source, event archive, message log archive, webhook logs | No (platform data)   | Never                                          | Platform operating data, not workspace files.                                                                                  |
| **Invoices and sales documents**                                    | **No, ever**         | Never                                          | See 3.1.                                                                                                                       |
| Database rows (messages, contacts, notes, audit)                    | No                   | n/a                                            | Metered by their own caps; a storage quota is for files.                                                                       |

### 3.1 Invoices: decision

Excluded, always. Reasoning: (a) today they are **not stored as files at all**: the PDF is rendered on demand from invoice rows (`invoice-pdf.service.ts`); (b) the rows are the workspace's tax
and accounting record, which the workspace may be legally obliged to keep (ADR-0028: the platform's own sales records are kept 8 years in `financial_records_archive`; a workspace's customer
invoices are the workspace's data); a quota that could block issuing an invoice, or a cold-tier or lapse flow that could make one unreadable, would turn a billing limit into a compliance
failure. If invoice PDFs are ever persisted, they stay out of the quota, out of lapse archival and out of cleanup suggestions, and only the tax-retention rule (not this spec) deletes them.

## 4. Metering design

### 4.1 Tables (tenant tables, forced RLS, composite `(org_id, id)` keys; written with the `add-migration` skill)

| Table                  | Purpose                                                                                                                                                                                                                                                                                                                                                                              |
| ---------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `storage_objects`      | One row per counted object: `key` (unique per org), `category`, `bytes`, `sha256` (when known), `state` (`pending`, `live`, `missing`), `tier` (`hot`, `cold`, `restored`), `owner_table` and `owner_id` (nullable until linked), `created_at`, `cold_at`, `restored_until`, `retain_until`. The registry the Settings screen, the archiver, the sweeps and the reconciliation read. |
| `storage_usage`        | Counters per `(org_id, category)`: `hot_bytes`, `cold_bytes`, `objects`. For the breakdown and reports.                                                                                                                                                                                                                                                                              |
| `storage_org_state`    | One row per workspace: `hot_bytes`, `reserved_bytes`, `grace_used_bytes`, `cap_bytes` (last computed, for display and sweeps), `level` (`ok`, `warn80`, `full`, `over`), `level_cycle`, `over_since`, `mode`. The row the atomic reservation updates.                                                                                                                                |
| `storage_reservations` | `uuid`, `bytes`, `category`, `expires_at` (15 minutes). A crash between "reserved" and "committed" cannot leak space for ever: a reaper returns expired reservations.                                                                                                                                                                                                                |

### 4.2 Write path (reserve, write, commit)

1. `StorageQuota.assertCanStore(orgId, bytes, kind)` computes the effective cap (plan + stacked packs + active grants, 5.3) and runs **one conditional UPDATE** on `storage_org_state`:
   `SET reserved_bytes = reserved_bytes + :n WHERE org_id = :org AND (:cap = 0 OR hot_bytes + reserved_bytes + :n <= :cap)`. Zero rows = refused. Because it is one atomic statement, two
   concurrent uploads cannot both squeeze under the limit; there is no read-then-write race and no table-wide lock. It returns a `StorageReservation`.
2. The caller writes the object to the store.
3. `reservation.commit({ key, sha256, owner }, tx?)` moves the bytes from `reserved` to `hot`, upserts the `storage_objects` row (`state = live`) and bumps `storage_usage`, in the caller's
   transaction when it has one (the owner row and the registry row commit together). On any failure the caller calls `release()`; the reaper covers a crash.
4. `ChatMediaStore.store*` and `MediaStorageService.put` do steps 1 to 3 themselves (a `pending` registry row is written by the store when it has no owner row yet, and linked by the
   caller's `commit`). **A `pending` row older than one hour with no owner is an orphan: the sweep deletes the object.** This also closes the existing leak documented in
   `media-fetch.service.ts` (a worker killed between storing the file and the UPDATE leaves one orphan object).

The cap is read per call from the entitlement services (no stale cache for the decision), and copied to `storage_org_state.cap_bytes` only for display and sweeps. An upload is a human-speed
event; one extra indexed read and one single-row UPDATE per file is far below the cost of the file itself. A very busy inbound workspace (tens of media per second) serialises on its own row only,
for a few milliseconds; if this ever shows in the profile, the row splits into N shards summed on read (kept out of v1).

### 4.3 Delete path

All removals already pass `ChatMediaStore.remove` / `MediaStorageService.remove` (retention sweeps, hand deletes, the purge worker). The decrement lives **there**: delete the registry row
`RETURNING bytes`, subtract from `hot_bytes` (or `cold_bytes`), idempotent because a second call finds no row. It is deliberately not in owner-table triggers: cascades and erasure queue their
keys and the purge worker is the one place the bytes actually go. A workspace erase drops its counters with the organization (`ON DELETE CASCADE`).

### 4.4 Reconciliation

| Job                           | Cadence                      | What it does                                                                                                                                                                                                                                                                                             | Cost                                                                                                                                                                                                                                                                                                             |
| ----------------------------- | ---------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Counter check                 | nightly, DB only             | Recomputes `storage_usage` and `hot_bytes` from `storage_objects`; fixes drift and logs it as a metric.                                                                                                                                                                                                  | One grouped scan per workspace.                                                                                                                                                                                                                                                                                  |
| Reservation reaper            | every 5 minutes              | Returns expired reservations.                                                                                                                                                                                                                                                                            | Trivial.                                                                                                                                                                                                                                                                                                         |
| Bucket verify                 | weekly per workspace, spread | Lists the workspace's prefixes (`chat/<org>/`, `marketing/<org>/`, `scheduled/<org>/`) and compares with the registry: **unregistered** objects are adopted as category `unknown` and queued for purge after 7 days if still unowned; **missing** objects are marked `missing`, decremented and alerted. | S3 list pages of 1,000 keys: 10 million objects = 10,000 requests, about a cent or two and some minutes, run as a background job with a page budget per run, **never on a request**. For very large buckets use the provider's inventory report (S3 Inventory) instead of listing. Local disk: a directory walk. |
| Orphan check (owner row gone) | weekly                       | Registry rows whose owner row no longer exists (for example after the lapsed-plan wipe, which keeps media files) are queued to `storage_purge_queue`.                                                                                                                                                    | One anti-join per owner table; the owner map is the `fileKeyColumns` catalogue ADR-0028 already uses.                                                                                                                                                                                                            |

### 4.5 Overage

Concurrent uploads cannot overshoot (4.2). Usage **can** exceed the cap only in four defined ways, all reported as level `over`/`full` and none deleting anything: (1) a downgrade, lapse or pack
expiry shrinks the cap; (2) the inbound grace allowance (6.2); (3) a recording that started while there was room (6.3); (4) kinds that are never blocked and not counted (section 3). In `over`
state: reads and playback work, deletes work and free space, every counted write is refused.

## 5. Plan limit and storage packs

### 5.1 The limit

A new core key `storage_gb` in `PLAN_LIMIT_DEFS` (group `workspace`): whole **GB**, `0 = unlimited`, the repo convention. 1 GB = 2^30 bytes, shown as "GB". Plan rows that lack the key read as
`0` (unlimited), so **adding the key changes nothing** until an operator sets values; that is also how the observe-then-enforce rollout works (mode flag in section 15). Platform-owned
workspaces stay unlimited. Bytes are the unit inside the system; GB only appears in the plan form, the pack and the screen.

### 5.2 Placeholder numbers (the owner sets the real ones; pricing is not decided here)

| Item                        | Placeholder                                                               | Note                                                                      |
| --------------------------- | ------------------------------------------------------------------------- | ------------------------------------------------------------------------- |
| Included in Free            | 1 GB                                                                      | Free has no packs (5.3), so it must be enough to try recording and media. |
| Included in paid plans      | 5 / 25 / 100 GB by tier                                                   | To be sized from the observe-mode data (15), not guessed.                 |
| Storage pack                | +10 GB, +50 GB, +250 GB, monthly recurring or one-time term, price `P`    | One catalogue row each (kind `addon`, `limits: { storage_gb: 10 }`).      |
| Sizing assumption to verify | a 10-minute call recording is roughly 5 to 10 MB (browser WebM, one file) | Measure in observe mode; the 50 MB per-file cap is not the typical size.  |

### 5.3 Effective cap and stacking

`cap = plan limit (or override) + sum of active packs + active operator grants`; `0` (unlimited plan) absorbs everything; a pack granting `-1` is unlimited. This is the existing
`mergeLimit` plus the grants of 11.2. Packs **stack** (each purchase is a row, `isStackable` is true for any pack with a limit), each with its own term; when one ends, only its delta leaves.
A pack can be bought only on an active paid plan (the existing rule, `eligible`); a free workspace upgrades its plan first. Settings > Storage shows the breakdown line:
"Plan 5 GB + 2 packs 20 GB + grant 1 GB (until 30 Nov) = 26 GB".

### 5.4 Proration, downgrade and lapse

| Event                                   | Behaviour                                                                                                                                                                                                             |
| --------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Buy a pack mid-period                   | Starts now, own term, **no proration** (as every boost today). Cap rises immediately: fulfilment refreshes `storage_org_state` in the same transaction and clears `full` / `over`.                                    |
| Recurring pack renewed / payment failed | Follows PR 525: renewed extends the term; `payment_failed` keeps the pack through `billing.grace_days`; ended removes its delta.                                                                                      |
| Pack ends or is cancelled               | Delta leaves at the term end. If usage now exceeds the cap the workspace is `over`: **no deletion**, new counted writes blocked, banner and mail. Cancelling a recurring pack says this up front.                     |
| Plan downgrade, or plan lapse to Free   | Cap becomes the target plan's. Same `over` behaviour. The plan-change screen warns before it applies: "You use 12 GB; Free allows 1 GB. You keep every file but cannot add new ones until you free space or upgrade." |
| Refund of a pack                        | Out of scope (no boost refund exists); the Marketplace refund path is untouched.                                                                                                                                      |

## 6. Enforcement

### 6.1 The one guard

`StorageQuota` (new domain module, bound into the media doors through a port, because `infra` may not import domain modules; the pattern is `media.ports.ts`, e.g. `MEDIA_QUOTA_GATE`):

| Method                                                   | Use                                                                                                                                                                                                                                                                                                |
| -------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `assertCanStore(orgId, bytes, kind): StorageReservation` | Every upload path, before the first byte is written. Throws `AppError(STORAGE_QUOTA_EXCEEDED, 422)` with `details` { `limit: 'storage_gb'`, `used`, `limitValue`, `requested`, `category`, `upgradeUrl` } (the `PLAN_LIMIT_REACHED` field names, so existing client handling degrades gracefully). |
| `reservation.commit(...)`, `reservation.release()`       | 4.2.                                                                                                                                                                                                                                                                                               |
| `StorageQuota.snapshot(orgId)`                           | Usage, cap, level, breakdown, for the screen, the banner, the usage panel and the plan-change warning.                                                                                                                                                                                             |
| `StorageQuota.canRestore(orgId, bytes)`                  | Headroom check for a restore (8.4).                                                                                                                                                                                                                                                                |

`kind` is a closed list (the categories of section 3); each kind carries its **origin** (`agent`, `customer`, `system`) and its policy (`block`, `grace_then_metadata_only`, `never`), kept in
one table in code so the behaviour of a kind is data. A new file feature that cannot name its kind does not compile into the guard.

### 6.2 Inbound media from customers (cannot be refused): decision

Store within a **grace allowance**, then **metadata only**:

| Rule                                      | Detail                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| ----------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Within the cap                            | Stored normally.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| Above the cap, inside the grace allowance | Stored, level `over`. Grace = `max(250 MB, 10% of the cap)` (placeholder), tracked in `grace_used_bytes`, released as space is freed. Protects a busy week from losing a customer's prescription photo while the admin reacts to the 100% mail.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| Beyond the grace                          | **Not stored.** The message and its metadata (name, type, size) are kept; the message shows the placeholder **"Media not stored: storage full"** and, where the provider still holds the file, a **Retry** that fetches it once space exists. WhatsApp reuses the existing `meta.mediaStatus` machine and the request kept on the row (a new terminal value `not_stored` with code `storage_full`, retry = the agent's existing Retry; the provider's retention of the media id bounds how long Retry works, to be confirmed per provider at build). Email reuses the existing `tooLarge` placeholder path with reason `storage_full`; the file is still in the mailbox and can be fetched again by its part id (`x-<partId>`) after space is freed. |
| What is never done                        | The conversation is never blocked, the message is never dropped, the customer is never told anything. Visitor uploads in the web chat widget are the exception: the visitor sees a friendly "File upload is unavailable right now" (the upload is theirs to retry later) and the agent's thread notes it.                                                                                                                                                                                                                                                                                                                                                                                                                                            |

### 6.3 Call recordings

The recording starts in the operator's browser and uploads when the call ends, so refusing at upload time would lose a recording that began legitimately. Therefore: (a) the existing
`recording-gate` (`GET /calls/:id/recording-gate`) also answers "storage full" **before** the call: recording does not start and the operator sees "This call will not be recorded: storage is
full"; (b) a recording that started while there was room is accepted at upload into the grace allowance (up to the 50 MB file cap); (c) only then is the upload refused with the standard
message.

## 8. Archival (the cold tier)

### 8.1 Mechanics: options and choice

| Option                                                 | How                                                                                                                                                                                                                                                           | For                                                                                                                                                                                                                                                                | Against                                                                                                                                                                                                                                                                                                        |
| ------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **A. Second bucket, app-driven (recommended default)** | A worker copies the object to a cold bucket (`S3_COLD_*`, an adapter beside `S3ArchiveStorage`), verifies size and ETag by reading back (the `RetentionWorker` pattern), flips `tier`, then deletes the hot copy. Restore copies it back to the **same key**. | Works on every provider already supported (S3, Wasabi, Bunny, Spaces, R2, MinIO) and on local disk (a `cold/` folder, dev only). Our state machine, legal hold and retention stay authoritative. Restore in minutes. The API process never holds cold credentials. | We own the move job; the cold bucket should be a cheaper class or provider chosen by the operator.                                                                                                                                                                                                             |
| B. S3 lifecycle rules to Infrequent Access / Glacier   | Tag objects, let the provider transition by age/tag.                                                                                                                                                                                                          | No move job.                                                                                                                                                                                                                                                       | AWS-specific; hand-signed requests would need tagging and `RestoreObject`; restore takes minutes to **hours** (Flexible/Deep); **minimum storage durations** (30 to 180 days) bill early deletion, and default retention (90 days) deletes inside them; the provider cannot see our legal hold or lapse state. |
| C. Both                                                | A for portability, B as an optional bucket-side class on the cold bucket.                                                                                                                                                                                     | Cheapest at scale on AWS.                                                                                                                                                                                                                                          | Later optimisation (phase S6), not v1.                                                                                                                                                                                                                                                                         |

Cold bucket rules: same region or jurisdiction as the hot bucket (data residency), server-side encryption, no public access, no object versioning (or noncurrent versions expire within 7
days, otherwise "deleted" is not deleted), separate credentials used only by the worker.

### 8.2 Object tier states

`hot` -> (archive job) -> `cold` -> (restore) -> `restored` (hot copy exists, cold copy kept) -> (window ends) -> `cold`. `deleted` ends the object from any state. A restored object costs
no second archive upload when its window ends: only the hot copy is deleted.

### 8.3 What moves to cold

| Trigger                                                                                                                                          | Scope (v1)                                      | When                                                              |
| ------------------------------------------------------------------------------------------------------------------------------------------------ | ----------------------------------------------- | ----------------------------------------------------------------- |
| A plan feature the category depends on has lapsed (`calling` for call recordings; resolved by `PlanEntitlementService` after the lapse fallback) | Call recordings only                            | `lapsed_at` + 30 days (ADR-0028-style reminders at day 0, 15, 25) |
| Workspace archived by ADR-0028 (idle) or closing (10.3)                                                                                          | All hot objects (optional, phase S6)            | at archive                                                        |
| Owner-initiated "Archive older than..." on Settings > Storage                                                                                    | Recordings and media the owner picks (phase S5) | on request                                                        |

Chat media tied to the inbox, which every plan has, **never** moves on lapse. The lapse flag is stored per `(org, category)` (`storage_category_state.lapsed_at`), set and cleared by a daily
sweep that asks the entitlement service; regaining the feature clears it and stops the clock (already-cold files stay cold until restored; 8.4 waives the fee).

### 8.4 Restore request flow

| State                             | Meaning                                                                                                                                                                                                          |
| --------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `requested`                       | An admin asked, with a **required reason** (10 to 300 characters) and a scope (one recording, all recordings of one call, or a list up to a cap of 200 objects / 5 GB per request). One open request per object. |
| `awaiting_payment`                | Only when the restore fee is on and above zero; the fee is debited or ordered before work starts (a failed restore refunds it). Skipped at fee 0.                                                                |
| `restoring`                       | `canRestore` passed (headroom for the bytes, otherwise `422 STORAGE_QUOTA_EXCEEDED` "Free up space or add a pack first"); the worker copies cold -> hot, verifies, flips tier to `restored`.                     |
| `available`                       | Playable for the **availability window** (default 7 days, 1 to 30). The request shows "Available until <date>".                                                                                                  |
| `expired`                         | Window over; hot copy deleted; object is `cold` again. A new request is needed.                                                                                                                                  |
| `failed` / `denied` / `cancelled` | Provider error (retried 3 times, then visible to the operator), a held-subject or permission refusal, or the requester cancelled before `restoring`.                                                             |

SLA: **target within 1 hour** on the second-bucket tier (typically minutes); stated to users as "usually within an hour, at most 24 hours". With option B or C the stated SLA follows the
storage class (hours). Cost note: a restore costs an egress/copy and a few days of hot storage; it is covered by the optional fee `restore_fee_per_gb_minor` (default **0** in v1, a platform
setting; the fee is charged through the workspace wallet or an order, decision O4) and by counting the restored bytes against the quota while they are hot.

**Permissions and audit** (new keys, seeded with the `rbac-permission` skill): `storage.restore.request` (system role admin by default); restoring an object under a legal hold also needs
`privacy.requests.manage` (the hold's own "authorised legal user" key). Every request, state change, fee and download writes an audit row (who, which object ids, reason, bytes, fee), and a
playback of a restored recording is audited as listening already is (`call-logs.service.ts`). Retention keeps running underneath: a restore never extends a recording's life (9.1).

### 8.5 Cold bytes and the quota

Cold bytes **do not count** toward the quota (they leave `hot_bytes` at the move) and are bounded by retention, which still deletes them at the end of the window. Gaming risk (park files in
cold by lapsing a feature) is bounded because the lapse path is the only automatic one, retention still applies, and a restore needs headroom. A cold-bytes ceiling per workspace is an
operator-visible report, not a block, in v1 (decision O5).

### 8.6 What the UI shows for archived items

| Surface                    | Archived item                                                                                                                                                                                           |
| -------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Call list                  | Unchanged: the row, duration, outcome, contact, consent evidence stay.                                                                                                                                  |
| Call detail                | The player is replaced by "Recording archived on <date>. It will be deleted on <retention date>." and a **Request restore** button (permission-gated; others see "Ask an administrator to restore it"). |
| After a request            | Status chip `Restore requested`, `Restoring`, `Available until <date>`, `Expired`, with the reason and requester.                                                                                       |
| After retention deleted it | "Recording deleted on <date> by the retention policy" (the existing deleted reason), no restore.                                                                                                        |
| Held subject               | Lock chip "On legal hold"; restore needs the legal key.                                                                                                                                                 |
| Settings > Storage         | An "Archived" section (counts, bytes, next deletion dates) and the request list.                                                                                                                        |

### 9.2 Legal hold (reference, not a copy)

[legal-hold.md](legal-hold.md) owns the model and the guard (`LegalHoldGuard`, `is_subject_held(org, subject_type, subject_id)`, `org_has_active_legal_hold(org)`, the database backstop).
This spec adds only the storage consequences: (a) every storage deletion path (retention sweep, owner cleanup, quota tools, cold expiry, purge worker for non-erasure reasons) calls the same
guard before deleting and counts `skippedHeld`; (b) a held object **may be archived** to cold (kept and locked, not destroyed) but never deleted, and restoring it needs the legal key;
(c) held objects keep counting toward the quota while hot; the cleanup suggestions never list them, and the delete button is replaced by a lock; (d) an operator **grace grant** (11.2) is
the remedy when held data fills a workspace; (e) `legal-hold-coverage.spec.ts` lists the storage deletion files too.

### 9.3 Erasure and the privacy registry

The registry already declares each table's object-key columns; a per-person erasure writes them to `privacy_erasure_files`, the worker copies them to `storage_purge_queue`, and a workspace erase queues them directly (ADR-0028). Required: `StoragePurgeService` removes a key from the hot **and** the cold
bucket and from the registry (so `cold_bytes` falls); `fileKeyColumns` discovery keeps working because keys do not change tier; the `ArchiveStorage` erase marker pattern is reused if the
cold bucket ever holds per-workspace bundles. A person's erasure outranks a restore: it cancels open restore requests for that person's objects. Backups are unchanged and still disclosed
(privacy spec G6: local 14 days, off-site up to 12 months).

## 13. Persona and plan interplay

| Topic                        | Rule                                                                                                                                                                                                                                                            |
| ---------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Quota applies to everyone    | Every workspace has a quota whatever its persona. **Hidden is not unlimited.**                                                                                                                                                                                  |
| Visibility                   | A persona ([persona-profiles.md](persona-profiles.md)) may hide the Settings > Storage tile, as it hides any module (`settings.storage` module id). It never hides the banner, the notification or the refusal message: those are safety messages, not modules. |
| Entitlement                  | The meter and screen are not plan-gated. **Buying** a pack needs an active paid plan (`eligible`), which persona never grants. A typed or bookmarked URL of a hidden Storage tile still opens when permission allows.                                           |
| Plan feature versus category | `calling` (plan feature) drives the lapse of call recordings; `storage_gb` (plan limit) drives the cap. They are different keys: losing calling archives recordings, losing space blocks new files.                                                             |
| Marketplace apps             | A paid app that stores files (for example a future documents app) declares its categories in the same closed list and calls the same guard; an app does not get its own quota.                                                                                  |

## 14. Security and privacy notes

| Topic                     | Note                                                                                                                                                                                                                                                                                 |
| ------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Tenant isolation          | All storage tables are tenant tables with forced RLS and `org_id` in every key; the platform views read through the privileged path with an audit row. No cross-tenant duplicate detection, ever (a side channel); duplicates are suggested only inside one workspace.               |
| Do not trust client sizes | Metering uses bytes counted by the server (`buffer.length`, the spool counter), never `file_size_bytes` from a client.                                                                                                                                                               |
| Recordings are sensitive  | Voice can be biometric data. Cold bucket: encrypted at rest, same jurisdiction, no public access, worker-only credentials, short-lived access only through the authenticated media route (existing rule: bytes never exposed as a public address). Restore and playback are audited. |
| No PII in keys or logs    | Keys stay `<area>/<org>/.../<random>`; logs carry org id, key id, bytes, never names or phone numbers. Restore reasons are PII-light by rule (the form says so, as the legal-hold note does).                                                                                        |
| Abuse                     | Restore requests are rate limited (per workspace per day, bytes per request cap); a refused upload at `full` is cheap (no bytes are read: the check runs before the body is spooled where the framework allows); the blocked-upload notification is limited to one per 24 hours.     |
| Deleted means deleted     | Cold bucket without versioning (or noncurrent expiry within 7 days); erasure reaches both tiers (9.3); backups remain disclosed.                                                                                                                                                     |
| Legal basis for charging  | Storage limitation (GDPR Art. 5(1)(e), DPDP s.8(7)) is served by the retention window; the quota is a commercial limit and never an excuse to delete earlier or to keep longer than the window. Counsel confirms wording of the notices (as the legal-hold spec says).               |

## 15. Migration and backfill without downtime

| Step | Action                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| ---- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1    | Deploy tables, guard and doors with `STORAGE_QUOTA_MODE=off` (default). No behaviour change; code is dormant.                                                                                                                                                                                                                                                                                                                                                                                                                                            |
| 2    | Switch to `observe`: new writes register in `storage_objects` and update counters; nothing is blocked; the operator fleet view fills.                                                                                                                                                                                                                                                                                                                                                                                                                    |
| 3    | **Backfill job** (idempotent upsert on `(org_id, key)`, batched per workspace, throttled, resumable, safe to run while writes continue): rows from `messages.media_key/media_size`, `scheduled_media`, `mail_outbound_attachments`, `team_chat_attachment_blobs.byte_size`, `contact_files`; recordings via one `HEAD` per object (no size column) or the `recording_stored` event size; other keys found by the `fileKeyColumns` catalogue. Then a **bucket verify** pass per workspace adopts unknown objects. Counters are rebuilt from the registry. |
| 4    | Two weeks of `observe`: read the distribution (median, p95, top workspaces, share of recordings), then the owner sets `storage_gb` on plans and the pack prices.                                                                                                                                                                                                                                                                                                                                                                                         |
| 5    | `enforce` per workspace (operator flag), starting with internal and platform-owned test workspaces. A workspace already over its cap on day one gets a notice and a **30-day over-quota notice period** before blocking starts (decision O7); never a deletion.                                                                                                                                                                                                                                                                                          |
| 6    | Then default `enforce` for new workspaces, and the rest in waves.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        |

| Concurrency (integration, real Postgres) | 50 parallel `assertCanStore` at the edge never exceed the cap; reservation reaper returns a crashed reservation; commit and release idempotent; delete decrement idempotent; counters equal the registry sum after a random mix.                                                                                                                                                                                                                             |
| Integration                              | Every door in 6.4 refuses at `full` with the code and `details`; inbound customer media goes through grace then placeholder, and Retry works after space is freed; recording gate and in-flight recording; RLS: workspace A cannot read B's registry or grants; a pack purchase raises the cap in the same transaction; a pack end puts the workspace `over` and deletes nothing; downgrade warning; backfill is idempotent and safe with concurrent writes. |
| Retention / hold / erasure               | Recording sweep deletes a `cold` and a `restored` object from both tiers and cancels restore requests; **a held subject's object survives every sweep, the cold expiry and the purge worker**; erasure removes the cold copy and the counters; workspace hold blocks the closing erase and freezes to cold; `legal-hold-coverage.spec.ts` lists the storage files.                                                                                           |

## 18. Risks

| #   | Risk                                                                                               | Mitigation                                                                                                                                 |
| --- | -------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------ |
| R1  | A writer bypasses the guard and usage drifts.                                                      | Two doors, coverage test, nightly counter check, weekly bucket verify.                                                                     |
| R2  | Blocking hurts a business at a bad moment (a recording lost, a customer photo dropped).            | Inbound grace + metadata only, recording gate before the call, early warnings, `observe` first, over-quota notice period, operator grants. |
| R3  | A data-loss bug in the cold move.                                                                  | Verify-by-read-back before delete (the pattern `RetentionWorker` already uses), feature flag, dry run, staged rollout.                     |
| R4  | Cold files outlive retention or ignore a hold or erasure.                                          | Selection independent of tier; the same guard; erasure reaches both buckets; tests in 17.                                                  |
| R5  | Orphan objects (lapsed-plan wipe keeps media files; kill between store and row).                   | `pending` sweep, owner-gone sweep, weekly bucket verify, adopt-or-purge rule.                                                              |
| R6  | Free-tier abuse (storage as a free file host).                                                     | Free cap small, per-file caps unchanged, public links not offered, existing upload policy (extension + signature).                         |
| R7  | Over-quota surprise after a pack ends or a plan lapses.                                            | Up-front copy at cancel and downgrade, mail at `over`, nothing deleted, grants for hardship.                                               |
| R8  | Legal exposure from charging for data the customer is obliged to keep.                             | Invoices and legal-duty files excluded (3.1); held data never auto-deleted; counsel reviews the notices.                                   |
| R9  | The platform's own cost exceeds revenue (cold tail after lapse, restores, held closed workspaces). | Operator fleet cost view, restore fee knob, cold bounded by retention, held-workspace list with review dates.                              |
