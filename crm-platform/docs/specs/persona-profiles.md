# Persona profiles: one product for many kinds of business (design only)

Status: **phases P0 and P1 built (the visibility runtime), P2 to P6 not built** (backlog BL-280; see section 15). Written 2026-10-18 from a read-only investigation of `origin/main`.
The design below is unchanged by P0 and P1; P0 changes no behaviour and P1 only changes it for a persona other than `generic`, which no workspace has yet. Owner direction: the product stays ONE generic system; a **persona** (doctor, dentist, sales
team, real estate, retail store, salon, education...) decides which words, which modules and which starter setup a workspace sees. It is an
owner-requested extension in the sense of [product-extensions.md](../threadwise-port/parity/product-extensions.md): the default persona
(`generic`) shows exactly what every workspace sees today, so Hard Rule 1 of the porting rules (no feature lost or changed) holds for every
existing customer. Add a row to that file when phase 1 ships.

Related: [contact-owner-leave-and-delegation.md](contact-owner-leave-and-delegation.md) (leave-aware availability builds on this),
[help-center.md](help-center.md), [marketplace-mini-apps-and-integrations.md](marketplace-mini-apps-and-integrations.md),
[../api/marketplace.md](../api/marketplace.md). The Meetings/Appointments plan (reminders and follow-ups per booking type) was not on `main`
when this was written; it builds on this spec and is referred to below as "the Meetings/Appointments plan".

## 1. Goals and non-goals

| Goals                                                                                                                                                      | Non-goals                                                                                                                  |
| ---------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------- |
| A persona maps four things: vocabulary, visible modules, starter presets, onboarding checklist.                                                            | Not a permission system. Roles and record scopes (`own`/`team`/`all`) are untouched; a hidden module is not a secured one. |
| Personas live in the platform admin (operator console): list, editor with live preview, versions, publish, audit.                                          | Not plan or pricing. Entitlement (plan features, add-ons, apps, channels) stays a separate gate and is never granted here. |
| The workspace picks a persona and a team size during onboarding (3 short, skippable screens, mobile friendly) and can change it later without losing data. | Not a fork of the product per niche, no per-persona code paths in services, no per-persona database schema.                |
| Hidden is not locked: a "Show more modules" switch in Settings reveals everything the plan allows.                                                         | Not full re-wording of the product: phase 1 covers key nouns (menu, page titles, tabs, main buttons), not 1,400 sentences. |
| Per-workspace overrides (operator, workspace admin) on top of the persona for the 10% that deviate; effective view always explainable item by item.        | No custom persona authored by a workspace (workspace overrides cover it). No per-user persona.                             |
| Solo mode: a one-seat workspace gets a simpler UI that grows when a second member joins.                                                                   | Reminders and follow-ups per booking type and leave-aware availability (separate follow-ups, listed in section 13).        |
| Existing workspaces are backfilled to `generic` with zero visible change.                                                                                  | No API change visible to integrations: the public API, webhooks and exports keep canonical field names and enums.          |

## 3. Concepts and glossary

| Term                | Meaning                                                                                                                                                                                                                                                                          |
| ------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Persona             | A named, versioned definition in the platform catalog: vocabulary, module visibility, starter presets, checklist. UI word for customers: **Business type**.                                                                                                                      |
| Persona version     | An immutable published snapshot. Editing happens on one draft per persona; publish creates version N+1.                                                                                                                                                                          |
| Module id           | A stable string for something that can be shown or hidden: `nav:<id>` (menu entry), `tile:<id>` (Settings tile), `section:contact.<id>` (contact tab), `card:dashboard.<id>`, `action:contact.<id>` (action-bar button). Same id convention the Help center uses in `documents`. |
| Vocabulary key      | A noun (`contact`, `deal`, `appointment`, `meeting`, `company`, `task`, `pipeline`) or a bound message key (`appointments.nav.appointments`). Overlay, not placeholder substitution.                                                                                             |
| Workspace persona   | The workspace's row: `persona_key`, the version it follows, team size, and two override layers.                                                                                                                                                                                  |
| Operator overrides  | Changes made from the platform admin for ONE workspace (add or remove a module, label, preset, add-on suggestion), each with a reason; can be `locked`.                                                                                                                          |
| Workspace overrides | The workspace admin's own choices: Show more modules, hide a module, rename a label.                                                                                                                                                                                             |
| Effective view      | What the workspace actually sees: persona defaults, then operator overrides, then workspace overrides (section 6), then the unchanged permission/entitlement gates.                                                                                                              |
| Solo mode           | A UI simplification for a workspace with one seat (no owner, assignment or team controls). Independent of the persona.                                                                                                                                                           |
| Starter pack        | The presets a persona offers (booking types, stages, templates, add-on suggestions, a few settings). Applied once, then ordinary editable rows.                                                                                                                                  |

## 4. Data model

All SQL below is a sketch for the implementing session (use the `add-migration` skill; hand-written, RLS enabled and forced, `touch_row` triggers).

### 4.1 Platform tables (no `org_id`)

| Table              | Columns (key ones)                                                                                                                                                                                                                                                                                                                                                                                                           | Policies                                                                                                                                      |
| ------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- |
| `personas`         | `id` bigint identity PK, `uuid`, `key` citext UNIQUE (`^[a-z][a-z0-9_]{1,39}$`, never reused), `status` (`active`,`archived`), `is_system` bool (`generic` cannot be archived), `sort_order`, `current_version` int NULL (latest published), `created_at`, `updated_at`, `row_version`                                                                                                                                       | SELECT: everyone (`USING (true)`, names only are not secret); write: `app_is_privileged()` (the `flow_templates` shape)                       |
| `persona_versions` | `persona_id` FK, `version` int, `status` (`draft`,`published`,`superseded`), `definition` jsonb (section 4.3), `compiled` jsonb (per-locale vocabulary overlay and the resolved module map, built at publish), `changes` jsonb (diff vs previous version with `appliesToExisting` per hide), `note`, `created_by`, `published_by`, `published_at`; PK `(persona_id, version)`; partial unique index: one `draft` per persona | SELECT: `status <> 'draft' OR app_is_privileged()` (tenants never read drafts); write privileged only; published rows are immutable (trigger) |

Both tables get `GRANT SELECT ... TO crm_app, crm_worker` plus write for the privileged path, like the other platform layer tables.

### 4.2 Tenant tables

| Table                       | Columns (key ones)                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  | Policies                                                                                                                                                                                                                                                                    |
| --------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `workspace_persona`         | `org_id` PK + FK; `persona_key` text FK to `personas(key)` NOT NULL DEFAULT `'generic'`; `persona_version` int (the version the workspace has accepted); `pinned` bool DEFAULT false (true: stay on `persona_version`, otherwise follow latest); `team_size` text (same five values as `sizeRange`); `solo_ui` text (`auto`,`on`,`off`) DEFAULT `'auto'`; `show_all_modules` bool DEFAULT false; `workspace_overrides` jsonb DEFAULT `'{}'`; `operator_overrides` jsonb DEFAULT `'{}'`; `operator_note` text; `operator_updated_by` bigint; `operator_updated_at`; `onboarding` jsonb (`{steps:{...}, skippedAt, completedAt}`); `rev` int DEFAULT 1 (bumped by EVERY change in this row, the cache key); `row_version`; timestamps | `tenant_isolation` (`org_id = current_org_id() OR app_is_privileged()`). A `BEFORE UPDATE` trigger rejects any change to `operator_*` columns unless `app_is_privileged()` (the pattern of `app.rbac_preset_sync` guards): RLS cannot restrict columns, so the trigger does |
| `workspace_persona_applied` | `org_id`, `preset_kind` (`booking_type`,`lifecycle_stage`,`pipeline`,`template`,`setting`), `preset_key`, `entity_uuid` NULL, `persona_key`, `persona_version`, `applied_by`, `applied_at`; PK `(org_id, preset_kind, preset_key)`                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  | `tenant_isolation`                                                                                                                                                                                                                                                          |
| `workspace_persona_log`     | `org_id`, `id`, `layer` (`persona_change`,`workspace`,`operator`), `actor_kind` (`user`,`operator`), `actor_id`, `action`, `item_id`, `before` jsonb, `after` jsonb, `reason` text (required for `operator`, CHECK length >= 5 like `retention_exempt_reason`), `created_at`. Append-only (no UPDATE/DELETE grant)                                                                                                                                                                                                                                                                                                                                                                                                                  | SELECT: `(org_id = current_org_id() AND layer <> 'operator') OR app_is_privileged()`; INSERT: tenant for its own layers, privileged for `operator`. Also written to the platform audit (`AuthAuditService`, `platform.persona.*`) and the tenant audit                      |

`organizations.settings.industry` and `sizeRange` stay (they feed analytics and old reads); the persona flow mirrors them (the persona's `industryHint`, the chosen team size) so nothing that reads them breaks.

### 4.3 Persona definition (JSON in `persona_versions.definition`, zod in `packages/contracts/src/persona/`)

```jsonc
{
  "schemaVersion": 1,
  "label": { "en": "Clinic / Doctor", "hi": "..." }, // en required, others optional
  "summary": { "en": "Appointments, patients and reminders. Nothing else." },
  "icon": "stethoscope",
  "industryHint": "healthcare", // mirrors organizations.settings.industry
  "teamSizes": ["1", "2-5", "6-20"], // sizes offered in onboarding; the rest are allowed too
  "vocabulary": {
    "nouns": {
      // forms per locale; a locale is used only if the noun is complete there
      "contact": { "en": { "one": "Patient", "other": "Patients" } },

    },
    "phrases": { "contacts-attributes-tags.list.addContact": { "en": "Add patient" } }, // bound keys only
  },
  "modules": {
    "default": "hide", // "show": new modules appear; "hide": allow-list persona (clinics)
    "ids": {
      "nav:inbox": "show",
      "nav:contacts": "show",

      "section:contact.meetings": "hide",
    },
  },
  "presets": {
    "addons": [{ "slug": "appointments", "level": "required" }], // Marketplace listing slugs; suggest only, never activates
    "bookingTypes": [
      {
        "key": "consultation-30",
        "name": { "en": "Consultation" },
        "kind": "appointment",
        "durationMinutes": 30,
        "location": "address",
      },
    ],
    "lifecycleStages": [{ "key": "booked", "name": { "en": "Booked" }, "color": "#2563eb" }],
    "pipelines": [],
    "templates": [
      {
        "key": "appt-reminder-24h",
        "channel": "whatsapp",
        "event": "reminder",
        "category": "utility",
        "body": { "en": "Hi {{1}}, a reminder of your visit on {{2}}." },
      },
    ],
```

Rules enforced at publish (not just in the form): every module id exists in the generated module catalog (P0 in section 13); every `presets.addons.slug` is a published Marketplace listing; every preset `settings` key is on an allow-list of typed settings (no free-form writes); template bodies pass the existing template validators; vocabulary keys exist in the bindings registry; a template is only ever created as a DRAFT (Meta approval is a separate, human step).

### 4.4 Override documents (both layers share one shape, `personaOverridesSchema`)

```jsonc
{
  "v": 1,
  "modules": {
    "nav:deals": { "state": "show", "locked": false, "reason": "wants a simple pipeline" },
  }, // "locked" is operator only
  "vocab": { "contact": { "en": { "one": "Client", "other": "Clients" } } },
  "addons": { "whatsapp-catalog": "suggest" }, // or "unsuggest"
  "presets": { "birthday-message": "exclude" }, // or "include"
  "settings": { "quietHours": { "from": "22:00", "to": "07:00" } }, // a different starter value, applied only if not yet applied
}
```

Applied presets are recorded in `workspace_persona_applied`: re-applying, changing persona or a persona update never creates a duplicate or overwrites a row the workspace has edited. Applied rows are ordinary tenant rows; deleting one is allowed and is not undone by a later apply (the ledger entry stays, the entity is marked gone).

## 6. Effective view: layering, conflicts, propagation

### 6.1 Precedence

For every module id: `effective = workspace ?? operator ?? persona`, where each layer may be silent. Silence falls through. Two refinements:

| Rule                     | Meaning                                                                                                                                                                                                                                                      |
| ------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Operator `locked`        | An operator override with `locked: true` wins over the workspace layer AND over "Show more modules". Without `locked`, the operator layer is a default the workspace admin may still change.                                                                 |
| Show more modules        | `show_all_modules = true` turns every persona-hidden item into shown, except items locked hidden by the operator. It is a switch, not a pile of per-item overrides; a per-item `hide` by the workspace still wins over it.                                   |
| Words                    | `workspace > operator > persona > default wording`, resolved per (key, locale). A locale whose pack is incomplete uses the default wording for the WHOLE persona layer in that locale (no half-renamed screens).                                             |
| Presets, add-ons         | Operator/workspace layers decide what is OFFERED (included/excluded, suggested/unsuggested). Anything already applied (ledger) is never changed by a layer.                                                                                                  |
| Conflict, same layer     | Not possible: one key, one value per layer. Concurrent edits are caught by `row_version`.                                                                                                                                                                    |
| Conflict, operator vs ws | If the operator later sets `locked` on an item the workspace already changed, the workspace value is kept in storage (so an unlock restores it) but ignored in the effective view; the workspace Settings page shows the item as "set by your account team". |

### 6.2 Entitlement is applied AFTER, and wins

Persona visibility is computed first, then the unchanged gates: permission (role), `channel`, `app` (removes), `planFeature` (locks). `effective = shown` never makes anything available. A persona-hidden item is NOT drawn at all (no lock icon, no upsell); once shown it behaves exactly as it does today (a locked feature shows its lock). See section 9.1.

### 6.3 Workspace admin limits

The workspace admin can hide anything (their screen) and reveal any persona-hidden item that is not operator-locked, but the reveal only restores what plan, add-ons, channels and permissions already allow. The Settings page lists a revealed item that needs something the workspace lacks as "needs Appointments" with a link to the Marketplace or Plans (the same paywall copy as today).

### 6.4 Persona version propagation

| Case                                                 | Behaviour                                                                                                                                                                                                                                                                      |
| ---------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Workspace follows latest (default)                   | The resolver reads `personas.current_version`; a publish reaches workspaces within the cache window (section 7.3) without touching their rows.                                                                                                                                 |
| Persona update SHOWS or relabels an item             | Flows to everyone following latest, unless that workspace has an explicit override for that item (any layer), which keeps winning.                                                                                                                                             |
| Persona update HIDES an item                         | By default it applies to workspaces created after the publish only (existing ones keep the item: `changes[].appliesToExisting = false`); the publisher can tick "also apply to existing" per item on the impact screen. No one loses a screen by surprise.                     |
| Item the workspace has data in                       | A hide never applies to a module the workspace uses (probe: e.g. deals count > 0, meetings/appointments count > 0): it is kept shown and listed in the Persona tab as "kept because it has data".                                                                              |
| Pinned workspace                                     | Stays on `persona_version` until the operator unpins; the Persona tab shows "N newer changes available" with the diff.                                                                                                                                                         |
| Item removed from the catalog (module id disappears) | Ignored by the resolver, listed in the admin as "unknown id" (never throws). A renamed nav/tile id needs an alias entry in the module catalog (risk 3).                                                                                                                        |
| Workspace changes persona                            | Non-destructive: data untouched, workspace and operator overrides kept (for ids that still exist), applied-preset ledger kept, new persona's presets are offered not forced; modules with data stay shown (a `show` override is written for them, logged as `persona_change`). |

### 7.3 Caching

| Layer              | Rule                                                                                                                                                                                                                                                                                                   |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| API catalog        | In-process snapshot of published versions, 5 s TTL (the `PlatformSettingsService` choice) and dropped on `persona.published` in the same process; other instances see it within the window.                                                                                                            |
| API workspace view | Memo per `(orgId, rev, personaVersion)`, 30 s; any write bumps `rev` in the same transaction, so a stale entry is simply never asked for again.                                                                                                                                                        |
| Web                | The session carries `org.persona = { key, version, rev, solo, showAll }` (small). `getPersonaView(orgId, rev, locale)` is `cache()`d per request and memoized in server memory by that key; ETag = hash of the same tuple. One call per page render at most, no extra call when the tuple is memoized. |
| Failure            | Unknown (call fails) => `hidden = null`: show everything, like entitlements ("nothing is hidden on a guess"), and fall back to default wording.                                                                                                                                                        |

### 7.4 Vocabulary mechanism (feasibility)

ICU placeholders (`{contact}` inside 1,450 sentences) are rejected: the nouns need case, gender and plural forms in `ru`, `pl`, `ar`, `he`, `hi`, `tr`..., and the strings are shared by 21 locales that would all need re-translation. Chosen mechanism: a **message overlay**.

1. A **bindings registry** (`apps/web/src/features/persona/vocab-bindings.ts`, about 150 keys in phase 1) lists the message keys that carry a key noun: `{ messageKey, noun, form: 'one'|'other' }` for labels (`contacts-attributes-tags.nav.contacts` -> `contact.other`, `appointments.nav.appointments`, `deals-pipelines.nav.deals`, page titles, tab names, column heads) and `{ messageKey, phrase: true }` for the "Add patient" kind of button, whose wording is authored per locale.
2. At **publish**, the console compiles, per locale, `messageKey -> string` from the nouns and phrases. A locale is compiled only if every binding resolves in it; otherwise that locale gets no overlay (default wording in that language).
3. At **request** time `i18n/request.ts` calls `loadMessages(locale)` then `deepMerge(messages, overlay)` where `overlay = persona overlay <- operator vocab <- workspace vocab` for that locale (small objects). Server and client components both see it because the merge happens in the request config; no component changes.
4. Scope for phase 1: nav labels, page titles, section/tab names, table column headers, "Add <noun>" buttons, empty-state titles. Not in phase 1: sentences inside dialogs, errors, notification text, emails and WhatsApp messages sent to customers, CSV headers, API fields, Help guide text (guides keep default wording; phase 6 adds noun tokens to the markdown compiler).
5. Safety nets: a unit test that every binding key exists in `en`; a coverage meter per locale in the editor; "default wording" always available; the English fallback in `loadMessages` is untouched.

## 9. Interactions

### 9.1 Plan, add-ons, channels (visibility vs entitlement)

| Question                                                        | Answer                                                                                                                                                                                                                                           |
| --------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Does a persona unlock a feature?                                | Never. Showing a module whose `app`/`planFeature` the workspace lacks changes nothing it can do; the existing gate still removes or locks it.                                                                                                    |
| Does an operator override unlock it?                            | No. Granting access (comping an app, a plan override, an add-on) is a separate explicit action with its own permission and audit (`platform.market.pricing`, the workspace plan dialog); the Persona tab only LINKS to it and never performs it. |
| Persona hides a locked feature: upsell?                         | No. A hidden item draws no lock and no upsell (a doctor is not nagged about Flows). Show more modules reveals it with today's lock.                                                                                                              |
| Persona suggests an add-on the workspace lacks                  | Marketplace shows a "Recommended for your business" strip and the Home checklist step "Turn on Appointments" links to the listing. Nothing is activated or billed.                                                                               |
| Appointments needs the paid app; the Clinic persona requires it | The onboarding recap says so plainly ("Appointments is an add-on; turn it on to continue") and Home keeps the checklist step until it is on. Until then the menu simply lacks it (as today).                                                     |
| Typed or bookmarked URL of a hidden module                      | Still opens when permission and entitlement allow (notification links, shared links keep working). Hiding is a menu decision, not a security boundary.                                                                                           |

### 9.2 Permissions and record scopes

The persona changes what is DRAWN. Role grants, `own`/`team`/`all` scopes, RLS and `@RequirePermission` are not read or changed by it. Workspace-side edits need the existing `admin.settings.manage` (same as onboarding) so no new tenant key and no `provision_workspace_presets` gap. A member sees the effective view whatever their role; a role without a module's permission still does not see it.

### 9.3 Help center

Guides hide with their screens (7.2). Phase 6: guide frontmatter `personas: [clinic, dental]` to boost the relevant ones on `/help`, and `getting-started` gets a persona-specific variant; guides stay in default wording until the markdown compiler supports noun tokens. The Help assistant (`help-agent`) receives the persona key and vocabulary so answers say "patients".

### 9.4 Meetings and Appointments

One underlying model each, no merge: meetings (`contact_meetings`, section `meetings`) and appointments (`booking_types` + `appointments`, section `appointments`, paid app). The persona decides which sections and words are visible: Clinic/Dental/Salon hide `meetings`; Sales shows both ("Discovery call" is a meeting, "In-person visit" an appointment); Real estate shows both with the appointment relabelled "Site visit"; Retail hides both. **Owner decision 6 stays as agreed: the Meetings/Appointments backfill runs for everyone at deploy; persona neither gates nor delays it** (it only decides what is visible afterwards).

What P0 delivers, and where it differs from the sketches above:

- **Contracts** (`packages/contracts/src/persona/`): `moduleIdSchema` and the five module kinds, `personaDefinitionSchema` with
  `GENERIC_PERSONA_DEFINITION`, the two override documents (`operatorOverridesSchema` requires a reason of 5+ characters and may `lock`;
  `workspaceOverridesSchema` rejects `locked`), `resolvePersona` / `explainModule` / `isModuleHidden` / `hiddenModuleIds` / `resolveNouns` (pure),
  `personaViewSchema`, and `org.persona` (optional) on `sessionOrgSchema`.
- **Module catalog**: `apps/web/scripts/gen-registry.mjs` writes `_registry/module-catalog.generated.ts` (and `home-cards.generated.ts`) from the nav,
  Settings, planned, home-card and contact-page registries. The Home cards are declared in `dashboards-analytics-charts/home-cards.ts` (phase 1
  makes the dashboard read them). A test holds every id a seeded persona names to the catalog.
- **Migrations** `20261230090000..090200`: all five tables of 4.1 and 4.2, the `generic` persona v1, the four `platform.persona.*` keys (no tenant
  key), and the batched, idempotent backfill. Differences from the sketch: `personas.key` is `text` with the pattern check (the pattern already
  forces lower case, so `citext` added nothing); `workspace_persona_applied` has `entity_gone_at` (the "marked gone" of 4.4); the log's tenant
  policies also hide every `actor_kind = 'operator'` row, not only layer `operator` (an operator-made persona switch carries the operator's
  reason, and a workspace must not read it) and its append policy binds `actor_id` to the acting user while the database stamps `created_at`;
  a workspace cannot DELETE its `workspace_persona` row (that would drop the operator's overrides); deleting a platform operator clears the

  reads the workspace row also joins `personas.current_version`, so "follow the latest" needs no catalog TTL; a published definition is immutable
  and is kept, the resolved view is memoised by `(org, row creation time, rev, version)` for 30 s, and a missing version is remembered for 5 s.

What P1 delivers, and where it differs from the sketches above:

- **One input, one hook.** `Capabilities.hidden` (`_registry/types.ts`) is the fourth input beside permissions, plan features and channels. It is
  optional (`null`, absent and an empty set all hide nothing) so no existing caller or test changes. `resolveNavAll`/`resolveNav` and
  `resolveSettings` skip an id in it BEFORE `evaluateGates` (`hiddenByPersona`), so a hidden entry draws no lock and no upsell. Client code asks
  `usePersonaVisibility()` (`apps/web/src/features/persona/`): `isHidden(id)` plus typed `isNavHidden`, `isTileHidden`, `isSectionHidden`,
  `isCardHidden`, `isActionHidden`, all built with `moduleId()` so no component spells an id by hand. `PersonaProvider` sits beside
  `PlanFeaturesProvider` in `(app)/layout.tsx` and takes the session's `org.persona`; no provider or no view hides nothing.
- **Server side.** `personaHiddenIds(view)` (`persona/server.ts`) turns the view into the set of hidden ids of the generated catalog. The app
  layout and the `/help` pages (`help-center/server.ts`) both call it, so the menu, the Settings tiles and Help cannot disagree. The view travels
  as `{ defaultVisibility, modules }`, so the client needs no catalog to answer `isHidden`.
- **Consumers.** Menu and Settings tiles (resolvers). Help: a guide whose documented screens are all hidden leaves with them (the existing
  "at least one documented screen is available" rule). Command palette and search: built from the resolved lists, so they follow. Contact page:
  `pageTabs`, `quickTabs`, `visibleSections` take an optional `hidden` predicate; the tab strip spares the section on screen, and the section a
  link names still opens (the permission check is the only one that closes a tab); the action bar (Note, Task, Call, Meeting, Add company), the
  compose box tabs, the Lead score chip and card, and the Tasks, Deals and Company cards beside the record follow the `section:` and `action:` ids.
  Home: `dashboard-screen.tsx` skips a card by the ids of `dashboards-analytics-charts/home-cards.ts` and drops the empty wrapper around hidden
  groups.
- **Not a lock.** `AppGate`, `PlanPaywall` and every route guard still read the unfiltered registries, so a typed or bookmarked address of a hidden
  module opens when permission and entitlement allow (decision 9). The API is untouched: nothing server-side reads the persona.
- **Golden test.** `apps/web/src/features/persona/golden.test.ts` compares, on five capability fixtures built from the real registries, the
  menu, the hub panes, the Settings tiles, the Help index, the contact tabs and the Home cards of the `generic` persona with a workspace that has
  no persona: identical. The same file holds the hidden-and-locked, Show-more, entitlement-wins and allow-list cases.
- **Not in P1 (open, listed so it is not lost):** the Settings tile "Business type" with the "Show more modules" switch and its endpoint
  `PATCH /v2/persona/settings` (the resolver already honours `showAll`; nothing can set it yet), the Home checklist card (phase 4), solo-mode
  hiding (`solo` is carried on the view; nothing reads it), the `persona.enabled` platform flag, and the quick-access and quick-action lists
  inside Home cards (a hidden module still appears there if the card itself is shown). No persona other than `generic` exists until phase 2, so
  nothing is hidden for anyone yet. Not browser-checked with a non-generic persona (see the PR).
