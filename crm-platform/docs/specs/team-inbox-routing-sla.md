# Team inbox routing, SLA, business hours and snooze: what the code does

Status: describes the code in `crm-platform/apps/api/src/modules/team-inbox-routing-sla/` and the shared code it calls, as read on 2026-10-29. The feature record is `crm-platform/docs/threadwise-port/inventory/team-inbox-routing-sla.md`. Where the code and the inventory differ, this spec follows the code and lists the difference under "Open disagreements". It is not a design proposal.

How proof is cited: each rule names a test file (short path under `crm-platform/apps/api/test/`, `unit/` or `e2e/`) and the start of the test title, so `grep -F` finds it. A rule with no such test is listed under "Not proven by a test" and is not claimed as covered. The spec has 83 rules: 62 with a test, 21 not proven.

## 1. Where the code is

- Routing: `routing-inbound.listener.ts` (entry point), `routing-engine.service.ts` (rules, pools, leave, chat limit, keep-contact-agent), `routing-rules.repository.ts` (`available()`, cursors, due escalations), `routing-escalation-sweep.service.ts`.
- Picking and availability: `common/agent-picker.ts`, `common/agent-status.ts` (effective status and the `routable` flag).
- SLA clock: `sla-inbound.listener.ts` (starts clocks), `sla-clock.service.ts` (writes due times), `common/sla-time.ts` (arithmetic and display state), `sla-policies.repository.ts` and the policy API.
- SLA sweep: `sla-sweep.service.ts`. Breach notification: `modules/notifications/sla-notification.consumer.ts`.
- Business hours: `common/business-hours.ts` (the engine), `business-hours.service.ts` and `business-hours-rules.ts` (settings), `packages/contracts/src/team-inbox-routing-sla/business-hours.ts` (schema).
- Waiting queue and away rules: `queue-timers.ts` (pure arithmetic), `queue-timers.service.ts`, `queue-timers-sweep.service.ts`, `away.service.ts`, `away.consumer.ts`.
- Snooze wake-up: `modules/team-inbox-conversations/inbox-snooze-wake.service.ts` calls `InboxTriageService.wakeDue()`. The wake reminder is in `modules/notifications/conversation-notification.consumer.ts`.
- The listeners and sweeps are provided by `team-inbox-routing-sla-worker.module.ts` only.

## 2. SLA clock

- **SLA-1 Start trigger.** A clock starts only when an inbound message creates a conversation, or reopens one that was resolved or closed. A message on a live thread, or a reopen from snoozed, starts nothing. Code: `sla-inbound.listener.ts` (`onStored`), `sla-clock.service.ts` (`start`). Test: `e2e/team-inbox-routing-sla/sla.e2e.spec.ts`, "the inbound listener starts a clock".
- **SLA-2 Plan gate.** No clock without the `inbox_sla` plan feature; the start returns `reason: 'plan'`. Code: `sla-clock.service.ts`. Test: `e2e/team-inbox-routing-sla/sla.e2e.spec.ts`, "starts nothing without a default policy".
- **SLA-3 Default policy only.** The clock uses the workspace policy marked default. With none, the start returns `reason: 'no_policy'`. Code: `sla-policies.repository.ts` (`defaultPolicy`). Test: `e2e/team-inbox-routing-sla/sla.e2e.spec.ts`, "starts nothing without a default policy".
- **SLA-4 No targets.** A policy whose targets are both empty returns `reason: 'no_targets'`; an unknown conversation returns `started: false`. Test: `e2e/team-inbox-routing-sla/sla.e2e.spec.ts`, "starts nothing without a default policy".
- **SLA-5 Targets.** The policy's first-response and resolution minutes apply. A priority override replaces each key it names and keeps the others. A null or zero target means no clock for that kind. Code: `common/sla-time.ts` (`effectiveTargets`). Test: `unit/team-inbox-routing-sla/sla-time.spec.ts`, "uses the policy targets when the priority has no override", "an override replaces only the keys it names", "a null or zero target is no clock".
- **SLA-6 Anchor.** The clock is anchored at `waiting_since` (the oldest unanswered customer message) when it is set, otherwise at the time of the start call. Code: `sla-clock.service.ts`. Test: `e2e/team-inbox-routing-sla/sla.e2e.spec.ts`, "starts from the customer wait".
- **SLA-7 Stored due times.** Due times are stored as absolute timestamps in `sla_first_response_due` and `sla_resolution_due`, with `sla_policy_id` set and `sla_breached` set to false. Code: `sla-clock.service.ts` (UPDATE). Test: `e2e/team-inbox-routing-sla/sla.e2e.spec.ts`, "starts from the customer wait" (reads the columns back).
- **SLA-8 Business time.** With the policy's `respectBusinessHours` on, the due time is computed by `addBusinessMinutes` (see section 4). With it off, due is anchor plus minutes. Code: `common/sla-time.ts` (`dueAt`). Test: `unit/team-inbox-routing-sla/sla-time.spec.ts`, "is business time when they are"; `e2e/team-inbox-routing-sla/sla.e2e.spec.ts`, "counts only business hours in the workspace time zone".
- **SLA-9 A person's reply stops the wait.** A reply from a person (sender kind `agent`) that the provider accepts clears `waiting_since` and stamps `first_response_at` once. Code: `modules/chat-conversations/message-dispatch.service.ts` (`humanReply`), `conversations.repository.ts` (`applyOutboundSent`). Test: `e2e/chat-conversations/message-send.e2e.spec.ts`, "is queued at once, sent by the worker".
- **SLA-10 A failed send stops nothing.** Test: `e2e/chat-conversations/message-send.e2e.spec.ts`, "/fail ends failed with the reason" (no first response, the wait continues).
- **SLA-11 Campaign sends do not stop the wait.** A message written by `recordOutbound` (sender kind not `agent`) leaves `waiting_since` and `first_response_at` alone. Test: `e2e/chat-conversations/conversations-facade.e2e.spec.ts`, "recordOutbound writes a message another domain sent as sent".
- **SLA-12 The sweep closes an answered first-response clock.** When `waiting_since` is clear, the sweep clears `sla_first_response_due` and writes a `first_response` event with `withinSla`. Code: `sla-sweep.service.ts` (`closeAnswered`). Test: `e2e/team-inbox-routing-sla/sla.e2e.spec.ts`, "an answered first-response clock is closed with a first_response event".
- **SLA-13 Lateness.** An answer after the first-response due time is a breach and is flagged. An answer in time is not. Test: `e2e/team-inbox-routing-sla/sla.e2e.spec.ts`, "an answered first-response clock is closed with a first_response event" (both cases).
- **SLA-14 Display clock.** The shown clock is first-response while the customer waits, otherwise resolution. Code: `common/sla-time.ts` (`slaStatus`). Test: `unit/team-inbox-routing-sla/sla-time.spec.ts`, "shows the first-response clock while the customer waits", "moves to the resolution clock once someone has answered".
- **SLA-15 Display states.** `at_risk` when 30 minutes or less remain; `breached` when flagged, or when the due time has passed but the sweep has not flagged it yet. Test: `unit/team-inbox-routing-sla/sla-time.spec.ts`, "is at risk within thirty minutes of the due time", "is breached when flagged".
- **SLA-16 Finished conversations.** A resolved, closed or spam conversation shows no clock unless it was breached. Code: `common/sla-time.ts` (`FINISHED`). Test: `unit/team-inbox-routing-sla/sla-time.spec.ts`, "shows nothing without a clock, or on a finished conversation unless it was breached".
- **SLA-17 New cycle on reopen.** A reopen from resolved or closed sets new due times and clears `sla_breached`. Test: `e2e/team-inbox-routing-sla/sla.e2e.spec.ts`, "the inbound listener starts a clock" (the reopened case asserts the flag is false and the due time is in the future).

## 3. SLA sweep and the breach event

- **SW-1 Plan scope.** Only workspaces with `inbox_sla` are swept. Code: `sla-sweep.service.ts` (`orgsWithWork`). Test: `e2e/team-inbox-routing-sla/sla.e2e.spec.ts`, "a workspace whose plan lost inbox_sla is not swept".
- **SW-2 First-response breach.** An open conversation whose customer is still waiting and whose first-response due time has passed is flagged, kind `first_response`. Test: `e2e/team-inbox-routing-sla/sla.e2e.spec.ts`, "the sweep flags a first-response breach once".
- **SW-3 Resolution breach.** An open conversation whose resolution due time has passed is flagged, kind `resolution`. Test: `e2e/team-inbox-routing-sla/sla.e2e.spec.ts`, "the sweep flags a resolution breach, and leaves alone what it must".
- **SW-4 Left alone.** Conversations with a future due time, that are snoozed, resolved or spam are not flagged. Test: `e2e/team-inbox-routing-sla/sla.e2e.spec.ts`, "the sweep flags a resolution breach, and leaves alone what it must".
- **SW-5 Once per cycle.** The flag is set only `WHERE NOT sla_breached`. A second pass writes no second flag, no second `sla_breach` event and no second outbox event. Test: `e2e/team-inbox-routing-sla/sla.e2e.spec.ts`, "the sweep flags a first-response breach once" (ends with "a second pass changes nothing").
- **SW-6 Timeline.** Each flag writes a `sla_breach` conversation event with `kind`. Test: `e2e/team-inbox-routing-sla/sla.e2e.spec.ts`, "the sweep flags a first-response breach once" and "the sweep flags a resolution breach, and leaves alone what it must".
- **SW-7 Breach stamp.** `sla_breached` is set to true by the sweep and is reset only when a new clock starts (SLA-17). Test: `e2e/team-inbox-routing-sla/sla.e2e.spec.ts`, "the sweep flags a first-response breach once" and "the inbound listener starts a clock".
- **EV-1 Outbox event.** The flag and the outbox event `conversation.sla_breached` are written in the same transaction. Code: `sla-sweep.service.ts` (`flag`, `SLA_BREACH_EVENT`). Test: `e2e/team-inbox-routing-sla/sla.e2e.spec.ts`, "the sweep flags a first-response breach once" (one event for the conversation).
- **EV-2 Payload.** The event carries the conversation uuid as `conversationId`, plus `kind` and `dueAt` (ISO time). Test: `e2e/team-inbox-routing-sla/sla.e2e.spec.ts`, "the sweep flags a first-response breach once" (the uuid is asserted; `kind` and `dueAt` are not, see section 8).
- **EV-3 Recipients.** The notification goes to the assignee if there is one, else to the members of the assigned team, else to the people with SLA-manage permission. Only active users. Code: `modules/notifications/sla-notification.consumer.ts` (`slaAudience`). Test: `e2e/team-inbox-routing-sla/sla.e2e.spec.ts`, "the breach notification goes to the assignee"; `unit/notifications/sla-notification-rules.spec.ts`, "falls back to the team, then to the people who manage SLA policies".
- **EV-4 One row per event.** Handling the same event id twice writes one row per recipient. Code: `sla-notification.consumer.ts` (dedupe key carries the outbox event id). Test: `e2e/team-inbox-routing-sla/sla.e2e.spec.ts`, "the breach notification goes to the assignee".

## 4. Business hours

- **BH-1 Source.** The weekly schedule is read from `workspace_settings.business_hours`; the zone from `organizations.settings.timezone`, defaulting to UTC. Code: `sla-clock.service.ts` (start query), `business-hours.service.ts`. Test: `e2e/team-inbox-routing-sla/sla.e2e.spec.ts`, "counts only business hours in the workspace time zone".
- **BH-2 No usable hours.** With no config, no `days`, or no enabled day, time is plain addition. Code: `common/sla-time.ts` (`addBusinessMinutes`). Test: `unit/team-inbox-routing-sla/sla-time.spec.ts`, "is plain addition with no hours configured".
- **BH-3 Closed time is skipped.** Minutes count only while open. A clock that starts while closed counts from the next opening. Weekends are skipped. Test: `unit/team-inbox-routing-sla/sla-time.spec.ts`, "stops at closing and carries the rest into the next morning", "skips the weekend", "a clock that starts while closed starts at the next opening".
- **BH-4 Zone.** Opening hours are read in the workspace zone, not UTC. Test: `unit/team-inbox-routing-sla/sla-time.spec.ts`, "reads the hours in the workspace time zone".
- **BH-5 Daylight saving.** Local wall-clock hours are used on both sides of a change, and an SLA clock counts open time across it. Code: `common/business-hours.ts` (`localParts`, Intl formatter per zone). Test: `unit/team-inbox-routing-sla/working-hours.spec.ts`, "reads the wall clock on both sides of the change"; `unit/team-inbox-routing-sla/sla-time.spec.ts`, "follows daylight saving: New York falls back on 1 November 2026".
- **BH-6 Day boundaries.** An overnight window (closing before opening) runs through midnight into the next morning, even when the next day is off. A window ending at `24:00` is open to the last minute of the day. Test: `unit/team-inbox-routing-sla/sla-time.spec.ts`, "an overnight shift counts through midnight"; `unit/team-inbox-routing-sla/working-hours.spec.ts`, "an overnight window runs into the next morning, even when that day is off", "a window to 24:00 is open until the last minute of the day".
- **BH-7 Several windows.** A gap between two windows of one day is closed time. Test: `unit/team-inbox-routing-sla/working-hours.spec.ts`, "does not count the break".
- **BH-8 Holidays.** A listed date (in the workspace zone) is closed all day. Test: `unit/team-inbox-routing-sla/working-hours.spec.ts`, "closes a listed date all day, in the workspace zone", "skips a holiday".
- **BH-9 Save rules.** Equal opening and closing times, `24:00` as an opening time, overlapping windows and a fourth window are refused. An unknown zone is refused. Only the owner's zone is kept; other members' day changes still save. Test: `unit/team-inbox-routing-sla/working-hours.spec.ts`, "rejects equal times, 24:00 as an opening time, overlaps and a fourth window"; `unit/team-inbox-routing-sla/business-hours-rules.spec.ts`, "refuses a missing day, a bad time and an unknown zone", "lets only the owner change it when the workspace names an owner"; `e2e/team-inbox-routing-sla/business-hours.e2e.spec.ts`, "a manager who is not the owner saves the days, and the zone is ignored".

## 5. Routing

- **RT-1 Trigger.** Rules run on a message that creates a conversation or reopens a finished one. A later message on a live thread runs only per-message actions and never reassigns. Code: `routing-inbound.listener.ts`, `routing-engine.service.ts` (`route`, `routeFollowUp`). Test: `e2e/team-inbox-routing-sla/routing-rules.e2e.spec.ts`, "a redelivered message and a later message of the same conversation do not assign again".
- **RT-2 Once per message.** A redelivered message is routed once (`already_routed`) and writes one `assigned` event. Test: `e2e/team-inbox-routing-sla/routing-rules.e2e.spec.ts`, "a redelivered message and a later message of the same conversation do not assign again".
- **RT-3 Order and stop.** Active rules are tried in sort order. The first rule that fires ends evaluation when stop-on-match is on, which is the default. With it off, a later firing rule takes over. Code: `routing-engine.service.ts`. Test: `e2e/team-inbox-routing-sla/routing-rules.e2e.spec.ts`, "the first matching rule wins and stops", "stop on match off: a later matching rule takes over"; `unit/team-inbox-routing-sla/routing-matcher.spec.ts`, "saves switched off unless asked, and stops on match by default".
- **RT-4 A rule fires only with a taker.** If nobody can take the conversation, the rule does not fire and evaluation goes on. A rule that lists a team hands the conversation to that team's queue. Test: `e2e/team-inbox-routing-sla/routing-rules.e2e.spec.ts`, "an agent who is suspended, or marked busy, is skipped", "a team in the rule is the queue when its people are all unavailable".
- **RT-5 Fallback.** When no primary rule fired, the fallback rule takes the conversation; with it off, the conversation stays unassigned. Test: `e2e/team-inbox-routing-sla/routing-rules.e2e.spec.ts`, "the fallback takes what no rule matched".
- **RT-6 Round robin.** The pool is taken in id order, starting after the rule's stored cursor and wrapping. The cursor is stored with the rule under a row lock. Code: `common/agent-picker.ts` (`pickRoundRobin`), `routing-engine.service.ts` (`choose`). Test: `unit/team-inbox-routing-sla/agent-picker.spec.ts`, "goes around in id order and wraps to the first", "keeps its place when the person who had the last turn is gone"; `e2e/team-inbox-routing-sla/routing-rules.e2e.spec.ts`, "the first matching rule wins and stops; round robin alternates".
- **RT-7 Least busy.** The person with the fewest open conversations is picked; ties follow the rotation. Code: `common/agent-picker.ts` (`pickLeastBusy`). Test: `unit/team-inbox-routing-sla/agent-picker.spec.ts`, "picks the fewest open conversations", "breaks a tie by the rotation so equal people take turns".
- **RT-8 Specific.** A `specific` rule must name exactly one person. Test: `unit/team-inbox-routing-sla/routing-matcher.spec.ts`, "needs someone to assign to, and exactly one agent for".
- **RT-9 Offline or busy.** A person whose effective status is offline or busy is not picked; setting Available puts them back. Code: `common/agent-status.ts` (`routable`). Test: `e2e/team-inbox-routing-sla/routing-chat-limit.e2e.spec.ts`, "an agent who switched Offline is skipped"; `e2e/team-inbox-routing-sla/routing-rules.e2e.spec.ts`, "an agent who is suspended, or marked busy, is skipped".
- **RT-10 Own working hours.** With agent status automation on, a person outside their own hours is not picked, and Try it says why. A manual Available overrides the schedule. Without automation the schedule is ignored. Test: `e2e/team-inbox-routing-sla/routing-working-hours.e2e.spec.ts`, "a round robin pool never picks the person outside their hours", "a manual Available beats the schedule", "without agent_status_automation the schedule is ignored".
- **RT-11 Leave.** A person on leave is never picked; the pool takes them back the day the leave ends. Test: `e2e/team-inbox-routing-sla/routing-leave.e2e.spec.ts`, "a round robin pool never picks the person on leave".
- **RT-12 Delegate.** A rule that names someone on leave gives the conversation to their delegate, ahead of the rule's teams. A delegate who cannot open the inbox, or is away, is not used. Test: `e2e/team-inbox-routing-sla/routing-leave.e2e.spec.ts`, "a rule that names somebody on leave gives the chat to their delegate", "a delegate who cannot open the inbox is not used".
- **RT-13 Nobody available.** When the whole team is away the conversation waits in the team queue, assigned to the team with no person, and the leads are not told. When a named person is away with nobody to take their place, the leads are told. Test: `e2e/team-inbox-routing-sla/routing-leave.e2e.spec.ts`, "with the whole team away the chat waits in the team queue", "the leads are told when a chat has nobody to take it because of leave".
- **RT-14 Chat limit.** A person with `user_profiles.chat_limit` open conversations is skipped until one closes. No limit means no cap. Code: `routing-rules.repository.ts` (`available`). Test: `e2e/team-inbox-routing-sla/routing-chat-limit.e2e.spec.ts`, "round robin skips an agent who already holds the limit", "least busy skips a full agent too", "a conversation that is resolved no longer counts".
- **RT-15 Keep returning contacts with their agent.** Off by default. The contact's owner is used, else the last active holder, if they can open the inbox. Availability is not checked. Code: `routing-engine.service.ts` (`contactAgent`). Test: `e2e/team-inbox-routing-sla/routing-rules.e2e.spec.ts`, "keep returning contacts with their agent".
- **RT-16 Escalation.** A matching rule can schedule an escalation. It runs when due only if the conversation is still open and we have not replied. A reply from us before the time cancels it. Code: `routing-escalation-sweep.service.ts`, `routing-rules.repository.ts` (`dueEscalations`). Test: `e2e/team-inbox-routing-sla/routing-rules.e2e.spec.ts`, "a matching message schedules the escalation", "when the time comes with no reply, the conversation is reassigned by the rule", "a reply from us before the time cancels it"; `e2e/team-inbox-routing-sla/smart-routing-gating.e2e.spec.ts`, "the escalation timer stops: a due escalation is dropped".

## 6. Waiting queue timers and away rules

- **QT-1 Steps.** A waiting chat gets, in order, a reminder, an offer to the overflow team and a final step (a message to the customer or a hand back to the bot). Each runs once per wait. Code: `queue-timers.ts` (`dueSteps`), `queue-timers.service.ts` (`runFor`). Test: `e2e/team-inbox-routing-sla/queue-timers.e2e.spec.ts`, "runs remind, offer and final in order as the minutes are reached, each once"; `unit/team-inbox-routing-sla/queue-timers.spec.ts`, "runs the steps in order as their minutes are reached, each only once".
- **QT-2 Open minutes only.** Minutes count only while the chat's team is open, in the team's zone. A team that is never open never times out. Code: `queue-timers.ts` (`waitedOpenMinutes`). Test: `unit/team-inbox-routing-sla/queue-timers.spec.ts`, "counts only the minutes the team is open"; `e2e/team-inbox-routing-sla/queue-timers.e2e.spec.ts`, "counts only the minutes the team is open".
- **QT-3 Stops when the chat is no longer waiting.** A claim, a resolve or a closed status cancels the remaining steps. Test: `e2e/team-inbox-routing-sla/queue-timers.e2e.spec.ts`, "a claim cancels the rest", "a resolved chat is left alone".
- **QT-4 Plan gate.** Nothing runs and nothing is cleared without `inbox_routing` and the queue-timer gate; the saved settings come back with the feature. Test: `e2e/team-inbox-routing-sla/queue-timers.e2e.spec.ts`, "without Smart routing nothing runs and nothing is cleared".
- **QT-5 Going offline or on leave.** When a person goes offline or starts a leave, their waiting chats (customer still waiting) go back to the team queue with a `returned_offline` trace. Answered chats stay. A repeat moves nothing. Code: `away.service.ts`. Test: `e2e/team-inbox-routing-sla/queue-timers.e2e.spec.ts`, "going offline returns the chats whose customer still waits", "a leave returns them too", "a stale leave event returns nothing".

## 7. Snooze and wake-up

- **SN-1 Snooze.** Snoozing sets the status to snoozed with a wake time, writes a `snoozed` event and an audit row. Snoozing again moves the wake time; a past time is refused. Code: `modules/team-inbox-conversations/inbox-triage.service.ts` (`snooze`). Test: `e2e/team-inbox-conversations/inbox-snooze-spam.e2e.spec.ts`, "it is listed under snoozed with its wake time", "a snooze to a time already set is a no-op; a past time is refused".
- **SN-2 Wake.** A due snoozed conversation returns to open, its wake time is cleared, and an `auto_unsnoozed` event is written. A conversation that is not yet due is not woken. A snoozed spam thread wakes as open. Code: `inbox-triage.service.ts` (`wakeDue`). Test: `e2e/team-inbox-conversations/inbox-snooze-spam.e2e.spec.ts`, "the sweep wakes a due thread back to open", "a snoozed spam thread that wakes comes back as open".
- **SN-3 Breach flags wait for the wake.** A snoozed conversation is not flagged by the SLA sweep. Test: `e2e/team-inbox-routing-sla/sla.e2e.spec.ts`, "the sweep flags a resolution breach, and leaves alone what it must".
- **SN-4 Wake reminder.** The wake emits `conversation.reopened` (by system, from snoozed). The assignee gets a `snooze_wake` notification and nobody else does. Code: `modules/notifications/conversation-notification.consumer.ts` (`onSnoozeWake`). Test: `e2e/notifications/conversation-notifications.e2e.spec.ts`, "a snoozed chat that comes back by its time tells its assignee, and nobody else".

## 8. Not proven by a test

These behaviours are in the code or follow from it, but no test in `apps/api/test/` asserts them. They are not claimed as covered.

- **NP-1** A workspace with policies but none marked default gets no clock (the code returns null from `defaultPolicy`).
- **NP-2** Due times are fixed at start. Later changes to the policy, the hours or the priority do not recompute them.
- **NP-3** A bot, AI-agent or flow reply does not stop the wait (same branch as SLA-11, no bot test).
- **NP-4** A reaction does not stop the wait (`message-dispatch.service.ts` excludes reactions).
- **NP-5** Lateness is judged on `last_outbound_at`, which any outbound can move, not on the human reply time. No test sends an automated message after a reply.
- **NP-6** A reopen after a resolve made while the customer was still waiting keeps the old `waiting_since`, so the new clock starts at the old wait time (`applyInbound` uses COALESCE).
- **NP-7** Sweep cadence (60 s), batch size (200) and `FOR UPDATE SKIP LOCKED` safety across workers are not tested.
- **NP-8** A closed conversation is not flagged (the status filter covers it; no test uses a closed conversation).
- **NP-9** A breach of the other kind does not add a second flag in the same cycle (`flag` checks `NOT sla_breached`).
- **NP-10** The `sla_breach` timeline event's `dueAt`, and the outbox payload's `kind` and `dueAt`, are written but no test reads them.
- **NP-11** After the sweep, touched conversations are re-published with the `sla` change. No test asserts it.
- **NP-12** The breach notification is skipped when the plan lacks `inbox_sla` (consumer check; no test).
- **NP-13** At run time an unknown zone falls back to UTC (saves refuse unknown zones; the fallback is untested).
- **NP-14** A holiday closes its whole date even when the previous day's overnight window reaches into it (the code checks holidays first).
- **NP-15** The snooze wake runs every 30 seconds with 100 rows per pass. No test covers cadence or batch.
- **NP-16** A snoozed conversation resolved before its wake time is not reopened by the wake (status change clears the snooze). No test.
- **NP-17** A snoozed conversation with no assignee wakes without a notification, and a team-assigned one tells the team. Only the assignee case is tested.
- **NP-18** After a wake, a clock that is still due is flagged by the next sweep. No test.
- **NP-19** Routing pools hold only active people who can open the inbox, team members included. Only the delegate case is tested.
- **NP-20** The escalation sweep runs every 30 seconds with 100 rows per pass. No test covers cadence or batch.
- **NP-21** The overflow offer does not restart the wait clock. The test checks only the team change.

## 9. Open disagreements

- **D1 Breach event.** The inventory (TW-TIB2-029) names a `SlaBreached` event that broadcasts `sla.breached` with `conversation_id`, `kind`, `due_at`. The code has no such symbol or realtime event; it emits outbox `conversation.sla_breached` with `conversationId`, `kind`, `dueAt` (EV-1, EV-2).
- **D2 Breach notification.** The inventory status for TW-TIB2-029 is "dead-code" and says no notification is produced. The code has `SlaNotificationConsumer`, and the inventory's own port note says it is wired (EV-3).
- **D3 Breach on resolve.** The inventory (TW-TIB2-027) says resolving after the resolution due time sets `sla_breached`. The code has no such check, and the sweep never flags a resolved conversation (SLA-16, SW-4).
- **D4 Business hours in SLA.** The inventory (TW-TIB2-026) says `respect_business_hours` is ignored. The code applies it at clock start (SLA-8, BH-3).
- **D5 Clock start.** The inventory says only the first inbound with no first response starts a clock. The code starts one on a new conversation or a reopen from resolved or closed (SLA-1).
- **D6 Policy choice.** The inventory describes device-scoped policies with a fallback to any policy. The code uses only the default policy and has no device scope (SLA-3).
- **D7 First-response stop.** The inventory lists three operator send routes. The code keys on sender kind `agent` in the shared send path (SLA-9).
- **D8 Sweep and at-risk.** The inventory says one global pass gated to once a minute, with no warning state. The code runs per worker with SKIP LOCKED batches and has an `at_risk` display state 30 minutes before due (SW-2, SLA-15).
- **D9 Snooze wake.** The inventory says 30 seconds per workspace, 50 rows. The code runs every 30 seconds across all workspaces, 100 rows (NP-15).
- **D10 Strategies and capacity.** The inventory (TW-TIB2-020) describes team strategies `manual`, `round_robin`, `least_loaded`, `sticky` and a pivot capacity of 20. The code's rules use `round_robin`, `least_busy`, `specific`, a `chat_limit` on the user profile, and sticky is the keep-contact-agent option (RT-6 to RT-15).
- **D11 Availability.** The inventory says away members stay eligible and only offline or busy are skipped. The code also skips people on leave, outside their own hours and on manual away (RT-9 to RT-11).
- **D12 Round robin order.** The inventory says the next person is the one with the oldest `updated_at` among assigned chats. The code keeps an id cursor on each rule (RT-6).
- **D13 Test versus schema.** `e2e/team-inbox-routing-sla/business-hours.e2e.spec.ts` (first test in "business hours API") expects 422 for an overnight Tuesday window, 18:00 to 09:00. The contract `packages/contracts/src/team-inbox-routing-sla/business-hours.ts` accepts that window, and `unit/team-inbox-routing-sla/working-hours.spec.ts` asserts it. One of them is stale; this spec does not rely on the e2e expectation.
