# Multi-tenancy

One database, one schema, every row tagged with `org_id`, and Postgres
enforcing that nobody sees anyone else's.

## The four mechanisms

### 1. `org_id` on every business table

Not just a column — the **first** column of the primary key, of every foreign
key, and of every index that matters.

```sql
PRIMARY KEY (org_id, id)
FOREIGN KEY (org_id, company_id) REFERENCES companies (org_id, id)
```

Composite foreign keys make a cross-tenant reference **structurally
impossible**. You cannot point a contact in org 1 at a company in org 2, because
the FK requires the `org_id` to match.

### 2. Row-Level Security, forced

```sql
ALTER TABLE contacts ENABLE ROW LEVEL SECURITY;
ALTER TABLE contacts FORCE  ROW LEVEL SECURITY;

CREATE POLICY tenant_isolation ON contacts
  FOR ALL
  USING      (org_id = current_org_id() OR app_is_privileged())
  WITH CHECK (org_id = current_org_id() OR app_is_privileged());
```

`USING` controls what is visible. `WITH CHECK` controls what may be written.
Both are required: with only `USING`, a tenant could INSERT a row into another
tenant that it then cannot see.

### 3. A non-superuser connection

**This is the part that is easy to get wrong.**

A Postgres **superuser bypasses RLS entirely** — `FORCE` does not apply to
them. The default `POSTGRES_USER` in a docker-compose file is a superuser. An
application connecting as that user has every policy in place and every one of
them inert.

So:

| Connection               | Role                                      | Used for             |
| ------------------------ | ----------------------------------------- | -------------------- |
| `DATABASE_URL`           | `crm_app_user` (NOSUPERUSER, NOBYPASSRLS) | the application      |
| `MIGRATION_DATABASE_URL` | `crm` (owner)                             | migrations and seeds |

Roles are created by `docker/postgres/init/01-app-roles.sql` locally, and by
your provisioning tool in production. Migration 0007 grants them membership of
`crm_app` / `crm_worker`.

`apps/api/test/integration/rls.spec.ts` asserts `rolsuper = false` and
`rolbypassrls = false` for the connection under test — because without that
check, every other assertion in the file is vacuous.

### 4. Transaction-scoped tenant context

```ts
await db.transaction(async (tx) => {
  await tx.execute(sql`select set_config('app.org_id', ${String(orgId)}, true)`);
  return fn(tx);
});
```

`set_config(..., true)` is **transaction-local**: it is reverted on COMMIT or
ROLLBACK, so a pooled connection cannot leak one tenant's context into the next
request that borrows it.

`set_config` is used rather than `SET LOCAL app.org_id = $1` because SET LOCAL
does not accept bind parameters — and string-interpolating an org id into SQL
is how you get a tenant bypass through injection.

## Failing closed

With no context set, `current_org_id()` is NULL, so `org_id = NULL` is never
true and every query returns **zero rows**. Not every row. That is the correct
failure mode, and there is a test for it.

`withTenant` also refuses to run with a missing or non-positive `orgId`, so the
failure surfaces as an exception rather than an empty result.

## The privileged escape hatch

Some work genuinely spans tenants:

```ts
await this.db.privileged(async (tx) => { ... });   // sets app.privileged = on
```

**Exactly four sanctioned uses:**

1. the outbox drain and other cross-tenant workers
2. billing roll-ups across orgs
3. partition maintenance
4. the API-key prefix lookup and the login org lookup — both must resolve the
   org _before_ a tenant context can exist

**Never from an HTTP request handler.**

The honest limitation: `app.privileged` is a GUC, so the mechanism is
application-enforced rather than database-enforced. It is kept honest by review,
by the fact that all queries are parameterised, and by keeping the call sites
countable on one hand.

## Adding a new table — the checklist

```sql
CREATE TABLE widgets (
  org_id      bigint NOT NULL REFERENCES organizations (id) ON DELETE CASCADE,
  id          bigint GENERATED BY DEFAULT AS IDENTITY,
  uuid        uuid NOT NULL DEFAULT gen_random_uuid(),
  -- ...
  created_at  timestamptz NOT NULL DEFAULT now(),
  updated_at  timestamptz NOT NULL DEFAULT now(),
  row_version integer NOT NULL DEFAULT 1,
  PRIMARY KEY (org_id, id),
  UNIQUE (org_id, uuid),
  FOREIGN KEY (org_id, owner_id) REFERENCES users (org_id, id)
);

ALTER TABLE widgets ENABLE ROW LEVEL SECURITY;
ALTER TABLE widgets FORCE  ROW LEVEL SECURITY;
CREATE POLICY tenant_isolation ON widgets FOR ALL
  USING      (org_id = current_org_id() OR app_is_privileged())
  WITH CHECK (org_id = current_org_id() OR app_is_privileged());

CREATE TRIGGER trg_widgets_touch BEFORE UPDATE ON widgets
  FOR EACH ROW EXECUTE FUNCTION touch_row();
```

Table privileges are covered by `ALTER DEFAULT PRIVILEGES` from migration 0007.
**RLS is not** — enabling and forcing it, and writing the policy, is per-table
and cannot be defaulted. It is on the PR checklist for that reason.

## Partitioning and tenancy

Hash-partitioning entity tables by `org_id` (64 buckets) is planned for the
high-volume tables. Because `org_id` is already first in every PK, that change
is additive. Whale tenants escalate to dedicated, time-subpartitioned
partitions. See [scale.md](scale.md).
