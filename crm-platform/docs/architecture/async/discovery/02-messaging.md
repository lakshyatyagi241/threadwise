# Async reliability audit: WhatsApp, inbox, webhooks (discovery 02)

Scope: inbound webhooks, outbound sends (inbox, broadcasts, campaigns), wallet charging on sends, receipt/status processing, counters,
fire-and-forget code. Read-only audit of `apps/api/src` (branch `claude/wadesk-async-architecture-7662c0`). Every claim below was
checked against the code at the cited line, not against config or docs. All paths are relative to `crm-platform/apps/api/src/`
unless they start with `test/` (then `apps/api/test/`).

Note on `docs/architecture/messaging.md`: it describes a design ("reserve budget", "counters batch-updated every 2-5s by a worker",
`COUNTER_FLUSH`, `BILLING_POSTING`, `SLA_SWEEP` queues) that is NOT what is built. Those queue names exist in
`infra/queue/queues.ts:12-28` with no processor anywhere (`@Processor` grep: 43 processors, none for OUTBOX, BILLING_POSTING, SLA_SWEEP,
COUNTER_FLUSH, PARTITION_MAINTENANCE, BULK_JOBS). Counters are recounted inline (D-3), budget is not reserved (C-3).

Severity: P0 = silent data loss or duplicate customer-visible message / double charge in a normal failure; P1 = loss or stuck state in a
plausible failure or at scale; P2 = hardening / observability.

## 2. Answers to the specific questions

1. Inbound webhooks
   - Signature validation: WhatsApp Cloud (HMAC raw body, constant time, platform + tenant app secrets, else `?k=` URL key or trusted IP) `waba-webhook.service.ts:99-142`; Facebook fail-open without secret (A-3); Telegram fail-open without secret token (A-3); LINE/Viber HMAC (`channel-line/channel-rules.ts:32-43`); Gmail OIDC; Graph clientState HMAC `channel-email/graph-push-rules.ts:20-41`; payments HMAC (+ 5 min timestamp for invoice gateway); Shopify/Woo HMAC + replay key; generic channel webhooks adapter `verifyInbound` fail-closed `chat-conversations/channel-webhooks.service.ts:87-89`; Instagram engine shared secret `channel-instagram/inbound.service.ts:14-34`.
   - Ack vs process: queued then ack: WhatsApp Cloud, generic channels (`channel-webhooks.service.ts:104-107`), Gmail/Graph, Shopify/Woo, telephony, leadgen. Inline then ack: Facebook, Telegram, LINE, Viber, WeChat (not read), Razorpay/gateway/invoice/platform payments (inline is acceptable there: single tx, idempotent, non-2xx makes the provider retry).
   - Dedup: WhatsApp job id = sha256(body) but `removeOnComplete:true` so only in-flight (D); real dedupe = Redis claim (A-4) + `ingest-<ch>-in-<wamid>` job id + `message_ledger` unique (authoritative). Statuses: forward-only SQL (inbox), `shouldAdvance` (broadcast), `isNewer` (campaign).
   - Ordering: inbox correct; broadcast has `delivered -> failed` and terminal-failed problems (D-2).
   - Durability after ack: Redis AOF everysec only (A-9); failed WABA jobs kept 3 days, no per-change DLQ (A-5).
   - Tenant resolution: SECURITY DEFINER lookups by phone/WABA id (`waba_route_lookup`), page id (`fb_page_lookup`), `tg_bot_lookup`, `bcast_receipt_lookup`, `camp_receipt_lookup`, `store_gateway_lookup`; unknown number acknowledged and dropped with an info log (`waba-ingest.service.ts:81-89`, no metric).
2. Outbound: durable async only for the inbox (B-1..B-3 gaps); bulk senders are queue-started loops with per-recipient inline sends (B-4..B-9). Idempotency: inbox Redis key + lock (B-2, B-3); bulk none. Timeout 15 s Cloud, 130 s Baileys. Classification table exists but bulk does not use it. Retry-After header never read. Per-number rate limit: none. Statuses: `queued -> sent -> delivered -> read | failed` (+ `held`, no `uncertain`).
3. Wallet: exactly-once on replay (C-1), but unbilled/never-billed paths (C-2, C-3, C-4).
4. Receipts/counters: D-1..D-4.
5. Fire-and-forget: section F.
