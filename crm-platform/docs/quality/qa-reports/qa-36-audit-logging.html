Fixed earlieraudit_log is append-only (PR #435)

A trigger refuses every UPDATE and refuses DELETE unless the transaction is privileged. The retention prune and workspace erasure already run privileged. Verified on Postgres 16 including a partition created after the trigger. The partner lead submission was also given audit rows in the same PR.

PassNo secret values in audit deltas; required columns present; e2e suite exists

No password, token or secret is placed in an audit delta (checked across every audit.record call). audit_log records who (actor_id), what (action, module), which record, when and the request id. An end-to-end suite exists at apps/api/test/e2e/audit-log.

Weak points

MediumThe AI copilot settings toggle was not audited (fixed in PR #488)

An admin switching the staff-channel copilot on or off changes what staff can do through an AI over WhatsApp, and nothing recorded who or when. PR #488 records the old and new value under a row lock, and nothing for a no-op toggle. Until it merges, the gap is open on main.

LowThe coverage check cannot see audit calls made by a delegated module

It counts audit.record calls inside a module's own files, so a controller that delegates to another module's service looks unaudited (this is how google-account was flagged). It also cannot tell whether a given route is the one that should audit. PR #488 lets the check use the reviewed-exceptions baseline and records google-account there with the reason.

MediumApplication-role bypass remains possible

The append-only trigger allows DELETE when app.privileged is on. Anything that can already run arbitrary SQL as the app role can set it. The trigger closes bugs and ordinary sessions, not a full SQL-level compromise. The export plus the retention window are the second line.

LowBehavior tests have not run

The e2e suite proves a row appears after a real mutation and (since #435) that audit rows cannot be changed, but it needs the Docker stack and was not executed here.
