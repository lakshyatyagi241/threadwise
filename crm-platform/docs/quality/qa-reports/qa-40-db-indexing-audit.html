What was found

PassEvery critical query pattern is served by an index

Critical query patterns have a serving index (19 reviewed). The register is tools/qa-suite/data/critical-queries.json. Btree indexes on tenant tables lead with org_id, so row-level security and tenant filters use them.

PassNo redundant indexes

No index is a strict prefix of another. Seven were dropped by migration 20261211110000_drop_redundant_indexes; apps/api/test/integration/db-guards.spec.ts proves they stay gone and their replacements stay in place.

Low206 of 939 foreign keys have no covering index (145 tables)

A foreign key without an index makes a delete or update of the parent row scan the child table, and slows joins by that key. This matters for tables that grow (contact timeline tables, flow logs) and rarely for small lookup tables. Largest groups: wpcampaigns 5, recurring_invoices 5, contact_notes 4, orders 4, privacy_requests 4, owner_reassign_batches 4, conversations 3, wa_calls 3. Full list in the appendix.

Weak points

MediumUnused-index and plan checks need a live database

The check that lists indexes never used since stats reset (pg_stat_user_indexes) was skipped because DATABASE_URL was not set. Without it, "unjustified" indexes cannot be identified, only "redundant" ones.

LowStatic model of the schema

Indexes come from reading the SQL migrations (including drops and renames), not from a real database. A hand-made index in production would be invisible, and so would an index that exists in a migration but failed to build.

How to finish this task

  • Keep the redundant-index check in PR checks: pnpm qa 40 -- --fail.
  • Add covering indexes for the foreign keys on tables that grow or are deleted from in bulk; baseline the small lookup tables with a reason.
  • Run with a seeded database: DATABASE_URL=… pnpm qa 40 for unused-index results; pair with task 42 (EXPLAIN plans).
