Load Testing QA Report

One task from the team sheet, handed over from Vedant: load testing, with 500 concurrent active users as the baseline. The baseline is not met on this machine. At 500 active users 20.9% of requests failed and the median took 17.8 seconds; the highest stage that stays usable is 100 users. The cause is specific and fixable: one inbox query takes 68% of all database time, and once it holds the pool of database connections every other request waits and times out.

How it was run. Six stages (50, 100, 200, 350, 500, 750 users), each ramped for 60 s and held for 120 s, on a database with 100,000 contacts, 50,000 conversations and 1,000,000 messages. Each user is a signed-in staff member doing what staff do, with 3 to 8 seconds between actions. The first attempt signed everyone in as one user and every request was refused: a user may hold only a few sessions at a time. 800 separate staff accounts were seeded and the run repeated.

One machine with four cores shared by the load generator, the API, Postgres and Redis, one API process and a pool of 20 database connections. Production likely has more of each, so the number of users it carries will be higher; the shape of the failure is what carries over. The sheet's second half, "raise from observed production demand", could not be done: there are no production figures here, so the load was raised in fixed steps.
