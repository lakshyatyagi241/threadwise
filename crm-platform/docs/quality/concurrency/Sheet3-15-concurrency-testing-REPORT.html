What is this, in plain words

A race is two things happening at the same moment on the same data. Picture one cash till and two cashiers who both look at the same "10 coins left" note, both hand out 8, and now the till is 6 coins short. Software does this when it first reads a number and then writes based on it, with a gap in between. This task proves that, for the places where the CRM touches money, logins, plan limits, messages and queues, many requests at once end in the right state, and fixes the places where they did not.

Why it matters. A race loses money (wallet, coupons), gives away paid features (plan limits), creates duplicate accounts, or double-sends messages. It does not show up in normal testing, because a person clicks one thing at a time.

Glossary

Term Meaning
Optimistic locking Each row carries a version number. An update says "I read version 3". If someone changed it meanwhile, the update is refused with 409 instead of overwriting.
Idempotency key A label a client puts on a request. Sending the same label twice must act once.
Advisory lock A named lock in Postgres. Requests with the same name wait their turn; others are not held up. It is released when the transaction ends.
Outbox A table of "things to tell other parts of the system", written in the same transaction as the change. Workers read and deliver them.
SKIP LOCKED A Postgres option so two workers reading the same queue never take the same row.
Refresh token rotation Each refresh swaps the login token for a new one; reusing an old one signals theft and ends the session.
Seed A number that fixes the random delays, so a failing run can be replayed (CONC_SEED=n).
P0 / P1 P0 = money, login, tenant isolation, data loss. P1 = other core flows.

How we tested

  1. Inventory first. The code was searched for every critical write path. Each became a scenario with an ID, a priority, the rule that must hold and the test that covers it (scenarios.json, table in the appendix). That list is the denominator of the coverage number.
  2. Parallel requests (6 to 24 at once, 700 events for the outbox) with small random delays, repeated for 5 rounds inside each test, so each round is a different interleaving.
  3. Assert the end state: exactly one winner, the rest get 409, 422 or the replayed answer; never a 5xx; no duplicate row; the wallet equals the sum of its ledger and never goes below zero.
  4. Defects: failing test first, then the smallest fix in shared code, test kept as the regression.
  5. Teeth check: the wallet row lock, the outbox SKIP LOCKED and the new plan-limit lock were removed temporarily. The wallet tests, the outbox tests and the limit tests for segments, forms, pipelines and saved replies went red; the code was restored. So these tests can detect the bug they guard against.
  6. Five full runs of every new file, a new seed each time, on the tree merged with the latest origin/main.

Findings

D-01 · The contact limit of a plan could be passed by parallel creates HIGH FIXED

What went wrong
Twelve people added contacts at the same moment on a workspace allowed 5. Every request counted the same existing rows, saw room, and inserted. All 12 were created.
Why it matters
A workspace could hold more contacts than it pays for. Plan limits are what the business charges for.
How we fixed it
One lock per workspace and limit (PlanEntitlementService.lockLimit, a Postgres advisory lock held until the transaction ends) is taken before the count in ContactQuotaService.assertCanAddOne. That one method serves the API, the inbound capture and the import. Commit 25e270ac5.
Test that proves it
api-races.e2e.spec.ts, CC-LIM-01 (failed before the fix: 12 created; passes after: exactly 5)
Not verified
The contact import running at the same time as the API was not tested (CC-LIM-07).

D-02 · The seat (user) limit could be passed by parallel invites HIGH FIXED

What went wrong
Eight invites sent at once on a plan with 3 seats all passed the seat check; the workspace ended with 9 users.
Why it matters
Free seats for the customer, lost revenue, and a plan page that shows more users than the plan allows.
How we fixed it
Same lock, taken at the start of the invite transaction in MembersService.invite. Commit 25e270ac5.
Test that proves it
api-races.e2e.spec.ts, CC-LIM-02 (failed before: 9 users; passes after: 3)
Not verified
Invitation acceptance and re-activation of an inactive member were not raced.

D-04 · Parallel sign-ups with one e-mail made several accounts HIGH FIXED

What went wrong
The rule "one e-mail, one account" was checked by a read before the account was written. Six sign-ups sent at once all passed the check and all returned 201 with six separate workspaces for one address.
Why it matters
Account confusion at login, duplicate trials, and a way around the sign-up rules. It is an authentication problem, so it is rated High.
How we fixed it
The check is repeated inside the provisioning transaction under a lock on the e-mail and the phone number (TenantDirectory.provisionOrganization, switched on by exclusiveIdentity from the three public sign-up paths). Paths that open an extra workspace for an existing person do not set it. Commit 25e270ac5.
Test that proves it
identity-races.e2e.spec.ts, CC-AUTH-01 (failed before: six 201; passes after: one 201, five 409)
Not verified
The social sign-up and the one-step OTP route use the same flag but were not raced separately.

D-05 · Every other capped create had the same unlocked count-then-insert MEDIUM FIXED

What went wrong
Segments, custom fields, saved replies, routing rules, team chat channels, pipelines, forms, lead sources, booking types, invoices per month and chatbot widgets all counted first and inserted later. Eight to nine parallel creates on a cap of 3 or 4 all succeeded (measured with the lock switched off: 9 segments, 9 forms, 8 pipelines, 9 saved replies).
Why it matters
Each could pass its plan limit under parallel requests, the same way D-01 to D-03 did.
How we fixed it
One helper. PlanUsageService.assertCanAddIn(tx, org, key) takes the lock and counts inside the inserting transaction; where a module counts for itself, a one-line lockLimit comes first. Sites: segments, custom fields (attributes and fields), saved replies (create, duplicate, import), routing rules (create, duplicate), team chat channels, pipelines, forms (create, duplicate, resume), lead sources (2), booking types, invoices, recurring invoices, chatbot widgets (3), devices, templates, catalog products, SMS senders, broadcasts, campaigns (2), appointments, scheduled messages. Commits 50e5ea788 and d9de88083. Files in other owners' zones are listed in section 10.
Test that proves it
limits-all.e2e.spec.ts, CC-LIM-08 to CC-LIM-18 (11 resources: the room is measured one by one, then the same creates are sent at once). With the lock switched off, segments, forms, pipelines and saved replies failed; the code was restored.
Not verified
Not raced one by one (fixed with the same lock, no own test): templates, recurring invoices, catalog products, SMS senders, custom fields via the fields endpoint, broadcasts, scheduled messages, campaigns, appointments, reply import (CC-LIM-06). Not behind the lock at all: tags auto-created by the contact resolver and the form submit, and the monthly invoice cap for store orders (CC-LIM-19, open, Low). The 'monthly_messages' allowance is billed, not blocked, and was left alone.

D-06 · A coupon with few uses left could be given to more buyers than allowed MEDIUM FIXED

What went wrong
The use limit was checked when the buyer previewed the price and counted only paid orders. Eight buyers placing orders at the same moment for a coupon with 3 uses left all got the discount (8 orders placed).
Why it matters
Discounts above what was planned. Money, bounded by how many buyers check out in the same moment.
How we fixed it
Deliberate deviation from the Reference product: enforces the advertised limit under concurrency. The coupons owner must confirm. When an order is placed, a per-coupon lock is taken and the order is refused (422 PAYGW_COUPON_REJECTED, "This coupon is fully used.") if paid uses plus open orders already reach max_uses. An open order (pending or awaiting approval) holds a use for 30 minutes; a failed or cancelled order frees it. The same Idempotency-Key replay is not counted against itself. Everything else about coupons is unchanged: quotes, the paid counter, per-user and first-purchase rules. Commits 2ef909ba1 and ca3aed550.
Test that proves it
coupon-limit.e2e.spec.ts, CC-CPN-03 (failed before: 8 orders placed on 3 uses; passes after: 3 placed, 5 refused), plus a failed order giving its use back and an unlimited coupon never refused
Not verified
The 30-minute hold is a choice, not Reference behaviour. A buyer who pays after 30 minutes on an order whose use was released can still push the counter above the limit. Free (zero-total) orders and add-on orders were not raced separately.

D-07 · A contact can be edited to an e-mail another contact already holds LOW INTENTIONALLY UNCHANGED

What went wrong
Found while checking CC-DATA-01. A lone edit (no race) is accepted, while creating the same contact returns the existing one.
Why it matters
Two contacts can share one address. This is not a race, so no concurrency test can close it.
How we fixed it
Intended, not changed. The Reference app does the same: its contact edit validates the e-mail as nullable|email|max:191 and stores it with no uniqueness check (reference app/Http/Controllers/ContactsController.php around lines 551 and 575; create at line 444 has the same rule). Our create returns the existing contact only because of our identity merge, which the project rules say to keep. Making edit refuse duplicates would change behaviour the port is meant to keep.
Test that proves it
identity-races.e2e.spec.ts, CC-DATA-01 only proves the race is no worse than the lone edit
Not verified
Whether the product owner wants edit to refuse duplicates was not asked.

Rollout and rollback

No staged deploy is needed. There is no migration and no new dependency. Rollback of each fix is a revert of its commit. User-visible changes: (1) a second sign-up for a taken e-mail always answers 409 AUTH_IDENTITY_EXISTS, also when it races with the first; (2) at checkout a coupon with no uses left is refused when the order is placed, not only at preview (D-06, to be confirmed by the coupons owner); (3) a create at the plan cap that used to slip through in a race now answers the normal 422 PLAN_LIMIT_REACHED. The lock is per workspace and per limit and is held only for the length of the create, so other workspaces and other limits are not slowed.

What this does NOT prove

  • Several machines. All workers ran in one process; the SQL claim of the outbox is the same on many nodes, but two real nodes were not run (CC-OBX-03).
  • Crash recovery: a worker killed mid-job (stalled job), a Redis outage during an idempotent request (CC-JOB-03, CC-IDEM-03). The shared Redis was not stopped.
  • Storage quota refusal: the quota is in observe mode, so only the counters are checked, not refusal (CC-STO-02).
  • Parallel tests for templates, recurring invoices, catalog products, SMS senders, broadcasts, scheduled messages, campaigns, appointments and reply import: they take the same lock, but no test raced them one by one (CC-LIM-06). Tags created automatically by the contact resolver and form submit, and the monthly invoice cap for store orders, are still not behind the lock (CC-LIM-19). A contact import racing the cap was not tested (CC-LIM-07).
  • That the 30-minute coupon hold (D-06) is the right product rule. It is a choice made here, and an order paid after the hold lapsed can still pass the limit.
  • Every channel's webhook signature layer under replay; only payment webhooks and the shared ingest layer were checked.
  • Load. 6 to 24 requests at once is a race detector, not a load test; production has more chances to hit a rare timing window.
  • CC-DATA-01 is weak by design: a lone edit already allows a shared e-mail (D-07), so the test only proves the race is no worse.
  • Randomness: five runs per file with five random seeds is evidence, not proof of zero flakiness.
  • The five re-run existing tests are counted as covering; others wrote them and they were not reviewed here.
