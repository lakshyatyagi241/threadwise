Phase 5 QA Report

Reports for five tasks from the team sheet: API latency benchmarking, slow endpoint detection, throughput benchmarking, spike testing, and network/bandwidth optimisation. Each report says what kind of work it is, what it covers, the tools used, what was run, what was found, and where it falls short of the sheet's target. All five are partly met. The tooling is built, tested and was run against a real Postgres, Redis and API with a realistic data volume. The numbers are real but come from one shared 4-core machine, so read them as a ranking and a trend.

What changed in how this was run. Earlier phases could not start Postgres or Redis. This phase found that both are installed in the sandbox, built pgvector 0.8 from source (the packaged 0.6 lacks a type the migrations use), ran all 440 migrations, and started the API in production mode with real secrets. A native k6 binary did the load. That is why this phase has real latency figures, not only scripts.

The most useful findings were about the product: the inbox counts (one aggregate over every conversation) is about 21 times over its budget and also decides class A and the throughput result; the contacts search is three times over; the API sent everything uncompressed (fixed here); and the web app ships close to a megabyte of JavaScript per route.

Nothing here runs on GitHub automatically: the check workflows were removed in #328 and jobs do not start on this account. The new Performance workflow is manual and has never run. k6, the API, Postgres and Redis shared four cores, with one organisation and one user and shortened phases; none of this is a production figure.

Test environment and tools

Item Detail
Machine Cloud Linux container, 4 cores, 15 GB, Node 22.22, pnpm 9.15.4. No Docker daemon. Postgres, Redis, the API, the mail sink and k6 all on this one machine.
Stack Postgres 16.15 (native, pg_stat_statements on), pgvector 0.8.0 built from source, Redis 7.0.15, the API built and run with NODE_ENV=production and generated secrets, 440 migrations applied
How it was built A scratch copy of crm-platform with the blocked libsignal package stubbed (as in Phases 3 and 4); the lockfile delta for the one new dependency (compression) was applied to the repository
Load tool k6 1.4.0 (downloaded as a release binary)
Data One organisation: 100,000 contacts, 5,000 companies, 20,000 tasks, 50,000 conversations, 1,000,000 messages, one admin user. Synthetic only
What ran 9 latency runs, 1 throughput run, 3 spike runs, API and web bandwidth, 45 Node tests for the tools, 11 vitest tests for the API changes, tsc and ESLint on the API changes, Prettier on every file touched
What did not run The manual Performance workflow; anything on a dedicated runner; Lighthouse; a worker with real jobs; the pre-pr gate
