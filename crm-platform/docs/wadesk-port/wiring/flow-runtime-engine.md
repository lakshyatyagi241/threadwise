# Wiring map: flow-runtime-engine (FLR)

Read with [the inventory entry](../inventory/flow-runtime-engine.md). `built` = in this repo and tested; `intended` = deliberately different
(reason in [parity/flow-runtime-engine.md](../parity/flow-runtime-engine.md)); `blocked:<domain>` = waits on a domain that does not exist yet;
`not built` = outside the 20 tracked features, listed so it is not lost. The inventory details 001 to 020; 021 to 071 are index rows, read from
the reference source directly.

## How a run moves

| Step              | WaDesk                                                                           | Ours                                                                                                                                                                            |
| ----------------- | -------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Decide who enters | Laravel hooks call `FlowEnrollmentService`; Node decides the keyword path itself | one door, `FlowLaunchService.start`; every path writes a `flow_runs` row with its `source`                                                                                      |
| Hold a run        | one JavaScript object in Node's memory, keyed `<sender>_<customer>`              | a row in `flow_runs` (graph snapshot, variables, visits, wait, step counter); one live run per (channel, customer) by a partial unique index                                    |
| Walk it           | recursive awaits, 1.5 s timers                                                   | one BullMQ job per step on queue `flow-run`; the job id is `flr-<org>-<run>-<step>` and the worker writes only if the run is still at that step (compare-and-set on `step_seq`) |
| Wait for a reply  | `waitingForInput` in memory                                                      | `flow_runs.wait` and `expires_at`; the inbox's inbound message resumes it                                                                                                       |
| Sleep (Delay)     | `setTimeout` inside the call stack                                               | `status = sleeping`, `resume_at`, a delayed job; the sweeper backs it up                                                                                                        |
| End               | `endFlowSession`, never marks the subscriber                                     | `completed` / `failed` / `expired` / `cancelled` with an `end_reason`; the subscriber follows                                                                                   |

## The analytics screens and what feeds them (WD-FLR-053 to 058)

Screen `/flow-runtime/analytics` (tabs Overview, Execution history, Error logs, Retry records; the state lives in the address). Reads need `flr.runs.read`, retries `flr.runs.manage`. WaDesk's "run" in the history, the errors and the retries is a `flow_subscribers` row, so those three read subscribers (a launch that failed before any run existed is listed); the Overview numbers read runs plus those launch failures.

| ------------------------- | --------------------------------------------- | -------------------------------- | -------------------------------------------------- | ----- |
| KPIs, trend, mix, board   | `GET /v2/flow-runtime/analytics`              | `FlowRuntimeService.analytics`   | `flow_runs`, `flow_subscribers`, `flow_retry_logs` | built |
| Execution history         | `GET /v2/flow-runtime/history`                | `FlowRuntimeService.history`     | `flow_subscribers`, `flows`, `contacts`            | built |

## Order events (WD-FLR-006)

The order trigger starts on three events, all read back by the order's uuid from `wa_orders` and handled as `order.placed`, so a repeat is the same enrolment (`order:<uuid>`):
`order.placed` (the commerce contract), `store.order_placed` (the storefront checkout) and `whatsapp.order.received` (a catalog cart on WhatsApp, WD-WABA-042).
Before this, the storefront emitted `store.order_placed` and nothing turned it into a flow trigger. Evidence: `flow-runtime.e2e.spec.ts` (store checkout and catalog cart, once per order).
