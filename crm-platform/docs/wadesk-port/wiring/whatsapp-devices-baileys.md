# Wiring map: whatsapp-devices-baileys (WADEV)

Read with [the inventory entry](../inventory/whatsapp-devices-baileys.md), the spec [personal-whatsapp-connect.md](../../specs/personal-whatsapp-connect.md) and
[wiring/node-bridge-runtime.md](node-bridge-runtime.md) (the runtime underneath). One row per feature: where it lives in WaDesk, what feeds it, what consumes it,
where it lands in our code. `built` = in this repo and tested (backend only: the screens are the web agent's part of BL-095 phase 1); `blocked:<id>` = waits on a
feature another domain owns or on a later phase; `intended` = deliberately different (reason in [parity/whatsapp-devices-baileys.md](../parity/whatsapp-devices-baileys.md)).

Only the personal-number (Baileys) slice of the devices domain is mapped: BL-095 phase 1. WABA and Twilio numbers, the engine chooser and the operator
device console are other rows, started when those features are.

## Upstream feeders and consumers of a `devices` row (read before changing it)

- Written by this API: `POST /v2/devices` (insert, `connection_state='created'`), `PATCH` (name, region, assignee, `active`, number), disconnect fallback, delete.
- Written by the worker (the only writer of connection state): `DeviceRuntimeService.applyStatus`, `flipStale`, `touch` (`last_seen_at`), `recordProxyResult`.
- Read by: `SenderResolver` (status + active), the dashboard devices card, the operator allow-list counts, the public `GET /v1/devices`, the warmer, the inbox bridge
  (`syncDeviceChannel`), broadcasts, campaigns, scheduled messages, flows, WooCommerce "send from".
