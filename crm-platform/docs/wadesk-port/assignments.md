# Assignments

Generated by `.claude/skills/wadesk-ownership-guard/scripts/gen_ownership.py` from `assignment-input.json`. Do not hand-edit; change the input and regenerate.

**How features are assigned.** Every feature belongs to its domain, and every domain has exactly one owner, so each `WD-<CODE>-<NNN>` in the
inventory has one owner (see `tracker/<owner>.md`, or `find_feature.py WD-...`). Domains that read and write the same tables are grouped under one person,
and each domain has exclusive directories in every layer, so the three of you do not edit the same files.

**Estimates.** `estDays` uses S=1.5, M=4, L=8, XL=15 dev-days from the inventory for domains already written, and a rough analogue-based guess for the rest
(marked `pending` or `partial`). Treat them as order-of-magnitude until the inventory is complete and the scope cut (P0 or P0+P1) is decided.

## Why these groups

- **Platform, identity, billing, admin and developer surface** (`lakshya`): Everything that defines who a user is, which workspace/plan they are on, what they pay, how admins run the platform and how outsiders integrate. Shares one data spine (users, workspaces, plans, wallet) and the kernel work (skeleton PR, web shell, operator layer), so one person owning it avoids the most cross-talk.
- **WhatsApp core, inbox and automation** (`vedant`): The WhatsApp connection engines, the Node bridge, chat, team inbox, broadcasts, campaigns, templates, auto-reply and the flow builder/runtime all read and write the same conversation, message and queue tables and share the channel core, so they must move together.
- **CRM, commerce, AI and the other channels** (`punya`): Contacts and the sales objects around them (deals, companies, tasks, proposals, invoices, appointments), the commerce stack (catalog, storefront, checkout, shop integrations), AI agents and the nine non-WhatsApp channel adapters. The channels are siblings of one adapter pattern, so one person builds them consistently once the channel core exists.
