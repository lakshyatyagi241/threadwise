# Parity: team inbox, conversations and assignment (TIB1 / TIB2, Phase 1 API)

What the Phase 1 API does differently from WaDesk, and what was not compared. Rules and routes: [docs/api/team-inbox-conversations.md](../../api/team-inbox-conversations.md).
The screens (A4) and the ingest and send pipeline (A1) have their own parity notes. **Not compared against the running reference**: the plan's
verification note applies (no signed-in reference session; behaviour here is from the WaDesk source and the inventory entries WD-TIB1-003, 004, 009,
010, 013, 017, 019, 032, 034, 038 and WD-TIB2-020 to 022). Status of every row: `intended`, pending sign-off by the domain owner.

## Intended differences

| #   | WaDesk                                                                                                                                                    | Here                                                                                                                                                     | Reason                                                                          |
| --- | --------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------- |
| 1   | Queue is a growing window (`per_page` 30, 60 ... up to 1,000) with a `sig` short-circuit                                                                  | Keyset cursor; counts in `meta.counts`; no `sig` (sockets plus a 60 second poll of `/counts`)                                                            | Architecture (cursor paging, realtime)                                          |
| 2   | Three view keys (`view_all_teams`, `view_team`, `view_assigned`) and a 403 for a thread you may not see                                                   | One read permission with scope all, team, own; **404** for a thread outside the scope                                                                    | Plan 3.7; a 403 would reveal that the thread exists                             |
| 3   | Search decrypts up to 500 rows in PHP and matches title and preview only; message text is not searchable                                                  | Trigram-indexed substring search over title, peer name, number (by digits), last message and the contact's name                                          | Plaintext bodies (decision 9); message-body search is Phase 4                   |
| 4   | Opening a thread (`GET`) clears unread as a side effect                                                                                                   | `POST .../read { upToSeq }`: a message that arrived meanwhile stays unread; the counter never goes up                                                    | A GET must not write; closes a lost-unread race                                 |
| 5   | Reply runs inside the request, answers 200 even when the send failed, stamps first response on request                                                    | `202` with the stored `queued` message; the worker sends; failures are `failed` with a Retry; refusals (window, plan, channel) before anything is stored | Plan 3.4, WD quirks 5 and 6                                                     |
| 6   | 24 hour window is shown, never enforced                                                                                                                   | Enforced at send: `SERVICE_WINDOW_CLOSED`                                                                                                                | Plan section 7 row 6                                                            |
| 7   | Resolve of a resolved thread re-runs everything; reopen fires no event; `closed` reachable only through bulk                                              | Guarded status machine (open, pending, resolved, closed; spam to open), idempotent; `conversation.reopened` is emitted                                   | WD-TIB1-034 port notes                                                          |
| 8   | Unassign clears the person only; no way to remove a team; assign to a team with no eligible member clears the person; `user_id` omitted clears the person | `userId` and `teamId` are each "leave", "clear" or "set"; both omitted is a validation error; an unchanged target is a no-op                             | WD-TIB2-020 rule 7 is a plain defect                                            |
| 9   | Strategy-driven team assignment (round robin, least loaded, sticky)                                                                                       | Manual only in Phase 1; `strategy` accepted (`manual`); every team assignment is manual                                                                  | Phase 3 (plan 5). **Blocked, not dropped**: WD-TIB2-020 strategies              |
| 10  | Assignment target only checked as a workspace member                                                                                                      | Must be an **active** member who can **open the inbox**                                                                                                  | A person who cannot open a thread cannot hold it                                |
| 11  | Note mentions parsed from text in the browser; `user_id` accepted if it is an integer; any agent deletes any note                                         | Structured user uuids, each an active member; author or `assign` holder deletes                                                                          | WD-TIB1-038 quirk 1 (cross-workspace notification) and port notes               |
| 12  | Mention and assignment notifications, push                                                                                                                | Outbox events only (`conversation.assigned`, `conversation.note_added`); no notification consumer yet                                                    | Phase 3. **Blocked, not dropped**                                               |
| 13  | Timeline written on reassign with actor type free text                                                                                                    | Five actor kinds; `payload` carries uuids; `reassigned` carries from and to                                                                              | Typed contract                                                                  |
| 14  | `agent_statuses.current_load` counter                                                                                                                     | Live count of open and pending conversations in the picker; the counter is not written                                                                   | WD-TIB2-020 rule 4 (drift)                                                      |
| 15  | Contact panel: profile, orders, past conversations                                                                                                        | Contact summary through the contacts barrel and up to 20 past conversations; orders (store domain) and custom attributes are not included                | Orders belong to the store domain; attributes are one click away on the contact |

## Not built here, recorded

Template send is built (picker, `kind: 'template'`), and the thread draws a template message as WhatsApp shows it (WD-TIB1-011): header text or a
media/location marker, the body with the values filled in, the footer, and the buttons as rows (quick reply, URL, call, copy code), from `template.preview`
(see `docs/api/team-inbox-conversations.md`). A media header shows only its kind: the file is not stored with the message. Snooze, spam, priority, labels, bulk, archive and pin routes, saved replies, saved views,
mention notifications, presence and typing, the AI takeover on human reply (nothing can attach an AI agent yet), and the sweep of expired uploads are later
phases (plan 5). The plan cap (`PLAN_LIMIT_REACHED`) is enforced by the core's dispatcher for metered channels; the simulator is never metered, so it is not
exercised by this domain's tests.
