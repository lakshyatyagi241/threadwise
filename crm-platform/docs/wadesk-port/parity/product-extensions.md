# Intended deviations from WaDesk: product extensions requested by the project owner

[PORTING_RULES.md](../PORTING_RULES.md) says features and UI do not change, and that a deviation is allowed only when documented
and approved. Everything below deviates on purpose. Each item was requested by the project owner (Lakshya) in chat on
2026-10-02; the rule text says only the human can waive a rule, in words, per case, so each entry states the words. Status:
**owner-requested, pending sign-off by the domain owner and reviewer**. Items 7, 8 and 9 (proposals and estimates, invoicing, the
tax engine) were compared side by side with the running reference on 2026-10-02: see [sales-proposals-estimates.md](sales-proposals-estimates.md)
and [sales-invoices-payments.md](sales-invoices-payments.md). The other items were not.

Standing product direction given by the owner: the product targets small businesses that want one bundled tool, so build what a
small business needs even when WaDesk does not have it, and make money and tax features country-aware.

## Segments

Owner-requested on 2026-10-02 (same status as the items above: **owner-requested, pending sign-off by the domain owner and
reviewer**). WaDesk has contact groups (static lists a person fills by hand: ported as `contact-groups`, unchanged) and nothing that
fills itself. Not compared with the reference, because the reference has no such feature. API: [../../api/segments.md](../../api/segments.md).

What it is. A **group** is a static list (manual membership). A **segment** is a saved rule, `{ name, description, color?,
visibility private|shared, owner, rules }`; membership is never stored, it is the rule evaluated against `contacts` right now. Rules are
a tree of AND/OR groups (depth 3, 50 conditions) over the same filters the contacts list has (stage, status, tags any/all/none,
groups, source, owner, consent, imported, search, created/updated/last-activity dates with relative operators, and custom properties
by type), validated strictly by `@crm/contracts` and shared with the web rule builder. One condition builder
(`contact-predicates.ts` / `contact-conditions.ts`) serves the list, the bulk actions, the export and a segment.

Differences from the existing contact features, on purpose:

| Area                    | Deviation                                                                                                                                                                                              | Why                                                                                                            |
| ----------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------- |
| Contacts filter         | `segmentId` and six date windows (`createdFrom/To`, `updatedFrom/To`, `lastActivityFrom/To`) were added to the list query, and so to every bulk action's `filter` (select all matching) and the export | The segment condition has to combine with the list's other filters, and its date operators needed the same SQL |
| Usage responses         | `GET /status-options/usage` and `GET /fields/usage` rows carry `segments`; tag, group, stage/status and property deletes put the affected segments in their audit row and event                        | A delete must not silently break a rule. It never blocks (the condition goes invalid and is flagged)           |
| Optimistic lock trigger | `segments` uses `segments_touch()` instead of `touch_row()`: identical, except that a write touching only the cached count or the usage stamp does not bump `row_version`                              | A count refresh or the worker sweep would otherwise turn the editor's next save into a 409                     |
| Visibility              | Private segments are visible to the owner and to callers holding `record.segments.update` with scope `all` (the admins); a segment that cannot be seen is 404                                          | Matches "private visible only to owner and admins" without a second admin concept                              |
| Counts                  | Cached 5 minutes, counted under a 3 second statement timeout (`countApproximate`), refreshed by a worker sweep for segments used in the last day                                                       | A segment can be any rule over millions of rows; no request waits on it                                        |

Not built (decisions for the owner): a segment as a broadcast or campaign audience (the broadcasts and campaigns owner will call

WaDesk's closed-tab push (WD-NOTIF-018 to 020, gated by `ti_pwa_enabled`) is a different, assignee-based design; this is an intended extension and WaDesk's was **not** compared in a browser.
Verified by unit tests (payload, tag, visibility rule, retry and revoke outcomes, preference defaults, queueing), integration tests against a real Postgres as the restricted role (device CRUD,
isolation between people and workspaces, the cap, the secret never returned, delivery bookkeeping, prune), web unit and render tests (card states, Push column, service worker in a sandbox).
It was not run against a real push service from a real browser by the build session unless the session report says so.

| Topic                           | WaDesk                                                            | Here                                                                                                                                              | Class    |
| ------------------------------- | ----------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------- | -------- |
| Who is pushed                   | The assignee, or every opted-in agent when the chat is unassigned | Whoever gets a bell row for the event and has `push` on for the type: the same audience and rules as the bell, never someone it would hide from   | intended |
| Control                         | A platform switch (`ti_pwa_enabled`) and a per-agent opt-in       | A per-person `push` channel per type (on only for chats, assignments, mentions), a device list with Remove, a test button, off without VAPID keys | intended |
| Keys                            | Generated in the platform settings and stored there               | `VAPID_PUBLIC_KEY`, `VAPID_PRIVATE_KEY`, `VAPID_SUBJECT` in the environment; empty = feature invisible                                            | intended |
| What it shows                   | Message text can appear                                           | Contact name and kind of event only, never message text (decision D4: it can show on a locked screen)                                             | decision |
| While the CRM is open           | n/a                                                               | No push while a tab reports visible (bell and toast cover it); the in-page desktop alert yields to push on a device where push is on              | intended |
| Revoked devices                 | Not modelled                                                      | 404, 410, 401, 403 revoke the device; ten failures in a row revoke it; revoked rows are deleted after 30 days                                     | intended |
| Preferences of a disabled event | n/a                                                               | A workspace that has an event off no longer greys the person's own switches: their choice wins, with a note on the row (fixed in the same change) | intended |

## Waiting for a reply (BL-098): a nudge for unassigned chats nobody answered, not a port

Approved by the project owner on 8 Oct 2026 (spec [realtime-notifications.md](../../specs/realtime-notifications.md) section 19; API [notifications.md](../../api/notifications.md) "Waiting for a reply").
WaDesk alerts an unassigned thread only at its first message and has no follow-up, so there is nothing to compare in a browser; this is an intended extension. Verified by unit tests (every exclusion, the episode rule,
recipients, wording, the push text and defaults, the configuration), an integration test against a real Postgres as the restricted role (the qualifying chats, each exclusion, idempotency across sweeps, a new episode after an answer,
tenant isolation, the per-person bell choice, the cap and the index), and web unit and render tests (catalogue, copy in en and ar, the preferences row, the toast and desktop text). Not run against a real browser and push service by the build session unless its report says so.

| Topic                                   | WaDesk                              | Here                                                                                                                                                             | Class    |
| --------------------------------------- | ----------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------- |
| Follow-up on an ignored unassigned chat | None (only the first-message alert) | One notification per waiting episode after N minutes (default 5, `NOTIFY_WAITING_MINUTES`), to everyone who may read and reply, through bell, toast and Web Push | intended |
| Not a reminder                          | n/a                                 | Never repeats while the chat stays unanswered; a new customer message after a human answer starts a new episode                                                  | decision |
| What counts as an answer                | n/a                                 | A human reply only (an auto-reply or bot does not); reading the chat also ends it (`unread_count`)                                                               | decision |
| Who is excluded                         | n/a                                 | Assigned (person, team or AI agent), muted, snoozed, closed, archived and group chats; groups are excluded even though the first-message alert still covers them | decision |
| What the push says                      | n/a                                 | The contact name and "Waiting for a reply", never the message; the bell and toast show the 80-character preview like a new chat                                  | decision |
| Defaults                                | n/a                                 | Bell on (owner's `new_customer_reply` toggle), pop-up on, sound off, push on (owner decision)                                                                    | decision |
| Setting N                               | n/a                                 | Environment value, not a workspace setting (nothing asked for one; it would put a settings join in the sweep)                                                    | decision |
