# Intended deviations from WaDesk: product extensions requested by the project owner

[PORTING_RULES.md](../PORTING_RULES.md) says features and UI do not change, and that a deviation is allowed only when documented
and approved. Everything below deviates on purpose. Each item was requested by the project owner (Lakshya) in chat on
2026-10-02; the rule text says only the human can waive a rule, in words, per case, so each entry states the words. Status:
**owner-requested, pending sign-off by the domain owner and reviewer**. Items 7, 8 and 9 (proposals and estimates, invoicing, the
tax engine) were compared side by side with the running reference on 2026-10-02: see [sales-proposals-estimates.md](sales-proposals-estimates.md)
and [sales-invoices-payments.md](sales-invoices-payments.md). The other items were not.

Standing product direction given by the owner: the product targets small businesses that want one bundled tool, so build what a
small business needs even when WaDesk does not have it, and make money and tax features country-aware.

## Segments

Owner-requested on 2026-10-02 (same status as the items above: **owner-requested, pending sign-off by the domain owner and
reviewer**). WaDesk has contact groups (static lists a person fills by hand: ported as `contact-groups`, unchanged) and nothing that
fills itself. Not compared with the reference, because the reference has no such feature. API: [../../api/segments.md](../../api/segments.md).

What it is. A **group** is a static list (manual membership). A **segment** is a saved rule, `{ name, description, color?,
visibility private|shared, owner, rules }`; membership is never stored, it is the rule evaluated against `contacts` right now. Rules are
a tree of AND/OR groups (depth 3, 50 conditions) over the same filters the contacts list has (stage, status, tags any/all/none,
groups, source, owner, consent, imported, search, created/updated/last-activity dates with relative operators, and custom properties
by type), validated strictly by `@crm/contracts` and shared with the web rule builder. One condition builder
(`contact-predicates.ts` / `contact-conditions.ts`) serves the list, the bulk actions, the export and a segment.

Differences from the existing contact features, on purpose:

| Area                    | Deviation                                                                                                                                                                                              | Why                                                                                                            |
| ----------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------- |
| Contacts filter         | `segmentId` and six date windows (`createdFrom/To`, `updatedFrom/To`, `lastActivityFrom/To`) were added to the list query, and so to every bulk action's `filter` (select all matching) and the export | The segment condition has to combine with the list's other filters, and its date operators needed the same SQL |
| Usage responses         | `GET /status-options/usage` and `GET /fields/usage` rows carry `segments`; tag, group, stage/status and property deletes put the affected segments in their audit row and event                        | A delete must not silently break a rule. It never blocks (the condition goes invalid and is flagged)           |
| Optimistic lock trigger | `segments` uses `segments_touch()` instead of `touch_row()`: identical, except that a write touching only the cached count or the usage stamp does not bump `row_version`                              | A count refresh or the worker sweep would otherwise turn the editor's next save into a 409                     |
| Visibility              | Private segments are visible to the owner and to callers holding `record.segments.update` with scope `all` (the admins); a segment that cannot be seen is 404                                          | Matches "private visible only to owner and admins" without a second admin concept                              |
| Counts                  | Cached 5 minutes, counted under a 3 second statement timeout (`countApproximate`), refreshed by a worker sweep for segments used in the last day                                                       | A segment can be any rule over millions of rows; no request waits on it                                        |

Not built (decisions for the owner): a segment as a broadcast or campaign audience (the broadcasts and campaigns owner will call
`SegmentsService.resolveMembers` / `countMembers`, documented in the API doc); "refresh on contact change" push updates (membership is
always computed, so there is nothing to push; only the cached counts lag by up to 5 minutes); dynamic exports or tags that keep
following the rule (tag and add-to-group are snapshots); org-timezone date boundaries (days are UTC); relative "owner is me".

| Status         | A guarded status machine over open, pending, resolved, closed, with a per-thread status route (WaDesk's resolve and reopen endpoints exist but its list view has no per-thread button), idempotent: resolving twice does nothing twice | WaDesk re-ran every side effect and counted a second resolution; the machine is shared with the web |
| Assignment     | A team can be cleared (`teamId: null`) and set without touching the person; the picker shows each person's live open-conversation count and availability                                                                               | WaDesk could not remove a team, and its stored load counter drifted                                 |
| Notes          | Mentions are structured user ids checked against the workspace's members; a note is deleted by its author or a manager                                                                                                                 | WaDesk parsed `@name` text in the browser and accepted any integer id                               |
| Thread reading | `afterSeq` gap filling and `before` paging over a per-conversation sequence; `hasMoreBefore` and `hasMoreAfter`                                                                                                                        | The reconnect and out-of-order cases WaDesk handled with a 60 second full reload                    |
| Attachments    | Upload before send with a held reference (24 hours, the uploader's, claimed by one send); a refused send gives the file back                                                                                                           | WaDesk sent the file inside the send request                                                        |

## Lead sources (the lead pipeline)

Owner-requested on 3 Oct 2026 (same status as the items above: **owner-requested, pending sign-off by the domain owner and reviewer**).
The behavioural reference is WaDesk's incoming webhook (`IncomingWebhookController::receive` and `captureLead`, `/hooks/in/{token}`): a
random token in the URL is the access control, a JSON or form body is accepted, phone, name and email are mapped from configurable paths
with a list of common names as fallback, a default country code is applied to local numbers, the contact is tagged "Lead", and the team
is notified. WaDesk has no Meta lead-ads ingestion and no source attribution; the spec is
[email-channel-and-social-leads.md](../../specs/email-channel-and-social-leads.md) (L-01 to L-12), the marketplace connectors call the same
pipeline ([marketplace-mini-apps-and-integrations.md](../../specs/marketplace-mini-apps-and-integrations.md) 6.3, 6.4). Not compared with
the running reference in a browser: the reference's incoming-webhook screen exists, but the pipeline behind a hook here has no WaDesk
counterpart for most of what it does. API and rules: [../../api/leads.md](../../api/leads.md); wiring: [../wiring/leads.md](../wiring/leads.md).

| Area                           | Deviation from the reference                                                                                                                                                                                                                                                                                       | Why                                                                                                                                                                                                             |
| ------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Tables                         | New `lead_sources`, `lead_events`, `contact_attributions`; the ported `incoming_webhooks` / `incoming_webhook_events` are left for the integrations domain's own hook inspector                                                                                                                                    | WaDesk's table keeps the token in plain text, has no idempotency key, a raw body capped at 64 KB with no retention clock, and carries a relay URL and a template-send config that belong to a different feature |
| Token                          | 256-bit token shown once, only its SHA-256 stored, rotatable, found through a SECURITY DEFINER lookup; optional shared secret in `X-Webhook-Secret`, sealed at rest                                                                                                                                                | WaDesk stored the token as text and had no rotation or secret                                                                                                                                                   |
| Door                           | Per-IP and per-token rate limits, JSON-object and form bodies only, a body cap, and one `{ ok, received }` answer that never says whether a contact existed or was created; an unknown, paused or plan-locked hook is one 404                                                                                      | WaDesk answered with the event id and had no limit                                                                                                                                                              |
| Idempotency                    | `(source, external id)` is unique; the id is a configured payload path, else a hash of the body; a repeat is acknowledged and counted, a `failed` delivery is processed again                                                                                                                                      | WaDesk stored every POST and created nothing twice only by phone                                                                                                                                                |
| Dedupe                         | Identity-first (email, then phone, then the stored normalised values), the contact is UPDATED (blanks filled, nothing curated overwritten, the other identity linked), never duplicated; an identity that belongs to another contact is not moved                                                                  | WaDesk matched by phone hash only and overwrote the name and email                                                                                                                                              |
| Leads that cannot be a contact | Stored as `needs_review` (no usable email or phone, an unreadable number, the plan's contact cap) with their payload and a reason, retried after a fix; never dropped                                                                                                                                              | WaDesk returned and forgot the payload                                                                                                                                                                          |
| Attribution                    | Append-only `contact_attributions` (platform, campaign, ad set, ad, form, source label, when): first touch, latest touch and history; `contacts.source` is filled with the platform label                                                                                                                          | WaDesk had only a free-text source                                                                                                                                                                              |
| Assignment                     | Per source: unassigned, a fixed user, or round robin over listed active users (contacts and deals had no auto-assignment); the cursor is bookkeeping and never bumps the editor's version                                                                                                                          | The spec asks for the minimum, reusing no routing engine because none exists                                                                                                                                    |
| Deal                           | Optional per source, off by default (spec open question 11): a deal with the new source value `lead_ad` (`DEAL_SOURCES`, `chk_deals_source`), in a chosen pipeline and stage, owned by the assignee; a contact that already has an open deal gets no second one; a deal that cannot be made does not undo the lead | WaDesk's webhook created no deal                                                                                                                                                                                |
| Notification                   | New type `new_lead` (the outbox consumer, deduplicated on the lead event), to the owner and extra users the source names; a test lead and a lead that needs review do not notify                                                                                                                                   | WaDesk notified the workspace's owner of the hook                                                                                                                                                               |
| Flow enrolment                 | Not built: a created lead emits the existing `contact.created` with the lead source in its payload (L-10), so a flow can react. WaDesk's per-hook "enrol this flow" is a flow-runtime decision                                                                                                                     | The flow runtime is built on another branch                                                                                                                                                                     |
| Template send, forward URL     | Not built: WaDesk's "send an approved template" and "forward to a URL" belong to the integrations domain's hook inspector, not to lead capture                                                                                                                                                                     | Same table split as above                                                                                                                                                                                       |
| Retention and audit            | Raw payloads purged by a worker sweep after 30 days by default (1 to 365 per source); opening a payload or previewing from one writes an audit row (`export`)                                                                                                                                                      | Spec L-12 and open question 9                                                                                                                                                                                   |
| Plan and permissions           | Plan feature and limit `lead_sources`; `leads.sources.read` and `leads.sources.manage` held by the Owner and Admin presets                                                                                                                                                                                         | WaDesk had no gate                                                                                                                                                                                              |

Open questions answered with the spec's recommendation or the narrowest safe choice, for the owner to confirm: 9 (30 days), 11 (deal off
until enabled), 12 (a per-source default country code; a number that cannot be read is `invalid_phone` when there is no email, and is
ignored when there is one).

## Marketplace (mini apps and integrations)

Owner-requested on 3 Oct 2026 (same status as the items above: **owner-requested, pending sign-off by the domain owner and reviewer**). WaDesk
has no marketplace: its only extension mechanism is the code-extension loader and the billing add-ons of `addons-extension-registry` (a super admin
uploads a ZIP that is unpacked and autoloaded into the one running application; add-ons are `packages` rows that grant plan features and limits).
The spec is [marketplace-mini-apps-and-integrations.md](../../specs/marketplace-mini-apps-and-integrations.md); what is built here is its phase 0
and the backend of phase 1, with the open questions answered by the spec's own recommendations: **third-party mini apps are out of process and
come later; arbitrary uploaded code is never run in the API process for tenants; the ZIP installer stays an operator-only tool for first-party
packages**. Reused from the add-ons domain: the manifest idea, the module registry (a first-party mini app is locked while its module is off) and
the entitlement service (a billing add-on that grants a plan feature unlocks an app, one that grants `installed_apps` raises the cap). Not compared
with the running reference in a browser: it has no counterpart screen. API: [../../api/marketplace.md](../../api/marketplace.md); runbook:
[../../runbooks/marketplace-publish-listing.md](../../runbooks/marketplace-publish-listing.md); wiring:
[../wiring/marketplace.md](../wiring/marketplace.md).
