# Event-loop metrics inventory

Every API, worker and web-server process exposes these from its own `GET /metrics` listener (`OBS_METRICS_PORT`, see the architecture note). Every series carries `service` (`api` | `worker` | `web`), `instance` (`<hostname>:<pid>`) and, when the process knows its release, `release` (the image tag from `OBS_RELEASE`, else `GIT_SHA` shortened, else `IMAGE_TAG`; absent when none is set). No tenant, user, contact or request id is ever a label.

Units are seconds and bytes (Prometheus convention); the engineering targets in the standard are in milliseconds, so 20 ms is `0.020`.

## The probe process (caller-side latency)

A third process, `dist/src/tools/event-loop-probe.js` (`Prober`), GETs the API from outside its event loop and exports its own series on its own `/metrics` (`service="probe"`, scrape job `crm-probe`). It is the only place the latency a caller sees is measured, because the API's own request histogram cannot see time queued behind a blocked loop.

| Series                                     | Type      | Extra labels                                                      | Meaning                                                                                   |
| ------------------------------------------ | --------- | ----------------------------------------------------------------- | ----------------------------------------------------------------------------------------- |
| `crm_probe_http_duration_seconds`          | histogram | `target`, `result` = `ok` \| `bad_status` \| `error` \| `timeout` | Time from sending the request to the end of the response body, timed by the probe process |
| `crm_probe_up`                             | gauge     | `target`                                                          | 1 if the last round got a 2xx/3xx answer, else 0                                          |
| `crm_probe_last_success_timestamp_seconds` | gauge     | `target`                                                          | Unix time of the last successful round; absent until the first success                    |

Targets come from `PROBE_TARGETS` (`name=url,name=url`, name `[a-z0-9_-]{1,32}`, http(s) only), `PROBE_INTERVAL_SECONDS` (default 10), `PROBE_TIMEOUT_SECONDS` (default 10). A round never overlaps the previous one. Labels are the configured names only, no URLs or paths. It measures from where it runs: the stack network in the Hostinger overlay, not the public ingress.

## The metrics listener guard

`OBS_METRICS_HOST` other than `127.0.0.1`/`::1`/`localhost` without `OBS_METRICS_TOKEN` makes the process refuse to open the listener and log a warning with the reason (`metricsListenerDecision`). The probe process exits 1 in that case. `OBS_METRICS_PORT` unset stays silent and off.

## Not covered, on purpose or for now

- **Webhook acknowledgement latency (#17)**: derived from `crm_http_request_duration_seconds` for the webhook route templates; no separate series.
- **Per-process OOM count (#20)**: an orchestrator signal (container restarts, exit code 137), not something a dying process can report. Use `crm_process_start_time_seconds` changes plus the orchestrator.
- **Queue job metrics come from one hook, with these limits** (`job-metrics.ts`, `JobMetricsModule` in the worker process; checked against a real BullMQ worker with `tools/event-loop-audit/verify-job-metrics.ts`, and in the booted worker module by `test/e2e/platform-infrastructure/worker-job-metrics.e2e.spec.ts`):
  - One observation per job that reaches a **final** state. BullMQ's `completed`/`failed` events do not fire for an attempt that will be retried, so failed attempts that are retried are invisible and `outcome="failed"` understates the real attempt failure rate. `crm_queue_job_retries_total` is the trace they leave: the number of extra starts of jobs that finished (a stall restart counts too, since it also raises `attemptsStarted`). A job that fails every attempt shows as one `failed` plus N-1 retries; one that keeps being retried and never finishes shows nothing yet.
  - Wait excludes the delay the producer asked for (a promoted delayed job reports `job.delay = 0`, so the original `opts.delay` is used), and is **not recorded for a job that needed a retry** (its enqueue time says nothing about queue pressure).
  - Duration is that of the final attempt.
  - Labels are the queue name and outcome only. `WorkerEventLoopBlockingWithQueueImpact` has fired from a real worker stall with 20,000 queued jobs (scrape demo). Not shown yet: any production-shaped queue load.
- **`apps/web` (Next.js server)** exports the loop, utilization, CPU, memory, GC and cgroup series, and `crm_http_request_duration_seconds` (EL-020): the route is a template derived from the URL, because Next does not tell the HTTP layer which route ran (ids become `:id`, every 404 is `unmatched`, `/_next/static` is folded, `/metrics` is not counted). It has no queue series. Like the API's, the histogram does not include time queued behind a blocked loop; the probe target `web` is the view that does.
- **Realtime series (EL-021)**, registered by `apps/api/src/realtime/realtime-metrics.ts` on the process's monitor: `crm_realtime_sockets` (gauge, API processes), `crm_realtime_connections_total{outcome}`, `crm_realtime_disconnects_total`, `crm_realtime_room_joins_total{result}`, `crm_realtime_events_published_total{type}`, `crm_realtime_rooms_published_total`, `crm_realtime_publish_failures_total{type}` and `crm_realtime_publish_duration_seconds` (the publisher's cost: sequence pipeline and emit). The publish series appear in every process that publishes (API and workers). **Added by EL-B23:** `crm_realtime_rooms` (gauge: rooms in the process's adapter map, read with the socket count) and `crm_realtime_delivery_lag_seconds` (histogram, buckets 0.05 to 120 s): each open browser tab reports, at most once a minute and not more than once per 20 s per connection, the worst time between the server stamping an event and the tab handling it (`telemetry:delivery`, validated with `realtimeDeliveryLagSchema`; the tab corrects for the clock offset it measured at the handshake from `rt.ready.serverTime`; a future stamp counts as 0). It is a client estimate, so the dashboard also draws the report rate, and it carries no user, workspace or event id. **The value is client-controlled:** any signed-in user can send any lag from 0 to 300 s once per 20 s per connection (and a reconnect starts a fresh allowance), so it can be skewed on purpose; there is no alert on it, and it should stay that way. The rooms gauge is refreshed on connect, disconnect, join and leave. **Still not measured:** Redis adapter lag by itself (the lag histogram includes it), and delivery to tabs that are closed or not reporting.

## Behaviour on bad data

- A window with no valid histogram sample publishes **nothing** for the loop series (they keep their previous value). Publishing zeros would claim a healthy loop that was too starved to be measured. The stale-timestamp alert covers a monitor that stops completing windows.
- Non-finite values are dropped by the registry. Histogram label sets are capped at 500 per series; past that they fold into an `overflow` set.
