V-02: idle session unloading, and Baileys against the Cloud API

Sheet4 task V-02 (owner Vishal). Scope agreed with the owner: the decision document, and idle unloading built behind a switch that is off by default, because no timeout has been agreed and unloading changes when a customer's message reaches the inbox.

What was built

PieceBehaviour
SwitchWA_IDLE_UNLOAD_MINUTES (default 0 = never) and WA_IDLE_WAKE_MINUTES (default 15). With 0, nothing changes: a test pins that an open number is never touched, however long it is quiet.
IdleNo message in or out for the unload time, the number open and past its first pairing, no QR showing. Any message in, send, action or group call counts as use.
UnloadThe socket is closed and its five caches emptied (V-01). The saved session and the lease stay, so no other worker takes the number and nothing logs it out. The screens still show it connected: the owning worker keeps its heartbeat, so the stale-device sweep does not mark it disconnected.
Wake for held messagesEvery wake interval the number reconnects, takes what WhatsApp delivers, and goes back to sleep after 2 minutes if nothing arrived. A message that arrives keeps it up for the whole idle time again. No "connecting" or "open" status is reported, so the device screen does not flicker; a wake that fails is an ordinary drop with the normal statuses and retries.
Wake for a sendA send, action or group call to an unloaded number wakes it and waits up to 30 s for the socket (a cold connect), not the usual 8 s.
Worker heartbeatAdds ready, unloaded and rssMb to each worker's wa:worker:* key, so production memory per open session can be read: (rssMb minus the worker's own base) divided by ready.

What unloading saves (measured) and what is not known

  • Measured (V-01, real factory, local fake endpoint): an idle, connecting session costs about 0.36 MB of RSS (0.12 MB heap). 1,000 numbers is about 360 MB of that. After sessions are ended nothing stays behind (0 caches, 0 timers per reconnect), so unload and wake cycles do not leak.
  • Not measured: a connected session with real chats. The fake endpoint never completes the WhatsApp handshake, so the signal sessions, app state and groups of a real number are not in the 0.36 MB. That is the figure the decision needs, and it needs a real linked number or the new heartbeat fields on a worker that holds real numbers.

What unloading costs

  • Inbound latency: a message sent to an unloaded number reaches the inbox at the next wake: up to the wake interval (15 min by default). With the switch on, "idle" numbers are no longer real time.
  • Assumed, not tested here: that WhatsApp holds messages for a linked device that is offline and delivers them on reconnect, and that regular short reconnects do not look unusual to WhatsApp. Both must be checked on a real test number before the switch is turned on anywhere (checklist below). A linked device that stays offline too long is unlinked by WhatsApp, so the wake interval must stay far below that.
  • Scope: the saving is the socket memory only. The device object, its lease renewal and its row stay.

Baileys against the Cloud API for high-volume workspaces

Baileys (unofficial, per number)WhatsApp Cloud API
Memory on our serversOne socket per number: 0.36 MB idle measured; connected figure unknown; grows with the number of numbersNone per number: webhooks in, HTTPS out
Cost per messageNone from WhatsAppMeta's per-message charges by category; needs the current rate card (not quoted here)
Reliability and rulesUnofficial: can be restricted or unlinked; a lost session means a new QR scan; the platform keeps the engine off unless a super admin turns it on (owner decision, 2026-10-05)Official, supported; templates and the 24-hour window apply
FeaturesPersonal-number behaviour, groupsTemplate and 24-hour-window rules for business-started messages; whether the groups a workspace uses are covered has to be checked per workspace
High volumeOne socket serialises sends; provider limits are not publishedDocumented messaging limits per number; our queues already carry the retry and rate-limit handling

Engineering input to the owner's decision. At 0.36 MB idle per number (connected: unknown), memory is not what separates the two: 1,000 numbers is a few hundred MB either way of the order measured, and unloading recovers the idle part. The deciding factors are the risk of restriction, the features needed (groups) and Meta's per-message cost. Recommendation: keep Baileys where groups or personal-number behaviour are needed and the Cloud API does not cover them and volume is modest; steer high-volume business numbers to the Cloud API for reliability; use idle unloading only for Baileys numbers that really are quiet, after the checklist below. This is a recommendation to weigh, not a measurement: the cost comparison needs Meta's current rates and the workspace's real message mix.

Checklist before turning the switch on

  1. On a real linked test number set WA_IDLE_UNLOAD_MINUTES=5, WA_IDLE_WAKE_MINUTES=2 on one worker.
  2. Wait for the unload (worker log and unloaded in wa:worker:* rises); the device screen must still say Connected.
  3. Send a message to the number from another phone while it is unloaded: record when it reaches the inbox (expected: at the next wake).
  4. Send a message from the inbox while unloaded: it must go out within a few seconds of the wake.
  5. Leave it unloaded for a day: the number must not be unlinked and no status flapping may appear in the device history.
  6. Read rssMb and ready with and without the switch for the real per-session figure, and put it in this document.
Not proven. Nothing here has run against a real WhatsApp number. The behaviour is tested with a fake socket (unload, wake, quiet reconnect, send wake, failed wake) and the unload/wake memory behaviour is the V-01 churn result. The checklist above is what proves the rest.
