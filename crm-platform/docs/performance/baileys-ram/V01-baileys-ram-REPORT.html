V-01: RAM per WhatsApp session

Sheet4 task V-01 (owner Vishal). Engine: Baileys 6.7.24, Node v24.19.0. Run 2026-10-26. All numbers come from the real BaileysSocketFactory against a local fake WhatsApp endpoint.

Verdict

Leak found and fixed. Every socket Baileys builds starts 5 cache timers that nothing stops, so an ended socket (every reconnect or restart of a device) stayed in memory. Before: 5 timers and 5 caches kept per reconnect. After: 0 and 0.

Soak (10 sessions, 430 reconnects, 15 min): RSS growth extrapolated to 12 h, upper bound of the 95% interval: before 524.0% FAIL, after 27.1% NOT PROVEN (target under 5%). A short window keeps the start-up settling in the slope, so a flat series (after: 0.33% over the window, heap 0.7 MB/h) can still extrapolate high: NOT PROVEN means only a longer run can settle it.

What this does not prove. The fake endpoint never completes the WhatsApp handshake, so every session is "connecting": this is the cost of the socket's own structures, not of a connected number with thousands of chats. A 12 h run on a real number is still needed for the sheet target; the same command does it (below). The 12 h figure here is an extrapolation from 15 minutes, not a measurement.

The fix

The factory gives each socket its own five caches (apps/api/src/infra/providers/node-bridge-runtime/ttl-cache.ts): same lifetimes as Baileys' (5 min for signal keys, device lists and call offers; 1 h for retry counters and placeholder resends), a size cap each, no timer, and end() empties them. An evicted signal key is read again from the database, so the cap costs a read, not correctness.
