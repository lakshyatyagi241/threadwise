3. What is this, in plain words

Redis is a very fast notebook that sits next to the database. The app writes short-lived notes in it (who is rate limited, which permissions a user has, a lock saying "I am sending this campaign") and it keeps the to-do list of background jobs in it (BullMQ queues). Think of a kitchen order rail: tickets go on, cooks take them off. If tickets are never taken down, or the rail is full, the kitchen stops.

In production the notebook has a fixed size (192 MB) and a rule: when it is full, refuse new notes and never throw old ones away (noeviction). That protects jobs from being lost, but it also means a full Redis refuses every new write.

Glossary
TTL: a lifetime on a key; after it Redis deletes the key. Key family: all keys with the same pattern, e.g. form:pub:ip:*. maxmemory / noeviction: the size cap and the "refuse, never delete" rule. OOM: the error "command not allowed when used memory > maxmemory". BullMQ: the job queue library. Retention: how many finished jobs are kept. MULTI: send several commands as one unit. Fail open: if the check cannot run, let the request through. Worker: a loop that takes jobs from one queue. AOF: Redis's on-disk log that survives restarts.

4. How we tested

  1. Wrote a scanner (tools/redis-audit/scan.mjs) that finds every Redis call, its TTL argument, every Lua script, every client, and every queue option.
  2. Generated inventory.json; a test fails if it is out of date.
  3. Wrote ratchet tests: no KEYS or FLUSH*, every SET has a TTL or a written reason, writes have a lifetime, Lua writes have a lifetime, keys have a prefix, queues have bounded retention and retries, no hand-made BullMQ objects, clients have a command timeout, no unbounded reads. Each has a commented allowlist that may only shrink.
  4. Started private Redis servers and ran the real classes: retention, 26,000 keys from 2,000 distinct callers in 12 families, a full server (12 MB cap), a 3 s server stall, a graceful restart and a SIGKILL.
  5. For each defect: wrote the failing test first, then the fix in shared code.
  6. Added only the missing metrics (crm_redis_*) with a test.

6. Findings

D1 Medium Fixed A lost EXPIRE could lock an address out for ever
What went wrong
The failed-API-key counters did INCR, then EXPIRE as a second command. If the second never arrived (dropped connection, timeout), the counter lived for ever. After 30 failures the address got 429 permanently.
Why it matters
A customer behind a shared address (an office) could be blocked from the API until someone deleted the key.
How we fixed it
New incrWithTtl (INCR + EXPIRE NX in one MULTI, also heals old keys with no TTL). Used at the 3 sites where a lost EXPIRE blocks someone: partner key failures, bearer key failures, the per-minute API rate counter.
Test that proves it
test/integration/redis/counter-ttl.spec.ts (failed before the fix: TTL was -1)
D2 Low Fixed Footer version counters never expired
What went wrong
auth:footer-v:<org> was INCR-ed with no lifetime: one key per workspace that ever saved a footer, forever.
Why it matters
Small (tens of bytes) but unbounded, and never freed when a workspace is deleted.
How we fixed it
30-day lifetime, longer than the 60 s the cache trusts a version, so an expired counter cannot match a cached entry.
Test
counter-ttl.spec.ts
D3 Medium Fixed Workers spin on a full Redis
What went wrong
When Redis is at its cap, BullMQ's "take next job" script is refused. BullMQ treats that as a script error and asks again at once, forever: about 900 to 1,800 error lines and 0.7 of a CPU core a second for one idle worker (2,641 lines and 2,003 ms CPU in 3 s, measured). Nothing frees memory, because trimming finished jobs needs a worker to finish a job.
Why it matters
One worker process runs up to 45 workers: log flood, CPU starvation of the other work in the process, no way to recover without an operator.
How we fixed it
guardWorkerAgainstOom on every worker (one place, same discovery as the job metrics): on the OOM error pause the worker 5 s, resume, pause again if still full. Other worker errors are still logged. Worker process only.
Test
test/unit/redis/redis-pressure.spec.ts (4 guard tests, written first) and oom-slow-restart.spec.ts (real BullMQ: 0 lines, 172 ms CPU, jobs finish 1.0 s after memory returns)
D4 Low Open 11 older INCR-then-EXPIRE sites
What
Same pattern as D1 on keys that carry a time bucket in the name (per-minute hit counters for channels, widgets, shop, FAQ-style limits) and two MFA attempt counters keyed by a random token.
Why open
A lost EXPIRE leaks one small key; it blocks nobody. They sit in other developers' modules and each has mocks to adapt. A ratchet stops new ones and lists these 11 so the list can only shrink.
D5 Medium Partly mitigated Retention can outgrow the memory cap
What
Section 5: up to about 260 MB of retained jobs against a 192 MB cap. A full Redis stops every queue and every producer (D3, section 5).
Mitigation on main
Failed-job cap lowered 2,000 to 500, and a queue guard trims at 75% and 90% of the cap.
Still open
The budget itself. Decision 1. The new crm_redis_memory_* series let you alert before the guard has to act.
D6 Low Open One Redis connection per queue
What
51 queue handles = 51 connections in every process (measured). BullMQ can share one connection for producers.
Why open
The change is in queue.module.ts, which had just been rewritten by #663. Suggested patch: build one Redis with the producer options and pass it as connection to every registerQueueAsync entry.
D7 Low Open Dev compose has no maxmemory
What
docker-compose.yml runs noeviction with no size cap; production caps at 192 MB. Memory problems are not seen until production.
Recommendation
Add '--maxmemory', '192mb' to the redis command in docker-compose.yml. Not edited here (deploy file).
D8 Low Open socket.io adapter clients have no command deadline
What
redis-io.adapter.ts builds publisher and subscriber with maxRetriesPerRequest: null and no commandTimeout. A silent Redis can hold a publish. The subscriber must not get a deadline.
Why open
Needs a decision on the publisher only; allowlisted in the ratchet with this reason.
D9 Info Open Security throttles fail open when Redis is full
What
Login rate limit, API-key failure counter, public form throttles let everything through while Redis refuses writes (measured). The code comments choose this on purpose.
Why it matters
A full Redis also removes brute-force protection. Another reason for the memory alert.
D10 Info Open History-import tally is read in full per batch
What
SMEMBERS and HGETALL of a run's chat tally every batch: O(chats). Bounded by the run's max_chats and a 3-day TTL, and its expire is set after each batch (a crash between leaves it until the next batch).
D11 Info Open One durable key
What
auth:epoch has no TTL by design (explained in code); allowlisted.
D12 Info Open Queue producers may answer an OOM as a plain error
What
queue.add on a full server rejects with the raw OOM error. Whether the HTTP layer maps it to a 503 (the dependency-outage handling from #663) was not verified here.

7. Rollout and rollback

Not a staged deploy: no schema change, no new dependency. The one behaviour change is that counters now use MULTI/EXEC (needs Redis 7 for EXPIRE ... NX, which the compose files pin and the existing code already used). Rollback: revert the commit; leftover keys are harmless and expire.

8. What this does NOT prove

  • The scan is textual. Key families are templates found in files that use Redis; which key a write touches is known per file, not per key. Value sizes are heuristics except where measured.
  • Only classes that need nothing but a Redis client were driven under load (12 families, 26,000 keys). The other families are checked statically.
  • Servers were Redis 7 on a laptop, 12 MB and 64 MB caps. Production is 192 MB on a shared host; absolute numbers (error rate, CPU) will differ.
  • Power loss or host crash with appendfsync everysec (up to about 1 s of writes) was not tested.
  • Whether a running job's completion is refused at the exact cap varies by a few KB and is not asserted.
  • Per-job bytes use a 0.5 KB payload and a short error; real jobs and stack traces are bigger.
  • Connection count for the worker process is computed from measured per-item numbers, not measured on a booted worker.
  • Redis Cluster / Sentinel behaviour, TLS, and network faults (silent, refused, reset) are not covered; the last is item 18 part 2.
  • Item #65 cache hit rate is not covered. The hit and miss path of each cache was not load-tested for latency.
  • The HTTP status an API client sees on a full Redis (D12) was not tested.
