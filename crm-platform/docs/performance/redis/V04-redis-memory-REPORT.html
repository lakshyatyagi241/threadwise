V-04: Redis memory audit

Sheet4 V-04 (owner Vishal). Run 2026-10-26 on a private 7.4.11 with the dev settings (AOF on, noeviction), the built API and worker, a ramp of 5 and 10 users.

Verdict

  • TTL or named owner: met for every key seen. 118 keys in 17 families; 56 expire, 62 never do, and every one of those belongs to a named owner (BullMQ job state, the worker heartbeat). 0 unowned.
  • Eviction policy: noeviction everywhere (dev compose; prod compose 192 MB; Hostinger 448 MB). Right for a server that holds BullMQ state: evicting a queue key loses the job. The risk it leaves is a full Redis refusing writes, which is what the TTL coverage and the per-queue retention limits are for (docs/performance/redis/measurements.json: OOM behaviour measured in item 67).
  • used_memory baseline: 3.60 MB after the run (peak 11.88 MB; an empty server is 1.04 MB). Key data is 50576 bytes; the rest is server overhead and the append-only buffer.
  • Valkey 8.1.10 vs Redis 7.4.11: the same 1180 keys use -5.1% memory on Valkey (0.70 MB vs 0.73 MB); an empty Valkey is 0.97 MB vs 1.04 MB. Drop-in for the commands this code uses, but this is one small data set, so it does not by itself justify a switch.
What this does not prove. The workload is a read ramp, so only 17 key families were created, of the 156 the code can write (the static inventory). The other families are covered by the static check (every write in 137 families has a TTL) and by the synthetic key-hygiene spec (12 families, 26,000 keys, 0 without a TTL), not by this run. The Valkey figure is from 118 keys copied 10 times (about 0.73 MB): per-key overhead, not a production data set. Production figures would need live.mjs run read-only against a production replica.
