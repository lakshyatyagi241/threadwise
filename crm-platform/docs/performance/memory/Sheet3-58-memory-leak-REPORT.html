2. What this is, in plain words

A memory leak is a server that slowly eats more memory the longer it runs, until it is killed. You only see it by running for a long time under steady traffic and watching the line. The harness starts the API and the worker, sends a steady mix of requests, and every 10 seconds writes down memory. Every minute it forces a garbage collection, so what remains is memory that is really held, not memory that is just not yet cleaned. It then draws a straight line through the samples after warm-up and says how many MB per hour that line climbs, with a 95% confidence range.

3. How we tested

  • API (dist/src/main.js) and worker (dist/src/worker.js) as built on this branch, each as its own Node process started with --expose-gc, inspector off. A small preload, tools/perf/soak-probe.cjs, answers the harness over IPC (memory, GC, handles, event loop lag, optional heap snapshot). It is script-only and is not imported by any production code.
  • Own throwaway database crm_soak_mem (migrated and seeded, dropped at the end), Redis db index 13 on the shared container.
  • Workload, about 15 requests/s: contact and company list reads, a search, contact create (POST with idempotency key), a webhook-like public POST, a login, and a socket.io connect/disconnect on /realtime. Contact creates also feed the outbox and queue jobs the worker handles.
  • Sampled every 10 s; GC forced every 60 s; warm-up 3 minutes excluded from the fit. Fitted: RSS (all samples), heap used, external, handles, Redis clients, Postgres connections (post-GC samples).

Noise: three other agents were running on the same machine and Postgres/Redis are shared. Absolute numbers (RSS around 906 MB for the API is large because of dev build, 3,000 source files loaded) are not meaningful; the slope after warm-up is the signal.

6. What this does NOT prove

  • It does not meet the sheet target: no 24 hour run was done, so slow leaks (a few MB per hour) and daily cycles (cron jobs, token expiry, log rotation) are untested.
  • 12 minutes and a shared, noisy machine. The "flagged" slopes come from tiny absolute changes and are inconclusive in both directions.
  • Only a dev-mode build against an empty seeded database; production data volumes, real provider webhooks, long-lived realtime sockets and the web app (Next.js) were not exercised. Only the paths in the workload list ran; most of the 600 source files that use in-process Maps and Sets were not hit.
  • Heap snapshots/constructor diff not run on a real heap. The workflow file was not run (GitHub Actions cannot start here) and its CI service setup (the crm_app_user role) is untested.
  • A leak of the kind "grows only under a particular endpoint" needs that endpoint added to the workload (ops list in soak.mjs).

7. How to run

pnpm --filter @crm/api build
# own database, migrated and seeded (never the shared dev database)
docker exec crm-platform-postgres psql -U crm -d postgres -c "CREATE DATABASE crm_soak_mem OWNER crm"
MIGRATION_DATABASE_URL=postgres://crm:crm@localhost:5432/crm_soak_mem pnpm db:migrate
MIGRATION_DATABASE_URL=postgres://crm:crm@localhost:5432/crm_soak_mem pnpm db:seed
node tools/perf/soak.mjs --minutes 60              # 1 h
node tools/perf/soak.mjs --minutes 1440 --warmup 30 # 24 h, quiet machine
# options: --interval 10 --gc-every 6 --rate 15 --threshold-mb-h 10 --no-worker --snapshots --out DIR

Environment: SOAK_DATABASE (default crm_soak_mem), SOAK_REDIS_DB (default 13). Output: soak.csv, soak.json in --out (default perf/results/soak). Exit 0 = no sustained growth, 1 = growth or a process died, 2 = harness error. For a 24 h run use a threshold you can defend (the default 10 MB/h over 24 h is 240 MB) and look at the CSV, not only the verdict.
