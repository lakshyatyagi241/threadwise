Why RSS is so much larger than the heap. RSS counts everything the process holds in RAM, not only the JavaScript heap. The gap is code memory (V8 compiled code, loaded source text), native modules, Node itself and allocator slack. See section 5.

2. What this is, in plain words

A memory baseline is "how much memory does the server use when it is healthy". Percentiles describe the spread: p50 is the typical sample, p95 means 95 out of 100 samples were at or below it, p99 is the near-worst case. A regression budget is a ceiling per number, set a bit above the baseline; a later run that exceeds it fails, so a change that suddenly costs 150 MB more per process is caught before release.

3. How we tested

  • Built dist of the API and worker, started by the soak harness from PR #737 (tools/perf/soak.mjs, extended with --profile), each as its own Node process with --expose-gc. NODE_ENV=production booted locally once throwaway JWT and encryption secrets were supplied and the channel simulator was switched off (the schema refuses the dev placeholders in production).
  • Throwaway database crm_mem57 (migrated, seeded, dropped at the end), shared Redis db index 10, API port 3923, worker 3924. Same mixed workload as #58 (about 15 requests/s: list reads, search, contact create, webhook POST, login, socket connect).
  • Boot sample right after the server listened (after a forced GC), then 5 minutes in total with a 2 minute warm-up, one sample every 5 s, forced GC every 6th sample. p50/p95/p99 are computed over the samples after warm-up (RSS from all samples, heapUsed from the non-GC samples because the forced-GC ones are floor values).
  • Per-endpoint cost: after the load stopped, for each endpoint the harness forced a GC, made 100 sequential calls, forced a GC and took the heapUsed difference.
  • Heap snapshots (v8.writeHeapSnapshot via the probe) in a separate 7 minute run, at boot and after warm-up for both processes, summarised by analyzeSnapshot (self size by V8 node type and constructor).

Noise: other agents were running on the same 12-core machine and Postgres/Redis are shared (load average 24.6, 20.8, 13.7 at the end of the run). The load window is only 36 samples. Treat absolute numbers as +/- 10% and read the percentiles, not single samples.

So RSS numbers in this section's run are inflated; the clean percentiles in section 4 come from a run without snapshots. Heap sizes were not affected (post-GC heap 233 to 235 MB in both).

Why the earlier reports saw 906 MB RSS and 233 MB heap

The #58 report ran a dev build (NODE_ENV unset) and saw RSS about 906 MB. This clean production-mode profile of the same dist shows: RSS p50 432.6 MB, heapUsed 264.2 MB. The difference between RSS and heapUsed is 168.4 MB that is not live JS objects: 4.9 MB external, 64 MB of committed-but-unused heap, and the rest is code, native libraries, thread stacks and allocator slack.

Measured on the API at boot, production mode (preload, require.cache): 5881 CommonJS files loaded, 37.7 MB of source on disk (app dist 2906 files, 20.3 MB). Top packages by loaded source size:

  • (apps/api dist): 2906 files, 20.26 MB
  • (workspace pkgs/other): 694 files, 4.09 MB
  • bullmq: 151 files, 1.08 MB
  • @sentry/server-utils: 217 files, 0.71 MB
  • @node-rs/argon2-linux-x64-gnu: 2 files, 0.69 MB
  • imapflow: 56 files, 0.66 MB
  • nodemailer: 38 files, 0.62 MB
  • @sentry/core: 209 files, 0.59 MB
  • @sentry/server-runtime-injection: 46 files, 0.53 MB
  • @sentry/conventions: 2 files, 0.51 MB

dist is not bundled: Node loads each compiled file from disk, parses it, and keeps the function code and source strings alive. The "string" and "code" node types in the snapshot above are that cost.

Ranked savings opportunities (recommendations only, nothing refactored here)

  1. Lazy-load rarely used modules. Most of the 2906 compiled app files are loaded at boot even though the 15 req/s workload touches a small fraction. Nest lazy modules / dynamic import() for provider adapters (WhatsApp, Telegram, Facebook, LINE, Viber, WeChat, payment gateways) and the AI studio. Expected saving: proportional to loaded source; measure with the boot sample before and after. Not measured here.
  2. Bundle the API for production (esbuild/swc bundle, minify, tree-shake) instead of 5881 loose files. Cuts file parsing and source-string retention; typical saving 15-30% of boot RSS for large Nest apps. Not measured here (would need a build change).
  3. Deduplicate dependency versions. The package list above shows which packages ship large sources; check for duplicate majors with pnpm why / pnpm dedupe --check. Not measured.
  4. Large static tables (locale data, permission catalogs, country/timezone lists) held as JS objects: move to lazy JSON loaded on first use. Check the "array" and "object" rows in the constructor chart for candidates.
  5. Tune V8 for containers: set --max-old-space-size to the container limit and consider --max-semi-space-size; stops heapTotal growing past what the pod can hold. Safe, config only.

8. What this does NOT prove

  • No 24 h or even 1 h run; the percentiles describe a 5 minute window of a synthetic workload, not real traffic. Leak detection is item #58.
  • Tiny seeded database: list, export and import-preview costs at production row counts are not measured.
  • The workflow file was never executed on GitHub; it mirrors soak.yml and generates throwaway production secrets per run, but untested YAML can still have a mistake.
  • Savings in section 5 are estimates or unmeasured, except where a number is shown.
  • The web app (Next.js), Redis and Postgres memory were not profiled.
