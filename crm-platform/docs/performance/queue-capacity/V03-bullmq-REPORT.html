V-03: BullMQ memory, payloads and concurrency

Sheet4 V-03 (owner Vishal). Target: worker RSS and Redis memory down 20%. Measured on the real BullMQ 4 variants against a private Redis 7.4.11: 12,000 ids-only jobs completed and 800 failed per variant, bytes by MEMORY USAGE (exact).

Verdict

  • Changed: the event stream of every queue is capped at 100 entries (BullMQ keeps 10,000). Nothing in this code base reads it (no QueueEvents). One busy queue: 2798 KB to 2268 KB, -18.9%. No behaviour change.
  • Short of the 20% target on its own (-18.9%). Not done, owner decision: keep 100 completed jobs per queue instead of 1,000 (removeOnComplete.count): -51.1% together with the cap. It shortens the "what finished in the last hour" view of every queue on the defaults, which queues.ts says is the point of the 1,000, so it is not made here.
  • Worst case against the Redis limit: 51 queues, all full, hold about 139 MB today against 192 MB of maxmemory (113 MB with the cap, 68 MB with both). Real queues are rarely all full; noeviction means a full Redis refuses writes, not that it drops keys.
  • Concurrency is oversubscribed against the DB pool. The worker runs 173 job slots; 55 are database-bound queues, and production sets DB_POOL_MAX to 10 (deploy/hostinger/docker-compose.yml; default 20). Up to 55 jobs can wait on 10 connections. Not changed: no real processor has been benchmarked (see worker-concurrency-recommendations.md), and lowering a queue's concurrency without that can slow ingest.
  • Payloads: most producers already pass ids (message send is {orgId, messageUuid, generation}; campaign and broadcast runs pass ids; the inbound queues drop completed jobs). The ones that carry bodies are listed below; none is changed here.
What this does not prove. The 19% is for ids-only jobs on one Redis: larger payloads make the stream a smaller share, so the saving is a floor per queue, not a measure of production. Worker RSS was not measured: the job-slot count and payload size bear on it, but no processor was run here. Real queue fill rates need production metrics (crm_queue_job_duration_seconds, Redis used_memory per queue prefix).
