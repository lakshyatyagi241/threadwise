V-05: image size and container limits

Sheet4 V-05 (owner Vishal). Targets: image size down 30%; CPU and memory limits on 100% of services. Host: 4 cores (given by the owner; the repo did not record it). Run 2026-10-27 on a laptop, images built with the repo's Dockerfiles, containers run with the limits that deploy/hostinger/docker-compose.yml ships.

Verdict

  • API/worker image: 813 MB to 479 MB, -41% (as docker image ls lists it); compressed layers (what a release ships) 154 MB to 97 MB, -37%. Target met.
  • Web image: 856 MB to 820 MB, -4%. Target not met. The image is already the traced standalone server (an earlier build shipped about 3 GB). Of the 820 MB, 333 MB is Next's route bundles under .next/server, which come from the app's build, not from packaging.
  • Limits: every service in the deployed compose files now has a memory, CPU and PID limit (10 services in docker-compose.yml, plus the 6 in redis-cache.compose.yml and observability.compose.yml). The resource-limits check passes with the two accepted gaps (RL-01, RL-02) and one stale gap removed. That check reads the main file only; the other two files are not covered by it.
  • Measured, not guessed: the API, worker and web ran as containers with their limits under load. No OOM kill; memory peak 27%, 33% and 50% of the limits; PIDs 19, 19 and 18 of 512; no limit was the bottleneck. Two limits were changed because of it (below).

The one-shot migrate job has no limits (the check covers long-running services only). The caps add up to more than 4 cores on purpose: they are ceilings per container, the second slot of a blue/green pair is idle outside a release, and the host is shared. Docker refuses a cpus value above the host's core count, so no value exceeds 4.

The CPU cap test (why web and API got 2)

Web, 600 requests, 8 at a timeTotal/login p50 / p95Periods throttled
cap 114.4 s215 / 555 ms196 of 225 (87%)
cap 26.9 s125 / 401 ms32 of 131 (24%)
cap 45.3 s116 / 160 ms3 of 111 (3%)

A 1 core cap would have doubled the time a web slot needs under load; the first draft of the limits had 1. The API gave the same requests per second with a 1.5 and a 2 core cap (about 100) and similar p95, so its cap is not the bottleneck either way: Node's single event loop is. The 2 leaves room for bursts (11 to 15% of periods were throttled at saturation with 2; 20% with 1.5).

What this does not prove. One laptop, one run per case, a 40,000 message scratch database and no real WhatsApp numbers: Baileys sockets add memory and PIDs that were not exercised (V-01 measured 0.36 MB per idle session). The worker ran with idle queues. Postgres, redis, backup, offsite, api-hooks and the observability services were not run under their limits; their numbers are reasoned from their configuration and should be watched after a release (deploy/observability/resource-limits.rules.yml alerts on memory, OOM and PIDs). The 4 core figure comes from the owner and is not read from the host. The local Docker has no BuildKit, so the images were built with the Dockerfiles' --mount cache lines taken out (same steps otherwise); CI with BuildKit builds the files as committed, and their prune and package-load checks run in the same step.

Found on the way, not changed

  • The web container logs at start: "[Sentry] Failed to register diagnostics-channel injection hooks (Cannot find module '.../@sentry/core/build/esm/index.js')". It also happens on the image before this change. Channel-based Sentry integrations do not record spans in the web server until it is fixed.
  • The root cause of the build tools in the API image is pnpm auto-installing the peers of @sentry/bundler-plugins. Preventing the install (a peerDependencyRules or override) would also shrink the install and the CI cache; this change prunes after the install because it is contained in the Dockerfile.
