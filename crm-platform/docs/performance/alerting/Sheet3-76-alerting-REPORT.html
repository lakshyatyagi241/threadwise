2. What this is, in plain words

An alert is a smoke detector: it must sound when there is a fire, stay quiet when there is none, and the sound must tell the person what to do. "Mapped to an actionable alert and runbook" means: for each way production can fail badly, there is a rule that notices it, and a short page that says what it means, how to check, how to fix and who to call. The risk is a detector that was never tested: it can be wired to a metric name that does not exist and stay silent forever. So each new alert was tested twice, once with fake numbers and once by really breaking something.

Glossary
Pending: the condition is true, the alert waits for its for: time. Firing: it has been true long enough, Alertmanager is told. promtool: Prometheus's rule checker and tester. Runbook: the page the alert links to. Gap: a failure mode with no metric to alert on.

3. How it was tested

  1. Inventory. 31 failure modes (28 P0) from the existing 4 rule files, the runbooks, the metrics matrix of #75 and the metrics the code really exports. Each is mapped to alert names, severity, runbook and test status in docs/performance/alerting/failure-modes.json.
  2. Gaps filled. New file deploy/observability/p0-failure-modes.rules.yml (8 alerts, each with severity, for, summary, description and a runbook annotation), mounted in prometheus.yml and observability.compose.yml with one line each. Runbook: docs/runbooks/p0-failure-modes.md. Existing rule files were not touched.
  3. promtool (image prom/prometheus:v2.55.0): check rules passes; p0-failure-modes.rules.test.yml has a must-fire and a must-not-fire case for each of the 8 alerts, including the exact annotations.
  4. Live test (tools/alerting/live-test.mjs). My own API (port 3921), worker and probe processes; my own Redis container with an 8 MB limit; a throwaway database alerting76_t1 reached only through a TCP proxy I control; my own Prometheus (59191) and Alertmanager (59193) containers; a tiny local webhook receiver (59194). The rules were a copy of the repo rules with every for: shortened to 20 s and the scrape interval 5 s, so each case takes seconds instead of minutes. The repo files were not changed for the test. One failure at a time: kill the worker, aim the probe at a dead port, kill the API, fill Redis to maxmemory, stop Redis, insert a dead outbox row, hold a due outbox row under a row lock, insert a 2-hour-old failed operation, make Postgres accept connections but never answer (pool max 2, 8 callers), make Postgres refuse connections (callers hit /ready).
  5. Alertmanager. amtool check-config passes on the repo config. amtool config routes test on a test copy whose critical child route has its own receiver sends severity=critical to that receiver and severity=warning to default, so the matcher works. Delivery to the local webhook receiver was NOT verified: in two attempts (inside the live run, and alone with tools/alerting/webhook-delivery-check.mjs) the private Alertmanager accepted the alert but the receiver got nothing within 40 s, and I ran out of time before finding why. The first attempt also had a config bug (only the commented line of the destination was swapped), fixed for the second; the second still failed.
  6. Ratchet. tools/alerting/check-alert-runbooks.mjs fails when an alert is missing from the matrix, a matrix alert is in no rules file, a new-file alert has no runbook annotation, a runbook file or #anchor does not exist, a "tested" mode has no promtool case or live result, or a gap names no metric. check-alert-runbooks.test.mjs proves it fails on 7 bad examples.

7. What this does NOT prove

  • Thresholds are guesses, not tuned on production traffic. No production alert has ever fired from these rules.
  • Alertmanager to receiver delivery was not demonstrated at all (not even to the local webhook), so the runbook link reaching a notification is unproven. Real Slack or PagerDuty was not tried.
  • Cannot be induced on a laptop: disk full, certificate expiry, replica lag (no replica), container memory limit kills (no cgroup limits here), a real failed release, Prometheus or Alertmanager dying. They are covered by promtool only or are gaps.
  • DeadLetterCaptureFailing and ContainerOom* were not induced live. 3 modes have no test at all.
  • The live cases used shortened for: durations, so the measured Firing time is not the production time (the table shows the estimate).
  • Single run per case; no repetition for variance.
  • The runbook wording was not exercised by an on-call person.
