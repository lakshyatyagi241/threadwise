What is this, in plain words

The four golden signals are the four questions you ask of any service: how long does it take (latency), how much is it doing (traffic), how often does it fail (errors), how full is it (saturation). A restaurant analogy: waiting time at the table, covers per hour, dishes sent back, and how many tables are taken. We checked every service for all four, and added the "how full" gauges that were missing for the database connection pool and the outbox (the to-do list of events waiting to be delivered).

How it was tested

  1. Read the metric definitions in packages/observability/src, the API observability modules, the web runtime monitor and the realtime metrics, and listed every metric name per service in golden-signals.json.
  2. Built the API and booted the worker locally (private Redis db 15, port 19475) and fetched /metrics: 24 metric families, including the new ones (see appendix).
  3. Unit test golden-signals.spec.ts: the ratchet fails if a signal marked present lists a metric name that is not in the code, or a missing/n-a cell has no reason; and the new gauges are written then read back from the exposition text.
  4. Type check of the API.

What this does NOT prove

  • Nothing was scraped by Prometheus or shown in Grafana (another agent owns deploy/observability/).
  • The API process was not booted, so the API-side series (service="api" pool gauges, HTTP histogram under load) were not read live. The pool code is shared with the worker, where it was.
  • The worker run was idle: pool total and idle read 0 and the outbox was empty, so non-zero values are only proven by the unit test, not by load.
  • Pool values are the client's view (this process), not the server's max_connections.
  • No overhead benchmark; the cost is one timer per process every 10 s and four property reads.
