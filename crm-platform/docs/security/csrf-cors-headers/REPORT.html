1. How the product defends against CSRF (what I verified)

  • The API is bearer-only. A login is the Authorization header, never a cookie, so a forged cross-site request has no credential to ride on. A test now fails if any API file starts reading a request cookie outside a reviewed list (only the public chat widget's anonymous visitor id does).
  • The web app holds the cookie (httpOnly, SameSite=Lax, Secure in production) and forwards calls to the API through /api/v2/* and /api/platform/*. Those proxies refuse a cross-site write with isSameOrigin before anything is sent upstream.
  • Every route handler that can change state was listed and checked: the auth routes, impersonation stop, the public forms / invoices / sales-docs / consent / appointments proxies, the storefront forms, and the two proxies. Two have no guard on purpose (section 4). A test now fails when a new writer is added without a guard.

4. Reviewed and left as they are

  • GET/POST /logout ends a session without a same-origin check, as Reference did. A forged call can only sign someone out. Listed in the route test with this reason.
  • POST /webhooks/storefront-pay is called by Razorpay server to server; the API verifies the signature and no cookie is involved.
  • GET /impersonate?code= needs a one-time secret code from an operator, so it cannot be forged cross-site.
  • The chat widget visitor cookie is SameSite=None on secure connections by design (it must work inside customers' pages) and carries an anonymous id only.

5. Open decisions

  • Script CSP for the web app (finding 4). The right fix is a nonce-based policy rolled out in Report-Only mode first, because Next.js inline scripts, the embedded sign-up popups and the Shopify and widget embeds can all break. It is not safe to add blindly, so it is not in this change. Overlaps with item 31 (XSS).
  • Cross-Origin-Opener-Policy was not added: the WhatsApp embedded sign-up and OAuth popups may depend on window.opener.

6. Limits of this test

  • The headers and CORS tests run a small Nest app with the product's real middleware and options, not the full app with its database. The real boot sequence in main.ts is covered only through the shared options and the middleware.
  • Next.js response headers (next.config.ts) were changed but not asserted over HTTP in this run, because that needs a built web server. The Permissions-Policy value is the same string as the API's.
  • Browser behaviour for Sec-Fetch-Site is taken from the specification; no browser matrix was run (that is item 19).
