What is this, in plain words

Fuzzing means feeding a program a huge number of strange, broken and hostile inputs and watching for anything it should never do. Think of a locksmith testing a new door lock. A person tries the right key and a few wrong ones. A fuzzer is a machine that tries a million odd things in a row: bent keys, a key pushed in upside down, a key of ten metres. It does not need to know how the lock works. It only needs to know what must never happen: the door opens for the wrong key, the lock jams, or the lock breaks and the building stops.

Here the "lock" is every place where the CRM takes text from outside: web forms, query strings, webhooks from other services, uploaded files, e-mail, and inbound messages. The "things that must never happen" (we call them invariants) are: the program crashes or answers 500 instead of a clean refusal; it freezes on one input; a fake signature is accepted; a web address pointing at an internal machine is accepted; a sanitiser lets a script through.

Why this matters. One 500 on a public route pages the on-call engineer. One input that freezes the server for 20 seconds can be sent again and again by anyone. A guard that wrongly accepts an internal address lets an attacker make our server read things it should not.

Glossary

TermMeaning
SeedA number that fixes the random choices. The same seed gives exactly the same inputs, so any failure can be replayed.
InvariantA rule that must always hold, for example "never answer 500 to a bad request".
ShrinkerA helper that takes a failing input (maybe 3 MB) and removes parts until the smallest input that still fails is left.
Schema (Zod)A written description of what a request must look like. The server checks every request against it.
ReDoS / quadratic regexA text pattern that gets very slow on a long, crafted input. Double the length, four times the time.
SSRFTricking our server into calling an internal address (for example the cloud metadata service) for the attacker.
SanitiserCode that cleans HTML so it cannot run scripts in a browser.
NULThe invisible character with code 0. The database cannot store it, so it turns into an error.
OracleAn independent way to know the right answer, used to check the code under test.
Prototype pollutionAn input that quietly changes the base object every JavaScript object inherits from.

How we tested

Method, step by step

  1. Generate. gen.ts (no new dependency, sfc32 random generator). Every input is a pure function of (seed, target, iteration). It makes empty, huge (to 300 KB), NUL, control, right-to-left, emoji, lone-surrogate and mojibake text; several hundred SQL, NoSQL, template, command, path-traversal, SSRF, XSS and CRLF payloads (then mutated); about 45 slow-regex shapes; number edge cases (NaN, -0, 2^53, 2^63, 1e21, negatives, floats); type confusion (array, object, null where a string belongs); JSON with __proto__, constructor, toString as own keys and chains nested up to 30,000 deep; and a "perturb" mode that damages 1 to 3 places of a valid sample, so a request that is almost right reaches the deeper checks.
  2. Run each input through the target and count it. Schemas run through ZodValidationPipe, the real entry of the request path.
  3. Check four things: an unexpected throw (anything except the target's own validation error); a broken invariant; a slow input (budget 1 s, measured twice so one garbage-collection pause does not count); a changed shared prototype (the engine puts it back and goes on).
  4. Shrink each failure to a minimal input (greedy delta-debugging over strings, arrays and objects).
  5. Run with tools/quality/fuzz.mjs (pnpm fuzz, pnpm fuzz:ci): 4 shards in parallel (inputs do not depend on the split), HTTP phase alongside, exit code 1 on a failure, a hang, a crashed shard, or fewer than 1,000,000 pure inputs.
  6. Profiles. ci: 20,000 inputs, fixed seed, inside pnpm test (time budgets x8 so a loaded machine does not flake). full: 1.3 million inputs, new seed each time, plus 9,000 HTTP requests. Manual workflow: .github/workflows/fuzz.yml.
  7. Independent oracles. Address rules are checked against Node's BlockList (IPv4) and an eight-group IPv6 expansion written separately from blocked-address.ts. Links and paths are judged by what a WHATWG URL parse does (what a browser does). HTML output is scanned for forbidden tags, event handlers and URL schemes after the entity and whitespace handling a browser applies. Signatures are tested with a forged and a genuine pair.
  8. HTTP phase. The whole Nest app runs in-process on its own throwaway Postgres 16 and Redis (the e2e harness starts and removes them; the shared containers were not touched), with installBodyLimits as in main.ts. Requests: hostile paths, queries (nesting, 1,200 parameters, bad percent escapes), JSON (perturbed samples, 12,000 deep, NUL, __proto__, invalid UTF-8), wrong content types, with the admin token, a garbage token and none. Checks: no 5xx, no stack trace in the body, an answer within 15 s, no unhandled rejection. Network access is shut inside the test process (DNS answers only for localhost; a connection to a non-loopback host is refused and counted).
  9. fast-check was not added. It brings a dependency, a replay model that is a path through a run rather than an input index, and generators I would still have to write for the hostile text classes. About 900 lines of generator and engine give per-input replay and an exact count. Cost: only simple shrinking, no stateful or model-based testing.

Findings

Sorted by severity, then status. All 17 fixed defects are first, then the 3 open items. Every fixed defect has a block of the same name (F-xx) in apps/api/test/unit/security/fuzz-regressions.spec.ts (F-12 also has a test in problem-exception-filter.spec.ts).

F-09 - A mail with many unclosed tags froze the mail worker HIGH FIXED

What went wrong
sanitizeEmailHtml: 1 MB of unclosed <div> took 19.8 s of synchronous CPU (200 KB: 0.3 s). The default MAIL_HTML_INPUT_MAX_CHARS is 1,000,000. The rich-text sanitiser has the same shape (200 KB of <: 1.2 s).
Why it matters
One inbound email from anyone blocks the mail-ingest worker for 20 s; repeat it to keep the worker down.
How we fixed it
Input is cut at 20,000 < (shared common/html-limits.ts) in both sanitisers. A mail with more tags is truncated and flagged.
Test
fuzz-regressions.spec.ts F-09, F-09b

F-15 - Quadratic trim patterns froze the server on long whitespace HIGH FIXED

What went wrong
Patterns of the form "trim spaces at both ends" were quadratic in trimLikeThreadwise (product text fields), trimLikePhp (tags box), normaliseConsentText (the STOP or START match on an inbound message), flbCleanVarName, appendOptOutLine and wspDisplayName. 50,000 spaces or tabs took 6 to 14 s; 300,000 does not finish in minutes. Two real hangs, caught by the watchdog.
Why it matters
One authenticated request with a 300 KB text field freezes the API or a worker. The inbound-message path is bounded by each channel's own size limit, which I did not check.
How we fixed it
One linear helper, trimEdges, used by all six.
Test
fuzz-regressions.spec.ts F-15

What went wrong

F-02 - The NUL guard missed keys and deep values MEDIUM FIXED

What went wrong
findNul (the NUL guard before Postgres) ignored object keys and everything deeper than 32 levels, and was recursive.
Why it matters
A NUL in a key or at depth 33 reaches jsonb or text and fails as a 500.
How we fixed it

F-03 - Error-text cleaner was quadratic MEDIUM FIXED

What went wrong
sanitizeErrorText runs unanchored patterns that are quadratic on a long run of one character (32 KB took 0.9 s, 300 KB would take about 80 s); it also threw on a value too deep to print.

Rollout and rollback

No staged deploy is needed for the fuzz tooling (test code only). The fixes are ordinary code changes in one commit (1c49517ae). To undo any single fix, revert that commit and re-run the fuzz: the matching regression test fails again, which proves the fix was doing its job. Behaviour changes a user could notice: a mail with more than 20,000 tags is truncated and flagged (F-09); a Postgres "bad value" error now answers 422 instead of 500 (F-16).

What this does NOT prove

  • Not fuzzed: real DNS and real connections. Resolution is stubbed; guardedRequest, SafeFetch, downloadSocialMedia and the IMAP connect never ran against anything (by rule). Their address rule is covered, their socket code is not.
  • Not fuzzed: 374 of the 465 exported contract functions (they take objects, not text).
  • Not fuzzed: parsers and sanitisers that are not exported or sit inside services (many are listed in O-02), the per-channel webhook payload parsers, the flow-builder runtime, file importers, image, PDF and media handling, JWT parsing, the AI prompt builders.
  • HTTP phase limits: one principal (an organisation admin with every permission), so no low-privilege and no cross-tenant fuzzing; about 4.4 requests per route; no valid multipart uploads; no WebSocket; no worker or queue consumers. main.ts extras (CORS, compression, OpenAPI document, Redis adapter) are not in the harness, so GET /docs/api.json, logout and the session-revoking routes were skipped.
  • Not fuzzed: apps/web, apps/partner, apps/mobile.
  • The scheduled trigger: Actions do not start on this account. fuzz.yml was not run anywhere; the same command was run by hand.
  • That the fixes hold under every seed: each run explores new inputs. Run it weekly and treat a failure as a finding, not a flake (the seed reproduces it).
  • Input count is not coverage. Many counted inputs are rejected by a schema at the first field; the perturb mode and a minimum of one input per schema push past that, but line and branch coverage of the fuzzed code was not measured.
  • Browser view of the sanitisers. Mutation XSS and parser differences between sanitize-html and a real DOM are judged by a scanner of the output, not by a browser.
  • Reachability of F-09 and F-15 by an unauthenticated sender on every channel: the inbound size limits of WhatsApp, SMS and email were not checked.
  • Consumers of the changed @crm/contracts helpers in apps/web and apps/partner: the contracts tests (188) and the API unit tests I ran pass for this change; the web and partner tests and typecheck were not run for it.
  • The security-review-gate: pnpm audit:tenancy, audit:authz and audit:auth exited non-zero here ("controls not executed or blocked"; they need the running stack). I did not establish whether they also fail on main, so that step is not verified, and the gate's model-driven security-review and code-review steps were not run.
  • The network block is in the test process, not an OS sandbox: a code path that opens a socket without net.Socket#connect (a native add-on) would not be caught.
  • Pre-existing, not changed, not confirmed against a clean checkout: the whole API unit suite showed 10 failures in 8 files (chatbot-widget x2, crm/activity-type-rules, dashboards-analytics-charts/health, flow-builder-editor/editor-field-seam, google-account/google-capabilities, infra/boundaries.matrix, infra/s3-sigv4, roles-permissions/route-permission-coverage, plus 2 in encryption-audit), none in code changed here.
