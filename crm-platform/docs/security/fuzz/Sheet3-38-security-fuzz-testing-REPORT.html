1. Method

  • Generator (apps/api/test/fuzz/gen.ts, no dependency): an sfc32 PRNG. Every input is a pure function of (seed, target name, iteration), so one input is replayed alone with node tools/quality/fuzz.mjs --seed S --target T --iter I. The seed is printed on every run and accepted with --seed. It makes: empty, huge (to 300 KB), NUL, control, bidi/RTL, emoji and ZWJ sequences, lone surrogates, mojibake and overlong-UTF-8 spellings; several hundred SQL, NoSQL, template, command, path-traversal, SSRF, XSS and CRLF payloads (then mutated); about 45 ReDoS shapes (a unit repeated, then a character that breaks the match); numeric edge cases (NaN, -0, 2^53, 2^63, 1e21, negatives, floats); type confusion (array, object, null, undefined where a string belongs); JSON with __proto__, constructor, toString as own keys (the way JSON.parse makes them) and chains nested up to 30,000 deep; and a "perturb" mode that damages 1 to 3 places of a valid sample built from the schema, so a body that is almost right reaches the checks past the first one.
  • Engine (engine.ts): runs each input, counts it, and reports four kinds of failure: an unexpected throw (anything but the target's own validation error type), a broken invariant, a slow input (budget 1 s by default, measured twice so one GC pause does not count), and a change to a shared prototype (Object, Array, Function, String, Number; the engine puts it back and goes on). A failing input is shrunk (greedy delta-debugging over strings, arrays and objects) to a minimal repro. A progress file is written every 128 inputs (every input for code that could hang) and the runner kills a shard whose file stops moving for 120 s and names the target and iteration. That is how two real hangs (F-15) were caught instead of freezing a run.
  • Runner (tools/quality/fuzz.mjs, pnpm fuzz, pnpm fuzz:ci): splits the targets over 4 shards (inputs do not depend on the split), runs the HTTP phase beside them, prints the total, throughput, per-group counts, and every failure with seed, minimal input and replay command; exits non-zero on a failure, a hang, a crashed shard, or fewer than 1,000,000 pure inputs in the full profile. The manual workflow is .github/workflows/fuzz.yml (workflow_dispatch only, with the same note as security.yml that Actions jobs do not start on this account).
  • Profiles: ci = 20,000 inputs, fixed seed, run inside pnpm test by test/unit/security/fuzz-ci.spec.ts (time budgets x8 so a loaded machine does not make it flaky); full = 1.3 million inputs and a new seed each time, plus 9,000 HTTP requests.
  • fast-check not added. It brings a dependency, a replay model that is a path through a run rather than an input index, and arbitraries I would still have had to write for the hostile text classes. About 900 lines of generator and engine give per-input replay and an exact input count. The cost: only simple shrinking, no stateful or model-based testing.
  • Oracles are independent where it matters. Address rules are checked against Node's BlockList (IPv4) and an eight-group IPv6 expansion written separately from blocked-address.ts; links and paths by what a WHATWG URL parse does with them (what a browser does); HTML by scanning the sanitiser's output for forbidden tags, event handlers and URL schemes after the entity and whitespace handling a browser applies; signatures by a forged and a genuine pair.

6. What is NOT verified

  • The scheduled trigger: Actions do not start on this account. fuzz.yml was not run anywhere; the same command was run by hand.
  • That the fixes hold under every seed: each run explores new inputs. Run it weekly and treat a failure as a finding, not a flake (the seed reproduces it).
  • An input count is not coverage. Many counted inputs are rejected by a schema at the first field; the perturb mode and a minimum of one input per schema push past that, but line and branch coverage of the fuzzed code was not measured.
  • The browser view of the sanitisers' output (mutation XSS, parser differences between sanitize-html and a real DOM) is judged by a scanner of the output, not by a browser.
  • Whether F-09 and F-15 are reachable by an unauthenticated sender on every channel: the inbound size limits of WhatsApp, SMS and email were not checked.
  • The consumers of the changed @crm/contracts helpers in apps/web and apps/partner: the contracts tests (188) and the API unit tests pass; the web and partner tests and typecheck were not run for this change.
  • pnpm audit:tenancy, audit:authz and audit:auth exited non-zero here ("controls not executed or blocked"; they need the running stack). I did not establish whether they also fail on main, so that step of the security-review-gate is not verified, and its model-driven security-review and code-review steps were not run.
  • The egress block is in the test process, not an OS sandbox: a code path that opens a socket without net.Socket#connect (a native add-on) would not be caught.

8. Is the sheet target genuinely met?

The number is met, with the caveats of section 6. One command (node tools/quality/fuzz.mjs) executed and counted 1,302,743 generated malicious or invalid inputs (1,311,743 with the HTTP requests) in 160 s and passed; the runner itself fails a full run below 1,000,000. It is not yet "per scheduled run" in the sense of a schedule, because the Actions trigger cannot run on this account and the workflow is manual, like security.yml. It is better described as tooling done and 17 defects fixed; three open classes and the schedule remaining than as closed.
