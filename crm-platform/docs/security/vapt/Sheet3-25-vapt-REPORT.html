3. What this is, in plain words

A VAPT (vulnerability assessment and penetration test) means "attack our own product the way a stranger would, then fix what works". On a copy of the product running on this laptop, with two fake companies (tenant A, tenant B) and users with different roles, we did four things:

  1. Ran the checks the repo already had (auth, authorisation, tenant isolation, static code scan, dependency scan, secret scan) with a real database this time, and read the code behind every red item to see whether it is real.
  2. Scanned the running API from outside with a small script of ours that tries the classic mistakes on every route: no login, a viewer calling admin routes, odd headers, redirects, brute-force login. OWASP ZAP was started as well but did not finish.
  3. Attacked the riskiest areas as automated tests: company B reading company A's data, a viewer acting as admin, forged login tokens, replayed refresh tokens, guessing public invoice/booking links, faked payment webhooks, spreadsheet-formula injection in exports, a bad upload.
  4. Made it repeatable: one script and one manual workflow run all of the above again.

7. Rollout and rollback

The only product change is one line (app.disable('x-powered-by')); rollback is reverting it. The runner, tests and workflow add no runtime code. The tests run only when VAPT_BASE_URL is set, so the normal pnpm test is unaffected.

8. What this does NOT prove

  • Not recurring. No scheduler runs it. Treat "recurring" as not achieved until Actions (or another runner) can start the workflow.
  • ZAP produced nothing (section 5).
  • Local, not staging or production. A real pre-release deep scan still needs: the staging URL with a written scope and scan window; real TLS and the real proxy / WAF / CDN (HSTS, headers, rate limits, trust-proxy IP handling); production-like data volume; real provider callbacks (WhatsApp, Razorpay, Stripe, Shopify) with signed test events; MFA switches on; the mobile app's API traffic; the Next.js web app (XSS, CSP, cookies) with an authenticated browser crawl; the realtime socket under live traffic; a full-length authenticated ZAP active scan, split by API area.
  • Not covered: the web front end (29 dangerouslySetInnerHTML sites unread), workers, file parsing beyond content type and size (no malware or polyglot files), reset-token reuse through a real mailbox, 5 unread redirect hits, secrets in git history, business-logic abuse (coupon, wallet, billing races), denial of service (excluded on purpose), cross-tenant API checks on modules other than contacts, companies, deals, tasks (the generated tenancy scenarios cover all 373 tenant tables at database level).
  • Most auth and authz e2e suites need Docker testcontainers and were not run (only the quick unit layer ran: 790 of 792 passed, 2 skipped).
  • A passing DAST walker is a smoke test: it finds classic misconfigurations, not clever bugs.
