What is this, in plain words

The product stores secrets for its customers: access tokens for WhatsApp and Telegram, passwords for payment gateways, webhook keys for online stores. If someone could read the database (a stolen backup, a leaked copy, a curious insider), every plain-text secret would be theirs to use.

Analogy. Think of the database as a filing cabinet. A secret stored in plaintext is a house key taped to the front of the drawer. A sealed secret is locked in a small safe; the key to the safe is kept somewhere else (the application). A hash is a fingerprint of the key: enough to recognise it when someone presents it, but useless for opening the door.

This audit asked four questions: (1) is every secret in the database sealed, hashed, or clearly not a secret? (2) do secrets leak into logs, audit rows or API answers? (3) are the connections to Postgres and Redis encrypted when they need to be? (4) can a new plaintext secret be added by accident? The last one is answered by an automatic check called the ratchet.

Glossary
Plaintext
A value stored as it is, readable by anyone who can read the database.
Sealed (encrypted)
Scrambled with AES-256-GCM through the app's CryptoService. Only the app, which holds the key, can read it back.
Hash
A one-way fingerprint (SHA-256). The app can check a value against it but cannot get the value back. Used to find a record by its token.
Bearer link / token
A web address whose secret part is the only thing needed to use it (for example an invoice link). Whoever holds it has access.
Webhook
An address another service calls to tell us something happened (for example a store reporting a new order).
Ratchet
A test that only lets things get better: if someone adds a new secret-looking column without a reason on the list, the test fails.
Allowlist
The commented list of columns the ratchet accepts, each with a reason (sealed, hash, public, or an open finding).
Associated data (AAD)
Extra text mixed into the sealing so a sealed value only opens in the place it belongs. A value copied to another row no longer opens.
TLS
Encryption of the network connection between the app and Postgres or Redis.
Blue-green deploy
Two copies of the app run side by side during a release, the old and the new, so the old must keep working against the new database.
Expand / contract
Release in two stages: first add new columns and keep the old ones working (expand), later remove the old ones (contract).
Mirror
While the old release may still run, the new release also writes the old plaintext column. A switch turns this off.
Backfill / scrub
Backfill: fill the new hash and sealed columns for rows that already exist. Scrub: set the old plaintext column to empty (NULL).
Migration
A script that changes the database structure.
Row-level security (RLS)
A database rule that stops one customer's workspace from reading another's rows.

E2 - Shopify / WooCommerce webhook secret in plaintext Medium Fixed in code, rollout pending

What went wrong
The webhook secret was stored in plain text in shopify_integrations and woocommerce_integrations. It is three things at once: the last part of the webhook address shown to the store owner, the key the public route uses to find the workspace (ecom_store_lookup(), before any workspace is known), and for WooCommerce the signing key given to the plugin (woocommerce.service.ts returns it to the store owner on purpose). Sealing the column alone would break the lookup and the address display; storing only a hash would break the display and the signing key.
Why it matters
Anyone who can read the database or a backup could forge a webhook for a store and read its WooCommerce signing key. Medium because it needs database access.
How we fixed it
Split into a lookup column and a key column (the round-1 design, section 10). Migration 20270202090200 adds webhook_secret_hash and webhook_secret_enc on both tables, makes webhook_secret nullable, adds a unique hash index and a trigger (only secrets of 16 characters or more are hashed), and ecom_store_lookup() now matches the hash or the old column. Connect and reconnect write mirror, hash and sealed copy. The address, the plugin download and the signature check read the secret from the sealed copy. Webhook addresses already installed in stores keep working at every step.
Test that proves it
test/integration/security/ecom-webhook-secret-hash.spec.ts (4 tests: both stores through legacy, backfilled and scrubbed rows; short fixture secrets; repository round trip with the mirror off).
Still to do
Run the rollout; zone owner (Punya) review.

E9 - Bearer links appeared in request logs Medium Fixed

What went wrong
The request log, the error filter and Sentry send the request address through maskSecretUrl(), which did not cover three bearer-link routes: /public/invoices/:token (view and pay), /public/sales-docs/:token (accept or decline a proposal) and /public/booking-manage/:token (reschedule or cancel).
Why it matters
Anyone who can read logs could open a customer's invoice or proposal.
How we fixed it
One pattern added in common/logging/mask-secret-url.ts. In round 2 the payment return token (?o=) was masked the same way. Left unmasked on purpose: /r/:token (a campaign short link, identifies a click only), /media/:token (a short-lived signed token) and /widget/:token (a public embed token, printed on the customer's site).
Test that proves it
test/unit/platform-infrastructure/observability.spec.ts: the first four masking cases failed before the fix; round 2 added two for the return token (7 cases added in total, including one that checks /public/booking/... is left alone).

E3 - Channel webhook tokens in plaintext Low Fixed in code, rollout pending One sub-item open

What went wrong
Telegram, LINE, Viber and WeChat each had a random token in their webhook address, stored in plaintext in webhook_token and used as the lookup key by the public route (first reported for Telegram only). The routes resolve the channel through SQL lookup functions (tg_bot_lookup and the line, viber, wechat equivalents), so a hash needed a migration. incoming_webhooks.token has the same pattern.
Why it matters
A database read exposes the live webhook addresses of customers' channels.
How we fixed it
Migration 20270202090000: webhook_token_hash, webhook_token_enc, nullable webhook_token, a unique hash index, a trigger that hashes rows written by the previous release, and the four lookup functions matching the hash or the old column (an empty token matches nothing). Writers store mirror, hash and sealed copy; the admin address is rebuilt from the sealed copy. Addresses already given to providers keep working at every step.
Still open
incoming_webhooks.token: no service writes or reads it, so there was nothing to fix. The writer, when added, must use tokenColumns() (hash + sealed copy).
Test that proves it
test/integration/security/webhook-token-hash.spec.ts (4 tests: legacy, backfilled and scrubbed rows resolve by the same token; the trigger), test/unit/security/secret-columns.spec.ts.

E4 - Sealed values are not tied to their row Low Partly fixed

What went wrong
AES-GCM blobs carried no associated data (crypto.service.ts never called setAAD), so a sealed value copied from one row to another still opened. Binding needs a new format and a context at every call site, and an old instance cannot read the new format.
Why it matters
Someone with database write access could move a secret between rows or customers. Low because it needs write access.
How we fixed it (partly)
New v2 format (v2:iv:tag:ct:keyid:label): a hash of the context is the associated data. encrypt(plain, context?) and decrypt(blob, context?) read v1 and v2. The label travels in the blob, so key rotation re-seals a bound blob without knowing its context, and the rotation scan finds v2. v2 is only written when CREDENTIALS_AAD_WRITE=on (default off), because a release that predates this one cannot parse it. Wired for one column: push_subscriptions.auth (bound to organisation and user). Existing rows stay unbound v1 (the backfill seals without a context) until they are rewritten.
Still open
1 of about 126 call sites is bound; the other 125 (listed by area below) still seal without a context.
Test that proves it
test/unit/security/crypto-bound-blobs.spec.ts (7), test/unit/notifications/push-auth-sealed.spec.ts (a bound blob is refused for another person).

E7 - Web Push auth secret in plaintext Low Fixed in code, rollout pending

What went wrong
push_subscriptions.auth (the Web Push auth secret) and user_device_tokens.fcm_token were stored in plaintext. Both are needed in clear to send a push.
Why it matters
Whoever holds the keys of a device subscription can push messages to that person's browser.
How we fixed it
push_subscriptions.auth is sealed when a browser subscribes and opened by the sender (sealed or legacy plaintext). The sender now fails one unreadable device instead of the whole batch. No migration and no mirror: the value is sealed in place. fcm_token has no writer, so nothing changed there; whoever adds one must seal it.
Known window
A device subscribed on the new release during the switch cannot be opened by the old release; its pushes there fail and are given up after 10 failures. Re-subscribing repairs it. Run the backfill after the switch.
Test that proves it
test/unit/notifications/push-auth-sealed.spec.ts (4), integration push-subscriptions.spec.ts (17), workers e2e push subset (11).

E8 - Bearer links stored in plaintext Low Fixed in code for 2 of 6, rollout pending 1 open, 3 need your confirmation

What went wrong
Six bearer links were kept in plaintext as the lookup key: crm_briefs.public_token, wa_link_clicks.token, wa_orders.recovery_token, orders.return_token, web_form_submissions.receipt_token, wa_form_submissions.flow_token. Invoices, sales documents and appointments already use the better pattern (*_hash for the lookup, *_cipher to show the link again).

Links already sent keep working.
Still open

Reclassified as public, owner to confirm: web_form_submissions.receipt_token (the code calls it "a handle for the thank-you page, not a credential"), wa_form_submissions.flow_token (form-<id>-<run uuid>, echoed by WhatsApp) and wa_link_clicks.token (the short link printed in the message to its recipient).
Test that proves it
test/integration/security/bearer-token-hash.spec.ts (2), the log masking cases, test/unit/security/secret-columns.spec.ts.

E1 - Empty value did not round-trip Low Fixed earlier, still holds

What went wrong
CryptoService.encrypt('') made a blob that decrypt rejected.
Why it matters
Any caller that sealed an empty value could not read it back.
Evidence now

E6 - TLS for Postgres and Redis Info Closed (one defect fixed)

What went wrong
The first audit found no TLS option for Postgres or Redis. In fact both can be switched on from the connection address. One real defect: queueRedisOptions() rebuilt the BullMQ (job queue) connection from the address parts and dropped the scheme, so with rediss:// every queue still connected in clear text.
Why it matters
On a managed Redis the job data would cross the network unencrypted although TLS looked configured.
How we fixed it
One line in apps/api/src/infra/queue/queue.module.ts: add tls: {} when the scheme is rediss:. Postgres: createDbClient passes DATABASE_URL straight to pg, which reads sslmode (sslmode=verify-full gives certificate-checked TLS; DATABASE_REPLICA_URL and the CLIs use the same path). Redis: ioredis turns TLS on for rediss:// (shared client and the socket.io adapter). With the default redis:// and no sslmode nothing changes.
Test that proves it
queue.module.spec.ts (the case "rediss:// turns TLS on for the queue connection" failed first, no tls key), test/unit/security/transport-tls.spec.ts (4).

D. The E2 design (round 1 proposal, implemented in round 2)

Problem. The webhook secret is three things at once: the path segment of the URL shown to the store owner, the key the public route uses to find the workspace (ecom_store_lookup(), before any tenant is known), and for WooCommerce the HMAC key given to the plugin. Encrypting the column alone breaks the lookup and the URL display. Storing only a hash breaks the display and the HMAC.

  1. Columns. On both tables add webhook_secret_hash text (SHA-256 hex of the secret; the secret is 240 bits of server-generated randomness, so an unsalted hash is safe) and webhook_secret_enc text (the secret sealed with CryptoService, so the URL can still be shown and the WooCommerce HMAC key can still be read). Move the existing uniqueness guarantee (uq_*_webhook_secret) to the hash column.
  2. Lookup. Change ecom_store_lookup() to hash its argument and match webhook_secret_hash. The receiver still refuses values shorter than 16 characters before calling it. Once the hash path works, the plaintext column is never read again.
  3. Service. shopify.service.ts and woocommerce.service.ts write hash and enc on create and rotate, and decrypt the enc column wherever the URL or the HMAC key is shown or used. Verifying an inbound signature is unchanged.
  4. Backfill. A one-off CLI under the owner role fills hash and enc for existing rows in batches. It is idempotent (skips rows already done) and prints the number of rows left. The key-rotation CLI finds sealed values by their format, so the new columns are covered by rotation without changes.
  5. Two-step deploy. Step 1 (expand): a migration adds the nullable columns and the unique index on the hash; new code writes plaintext, hash and enc and looks up by hash with a fallback to the plaintext column; run the backfill; gate: count(*) where webhook_secret_hash is null is 0 on both tables; rolling back is safe. Step 2 (contract): code stops reading and writing the plaintext column; a second migration drops it; rolling back after this means decrypting webhook_secret_enc into a restored column, so take a database backup before step 2. (As built in round 2, the plaintext column is emptied by the seal tool's --scrub instead of being dropped.)
  6. Result. A database read no longer yields a usable webhook URL or HMAC key; only the hash and the ciphertext are stored. The same hash-plus-ciphertext shape was reused for E3 and E8.

Cost and risks. Migrations, a change to a SQL function that serves a public unauthenticated route, a backfill job, and tests for the lookup and both signature-verify paths. The module is owned by ecommerce (Punya). If the owner prefers not to do this, the residual risk is that a database or backup reader can forge a webhook for a store and read its WooCommerce HMAC key: Medium, and it needs database access.
