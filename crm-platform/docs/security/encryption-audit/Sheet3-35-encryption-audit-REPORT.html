1. Scope and method

  • Re-checked E1 to E6 against current main (eedae60d7, after the Waboo migration, Google OAuth, Marketplace, integrations and the WhatsApp provider changes).
  • Listed every Drizzle column in packages/db/src/schema/** whose name looks like a secret (token, secret, key, password, credential, private, access, refresh, auth, signature, hmac, otp, cert, bearer), then followed each one to the service that writes it. Each ends up as one of: sealed with CryptoService, a hash, a public identifier, or a named finding.
  • Applied all 453 migrations to a throwaway database on the shared Postgres server (enc_audit_tmp_35, dropped afterwards; no container was touched) and listed secret-looking columns from information_schema. The result matches the Drizzle schema, so the schema scan does not miss a table that only exists in SQL. Four old plaintext columns named in earlier migrations (appointments.manage_token, invoices.public_token, sales_docs.public_token, google_form_sessions.webhook_token) no longer exist.
  • Sampled the places a secret can leak: request logs and error reports, audit rows, outbox payloads, API responses and contracts.
  • Checked how the Postgres and Redis clients are configured for TLS.

6. E2 design proposal (owner decision, nothing implemented)

Problem. The webhook secret is three things at once: the path segment of the URL shown to the store owner, the key the public route uses to find the workspace (ecom_store_lookup(), before any tenant is known), and for WooCommerce the HMAC key given to the plugin. Encrypting the column alone breaks the lookup and the URL display. Storing only a hash breaks the display and the HMAC.

Proposal: split it into a lookup column and a key column.

  1. Columns. On both tables add webhook_secret_hash text (SHA-256 hex of the secret; the secret is 240 bits of server-generated randomness, so an unsalted hash is safe) and webhook_secret_enc text (the secret sealed with CryptoService, so the URL can still be shown and the WooCommerce HMAC key can still be read). Move the existing uniqueness guarantee (uq_*_webhook_secret) to the hash column.
  2. Lookup. Change ecom_store_lookup() to hash its argument and match webhook_secret_hash. The receiver still refuses values shorter than 16 characters before calling it. Once the hash path works, the plaintext column is never read again.
  3. Service. shopify.service.ts and woocommerce.service.ts write hash and enc on create and rotate, and decrypt the enc column wherever the URL or the HMAC key is shown or used. Verifying an inbound signature is unchanged.
  4. Backfill. A one-off CLI under the owner role fills hash and enc for existing rows in batches. It is idempotent (skips rows already done) and prints the number of rows left. The key-rotation CLI finds sealed values by their format, so the new columns are covered by rotation without changes.
  5. Two-step deploy.
    • Step 1 (expand). A migration adds the nullable columns and the unique index on the hash. New code writes plaintext, hash and enc, and looks up by hash with a fallback to the plaintext column. Run the backfill. Gate: count(*) where webhook_secret_hash is null is 0 on both tables. Rolling back is safe: the plaintext is still there.
    • Step 2 (contract). Code stops reading and writing the plaintext column. A second migration makes hash and enc NOT NULL, drops the old unique index and then drops webhook_secret. Rolling back after this means decrypting webhook_secret_enc into a restored column, so take a database backup before step 2.
  6. Result. A database read no longer yields a usable webhook URL or HMAC key; only the hash and the ciphertext are stored. The same hash-plus-ciphertext shape can then be reused for E3 and E8.

Cost and risks. Two migrations, a change to a SQL function that serves a public unauthenticated route, a backfill job, and tests for the lookup and both signature-verify paths. The module is owned by ecommerce (Punya). If the owner prefers not to do this, the residual risk is that a database or backup reader can forge a webhook for a store and read its WooCommerce HMAC key: Medium, and it needs database access.

Decision needed: approve (and name who implements), or reject and record E2 as an accepted risk (the ratchet already lists it as E2).

8. Not verified

  • No real TLS handshake against a TLS-enabled Postgres or Redis. The tests check the options the clients are built with, not a live connection.
  • queueRedisOptions() still drops a username in the Redis URL (ACL users). That is not a TLS issue, but a managed Redis that needs a non-default user would not authenticate. Not changed.
  • The leakage review is a sample, not every serializer, mapper and log call. No gitleaks run (not installed); the diff contains test values only.
  • The "encrypted" entries were checked by reading the writing service, not by reading rows in a running system. No integration, e2e or live-RLS test was run, and pnpm audit:tenancy was not run (no migration or table was changed).
  • Writers that do not exist yet (TikTok, HubSpot, Slack, Trello, proxy password) cannot be checked.
  • Existing logs and backups were not inspected for tokens that leaked before the E9 fix.
