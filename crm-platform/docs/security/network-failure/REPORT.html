1. Method

A local server that misbehaves on purpose (test/unit/network-failure/fault-server.ts, bound to 127.0.0.1 only) is pointed at the real outbound clients. Each fault is run with a 300 ms deadline, and each run must (1) end within the deadline plus 1.2 s, (2) end with an error the caller can classify, and (3) leave no socket open on the server side.

FaultWhat the server does
refusednothing listens on the port
resetaccepts, then drops the connection with no answer
hangaccepts and never answers
headers-then-hangsends 200 and part of a body, then goes silent
truncatedpromises 1000 bytes, sends 11, closes
dripsends 200, then one byte every 50 ms (a slow-loris answer)
hugestreams far more than any cap, fast
5xx, 503 with Retry-After, bad JSON, empty 200ordinary but awkward answers

Clients tested: guardedRequest (customer webhooks, webhook fan-out, WooCommerce), SafeFetch (API Library, flow Webhook node, media), WabaHttp (WhatsApp Cloud API and Interakt), and the web app's proxy to the API. A ratchet test also scans every outbound call in the API and fails if a new one has no timeout.

4. Not done (why this item is not Completed)

  • Database and Redis outages. Not tested: what the API does when Postgres or Redis stops, restarts, or answers slowly (readiness, in-flight requests, pool recovery). It needs a running stack with containers I can stop; it was not run here.
  • Queues. Worker behaviour when a job's upstream fails: retries, back-off, dead letters, duplicate sends on retry. This overlaps items 69 to 72 (owner Lakshya) and needs the real queue.
  • The other outbound clients (Telegram, Facebook, payment gateways, AI vendors) use AbortSignal.timeout, which is a total deadline, so they pass the timeout ratchet, but their error classification was not exercised with the fault server.
  • About 45 server-side fetch calls in the web app (feature API helpers, storefront and form proxies, dashboards) still have no timeout. Only the proxy and session calls on every request were fixed here.
  • Browser-side offline behaviour (what the UI shows when the network drops) needs a browser and belongs with item 10 (Playwright).

5. Limits

  • All faults are injected at the HTTP layer on loopback. TLS failures, DNS failure and packet loss are not simulated.
  • Timing assertions use a 300 ms deadline and a 1.2 s allowance; on a heavily loaded CI runner they may need a wider allowance.
  • A 30 s first-byte deadline in the web proxy is a judgement call; an endpoint that legitimately takes longer than 30 s to start answering would now get a 504. None is known.
