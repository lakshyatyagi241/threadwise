1. Method

Nothing was stopped or restarted. Faults come from a TCP proxy (test/unit/network-failure/tcp-fault-proxy.ts, 127.0.0.1 only) placed in front of Postgres and Redis, or from a port nobody listens on. Two small fakes (frozen-backends.ts) complete the Postgres or Redis handshake and then never answer: the "connected, then silent" case, which raises no error on its own. Each case must (1) end within a deadline, (2) end in an error the caller can classify (503 / typed error, no stack, no address), (3) leave no connection or pool slot behind, and (4) recover by itself when the dependency returns.

FaultWhat the proxy does
refusenothing listens: connect is refused at once
resetconnections are dropped (existing ones killed, new ones closed unanswered)
stallconnections stay open, bytes are held and delivered when the link returns
blackholenew connections are accepted and swallowed, existing ones go silent
connected, then silent (fake)handshake done, every later request ignored
dies at first statement (fake)handshake done, connection dropped at the first query (a restarted server under a pooled connection)

Layers: the unit file needs no server. The integration files (test/integration/network-failure/) use real Postgres and Redis. By default they start their own containers like every other integration test; with NF_PG_ADMIN_URL and NF_REDIS_URL set they use running servers, create a throwaway database crm_nf2_<random> (dropped at the end), and give every BullMQ queue a random prefix (obliterated at the end). Redis keys written by the full-app run (rate limits, sessions) were not deleted from the shared Redis; they carry TTLs.
