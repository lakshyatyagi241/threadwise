What is this, in plain words

Our application depends on three things it does not own: a database (Postgres) that stores everything, a cache (Redis) that remembers who is signed in and counts requests, and a job queue (BullMQ, which also uses Redis) that holds background work such as sending messages. Servers break, networks drop, and machines restart. The question is not "will it break" but "how does our system behave when it does".

Analogy. A shop whose till (the database) or card reader (the cache) stops working. A good shop tells the customer "the card reader is down, please try again in a minute" and carries on when it is fixed. A bad shop leaves the customer standing at the counter for ever, or locks the door and never reopens. We tested which kind of shop we are.

Part 1 of this item (PR #436) tested our calls to outside services (WhatsApp, customer webhooks). This part tests the inside dependencies and also reviews every fetch call in the web app.

Glossary
Timeout / deadline
The longest we wait for an answer before giving up.
503
The standard "service unavailable, try again shortly" answer. A 500 means "something is broken in your request".
Connection pool
A fixed set of ready database connections that requests borrow and return. If borrowed ones are never returned, the pool runs dry.
Silent (hung) connection
The connection looks open but the other side no longer answers. No error ever arrives, so only our own deadline can end the wait.
Half-open link
A network path that was cut without telling us. The operating system only notices after minutes.
Fail fast
Refuse at once instead of waiting.
Outbox
A database table where events are saved with the change that caused them, then delivered by a background process.
Worker
A background process that takes jobs from the queue.
Producer
Code that puts a job on the queue (usually inside a web request).
Readiness (/ready) and liveness (/health)
Two probe addresses the hosting platform calls. Liveness asks "is the process alive". Readiness asks "can it serve traffic right now".
Ratchet test
A test that fails when someone adds a new case of a known problem, so the problem cannot creep back.
Closed / open mode
Setting AUTH_REDIS_FAILURE_MODE. Closed: if the cache is down, refuse sign-in related checks with 503 (production default). Open: carry on without the check (non-production default).

How we tested

We never stopped, restarted or changed the shared database and cache. Instead the application under test was pointed at a small fault proxy that sits in front of the real service and misbehaves on command.

Method

  1. Point the part of the system under test at the proxy, never at the real service.
  2. Inject one fault. Each case must (a) end within a deadline, (b) end in an error the caller can classify (503 or a typed error, no stack trace, no address), and (c) leave no connection or pool slot behind.
  3. Remove the fault. The same app instance, pool or client must (d) work again by itself, with no restart.
  4. Layers: a hermetic unit file (no server needed); integration files on real Postgres and Redis; and the real application (AppModule) behind the proxies, exercising sign-in, session, a read, a write, /ready and /health.
  5. Integration files use their own containers by default. With NF_PG_ADMIN_URL and NF_REDIS_URL set they use running servers: a throwaway database crm_nf2_<random> (dropped at the end) and BullMQ queues with a random prefix (removed at the end). Redis keys written by the full-application run (rate limits, sessions) were not deleted from the shared Redis; they carry expiry times.
  6. Review all fetch calls in the web app, fix the unsafe ones, and add a ratchet test.

Findings

Sorted by severity, then status. All 8 are fixed. "Test that proves it" files are under apps/api/test/ unless noted; the same behaviour is also covered by integration/network-failure/api-outage.spec.ts where it touches the request path.

HIGH ▲ N6 — A silent database hung requests and stopped the outbox ✓ Fixed

What went wrong
Postgres had no client-side query timeout. The server-side limit (statement_timeout) cannot fire when the connection is up but the other end is silent, so the query waited for ever. Before the fix the test hung until the test runner's timeout.
Why it matters
A web request hangs. A background outbox tick hangs too, and its "already running" guard is never cleared, so the outbox stops delivering events for good, even after the database returns.
How we fixed it
query_timeout = statement timeout + 2.5 s (packages/db/src/client.ts).
Test that proves it
unit/network-failure/dependency-outage.spec.ts ("connected, then silent", outbox drain); integration/network-failure/recovery.spec.ts.

HIGH ▲ N10 — A failed transaction start leaked a database connection for good ✓ Fixed

What went wrong
The database library (drizzle) runs begin outside its try/finally. When begin fails (the connection died or went silent between checkout and first statement) the connection is never released: one pool slot lost per failure. Observed: the 3rd transaction on a 2-slot pool waited the full 10 s connection timeout. The dead checked-out connection also raises an unhandled error event, which is a process crash.
Why it matters
A database restart or network blip drains the pool, so the API cannot recover even after the database is back. Process-level exception risk.
How we fixed it
Fixed once in shared code: runTransaction, used by withTenant and withPrivileged, so every tenant and privileged transaction. It always releases the connection, discards one with an unanswered query, and holds an error listener while the connection is checked out.
Test that proves it
unit/network-failure/dependency-outage.spec.ts ("dies at the first statement ... gives its pool slot back (N10)"); integration/network-failure/recovery.spec.ts.

HIGH ▲ N7 — A silent Redis hung every request ✓ Fixed

What went wrong
The shared Redis client had no command timeout. A connected-but-silent Redis hangs every auth check, rate limit and cache read.
Why it matters
Every authenticated request hangs.
How we fixed it
commandTimeout of 2 s (nothing blocks on this client) in infra/redis/redis.module.ts.
Test that proves it
unit/network-failure/dependency-outage.spec.ts (shared Redis client); integration/network-failure/recovery.spec.ts and api-outage.spec.ts.

MEDIUM ◆ N8 — Queue producers could wait for ever ✓ Fixed

What went wrong
BullMQ producers: (a) with a connected-but-silent Redis, queue.add waits for ever; (b) a process that started while Redis was down waits for ever on its first connection, whatever the "fail fast" options say. Outages in mid-life already failed fast, as the earlier commit intended.
Why it matters
Any request that adds a job hangs for the length of the outage after a restart during an outage.
How we fixed it
Producer commandTimeout, and BoundedQueue (registered for all Nest queues) bounds the first-connection wait to 3 s on add and addBulk. The wait carries on in the background, so the queue works once Redis returns. Workers keep waiting (commandTimeout is explicitly unset for them).
Test that proves it
unit/network-failure/dependency-outage.spec.ts (producer cold start and silent); integration/network-failure/recovery.spec.ts (cold start, mid-life, workers).

MEDIUM ◆ N9 — The readiness probe could hang and told strangers internal addresses ✓ Fixed

What went wrong
/ready had no deadline per check and returned the driver's raw message on a public endpoint (host, port, role name).
Why it matters
A hanging probe makes the platform kill a healthy pod. Internal addresses are disclosed to anonymous callers.
How we fixed it
2 s per check, all checks in parallel, and the error is one of timeout, unreachable, error (health/health.controller.ts).
Test that proves it
unit/network-failure/dependency-outage.spec.ts (readiness: refused, silent); integration/network-failure/api-outage.spec.ts.

MEDIUM ◆ N11 — An outage was reported as a 500 ✓ Fixed

What went wrong
A dead database, Redis or queue surfaced as 500 INTERNAL, which a client reads as "my request is broken".
Why it matters
Clients and retry logic cannot tell an outage from a bug. The web app retries reads on 5xx other than 501, so a 503 now gets that retry.
How we fixed it
The isDependencyOutage classifier and ProblemExceptionFilter answer 503 SERVICE_UNAVAILABLE with Retry-After: 5 (new code in @crm/contracts); no address or driver text in the body.
Test that proves it
unit/network-failure/dependency-outage.spec.ts (error mapping); integration/network-failure/api-outage.spec.ts.

MEDIUM ◆ N12 — Redis retry back-off made every request take 11 to 35 seconds ✓ Fixed

What went wrong
The Redis client's back-off grew to 2 s a try and maxRetriesPerRequest counts tries, so in a long outage each Redis command took about 5 s to fail. An authenticated request took 11 to 35 s.
Why it matters
Slow, not stuck, but the request path is unusable during an outage.
How we fixed it
Back-off capped at 500 ms. Measured evidence: in closed mode each call finished under the 6 s test limit (see Figure 5); the previous version of this report said "about 2 s", which was not measured.
Test that proves it
integration/network-failure/api-outage.spec.ts (Redis outage, closed and open mode).

MEDIUM ◆ N13 — Web app calls with no deadline ✓ Fixed

What went wrong
27 server-side calls to the API (SSR pages, route handlers, public proxies, widget proxy) had no deadline. In the browser, 13 JSON helpers and 7 sign-out calls had none either, and neither did the central apiFetch unless the caller passed a signal. (The previous version of this report counted these as "16 browser JSON helpers"; the call-by-call count is 13 JSON + 7 sign-out = 20.)
Why it matters
A stalled API freezes page renders, the sign-in form, the sign-out button and public form submits.
How we fixed it
Server-side calls use upstreamFetch (30 s to first byte). Browser JSON calls 30 s, sign-out 5 s, apiFetch 60 s unless the caller passes its own signal.
Test that proves it
apps/web/src/lib/network-failure/fetch-ratchet.test.ts; apps/web/src/lib/api/client-deadline.test.ts.

Already correct before this work: a Postgres or Redis that is refused or resets fails in milliseconds; a worker keeps waiting through an outage and picks the next job up; a producer that lost Redis mid-life fails at once and recovers; liveness (/health) stays 200 during every outage; the closed-mode auth path answers 503 AUTH_SERVICE_DEGRADED.

Rollout and rollback

No staged deploy is needed. All changes ship in one release and are tuning-level: timeouts, a connection-release fix, a new error code, and a stable /ready error vocabulary. To undo, revert the commit ec161dac3. One thing to watch after release: monitoring that parses the old /ready error text will now see timeout, unreachable or error, and API clients will now see 503 SERVICE_UNAVAILABLE where they saw 500. Whether any dashboard or alert depends on the old text was not checked.
