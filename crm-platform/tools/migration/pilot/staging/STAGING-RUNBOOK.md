# Staging load runbook: ONE Waboo client into desk.wabo.ai

Nothing here has been run against the server. Every command below was only exercised against the local scratch database (see "Not testable without the server").
Staging = Docker Compose project `desk` in `/opt/desk` on a shared Dokploy host (`crm` database, Postgres inside the compose network as host `postgres`, no published port, 1 GB memory cap).
The tool runs INSIDE the existing `desk-api` image (node:22-alpine), as a one-off container on the compose network; the image is never rebuilt.

## Fast loop (preferred)

Everything from one workstation (Git Bash), no dump file on the laptop, no manual ssh. From `crm-platform/tools/migration`, per client (`iskm`, `rhythm`). Server details come from `db-migration/server-access/server.env`; the per-client flags from `pilot/staging/clients/<client>.json` (copy-fill the template once: org name/slug/plan, owner, channel map, credit opening or null = `--no-wallet`). Output is counts only, e-mails and long digit runs masked; every command prints its exit code.

```bash
C=iskm
KIT=/d/wadesk-vedant/db-migration/geta-mongodb-read-replica-prod/geta-mongodb-read-replica-prod
CY="node pilot/staging/cycle.cjs"
# 1. [user: Mongo access, runs it] stream Waboo -> staging server (no local file; sha256 verified on the server; manifest.json written there)
node $KIT/bin/mongo-export.cjs --db <db of the client> --client $C --to-ssh --i-confirm-server-is-staging --registry-classes MIGRATE,MIGRATE_LATER
# 2. bundle + ship + preflight + dry run + report in one go (build, ship, preflight, dry, report)
$CY all-dry --client $C           # first time only, before it: $CY ship --client $C && $CY init --client $C
# 3. [user] READ the report (_work/migration/runs/$C/<timestamp>/: dry-run.txt, status.json). Stop on any WARNING / unaccounted you do not understand.
# 4. [user: written go from the client owner] backup, then load (load refuses without a backup from today, a fresh successful dry run with unaccounted 0 and an unchanged config)
$CY backup --client $C
$CY load --client $C --yes-load-into-staging
# 5. reconcile and fetch the masked report (exit 0 + PASS required)
$CY reconcile --client $C && $CY report --client $C
# 6. [user: chooses the password] make the owner able to sign in (password from the environment, sent over stdin)
read -rs OWNER_NEW_PASSWORD; export OWNER_NEW_PASSWORD; $CY set-owner-password --client $C; unset OWNER_NEW_PASSWORD
```

Iterating after a code change: `$CY all-dry --client $C` (rebuilds, re-ships, re-preflights, re-dries, pulls the report). Re-running the export resumes per collection (a collection whose server file and export record match is skipped; `--force` re-exports).

How it works / what to know:

- `--to-ssh` pipes each collection from the jump-host ssh into `ssh root@staging 'umask 077; cat > /opt/desk/migration/dumps/<client>/<collection>.ndjson.part'`; sha256 and byte count are computed locally while streaming, the server re-hashes the `.part`, and only a matching one is renamed (then `chown 10001:10001`). If either ssh dies, the `.part` is deleted and the exit code is non-zero (1; 3 count mismatch; 4 host key; 5 size cap). Only paths under `/opt/desk/migration/dumps` are accepted, never `..`.
- `manifest.json` is generated by the exporter on the server from the per-collection export records (`.export/<collection>.json`) in exactly the shape the tool's `manifest` command writes (docs, `badLines` 0, bytes, sha256). The tool still re-hashes every dump file against it at `dry` and `load`, so a mismatch shows up there (`DUMP_CHANGED`). If you prefer the tool's own command: `$RUN worker sh -c 'SOURCE_DUMPS_DIR=/mig/dumps ...'` with `-v $MIG/dumps:/mig/dumps` (read-write) and `manifest --client $C`.
- `cycle.cjs` uploads through `ssh ... cat > file.part` + sha256 check + `mv` (same effect as `scp` + `sha256sum -c`), and runs the bundle with the exact `docker compose ... run --rm --no-deps -T --user 10001:10001 ... worker sh -c '...' </dev/null` of the steps below; `$DATABASE_URL` is expanded inside the container.
- The `dry` command writes `out/status-<client>.json` on the server; `load` reads it. Transcripts are kept as `out/dry-run-<client>.txt`, `out/run-<client>.txt` on the server.
- Guards: every server command first checks `DOMAIN=desk.wabo.ai` in `/opt/desk/.env`.
- The steps below stay the reference for what each command does and for rollback / cleanup (steps 10 and 11 are not in `cycle.cjs`).

## One command per client: `migrate`, `batch`, `new-client`

From `crm-platform/tools/migration`. These sit on top of the fast loop above; every single command and flag of the loop still works as before.

```bash
CY="node pilot/staging/cycle.cjs"
# once per new client: config + channel map (no server access needed)
$CY new-client --client acme --name "Acme Ltd" --slug acme --owner-email owner@acme.example --owner-name "Ann Owner" \
   --plan enterprise --channel-id <botid>=<phone number id> --db <waboo db name>
# the whole migration of one client (stops at the first failure and prints the resume command)
$CY migrate --client acme --db <waboo db name> --yes-load-into-staging --with-dry-run
# several clients, one or two at a time, one shared build/ship/preflight and ONE summary
$CY batch --clients acme,beta --concurrency 2 --yes-load-into-staging --with-dry-run
```

`migrate` chain: `export` (the kit's `mongo-export.cjs --db <db> --client <c> --to-ssh --i-confirm-server-is-staging --registry-classes MIGRATE,MIGRATE_LATER`; skipped by `--skip-export`, or automatically when the server already has a `manifest.json` younger than 24 h whose files all have the listed sizes; `--force-export` overrides) -> `ship` (`--build` rebuilds first) -> `preflight` (runs `init` and a second preflight `--after-init` by itself when the migration schema is absent) -> `dry` (only with `--with-dry-run`) -> `backup` -> `load` (all steps; `--steps` / `--skip-steps` honoured; the existing gate applies: a clean dry run with unaccounted 0 and an unchanged config, or BOTH `--skip-dry-run-check --i-accept-no-dry-run`) -> `reconcile` -> `report` -> `complete` (the `migration-complete` generator for that client). `--yes-load-into-staging` is required up front, so a missing flag fails before a 15-minute export, not after.

- A failure stops the chain and prints `migrate: resume with: node pilot/staging/cycle.cjs migrate --client <c> ... --from <step>` (same client, db, steps and explicit flags). `--from` is one of `export ship preflight dry backup load reconcile report complete`; a load is resumable, so `--from load` is safe after a crash.
- Every step prints `migrate: <step> ok <seconds>s`; at the end a table per step (seconds, rows migrated, quarantined, excluded; the `load` row is followed by one line per load step with its own seconds). It is written to `_work\migration\runs\<client>\<timestamp>\timings.json` (next to the fetched reports). A run that stopped before `report` writes `runs\_timings\<client>-<timestamp>.json` instead, so the newest-run lookup of `migration-complete.cjs` never lands on a folder without a reconcile. Per-step seconds come from the arrival time of the step lines in the transcript; the first step also carries start-up and source indexing.
- Every other command prints `timing: <command> <s>s`; `load` prints the per-step table too.
- `batch` refuses `--concurrency` above 2 (staging Postgres is capped at 1 GB, the host has little free memory) and checks `MemAvailable` on the server first: **700 MB for one client at a time, 1200 MB for two** (a migrate container uses up to ~400 MB, on top of Postgres and the live stack). It builds and ships the bundle once and runs ONE preflight (and `init` if needed) on the first client. A failing client does not stop the others; the aggregated table and `runs\_batch\<timestamp>.json` list each client's result, totals and resume command. Per-client log lines are prefixed `[client]`. `batch` takes the Mongo database from each client's `mongoDb` field (written by `new-client --db`); `--skip-build` skips the shared build.
- `new-client` writes `pilot/staging/clients/<key>.json` (or the folder `CYCLE_CLIENTS_DIR` points to) and `<key>-channel-map.json` in `_work\migration\runs\config` (`CYCLE_CONFIG_DIR`). It validates the slug (lowercase, digits, dashes, unique among the existing configs), the e-mail and the plan slug, and rejects anything that looks like a secret or a URL. It never overwrites. Without `--channel-id` the map holds a `REPLACE-WITH-BOT-ID` entry with a placeholder phone number id, clearly marked.

## Speed notes (where the time went on staging, and the levers)

Measured on the first real runs (ISKM, 146,190 documents):

| Phase | Time | Notes |
| --- | --- | --- |
| Mongo export to the server | ~15 min | streamed through the jump host; scales with the number of documents, network-bound |
| load: field options | ~8 min for 53k rows (~110 rows/s) | the slowest step per row; one transaction per batch on a 1 GB Postgres |
| load: contacts, inbox | the rest of the load | inbox is batched per thread (a thread and its messages are one unit) |
| build, ship, preflight, backup, reconcile, report | seconds to a few minutes | not worth optimising |

Levers, in order of payoff:

1. **Do not re-export.** `migrate` reuses a fresh export on the server (24 h); `--skip-export` forces it. This removes the biggest block when you iterate on the load.
2. **Run two clients in parallel** (`batch --concurrency 2`): export and load of two clients overlap. Two is the ceiling on this host: each container needs ~400 MB and Postgres is capped at 1 GB. If `docker stats` shows postgres above ~900 MiB, go back to 1.
3. **Skip steps a client does not need**: `--skip-steps` with names from the `steps` command (33 steps, grouped access/fields/broadcasts/credits/flows/chat). A client without credits or flows can skip `credits` / `flows`. A step another one depends on (for example the field-option dependencies) must not be skipped on its own; the tool refuses a selection that breaks a dependency. To look at the data between groups, split the load: `--steps access,fields`, then contacts, then `broadcasts,flows,credits,chat`; the load is idempotent.
4. **Batch size**: `batch` in the client config (default 250; `new-client --batch`). Larger batches mean fewer transactions and are faster per row, but a bigger transaction on a 1 GB Postgres; 100 is the fallback after an OOM. Do not go above 500 without watching `docker stats`.
5. **Keep the dry run** unless you accept the override: it costs about as much as a load, but it is the only way to see unaccounted rows before anything is written. `--with-dry-run` makes it part of the chain.

Recommendation: per new client run `new-client`, fix the human fields (table above), then `migrate --with-dry-run`; with two clients waiting use `batch --concurrency 2`; use `--skip-export` for re-runs. The long blocks are the export, the dry run and the load.

## Missing in WaDesk: what to log

Whatever the report shows as not carried over is a product gap, not a migration bug. After each `report`, open the **NOT PRESENT IN WADESK** section of `reconcile.md` (collections with no target table, unknown / undecided collections, source fields dropped with a reason, MIGRATE_LATER deferrals) and add each new item, with the client, the collection or field and the counts, to `D:\wadesk-vedant\_work\migration\missing-in-wadesk-log.md`. Counts and names only, no customer content.

Legend: **[you]** = a person at their workstation, **[server]** = typed on the server over ssh, **[approver]** = the project owner. "Proves" says what a successful step establishes.

Variables used below (set them in your shell on the server; none of them is a secret):

```bash
cd /opt/desk
C=iskm                     # client key (dump folder name)
SLUG=iskm                  # planned organization slug
MIG=/opt/desk/migration    # bundle/ dumps/ out/ live here
RUN="docker compose --env-file .env run --rm --no-deps -T --user 10001:10001 -e NODE_OPTIONS=--max-old-space-size=384 \
  -v $MIG/bundle:/mig/bundle:ro -v $MIG/dumps:/mig/dumps:ro -v $MIG/out:/mig/out"
GUARD="--allow-docker-host postgres --confirm-db-name crm"
```

Why this shape:

- The service `worker` already has `DATABASE_URL` = the `crm_worker_user` login and `MIGRATION_DATABASE_URL` = the owner login. The tool wants them as `TARGET_DATABASE_URL` / `MIGRATION_DATABASE_URL`, so every command runs as
  `sh -c 'TARGET_DATABASE_URL="$DATABASE_URL" SOURCE_DUMPS_DIR=/mig/dumps exec node /mig/bundle/waboo-migrate.cjs ...'`.
  The single quotes keep `$DATABASE_URL` for the shell INSIDE the container: the URL is never on the host command line, in `ps`, in your shell history or in any output. The tool and the preflight print only `host= port= db= role=`.
- `--user 10001:10001` runs as a non-root uid that owns `$MIG` (step 1), so the dumps can stay root-and-that-uid-only (700). The image's own `app` user is not needed.
- `--no-deps` starts nothing else; `run` takes `worker`'s limits (1 GB) and its logging. `-T` = no TTY (works from ssh and scripts).
- `--allow-docker-host postgres` is needed because `postgres` is not on the tool's built-in list of local names; `--confirm-db-name crm` is the exact database name and is required for every non-dry-run write (dry runs do not need it).
- The migrate container is a SECOND process next to the running `api`, `worker` and `postgres`; see "Memory" at the end.

### Step 0b. Backup [server] (proves: a restore point exists, and it is readable)

```bash
cd /opt/desk
docker compose --env-file .env exec -T backup desk-backup once pre-migration-$C
ls -l backups/desk-pre-migration-$C-*.dump                       # one new file, size plausible (not a few KB)
F=$(ls -1t backups/desk-pre-migration-$C-*.dump | head -1)

```

`desk-backup` itself only accepts a dump after `pg_restore --list` could read it, and prints `backup: ok <file> <size>` (`docker compose logs --tail 3 backup`). The backups are mode 600 and live on the same host: if you also want an off-host copy, see `docs/runbooks/backup-restore.md`.

## Step 2. Preflight [server] (proves: the database is ready for the tool; changes nothing)

```bash
$RUN worker sh -c 'TARGET_DATABASE_URL="$DATABASE_URL" exec node /mig/bundle/waboo-preflight.cjs \
   --org-slug '$SLUG' --client '$C' --org-plan <plan slug> --allow-docker-host postgres --confirm-db-name crm'
```

Read-only sessions (`default_transaction_read_only=on`). Eight checks, PASS/FAIL each, exit 1 on any FAIL: (a) every migration file recorded in `_migrations` (read through the owner URL, which the worker may not read; the expected list is the image's own `/app/migrations` when present, else the list embedded in the bundle), (b) every table and column the tool writes exists with an assignable type and no unwritten NOT NULL column, (c) RLS enabled AND forced with a `current_org_id()` policy on each of those tenant tables, (d) the login is `crm_worker_user`, not superuser, no BYPASSRLS, has the table privileges and can EXECUTE `ensure_monthly_partition`, (e) server settings, (f) pgvector, (g) the `migration` schema state (absent = needs `init`), (h) no organization with the planned slug.
A (a) failure with "the server is BEHIND this checkout" means: stop, deploy the server to the bundle's revision (`ship.sh`), rebuild nothing else, rerun. Do not "fix" the database by hand.

## Step 3. init [server] (once per database; proves: the tool's bookkeeping schema exists)

```bash
$RUN worker sh -c 'TARGET_DATABASE_URL="$DATABASE_URL" exec node /mig/bundle/waboo-migrate.cjs init '"$GUARD"
```

Uses `MIGRATION_DATABASE_URL` (owner) from the container's environment; creates `migration.id_map`, `quarantine`, `run_log` and grants the worker role. Idempotent. Then rerun step 2 with `--after-init`: check (g) must be PASS "present".

## Step 4. Dry run [server] (proves: the whole load works on this data and this schema; rolled back, nothing stays)

```bash
$RUN worker sh -c 'TARGET_DATABASE_URL="$DATABASE_URL" SOURCE_DUMPS_DIR=/mig/dumps exec node /mig/bundle/waboo-migrate.cjs run \
  --client '$C' --dry-run --batch 250 '"$GUARD"' \
  --org-name "<Organization name>" --org-slug '$SLUG' --org-plan <plan slug> \
  --owner-email <owner email> --owner-name "<Owner name>" --default-cc 91 \
  --channel-map /mig/dumps/'$C'/channel-map.json --credit-opening /mig/dumps/'$C'/credit-opening.json' \
  | tee $MIG/out/dry-run-$C.txt
```

The whole run is one transaction that is rolled back (the output ends with `done: org N (dry run, rolled back)`). `--batch 250` (default is larger) keeps each transaction small for the 1 GB Postgres; lower it to 100 if `docker stats` shows postgres above ~900 MiB. The dry run holds ONE long transaction: `idle_in_transaction_session_timeout` must be 0 (preflight warns).
Role map and permission map are the ones embedded in the bundle (see `BUILD-INFO.json` `embedded.accessMaps` sha256); the run prints the access review.

## Step 5. Review the dry run [you + the person who owns the client]

Read `$MIG/out/dry-run-$C.txt` (`scp` it back; it holds counts and keys only):

- per step: read = migrated + quarantined + excluded; unexplained quarantine is a reason to stop (the codes are in the tool README),
- the WARNING lines (unmapped permissions grant nothing; `NO-ADMIN`; seats vs plan),
- the credits plan line (opening balance equals the confirmed number), the inbox line (channels, threads, partitions),
- no row of the organization exists afterwards: `docker compose --env-file .env exec -T postgres psql -U "$POSTGRES_USER" -d "$POSTGRES_DB" -Atc "select count(*) from organizations where slug='$SLUG'"` prints 0 (the `$POSTGRES_*` variables come from `.env`: `set -a; . ./.env; set +a` first, without echo).

Proceed only with a written go from the person who owns the client.

- Watch from a second ssh session: `docker stats` (postgres, worker, api) and `docker compose --env-file .env logs --tail 20 postgres`.

## Step 8. Make the workspace openable [server] (proves: a person can sign in to the migrated workspace)

Migrated users have no password, the owner's email is not verified, and staging has no outgoing mail and no Clerk, so the invite and reset emails cannot be sent. Set the owner's password directly. Choose the password on the server without echoing it; it is read ONLY from the environment variable, never from an argument:

```bash
read -rs -p 'new owner password: ' PW; echo
docker compose --env-file .env run --rm --no-deps -T --user 10001:10001 \
  -v $MIG/bundle/set-owner-password.cjs:/app/set-owner-password.cjs:ro -e OWNER_NEW_PASSWORD="$PW" worker \
  sh -c 'TARGET_DATABASE_URL="$DATABASE_URL" exec node /app/set-owner-password.cjs \
         --org-slug '$SLUG' --email <owner email> --confirm-db-name crm --allow-docker-host postgres'
unset PW
```

(`-e OWNER_NEW_PASSWORD="$PW"` puts the password in the docker CLI's argv for a moment on this host; if that matters, use `-e OWNER_NEW_PASSWORD` with the variable exported instead.) It prints `ok <user uuid>` and nothing else. It refuses: a non-owner, an unknown org, more than one match, a superuser/BYPASSRLS login, a wrong `--confirm-db-name`, a host the tool would refuse, an unknown flag, a password under 12 characters / without upper+lower+digit+symbol / containing the email name. It writes `users.password_hash` (argon2id, the app's own parameters) and the owner's `user_security` row (`email_verified_at`, `password_changed_at`, `force_password_change=false`), in one transaction, the same two writes as the app's password reset.
Hand the password to the owner over a channel that is not the ticket. Sign in at **https://desk.wabo.ai/login** with the organization slug (`$SLUG`), the owner email and the password. If the security policy requires MFA for owners, the app asks to enrol on first sign-in.

## Step 9. What to look at in the UI [you], per feature

Log in as the owner. For each line compare with the reconcile counts and with Waboo:

- **Contacts**: list count = contacts migrated; open 3-5 contacts incl. one with many custom fields; search by a phone number; fields/sections/options and their dependencies under settings; tags; groups (member counts); notes; lifecycle stages/statuses.
- **Inbox**: channels exist as "disconnected" (no credentials: connecting WhatsApp again is a separate step); conversations count; open a long thread, one with media, one assigned to an agent; the 24h window state; threads are closed or open as chosen by `--thread-status`.

## Step 10. Rollback [server]

The app has NO organization delete/purge path (no API, no SQL function; deleting an organization from the console is not offered). Checked in the code and migrations.

**Preferred: remove ONE migrated organization with `rollback-org.sql`** (tested locally: loads two clients, removes one; the database then equals "the other client alone", the other client still reconciles PASS, and removing both returns every table in `public` and `migration` to its pre-load row count). It is one transaction, owner login, triggers off for that transaction, deletes every row with that `org_id` in every table, then the organization, then the tool's `migration.*` bookkeeping for the client, then checks no foreign key still points at it. Default is a DRY RUN that lists rows per table:

```bash
cd /opt/desk && set -a && . ./.env && set +a      # no echo
docker compose --env-file .env exec -T postgres psql -U "$POSTGRES_USER" -d "$POSTGRES_DB" -v ON_ERROR_STOP=1 -v slug=$SLUG -f - < migration/bundle/rollback-org.sql
# read the table, then:
docker compose --env-file .env exec -T postgres psql -U "$POSTGRES_USER" -d "$POSTGRES_DB" -v ON_ERROR_STOP=1 -v slug=$SLUG -v commit=1 -f - < migration/bundle/rollback-org.sql
```

It refuses an organization the tool did not create (no `settings.legacy.waboo.client`). Take a fresh backup first (`desk-backup once pre-rollback-$C`). Lost by this: that organization's rows only (contacts, inbox, wallet ledger, users, roles, channels ...) and the rebuilt-by-hand owner password. Not lost: other organizations. Not touched: object storage (the tool writes none), Redis, sequences (ids are not reused). Sessions the owner opened are dead because the user is gone.
After it: rerun step 2 (check h: slug free) and the load can start again from step 4 (a client rerun after a rollback is a fresh load).

**Fallback: restore the pre-migration backup** (`docs/runbooks/backup-restore.md`, "Undo a bad migration"): stop `api worker web`, `pg_restore --clean --if-exists --exit-on-error` of `desk-pre-migration-$C-*.dump`, start them, check `/ready`. What is LOST in that case: EVERYTHING written to the database after the dump, for ALL organizations on staging (other tenants' edits, logins, sessions, settings, audit rows, anything created between step 0b and the restore), and the restore also reverts migrations applied after the dump. Use only if the targeted rollback fails or the database is damaged; say so to everyone who uses staging first.

## Step 11. Cleanup [server] (proves: no customer data is left lying around on the host)

```bash
cd /opt/desk
# 1. secure delete of the dumps (customer PII); shred does not help on journaling/SSD alone, so also remove the files
find $MIG/dumps -type f -exec shred -u -n 1 {} + 2>/dev/null; rm -rf $MIG/dumps
# 2. remove the bundle (no data, but it embeds the maps) and the password helper
rm -rf $MIG/bundle
# 3. out/: keep ONLY masked reports (reconcile.md/json hold keys and counts). Delete dry-run/run transcripts after the review if they list keys you do not want to keep
ls -lR $MIG/out
# 4. no containers left, no stray volumes
docker ps -a --filter name=desk-worker-run --format '{{.Names}}'     # prints nothing (--rm removes them)
docker volume ls -qf dangling=true | wc -l                           # equals the number from before step 1
history -c                                                           # no secret was typed into a command, but clear it anyway
```

Then record in the ticket: bundle sha256 (BUILD-INFO), manifest hashes, backup file + sha256, reconcile PASS, who approved, who loaded, when the dumps were deleted. The `pre-migration-$C` backup contains the pre-load state; keep it per the backups' retention (14 days, newest 3 always).

## Memory: Postgres has 1 GB

- One client at a time by default. `batch --concurrency 2` is the tested ceiling (it refuses below 1200 MB available on the server); never more than two `run` containers (the advisory lock only guards the same client).
- Batch size: `--batch 250` above; the tool default is larger. A batch is one transaction of that many documents (jsonb parsed in Postgres). If `docker stats` shows postgres near its limit (OOM kill = Postgres restarts, the run resumes cleanly, but the stack blips), stop, lower to `--batch 100`, rerun (resume).
- `NODE_OPTIONS=--max-old-space-size=384` caps the tool; the biggest client's `chathistory` is indexed in memory in pass 1: if the tool is killed (exit 137) the dump is too big for 384 MB; raise to 640 only after checking `free -m`.
- Optional while loading: `docker compose --env-file .env stop worker` (frees up to 1 GB and the worker does nothing for a migrated org yet); start it again afterwards. Do not stop `postgres`, `api` need not stop.
- Watch `docker stats` and `docker compose logs --tail 20 postgres` during the run; `log_min_duration_statement=500` makes slow batches visible.
