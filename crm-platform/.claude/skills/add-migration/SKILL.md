# Add migration

Full ground rules: [docs/runbooks/migrations.md](../../../docs/runbooks/migrations.md).
This skill is the condensed, do-it-now version plus a script that actually
checks the result instead of asserting it.

## 1. Create the file

```bash
pnpm db:new <name>     # e.g. pnpm db:new add_deals
```

This numbers it correctly (`packages/db/migrations/0009_add_deals.sql`, next
after whatever currently exists) and drops in a header comment reminding you
to explain _why_ the migration exists, not what it does — the SQL already
says what.

**Never edit a migration file that's already been applied.** The runner
checksums every applied file and refuses to proceed if one changed — that's
not a bug to work around, it's the thing stopping the repo and the database
from silently disagreeing. If you need to change something already applied,
that's a new migration.

## 2. The shape every tenant table needs

Copy this, don't reconstruct it from memory — every clause here exists because
something breaks without it:

```sql
CREATE TABLE widgets (
  org_id      bigint NOT NULL REFERENCES organizations (id) ON DELETE CASCADE,
  id          bigint GENERATED BY DEFAULT AS IDENTITY,
  uuid        uuid NOT NULL DEFAULT gen_random_uuid(),
  -- ...your columns...
  created_at  timestamptz NOT NULL DEFAULT now(),
  updated_at  timestamptz NOT NULL DEFAULT now(),
  row_version integer NOT NULL DEFAULT 1,
  PRIMARY KEY (org_id, id),
  UNIQUE (org_id, uuid),
  -- composite FK, NOT `owner_id bigint REFERENCES users(id)` — a single-column
  -- FK to another tenant table lets a row reference a DIFFERENT org's parent.
  FOREIGN KEY (org_id, owner_id) REFERENCES users (org_id, id)
);

ALTER TABLE widgets ENABLE ROW LEVEL SECURITY;
ALTER TABLE widgets FORCE  ROW LEVEL SECURITY;   -- see why below
CREATE POLICY tenant_isolation ON widgets FOR ALL
  USING      (org_id = current_org_id() OR app_is_privileged())
  WITH CHECK (org_id = current_org_id() OR app_is_privileged());

CREATE TRIGGER trg_widgets_touch BEFORE UPDATE ON widgets
  FOR EACH ROW EXECUTE FUNCTION touch_row();
```

**Why `FORCE`, specifically:** without it, the table's _owner_ role bypasses
every policy — and the migration role that creates the table IS its owner.
`ENABLE` alone would make every isolation test in this repo pass against a
table that has no real isolation. This is the single most common way RLS
migrations look correct and aren't.

**Why the FK is composite:** `(org_id, owner_id) REFERENCES users (org_id, id)`
makes a cross-tenant reference a constraint violation, not just a bug. A plain
`owner_id REFERENCES users(id)` lets a row in org 1 point at a user in org 2 —
Postgres has no way to know that's wrong.

**Table privileges are inherited automatically** (see `0007_rls_policies.sql`'s
`ALTER DEFAULT PRIVILEGES`) — you don't need a `GRANT` statement. **RLS is
not inherited** — the `ENABLE`/`FORCE`/`CREATE POLICY` block above is required
in every migration that adds a tenant table, with no exceptions and no way to
default it away.

## 3. Two exceptions to the pattern above

**Global tables** (no `org_id` at all — currently only `permission_defs`):
skip RLS entirely, it's not tenant data. If you're not certain a new table is
truly global, it isn't — default to the tenant shape.

**High-volume append-only streams** (like `event_outbox`, `audit_log`):
RANGE-partitioned monthly by `created_at`, primary key is `(id, created_at)`
not `(org_id, id)` because Postgres requires the partition key in every
unique constraint, and they use an explicit `CREATE SEQUENCE` since a
partitioned parent can't own an identity column. Copy
`0006_outbox_audit.sql` for this shape rather than the plain-table one above
— including the `ensure_monthly_partition()` bootstrap loop and the
`_default` catch-all partition. Row-level security is not inherited by a
partition: a query that names one skips the parent's policies, so run
`SELECT inherit_partition_rls('<table>_default')` on the default partition you
create by hand (`ensure_monthly_partition()` already does it for monthly ones).
`schema-invariants.spec.ts` fails if a partition of a protected parent has no
policy of its own.

## 4. Statements that can't run in a transaction

If the migration needs `CREATE INDEX CONCURRENTLY` or
`ALTER TYPE ... ADD VALUE`, put `-- @no-transaction` as the literal first line
of the file. Full detail on the failure mode if you skip this (an invalid
index left behind) is in the migrations runbook.

## 5. Verify — don't just eyeball it

```bash
pnpm db:migrate
bash .claude/skills/add-migration/scripts/check-rls.sh widgets
```

The script queries `pg_class` and `pg_policies` on the actual running
database — `relrowsecurity`, `relforcerowsecurity`, and whether a policy
exists — rather than trusting that the SQL you wrote does what it looks like
it does. `OK` or `FAIL` per table, non-zero exit if anything failed. Run it
against every table your migration touches, comma-separated in one call.

Then confirm it's tracked correctly and the code that queries it agrees with
the schema:

```bash
pnpm db:status        # confirms the migration applied and checksums match
pnpm test:integration # if you can — this is what actually exercises RLS end-to-end
```

## 7. Mirror the change in Drizzle

`packages/db/src/schema/*.ts` is typed access to the same tables — it does
NOT generate the SQL (see
[docs/adr/0004-handwritten-sql-migrations.md](../../../docs/adr/0004-handwritten-sql-migrations.md)).
Add the table there in the same commit. Nothing checks that the two agree
automatically; a mismatch is a runtime error, which is exactly why this step
is easy to forget and important not to.

## If you added an enum value

`ALTER TYPE ... ADD VALUE` needs `-- @no-transaction` and is append-only —
Postgres cannot remove a value once added. Mirror the new value in
`packages/contracts/src/common/enums.ts` in the same commit, or the frontend
never learns it's a legal value.
