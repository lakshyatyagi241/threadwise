# Scenario catalogue: what "all the test cases and edge cases" means

Walk this list for **every** feature before you call a twin spec finished. Each line is either generated by the harness (declare the page / form / list / delete and you get it), or it needs a custom scenario, or it is explicitly out of scope with a `skip` and a reason. A line you silently leave out is a hole in the comparison.

Source of truth for what the feature does: the inventory entry (UX & screens, Rules & edge cases, Acceptance criteria, every `QUIRK:`), then the running Reference. The catalogue tells you which kinds of behaviour to look for; the entry tells you which ones this feature has.

## A. Every screen (page probes, generated)

| Case                                                                                                     | How                                                                      |
| -------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------ |
| Loads without console errors, uncaught exceptions, failed requests, 4xx/5xx, broken images               | `pages[]` probe `load`                                                   |
| Title, one `h1`, landmarks, language; headings, tables (columns), forms, buttons, tabs, pagination style | `load` (structure keys, review level)                                    |
| Three viewports (390, 820, 1366): horizontal overflow, nav collapse, tap targets, clipped text           | `responsive`                                                             |
| Accessibility: axe-core WCAG 2.x A/AA + best practice, grouped by impact                                 | `a11y`                                                                   |
| Keyboard only: every control reachable, no trap, visible focus, skip link                                | `keyboard`                                                               |
| Data requests fail with 500 while loading: error state, not a blank page or endless spinner              | `degraded`                                                               |
| No session: redirect to login, never content (`sec.unauthContentVisible`)                                | `auth` (not for `public: true` pages)                                    |
| Timing: median of three loads, LCP                                                                       | `perf`                                                                   |
| RTL layout (`dir=rtl`), long content, 200% zoom, dark/light                                              | custom scenario: set the attribute / viewport, record `low.overflowX.*`  |
| Deep link, refresh, Back/Forward keep state (filters, tab, open record)                                  | custom scenario                                                          |
| Role that lacks the permission: control hidden vs disabled vs 403 page                                   | custom scenario with `role` (needs a seeded second role on both sides)   |
| Another tenant's record id: 404 (ours) vs whatever Reference does                                           | custom API scenario, `enum.crossTenant` (rule `tenant-404` is automatic) |
| Plan / limit reached: control disabled, message shown, API refuses                                       | custom scenario; set the limit through the admin UI on both sides        |

## C. Every list (`lists[]`, generated)

First view; search hit, miss (empty state), 12 edge strings (`%`, `_`, quotes, backslash, script, spaces, unicode, 400 chars, SQL, wildcard, case); search survives reload; per-column sort (direction, toggle); each filter (narrows, survives reload, in the URL); load more / next page; row opens and Back returns. Custom: combined filters, saved views, column chooser, bulk select + bulk action, import (valid, malformed, duplicate rows, 10k rows), export (columns, encoding, injection into CSV cells), pagination boundaries (exactly one page, empty last page).

## D. Destructive actions (`deletes[]`, generated)

Confirmation shown; cancel keeps the row; confirm removes it; still gone after reload. Custom: delete a row other rows reference (what happens to them), delete twice from two tabs, bulk delete, undo, restore (rule `hard-delete-audit` explains why ours differs).

## E. Side effects (custom, usually API-level)

Audit row written, outbox event queued, job enqueued, email in Mailpit (`:8025`), webhook sent, realtime event received, counters updated, notification created. Compare the _effect_ (a row, a mail, a job) not the mechanism. Anything that needs a live WhatsApp/provider session is compared from payload fixtures and the code path in the inventory entry; say so with a `skip`.

## F. Security-flavoured checks that cost nothing

Stored and reflected XSS (script values + readback, `sec.xssExecuted`), HTML in names, open redirect (`next=` pointing offsite), IDOR (other tenant's id), unauthenticated write (`enum.unauthenticated`), secrets in responses, CSRF on writes (Reference token vs our bearer/idempotency), double submit with the same Idempotency-Key, response caching of private data.

## G. What to record when Reference looks wrong

A Reference behaviour that looks like a bug but is relied on is a `QUIRK:` in the inventory. If ours deliberately differs, record it in `intended[]` with `quirk:` and the reason; if the difference is accidental, it is a defect. Never reproduce a Reference bug silently, never fix one silently.
