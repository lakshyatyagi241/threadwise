Read this first

Server time on one shared machine. API, worker, Postgres, Redis and the load generator all ran on one 4-vCPU sandbox over loopback, using a development-mode build with debug logging. Compare endpoints with each other; do not read the values as production latency.

Small data. Two organisations and about 520 contacts. Large-tenant behaviour is not measured.

No external providers. WhatsApp, Telegram, payment gateways and calendar providers were unreachable, so their latency is not included.

Only 399 of 2,045 operations returned a real success with the generic harness. The others were measured on their reject path (authentication, routing, validation), which is much cheaper than real work. Treat those timings as a lower bound.

Queues and the outbox

The system defines 52 BullMQ queues (apps/api/src/infra/queue/queues.ts). Default: 5 attempts with exponential backoff from 2 s; inbound-ingest queues: 10 attempts from 5 s, about 40 minutes. Processor concurrency ranges from 1 to 16.

Adding a job costs about 0.1 ms; adding 500 at once takes 15 to 22 ms. With an empty handler BullMQ adds 0 to 1 ms and handles about 4,500 jobs per second at concurrency 8. The long waits in the 20 ms probes are backlog from queueing 1,000 jobs at once, not overhead: throughput matches concurrency divided by handler time (8 / 20 ms = 400 per second, measured 380; 1 / 20 ms = 50, measured 48).

Transactional outbox

6,157 events processed, none dead, none pending.
Created to processed: average 1,002 ms · p50 1,009 · p95 1,894 · p99 1,981 · max 2,007.
This is a polling floor, not a slowdown. OutboxDrainService runs on a 2-second timer (workers/outbox-drain.service.ts:67), so every event waits 0 to 2 seconds, 1 second on average, before it reaches a queue.

Database

pg_stat_statements across all tests: every frequent statement averages under 0.1 ms and the worst among the top twelve by total time is 1.5 ms. The only slow statement was a one-off timezone-name lookup (59 ms, first call). Time goes into request handling, guards, per-request transaction setup (set_config ran 30,794 times) and serialisation, not into Postgres.

A write performs: session lookup, plan lookup, tenant setting, the business write, an audit-log insert, a security-event insert and an outbox insert, all in one transaction at roughly 0.04 to 0.06 ms each.

Findings worth acting on

  • Outbox delay of 1 s average, 2 s worst. Notifications, automations and webhooks that go through the outbox wait for the next 2-second tick. Shorten the timer or wake the drain after commit if you need near-real-time effects.
  • Heaviest endpoints: /v2/crm/dashboard (24 ms alone, 544 ms median at 50 clients), /v2/shell/overview-stats (31 ms), marketplace app listings (20 ms, 7.6 KB) and /v2/billing/usage (19 ms). Good caching candidates.
  • Every staff login revokes the user's previous session. One person cannot be signed in on two devices, and any script that logs in repeatedly signs the human out. The benchmark hit this itself.
  • Staff login costs about 23 ms (password hashing plus session and audit writes), the most expensive common call and the one to rate-limit.
  • Contact lists return about 1 KB per row. A slimmer list projection would cut the 105 KB page of 100 rows.
  • No failures. Zero 5xx responses across the sweep and all follow-up tests, and zero errors at every concurrency level up to 100 clients.
  • The repository already has a k6 suite (perf/latency.js, load.js, spike.js). k6 could not be installed here, so an equivalent Node harness was used. Run the k6 suite on production-like hardware for CI-grade numbers.
